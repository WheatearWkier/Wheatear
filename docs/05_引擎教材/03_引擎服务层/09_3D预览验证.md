# 第 3 编 09：3D 预览验证

> 本章所属层级：**引擎服务层**
>
> 本章目标：把一个“以 2D 为主”的引擎里那套 3D 预览能力讲透。  
> 重点不是“我做了多少 3D 功能”，而是“每个功能是怎么从 C++、渲染命令、FBO/UBO、shader 一路落到画面的”。

这章要解决的核心问题很简单：

1. `RenderCommand` 和 `RendererAPI` 到底包了哪些底层 OpenGL 命令。
2. `Renderer3D` 为什么能把 Mesh、Material、Shadow、IBL、SSAO 串成一条完整链路。
3. `OpenGLIBL::Compute()` 为什么要把 HDR 拆成 `envCubemap / IrradianceMap / PrefilterMap / BrdfLUT`。
4. `Renderer3D_Mesh_PBR.glsl` 里阴影、环境光、SSAO 最后是怎么合成的。

如果你把这章读懂了，就能回答一句很面试化的话：

> “我这套 3D 不是拿来做完整 3A 引擎的，而是拿来验证材质、光照、阴影、环境光和后处理的渲染链路。”

---

## 3.9.1 这一层在架构里的位置

这一章仍然属于**引擎服务层**。

它不负责玩法，不负责剧情，不负责战斗规则；它负责的是“怎么把场景里的 3D 物体正确画出来”。

对应到本项目，3D 预览能力主要做了这些事：

- 把 `Mesh` 变成 GPU 能画的顶点/索引数据
- 把 `Material` 变成 shader 里能读到的参数和贴图
- 把 `Scene` 里的 `MeshRendererComponent` 收集起来
- 先画 Shadow Map，再画主 PBR pass
- 用 HDR 预计算出 IBL 所需的三张图
- 用 SSAO 让接触区域更有层次
- 给编辑器提供天空盒和网格辅助

它的定位不是“完整 3D 商业引擎”，而是“3D 预览验证层”。  
对一个以 2D 游戏为主的引擎来说，这个层很实用，因为它能帮你检查：

- 材质球对不对
- 法线图对不对
- 阴影方向对不对
- HDR 是否喂对了
- 环境光是否正确
- SSAO 是否只压暗 ambient

## 3.9.2 先看主链路：从 Scene 到 OpenGL

本章先抓住这条线：

```text
Scene / ECS
  -> RenderSystem
  -> Renderer3D
  -> RenderCommand
  -> OpenGLRendererAPI
  -> OpenGL / GLAD
```

数据链路则是：

```text
Mesh / Material
  -> UBO / Texture
  -> Shader
  -> FBO 输出
  -> 最终画面
```

如果你只记一件事，就记住这个：

> `RenderSystem` 决定“谁来画”；  
> `Renderer3D` 决定“怎么画”；  
> `RenderCommand` 决定“落到哪条 OpenGL 命令”。

### 3.9.2.1 `RenderCommand` 包了什么

`RenderCommand` 不是摆设，它是一个很薄的渲染命令壳，负责把上层服务层的动作翻译成真正的图形 API。

它的接口很简单：

```cpp
RenderCommand::SetViewport(...)
RenderCommand::SetClearColor(...)
RenderCommand::Clear()
RenderCommand::DrawIndexed(...)
RenderCommand::DrawArrays(...)
RenderCommand::SetDepthWrite(...)
RenderCommand::SetDepthFunc(...)
RenderCommand::SetBlend(...)
RenderCommand::GetBoundFramebuffer()
RenderCommand::BindFramebuffer(...)
RenderCommand::BindTextureUnit(...)
```

对应到 `OpenGLRendererAPI.cpp`，就是这些底层调用：

| 上层命令 | OpenGL 实现 |
| --- | --- |
| `SetViewport` | `glViewport` |
| `SetClearColor` | `glClearColor` |
| `Clear` | `glClear(GL_COLOR_BUFFER_BIT | GL_DEPTH_BUFFER_BIT)` |
| `DrawIndexed` | `glDrawElements(GL_TRIANGLES, ...)` |
| `DrawArrays` | `glDrawArrays(GL_TRIANGLES, ...)` |
| `SetDepthWrite` | `glDepthMask` |
| `SetDepthFunc` | `glDepthFunc(GL_LESS / GL_LEQUAL)` |
| `SetBlend` | `glEnable/Disable(GL_BLEND)` + `glBlendFunc` |
| `BindFramebuffer` | `glBindFramebuffer(GL_FRAMEBUFFER, id)` |
| `BindTextureUnit` | `glBindTextureUnit(slot, textureID)` |
| `GetBoundFramebuffer` | `glGetIntegerv(GL_FRAMEBUFFER_BINDING, ...)` |

### 3.9.2.2 初始化时默认开了哪些状态

`OpenGLRendererAPI::Init()` 里做了几个基础状态设置：

- `glEnable(GL_BLEND)`
- `glBlendFunc(GL_SRC_ALPHA, GL_ONE_MINUS_SRC_ALPHA)`
- `glEnable(GL_DEPTH_TEST)`
- `glEnable(GL_LINE_SMOOTH)`
- `glDisable(GL_SCISSOR_TEST)`

这很重要，因为后面的 3D pass、阴影 pass、SSAO pass 都默认建立在这些状态上。

### 3.9.2.3 为什么要有这个抽象

因为后面会有很多地方需要画东西：

- Shadow pass 要画深度
- 主 PBR pass 要画模型
- SSAO pass 要画全屏三角形
- IBL precompute 要画 cubemap 六个面
- BRDF LUT 要画一个全屏三角形

如果每个地方都直接写一堆 `glBindFramebuffer / glDrawArrays / glDrawElements`，你会很快把渲染代码写成散装 OpenGL 脚本。  
现在的写法把“我想画什么”和“OpenGL 怎么画”隔开了。

## 3.9.3 FBO、UBO、VAO：3D 预览真正依赖的三种底层容器

3D 预览不是只靠 shader。它真正依赖的是三种 GPU 容器：

### 3.9.3.1 Framebuffer：决定输出写到哪里

`OpenGLFramebuffer.cpp` 负责创建和管理 FBO。

它做的事包括：

- `glCreateFramebuffers`
- `glCreateTextures`
- `glTexImage2D / glTexStorage2D`
- `glFramebufferTexture2D`
- `glNamedFramebufferTextureLayer`
- `glDrawBuffers`
- `glCheckFramebufferStatus`

这套东西决定了一个 pass 的输出会写到哪些附件上。

本项目的主 3D 渲染目标不是单一颜色，而是多目标输出：

- attachment 0：最终颜色
- attachment 1：视图空间法线
- attachment 2：Entity ID
- depth attachment：深度

所以你在 `Renderer3D_Mesh_PBR.glsl` 里会看到：

```glsl
layout(location = 0) out vec4 o_Color;
layout(location = 1) out vec3 o_ViewNormal;
layout(location = 2) out int  o_EntityID;
```

这不是为了炫技，而是为了后面的 SSAO、编辑器拾取和调试。

### 3.9.3.2 Uniform Buffer：决定 CPU 和 shader 怎么对齐

`OpenGLUniformBuffer.cpp` 里最关键的两句是：

```cpp
glNamedBufferData(...);
glBindBufferBase(GL_UNIFORM_BUFFER, binding, m_RendererID);
```

这说明 UBO 的核心不是“把数据塞进 buffer”，而是“绑定到约定好的 binding 点”。

本项目里，3D 最关键的 UBO 是这些：

- `binding = 1`：Camera
- `binding = 2`：Transform
- `binding = 3`：Material
- `binding = 5`：LightData
- `binding = 10`：IBLData
- `binding = 14`：SkyboxGradient
- `binding = 15`：SSAOParams
- `binding = 16`：SSAOKernel

这就是为什么 shader 里会直接写：

```glsl
layout(std140, binding = 1) uniform Camera { ... };
layout(std140, binding = 2) uniform Transform { ... };
layout(std140, binding = 3) uniform Material { ... };
```

### 3.9.3.3 VAO / VBO / IBO：决定几何体怎么送进 GPU

`Mesh::UploadToGPU()` 会创建：

- Vertex Array Object
- Vertex Buffer Object
- Index Buffer Object

并把 `MeshVertex` 的布局对齐到 shader 输入：

```cpp
struct MeshVertex
{
    glm::vec3 Position;
    glm::vec3 Normal;
    glm::vec2 TexCoord;
};
```

对应的 shader 输入就是：

```glsl
layout(location = 0) in vec3 a_Position;
layout(location = 1) in vec3 a_Normal;
layout(location = 2) in vec2 a_TexCoord;
```

所以 Mesh 的最小单位其实就是：

> 顶点布局 + 索引布局 + 一个能被 shader 读懂的 VAO。

## 3.9.4 `Mesh` 和 `Material`：3D 预览的最小资产单元

### 3.9.4.1 `Mesh` 做了什么

`Mesh::Create(filepath)` 会：

1. 通过 `AssetPath::Resolve()` 找到真实文件
2. 用 tinyobjloader 读 OBJ
3. 去重顶点
4. 如果模型没法线，就自己算法线
5. 上传到 GPU

你可以把这个过程理解成：

```text
OBJ 文件
  -> 顶点/法线/UV
  -> 去重
  -> VertexArray + VertexBuffer + IndexBuffer
  -> GPU 可画网格
```

`Mesh::CreateCube()` 和 `Mesh::CreateSphere()` 是两个很重要的验证资产：

- Cube 适合看阴影、天空盒、立方体贴图
- Sphere 适合看材质球、粗糙度、金属度、IBL

### 3.9.4.2 `Material` 做了什么

`Material` 不是“一个贴图路径而已”，它是 shader 参数的来源。

它存的内容是：

- `Albedo`
- `Metallic`
- `Roughness`
- `FlipNormals`
- `AlbedoMap`
- `NormalMap`
- `RoughnessMap`
- `MetallicMap`

它通过 YAML 读写：

```yaml
Material:
  Albedo: [1, 1, 1, 1]
  Metallic: 0.0
  Roughness: 0.5
  FlipNormals: false
  AlbedoMap: assets/textures/wood.png
  NormalMap: assets/textures/wood_n.png
```

这意味着材质数据不是写死在 shader 里的，而是可以被编辑器保存和加载。

### 3.9.4.3 `MeshRendererComponent`

在 ECS 中，3D 物体靠这个组件接入渲染：

```cpp
struct MeshRendererComponent
{
    Ref<Mesh> Mesh;
    Ref<Material> Material;
};
```

所以场景里的一个 3D 物体，本质上就是：

> 一个 Transform + 一个 MeshRendererComponent。

## 3.9.5 `RenderSystem -> Renderer3D`：场景是怎么进入渲染层的

`RenderSystem` 是把 ECS 场景送进渲染器的入口。

它会先找主相机，再分出多个 pass：

1. Shadow pass
2. 2D pass
3. 3D pass
4. UI pass

### 3.9.5.1 运行时的顺序

运行时链路是：

```text
Scene::OnUpdateRuntime
  -> RenderSystem::OnUpdateRuntime
      -> Shadow pass
      -> Renderer2D
      -> Renderer3D
      -> UIRenderer
```

`RenderSystem` 里最关键的一段逻辑是：

- `RenderSceneShadow()` 遍历 `MeshRendererComponent`，调用 `Renderer3D::DrawMeshShadow()`
- `RenderScene3D()` 遍历 `MeshRendererComponent`，调用 `Renderer3D::DrawMesh()`
- `CollectLights()` 把 `DirectionalLightComponent` 和 `PointLightComponent` 写进 `Renderer3D`

### 3.9.5.2 编辑器里的顺序

编辑器里也类似，只是相机换成了 EditorCamera，并且会保留编辑器可见性。

为什么要先 shadow 再主 pass？

因为主 pass 里要采样 shadow map。  
也就是说，阴影必须先算出来，主 shader 才能读到 `u_ShadowMap`。

### 3.9.5.3 `BeginScene()` 在做什么

`Renderer3D::BeginScene()` 会把相机信息写进 Camera UBO：

```cpp
s_Data.CameraBuffer.ViewProjection = camera.GetProjection() * view;
s_Data.CameraBuffer.View           = view;
s_Data.CameraBuffer.Projection     = camera.GetProjection();
s_Data.CameraBuffer.CameraPosition = cameraPosition;
s_Data.CameraUBO->SetData(...);
```

它还会：

- 清空 light buffer
- `FlushLights()`
- 重置统计信息

所以 `BeginScene()` 不是一个空壳，它是“本帧 3D 画面开始”的真正分界线。

## 3.9.6 渲染底层命令：`DrawMesh()` 最后到底做了什么

这是本章最值得看的一节。

### 3.9.6.1 `Renderer3D::DrawMesh()` 的真实顺序

它大致是这样：

1. 如果灯光有变化，先 `FlushLights()`
2. 写 Transform UBO
3. 写 Material UBO
4. 绑定纹理：albedo / normal / roughness / metallic / shadow / IBL / SSAO
5. 绑定 mesh shader
6. `RenderCommand::DrawIndexed(...)`

对应的关键代码逻辑是：

```cpp
s_Data.TransformBuffer.Model = transform;
s_Data.TransformBuffer.NormalMatrix = glm::transpose(glm::inverse(transform));
s_Data.TransformBuffer.LightSpaceMatrix = s_Data.LightSpaceMatrix;
s_Data.TransformUBO->SetData(...);

s_Data.MaterialBuffer.Albedo = mat.Albedo;
s_Data.MaterialBuffer.Metallic = mat.Metallic;
s_Data.MaterialBuffer.Roughness = mat.Roughness;
s_Data.MaterialBuffer.EntityID = entityID;
s_Data.MaterialUBO->SetData(...);

(mat.AlbedoMap ? mat.AlbedoMap : white)->Bind(4);
(mat.NormalMap ? mat.NormalMap : white)->Bind(6);
(mat.RoughnessMap ? mat.RoughnessMap : white)->Bind(7);
(mat.MetallicMap ? mat.MetallicMap : white)->Bind(8);
shadowFB->BindDepthAttachment(9);

RenderCommand::DrawIndexed(mesh->GetVertexArray(), mesh->GetIndexCount());
```

### 3.9.6.2 为什么要写 NormalMatrix

因为法线不能直接用 Model 矩阵乘。  
非均匀缩放会破坏法线方向，所以 shader 里用的是：

```glsl
v_Normal = normalize(mat3(u_NormalMatrix) * a_Normal);
```

而 `u_NormalMatrix` 在 C++ 里是：

```cpp
glm::transpose(glm::inverse(transform))
```

这一步是标准做法。

### 3.9.6.3 为什么需要 `EntityID`

主 fragment shader 会输出一个实体 ID：

```glsl
layout(location = 2) out int o_EntityID;
o_EntityID = u_EntityID;
```

这给编辑器拾取、调试和高亮留了接口。  
也就是说，这个 3D 层不是只负责“看起来对”，它还给编辑器“找得到对象”。

## 3.9.7 阴影：从 Shadow Map 到 PCF

阴影是本章第一条完整的 3D 真实链路。

### 3.9.7.1 Shadow pass 先画什么

`RenderSystem::RenderSceneShadow()` 遍历所有 `MeshRendererComponent`，调用：

```cpp
Renderer3D::DrawMeshShadow(tc.GetTransform(), mr.Mesh);
```

这个 pass 只画深度，不画颜色。

`Renderer3D::Init()` 里创建的 shadow framebuffer 是：

- `DEPTH32F`
- 尺寸 `2048 x 2048`

因为阴影图本质上是深度图，不需要颜色附件。

### 3.9.7.2 `Renderer3D_Shadow.glsl` 为什么这么短

它的顶点 shader 只做一件事：

```glsl
gl_Position = u_LightSpaceMatrix * u_Model * vec4(a_Position, 1.0);
```

fragment shader 甚至是空的。

这说明 shadow pass 的任务非常纯粹：

> 从光源视角记录“这个位置离光多远”。

### 3.9.7.3 `DrawMeshShadow()` 落到哪里

`Renderer3D::DrawMeshShadow()` 的核心是：

- 写 `Transform` UBO
- 用 `glDrawElements` 画索引

也就是说，shadow pass 本质上还是一次普通几何绘制，只不过：

- shader 简化了
- 输出目标变成 depth map

### 3.9.7.4 主 shader 里怎么读 shadow map

`Renderer3D_Mesh_PBR.glsl` 里，阴影计算走的是 `CalcShadow()`：

```glsl
float shadow = (u_HasShadowMap != 0)
             ? CalcShadow(v_LightSpacePos, N, dirL)
             : 0.0;
```

`CalcShadow()` 做的事可以拆成四步：

1. 把光空间坐标除以 `w`
2. 投到 0..1 区间
3. 把当前深度和 shadow map 里的深度比
4. 用 3x3 PCF 做软化

简化成伪代码就是：

```text
proj = lightSpacePos / w
proj = proj * 0.5 + 0.5
currentDepth = proj.z
bias = max(0.005 * (1 - dot(N, L)), 0.0005)
shadow = average(3x3 compare)
```

### 3.9.7.5 为什么要分 shadow pass

因为 shadow 不是“主渲染顺手算一下”就能做好。

分开以后有几个好处：

- 深度图只写一次，成本低
- 主 pass 可以统一读取阴影
- 代码结构清晰
- 便于调试 shadow map

## 3.9.8 HDR / IBL：这章最容易问倒人的部分

### 3.9.8.1 先回答你之前那个问题

如果按教材讲法，IBL 可以分成四个东西：

1. HDR 环境图
2. Irradiance Map
3. Prefilter Map
4. BRDF LUT

但按源码结构，必须更准确地说：

- HDR 是输入源
- `envCubemap` 是中间产物
- `IBLResult` 只保存后三个输出

所以真实链路是：

```text
HDR equirect
  -> envCubemap
  -> IrradianceMap
  -> PrefilterMap
  -> BrdfLUT
```

### 3.9.8.2 `IBLPrecompute` 这一层干什么

`IBLPrecompute.cpp` 只负责根据当前渲染后端分发：

- OpenGL 就走 `OpenGLIBL::ComputeOrLoad()`
- 以后如果换后端，也可以继续扩

也就是说，`IBLPrecompute` 是一层薄分发，真正干活的是 `OpenGLIBL`。

### 3.9.8.3 `OpenGLIBL::Compute()` 的完整顺序

`OpenGLIBL::Compute()` 做了这几步：

1. 用 `stbi_loadf` 读 HDR
2. 创建 equirect 2D 纹理
3. 创建 capture FBO / RBO
4. 创建 `envCubemap`
5. 用 `IBL_EquirectToCubemap.glsl` 把 HDR 转成 cubemap
6. 给 cubemap 生成 mipmap
7. 创建 `IrradianceMap`
8. 用 `IBL_Irradiance.glsl` 做漫反射卷积
9. 创建 `PrefilterMap`
10. 用 `IBL_Prefilter.glsl` 按 roughness 逐 mip 预滤波
11. 创建 `BrdfLUT`
12. 用 `IBL_BrdfLUT.glsl` 预积分 BRDF
13. 组装到 `IBLResult`
14. 删除临时的 `envCubemap` 和 FBO/RBO

### 3.9.8.4 这几个 OpenGL 命令为什么关键

这里最值得记的是这几个 API：

- `glCreateTextures(GL_TEXTURE_CUBE_MAP, ...)`
- `glTextureStorage2D(...)`
- `glNamedFramebufferTextureLayer(...)`
- `glViewport(...)`
- `glClear(...)`
- `glDrawArrays(GL_TRIANGLES, 0, 36)`
- `glGenerateTextureMipmap(...)`

这说明 IBL 预计算不是“CPU 算完再传回去”，而是“用 GPU 绘制 6 个面 + 多个 mip 层”。

### 3.9.8.5 `IBL_EquirectToCubemap.glsl`

这个 shader 的任务是把等距柱状 HDR 转成 cubemap。

核心函数是：

```glsl
vec2 SampleSphericalMap(vec3 v)
{
    vec2 uv = vec2(atan(v.z, v.x), asin(v.y));
    uv *= vec2(0.1591, 0.3183);
    uv += 0.5;
    return uv;
}
```

它做的事情很简单：

> 把方向向量变成 HDR 2D 贴图的采样坐标。

### 3.9.8.6 `IBL_Irradiance.glsl`

这个 shader 做的是漫反射卷积。

它不是“复制一张贴图”，而是：

- 在法线方向周围的半球上做积分
- 得到低频环境光
- 输出到低分辨率 cubemap

所以 `IrradianceMap` 看起来会比 HDR 模糊很多，这是对的。

### 3.9.8.7 `IBL_Prefilter.glsl`

这个 shader 是镜面高光预滤波，核心是 GGX importance sampling。

它里面用了几个关键概念：

- `Hammersley` 序列：让采样更均匀
- `ImportanceSampleGGX`：按 GGX 分布采样半程向量
- `mipLevel`：根据 roughness 选择不同模糊程度

简化理解：

> 粗糙度越大，反射越糊；  
> 粗糙度越小，反射越清晰。

所以 `PrefilterMap` 不是普通反射图，而是一张“按 roughness 预先卷积好的环境反射图”。

### 3.9.8.8 `IBL_BrdfLUT.glsl`

这张 LUT 是 split-sum 近似里的第二半。

输出是一个 `RG16F` 2D 纹理：

- R = scale
- G = bias

它把 `NdotV` 和 `roughness` 作为坐标，提前把积分结果算好。  
这样主 shader 就不用每个像素都去做昂贵积分了。

### 3.9.8.9 `Renderer3D::SetIBL()` 和 `CalcIBL()`

`Renderer3D::SetIBL()` 会：

- 存当前 `IBLResult`
- 设 `HasIBL`
- 更新 `IBLDataUBO`

`Renderer3D::SetIBLIntensity()` 则只改强度。

主 shader 的 `CalcIBL()` 逻辑非常典型：

```glsl
vec3 irradiance = texture(u_IrradianceMap, N).rgb;
vec3 diffuse = kD * irradiance * albedo;

float lod = roughness * MAX_PREFILTER_LOD;
vec3 prefilteredColor = textureLod(u_PrefilterMap, R, lod).rgb;
vec2 brdf = texture(u_BrdfLUT, vec2(NdotV, roughness)).rg;
vec3 specular = prefilteredColor * (kS * brdf.x + brdf.y);
```

这段代码可以直接解释成：

- diffuse = 低频环境光 × 漫反射
- specular = 预滤波环境反射 × BRDF LUT

### 3.9.8.10 缓存为什么重要

`OpenGLIBL::ComputeOrLoad()` 不是每次都重新算，而是先读缓存。

缓存文件保存了：

- irradiance cubemap
- prefilter cubemap
- BRDF LUT

这对编辑器特别重要，因为 HDR 一旦换文件，重新计算 IBL 可能比较慢；有缓存就能快很多。

---

## 3.9.9 SSAO：为什么它是“补层次”，不是“主光照”

SSAO 是屏幕空间环境光遮蔽。

它的逻辑不是“从世界里真实算全局光”，而是：

> 利用当前帧已经有的 depth / normal，估计接触区域应该更暗。

### 3.9.9.1 它依赖什么输入

SSAO 依赖两张关键图：

- 主 FBO 的 normal attachment
- 主 FBO 的 depth attachment

本项目里，主 shader 会输出：

```glsl
layout(location = 1) out vec3 o_ViewNormal;
```

然后编辑器层把这个 attachment 传给 SSAO pass。

### 3.9.9.2 `Renderer3D::InitSSAO()` 做了什么

初始化时，Renderer3D 会：

- 生成 64 个半球采样点
- 生成 4x4 噪声纹理
- 创建 `RawFBO`
- 创建 `BlurFBO`
- 创建 `SSAO.glsl`
- 创建 `SSAO_Blur.glsl`
- 初始化 `Radius / Bias / Power`

这里的 64 个 sample 不是随机扔出来的，而是逐步缩放的半球采样点。

### 3.9.9.3 `ComputeSSAO()` 的实际流程

`ComputeSSAO()` 分两步：

#### 第一步：Raw AO

它会绑定原始 SSAO FBO，然后：

- 绑 normalTex 到 slot 20
- 绑 depthTex 到 slot 21
- 绑 noiseTex 到 slot 22
- 画一个全屏三角形

注意，这里不是画模型，而是画全屏 quad。

`SSAO.glsl` 的顶点 shader 甚至只靠 `gl_VertexID` 生成 6 个顶点：

```glsl
if      (gl_VertexID == 0) { x = -1.0; y = -1.0; }
else if (gl_VertexID == 1) { x =  1.0; y = -1.0; }
...
gl_Position = vec4(x, y, 0.0, 1.0);
```

#### 第二步：Blur AO

接着把 Raw AO 送进 `SSAO_Blur.glsl`，做一个 5x5 box blur。

为什么要 blur？

因为屏幕空间采样天生有噪点，不模糊会很脏。

### 3.9.9.4 SSAO shader 到底怎么算

核心流程是：

1. 从 depth 重建视图空间位置
2. 从 normal 和 noise 构建 TBN
3. 用 64 个采样点在半球上测试遮蔽
4. 用 rangeCheck 限制远处误差
5. 用 `pow(1.0 - occlusion / 64.0, u_Power)` 得到最终 AO

简化伪代码：

```text
fragPos = ReconstructViewPos(uv, depth)
normal  = normalize(normalTex)
TBN     = tangent frame from noise + normal

occlusion = 0
for each sample:
    samplePos = fragPos + TBN * sample * radius
    compare sample depth with samplePos depth
    accumulate occlusion

ao = pow(1 - occlusion / 64, power)
```

### 3.9.9.5 AO 为什么只乘 ambient

主 shader 里最后是这样用的：

```glsl
ambient = CalcIBL(...) * ao;
```

这很重要：

- 直接光还在
- 阴影还是由 shadow map 管
- AO 只是在压暗间接光

所以 SSAO 是“补层次”，不是“替代阴影”。

## 3.9.10 主 PBR shader：最终颜色是怎么出来的

`Renderer3D_Mesh_PBR.glsl` 是这章的总合点。

它把几件事真的串到了一起：

- 直接光
- 阴影
- IBL
- SSAO
- tone mapping
- gamma correction

### 3.9.10.1 输入数据

vertex shader 输出：

- 世界坐标
- 法线
- UV
- 光空间坐标
- 视图空间法线

fragment shader 读取：

- Camera UBO
- Material UBO
- LightData UBO
- IBLData UBO
- albedo / normal / roughness / metallic / shadow / IBL / SSAO 纹理

### 3.9.10.2 材质参数如何进来

材质采样逻辑是：

```glsl
vec4 albedoSample = texture(u_AlbedoMap, v_TexCoord) * u_Albedo;
vec3 albedo = pow(albedoSample.rgb, vec3(2.2));

float roughness = hasRoughnessMap ? texture(u_RoughnessMap, v_TexCoord).r : u_Roughness;
float metallic  = hasMetallicMap  ? texture(u_MetallicMap,  v_TexCoord).r : u_Metallic;
roughness = max(roughness, 0.04);
```

这里的 `pow(..., 2.2)` 是把 sRGB 转成线性空间。  
如果不做这一步，光照会不对。

### 3.9.10.3 法线为什么要重新建 TBN

如果有 normal map，shader 会重新算 TBN：

```glsl
vec3 dp1  = dFdx(v_WorldPos);
vec3 dp2  = dFdy(v_WorldPos);
vec2 duv1 = dFdx(v_TexCoord);
vec2 duv2 = dFdy(v_TexCoord);

vec3 T = normalize(dp1 * duv2.t - dp2 * duv1.t);
vec3 B = cross(N, T);
vec3 normalSample = texture(u_NormalMap, v_TexCoord).rgb * 2.0 - 1.0;
N = normalize(mat3(T, B, N) * normalSample);
```

这就是 normal map 真正起作用的地方。

### 3.9.10.4 最终光照公式

主颜色由三部分组成：

1. `Lo`：直接光 + 点光
2. `ambient`：IBL 或 fallback
3. `ao`：SSAO 乘子

最后：

```glsl
vec3 color = ambient + Lo;
color = ToneMap(color);
color = GammaCorrect(color);
```

你可以把它理解成：

```text
最终颜色 = 直接光 + 间接光
间接光 = IBL × AO
再做 tone mapping 和 gamma correction
```

### 3.9.10.5 为什么要输出 entity id

`o_EntityID = u_EntityID;`

这给编辑器选择实体、调试和后期交互留下了接口。  
它说明这个 3D 层不是离线 demo，而是和编辑器互通的生产工具链。

## 3.9.11 编辑器里怎么把这套 3D 跑起来

`EditorLayer3D.cpp` 里，3D 预览和编辑器绑定得很紧。

### 3.9.11.1 初始化

`OnAttach()` 会：

- `Renderer3D::InitSSAO(1920, 1080)`
- 读取默认 HDR
- `IBLPrecompute::ComputeOrLoad(default.hdr)`
- `Renderer3D::SetIBL(...)`

这意味着编辑器一启动，就能直接看到 IBL 效果。

### 3.9.11.2 每帧后处理

`OnPostSceneUpdate()` 会：

- 检查 viewport 变化
- 必要时 `ResizeSSAO()`
- 调 `Renderer3D::ComputeSSAO(...)`

也就是说，SSAO 是在场景渲染之后补上的。

### 3.9.11.3 视图辅助

`DrawEditorSkybox()` 和 `DrawEditorGrid()` 的作用是：

- 给编辑器一个可读的空间背景
- 给模型一个尺度参考
- 方便看相机和坐标是否正常

如果有 IBL，就用 `PrefilterMap` 画天空盒；  
如果没有，就用渐变色 fallback。

## 3.9.13 这一层的好处和坏处

### 好处

- 可以验证材质、光照、阴影、环境光、后处理
- 可以让 2D 引擎也拥有靠谱的 3D 预览能力
- 可以把 shader 链路和 C++ 链路统一讲清楚
- 可以辅助编辑器调试

### 坏处

- 不是完整 3D 商业引擎级别
- UBO / FBO / 多贴图槽一多，排查会变复杂
- IBL 和 SSAO 对初学者门槛较高
- 如果把 3D 预览和主 2D 主线混太深，会影响学习节奏

所以这层最好按“验证链路”理解，而不是按“大而全 3D 引擎”理解。

---

## 3.9.14 常见误区

- 把 HDR 直接等同于 IBL
- 以为 `IBLResult` 里也该存 HDR，其实 HDR 是输入源
- 以为 `PrefilterMap` 是普通反射图，其实它按 roughness 分了 mip
- 以为 SSAO 会直接改最终颜色，其实它主要压暗 ambient
- 把 shadow pass 和主 pass 混成一个 shader
- 以为 Material 只是贴图路径，其实它还是 shader 参数来源
- 忽略 UBO 布局，导致 C++ 和 shader 不同步

## 3.9.15 面试时怎么讲

你可以准备三层回答。

### 3.9.15.1 先讲定位

“我们引擎是 2D 为主，但补了一套 3D 预览验证能力，用来检查 Mesh、Material、Shadow、IBL 和 SSAO 的渲染链路。”

### 3.9.15.2 再讲链路

“Scene 里的 `MeshRendererComponent` 会被 `RenderSystem` 收集，交给 `Renderer3D`。`Renderer3D` 先做 shadow pass，再做主 PBR pass。PBR shader 里把阴影、IBL 和 SSAO 乘进去。”

### 3.9.15.3 最后讲 IBL

“HDR 输入先转成 environment cubemap，再生成 irradiance map、prefilter map 和 BRDF LUT。最终在 shader 里通过 `u_IrradianceMap`、`u_PrefilterMap` 和 `u_BrdfLUT` 做 split-sum 近似。”

## 3.9.16 初学者建议怎么读

如果你是第一次看这一章，建议按这个顺序：

1. 先看 `Mesh` 和 `Material`，知道 3D 物体的最小资产是什么。
2. 再看 `MeshRendererComponent`，知道场景怎么挂 3D 物体。

4. 再看 `RenderCommand` 和 `OpenGLRendererAPI`，知道底层 OpenGL 命令是什么。
5. 再看 `Renderer3D.cpp`，知道 UBO、FBO、纹理槽怎么组织。
6. 再看 `Renderer3D_Mesh_PBR.glsl`，把阴影、IBL、SSAO 串起来。
7. 最后看 `OpenGLIBL.cpp` 和 IBL shader，理解 HDR 是怎么变成环境光的。

如果你只想先抓住“结果是怎么出来的”，先盯这三条：

- `MeshRendererComponent -> RenderSystem -> DrawMesh()`
- `HDR -> envCubemap -> Irradiance / Prefilter / BRDF LUT`
- `SSAO -> Blur -> u_SSAOTex -> ambient * ao`

## 3.9.18 本章总结

这套 3D 预览验证能力，最重要的不是“我做了多少 3D 特效”，而是：

> 我把一条完整的 3D 渲染链做得足够清楚、足够可验证。

它的工程价值在于：

- 用 `Mesh` 和 `Material` 把资产统一起来
- 用 `RenderSystem` 和 `Renderer3D` 把 ECS 接起来
- 用 shader 把阴影、IBL、SSAO 串起来
- 用验证场景把所有结果看见

所以这层对于一个以 2D 为主的引擎来说，不是多余功能，而是“渲染可信度补强”。
