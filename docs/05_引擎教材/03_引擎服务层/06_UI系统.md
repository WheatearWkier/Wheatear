# 第 3 编 06：UI 系统

> 本章所属层级：**引擎服务层**
>
> 本章目标：理解运行时 UI 是怎么从 Scene 数据里长出来的，怎么被布局、渲染、点击、拖拽、滚动、动画化，最后又怎么反向驱动剧情、战斗、设置和存读档流程。
>
> 这一章只讲**运行时 UI**。  
> 编辑器里的 `ImGui` 面板属于**应用层**，它和这里的“游戏内 HUD / 对话框 / 菜单 / 滑条 / 技能树”不是一回事。

如果说输入那一章回答的是“玩家按了什么”，那这一章回答的就是：

```text
Scene 里的 UI 数据，怎么变成屏幕上的按钮、文本、血条、对话框和菜单？
```

Wheatear 的 UI 不是纯粹的即时模式 GUI，也不是一套独立在 Scene 外面的前端框架。  
它更像是一个**场景内的数据驱动 UI 系统**：

```text
Scene / ECS
    ↓
UISystem
    ├─ UIInputSystem      -> hover / click / drag / scroll
    ├─ UIWidgetLayout     -> 计算最终矩形、可见性、裁剪
    ├─ UIRenderer         -> 交给 Renderer2D 画出来
    └─ UIAnimatorComponent -> 让 UI 动起来
```

这套结构的好处是，UI 不会散落成一堆手写 OpenGL 代码，也不会和玩法逻辑缠死。  
它能既服务战斗 HUD，也服务 VN 对话框，还能顺手支撑设置页、存档页、技能树、工具提示和编辑器内的运行预览。

## 3.6.2 先分清两种 UI

Wheatear 里至少有两类 UI：

### 1. 运行时 UI

也就是本章要讲的东西。

它们会出现在：

- VN 对话框
- 战斗 HUD
- 设置页面
- 存档 / 读档界面
- 结果页
- 技能树
- 提示框
- 滑条

这些 UI 不是写在 `ImGui` 窗口里的，而是作为 Scene 的一部分被序列化、加载、更新、渲染。

### 2. 编辑器 UI

这部分属于应用层，主要是 `ImGui`。

它们负责：

- Hierarchy
- Inspector
- 资源浏览器
- 场景预览窗口
- 调试面板

这类 UI 的目标不是给玩家看，而是给开发者用。  
所以它的生命周期、布局方式、输入模型，和运行时 UI 都不一样。

教材里一定要把这两者分开，不然很容易把“编辑器面板”和“游戏内界面”混成一锅。

## 3.6.3 UI 的数据模型：从 Canvas 到 Widget

UI 系统的核心不是按钮，而是**Widget**。

在 Wheatear 里，UI 的很多组件都挂在 `UIWidgetComponent` 这层基底上：

- `UICanvasComponent`
- `UIWidgetComponent`
- `UIPanelComponent`
- `UITextComponent`
- `UIImageComponent`
- `UIButtonComponent`
- `UIProgressBarComponent`
- `UISliderComponent`
- `UIScrollViewComponent`
- `UICheckboxComponent`
- `UIPathComponent`
- `UISkillTreeViewComponent`
- `UIRadialCooldownComponent`
- `UIAnimatorComponent`
- `UIPageItemComponent`

### 3.6.3.1 `UICanvasComponent`

它是 UI 的根坐标系。

可以把它理解成：

```text
“这一套 UI 该按什么参考分辨率去排版？”
```

这个组件通常放在一个场景里最顶层的 UI 根实体上，用来承接整棵 UI 树。

### 3.6.3.2 `UIWidgetComponent`

它是最重要的公共层。

你可以把它理解成 UI 里的 `Transform + Layout + Hierarchy + State` 的混合体。  
它保存了几类最基础的信息：

- `Visible`
- `EditorVisible`
- `Position`
- `Size`
- `Rotation`
- `Anchor`
- `SortOrder`
- `ParentEntity`

也就是说，UI 不是一块块散开的屏幕坐标，而是一棵有父子关系的树。

### 3.6.3.3 视觉组件

这些组件决定“长什么样”：

- `UIPanelComponent`：面板底板、边框、背景
- `UIImageComponent`：纹理、图集、子矩形
- `UITextComponent`：字体、颜色、描边、阴影、自动换行
- `UIProgressBarComponent`：进度条
- `UICircleComponent`：圆形或圆环类绘制
- `UIRadialCooldownComponent`：扇形冷却遮罩
- `UIPathComponent`：线段、折线、贝塞尔路径

### 3.6.3.4 交互组件

这些组件决定“怎么被点、怎么被拖、怎么被选中”：

- `UIButtonComponent`
- `UISliderComponent`
- `UIScrollViewComponent`
- `UICheckboxComponent`
- `UISkillTreeViewComponent`

### 3.6.3.5 状态组件

`UIAnimatorComponent` 和 `UIPageItemComponent` 更像状态层。

- `UIAnimatorComponent` 负责入场、出场、悬停、结果页弹出等动画
- `UIPageItemComponent` 负责页面切换和可见性分组

这说明 UI 并不是只有“画”和“点”，还有“如何进入屏幕”和“如何分页切换”的问题。

## 3.6.4 布局系统：`UIWidgetLayout` 怎么算出最终矩形

UI 真正难的地方不是渲染，而是布局。

因为一个按钮显示在屏幕上的最终位置，不是只看自己的 `Position`，还要考虑：

- 父节点位置
- 父节点尺寸
- anchor
- scroll offset
- page 可见性
- editor/runtime 可见性
- 裁剪区域

这就是 `UIWidgetLayout` 的任务。

它的关键点有三个：

### 3.6.4.1 递归向上找父节点

`ResolveRect()` 不是只看当前节点，而是会沿着 `ParentEntity` 一层层往上算。

这意味着一个按钮的最终位置，实际上是“自己相对父节点的位置”再叠加“父节点相对它父节点的位置”。

这和 `RectTransform` / `Control` / `WidgetTree` 的思路很像。

### 3.6.4.2 结果会缓存

`UIWidgetLayout::Context` 里有：

- `RectCache`
- `VisibilityCache`
- `ScratchVisiting`

这说明布局不是每次都傻算一遍，而是会做缓存和循环保护。

这点很重要。  
因为 UI 树往往会被频繁查询，如果每个控件都反复递归整棵树，开销会很快放大。

### 3.6.4.3 可见性不是一个布尔值那么简单

`ResolveVisible()` 不只是看 `Visible`。

它还要看：

- 父节点是否可见
- 当前节点是否属于当前页面
- 编辑器模式下是否应该显示
- 是否被裁剪区域挡住

所以你可以把 UI 的可见性理解成：

```text
最终可见 = 自己可见 && 父级可见 && 页面可见 && 编辑器规则允许 && 没被裁掉
```

### 3.6.4.4 剪裁区域很关键

滚动列表、分页面板、对话框内容区都需要剪裁。

`UIWidgetLayout` 负责算父级裁剪区域，`UISystem` 负责把裁剪结果交给渲染命令。

这就是为什么 UI 不是简单地“摆上去就完了”，而是要有一个完整的布局与裁剪流程。

## 3.6.5 渲染链路：`UISystem -> UIRenderer -> Renderer2D`

UI 的绘制不是直接写 OpenGL，而是经过一层 UI 渲染器。

### 3.6.5.1 主流程

`UISystem::RenderUI()` 做的是整套 UI 的总调度。

它会：

1. 收集场景里的 UI 实体
2. 按 `SortOrder` 排序
3. 算布局
4. 算可见性
5. 设置剪裁
6. 按组件类型逐个调用 `UIRenderer`

然后 `UIRenderer` 再把这些 UI 元素翻译成 `Renderer2D` 的绘制调用。

### 3.6.5.2 `BeginUIPass` 和 `EndUIPass`

`UIRenderer::BeginUIPass()` 会做几件事：

- 关闭深度测试
- 关闭 scissor 的旧状态
- 建一个 UI 正交相机
- 调用 `Renderer2D::BeginScene(...)`

`UIRenderer::EndUIPass()` 会：

- `Renderer2D::EndScene()`
- 恢复深度测试
- 恢复原来的 view-projection

这说明 UI 是一条独立的渲染 pass，而不是随便混到 3D 场景里一起画。

### 3.6.5.3 为什么 UI 适合走 `Renderer2D`

因为大部分 UI 都是二维矩形、文本和少量曲线：

- 面板是 quad
- 按钮是 quad
- 图片是 quad
- 进度条是 quad
- 滑条是 quad
- 文本也是一堆 glyph quad
- 技能树连线是 line / path

所以 UI 最自然的落点就是 `Renderer2D`。

### 3.6.5.4 典型绘制顺序

`UISystem` 里会按照固定顺序画组件，保证叠放关系稳定：

```text
Panel
ProgressBar
Button
Circle
Slider
ScrollView
Path
SkillTreeView
Checkbox
Text
Image
RadialCooldown
```

这不是随便排的。  
它代表一种常见 UI 组合逻辑：

- 先画底
- 再画填充
- 再画交互控件
- 再画文字和图标
- 最后画遮罩或特效

### 3.6.5.5 `RenderCommand` 在这里干什么

UI 渲染很依赖这些底层命令：

- `SetScissorTest`
- `SetScissor`
- `DisableDepthTest`
- `EnableDepthTest`
- `Flush`

尤其是 `Flush()`。

因为一旦裁剪区域变化，前面的批次就不能混到后面的裁剪里去了，所以要先把 batch 刷出去，再改 scissor。

这也是 UI 渲染里非常经典的一点：  
**批处理和裁剪天生有冲突，必须通过 flush 协调。**

### 3.6.5.6 `UIRenderer` 画了哪些东西

`UIRenderer` 里不只是简单画图片和文本。  
它还封装了很多具体控件：

- `DrawUIPanel`
- `DrawUIButton`
- `DrawUIProgressBar`
- `DrawUISlider`
- `DrawUIScrollView`
- `DrawUIPath`
- `DrawUIBezier`
- `DrawUISkillTreeView`
- `DrawUICheckbox`
- `DrawUIRadialCooldown`
- `DrawUIText`

这说明 Wheatear 的 UI 不是“一个矩形 + 一行字”的最低配，而是已经有了一套偏完整的运行时组件库。

### 3.6.5.7 文字是怎么从组件走到屏幕上的

UI 里最容易被忽略、但最值得细讲的一条链路，其实是文字。

在 Wheatear 里，`UITextComponent` 不是“存一段字符串”那么简单，它还带着：

- `Text`
- `FontPath`
- `FontSize`
- `Padding`
- `AutoFit`
- 对齐方式
- 描边和阴影

真正的绘制链路大致是：

```text
UITextComponent
    ↓
UIRenderer::DrawUIText()
    ↓
GetUIFont(FontPath)
    ↓
AssetAliasRegistry::Resolve() -> AssetPath::Resolve()
    ↓
Font::Create() / Font 缓存 / 默认字体兜底
    ↓
TextRenderer::MeasureText()
    ↓
TextRenderer::DrawText()
    ↓
Renderer2D::DrawTextGlyph()
```

这条链路里有几个关键点很适合教材里展开讲：

1. **字体不是硬编码路径**  
   `GetUIFont()` 先走资源别名，再走资源路径解析，最后才真正去创建 `Font`。  
   这样 UI 文本可以只写 `"font.ui_default"` 这种逻辑名，而不用把磁盘路径写死。

2. **字体有兜底机制**  
   默认字体会尝试一串候选项：项目字体、系统字体、中文回退字体、拉丁字体。  
   这意味着哪怕项目资源不完整，UI 也不至于整块崩掉。

3. **绘制前先测量**  
   `TextRenderer::MeasureText()` 会先算字宽、行高、换行、缩放、裁剪，再决定最终摆放位置。  
   所以文字不是“直接画”，而是“先算，再画”。

4. **阴影和描边是额外的绘制参数**  
   `TextRenderParams` 里带着 outline、shadow、clip、wrap、max height。  
   这说明文本渲染已经不是最原始的 bitmap 字符拼接，而是一套可控的 UI 文本管线。

5. **可以提前预热字体和字形**  
   `UIRenderer::PreloadUIText()` 会在真正绘制前把文本对应的字形先准备好。  
   这样长对白、设置页、列表页第一次打开时，不容易因为临时加载字体而卡顿。

如果用一个最常见的 VN 对话框来理解，就是：

```text
对白脚本更新文本
    ↓
UITextComponent.Text 变化
    ↓
UIRenderer 先测量这句话能不能塞进气泡
    ↓
必要时 AutoFit
    ↓
TextRenderer 逐字布局
    ↓
Renderer2D 画出字形 quad
    ↓
屏幕上出现对白
```

这条链路的价值在于：  
**UI 的“字”不只是显示内容，而是一个完整的布局、资源、渲染协作结果。**

## 3.6.6 输入链路：`UIInputSystem` 怎么处理点击、拖拽、滚动

UI 最有意思的地方之一，是它会把“鼠标输入”翻译成“控件状态变化”。

### 3.6.6.1 主入口

`UIInputSystem::OnUpdate(scene, mouseX, mouseY, viewportWidth, viewportHeight)` 是主入口。

它会把鼠标坐标换算到 UI 需要的空间里，然后逐个检查当前鼠标命中的 widget。

### 3.6.6.2 它关心哪些状态

UIInputSystem 不只是判断“点中了没”，它还维护了很多运行时拖拽状态：

- 拖动面板
- 拖动滚动条
- 拖动技能树视图
- 拖动滑条
- 鼠标是否处于按下状态

也就是说，UI 输入系统本质上是一个很小的交互状态机。

### 3.6.6.3 按钮怎么触发

按钮的点击流程大致是：

```text
鼠标按下 / 松开
    ↓
Hit Test
    ↓
确认当前 widget 是 UIButton
    ↓
FireOnClick()
    ↓
CommandBus::Execute(...)
```

这点非常重要。

因为按钮本身不直接知道“点击后要干什么”，它只负责触发一个命令名。  
真正的业务逻辑交给 `CommandBus` 和上层系统处理。

这就是 UI 和玩法解耦的典型方式。

### 3.6.6.4 滑条怎么改值

`UISliderComponent` 不是静态图片，它是可交互控件。

拖动时，`UIInputSystem` 会算出归一化值，然后更新滑条状态。  
如果该滑条绑定了 `OnValueChangedFunction`，还会继续触发命令。

源码里还专门有一类 native command 处理，比如：

- `progression:set_text_speed`
- `progression:set_master_volume`
- `progression:set_bgm_volume`
- `progression:set_sfx_volume`
- `progression:equipment_page_slider`

这就说明滑条不只是调一个数，还可以直接接到设置页、装备页、音量页这样的玩法流程里。

### 3.6.6.5 滚动视图怎么工作

`UIScrollViewComponent` 维护：

- 内容高度
- 当前偏移
- 鼠标滚轮状态
- 滚动条拖拽状态

所以一个列表能滚，不只是因为“摆了很多项”，而是因为输入系统把滚轮、拖拽和剪裁一起处理了。

### 3.6.6.6 复选框和技能树

复选框和技能树是很好的例子。

- 复选框在鼠标释放时切换状态
- 技能树节点点击后可以变成选中节点
- 节点命令可以拼出 `CommandPrefix + nodeId`

这说明 UI 输入系统并不只服务传统按钮，还服务图状交互界面。

### 3.6.6.7 一个完整输入例子：设置页滑条怎么把值送到命令总线

滑条是最适合拿来讲“输入如何驱动业务”的例子。

完整链路大致是：

```text
鼠标按下
    ↓
UIInputSystem::OnMousePressed()
    ↓
OnUpdate() 里做 Hit Test
    ↓
命中 UISliderComponent
    ↓
拖动时调用 SetNormalized()
    ↓
鼠标释放
    ↓
OnMouseReleased()
    ↓
ExecuteSliderNativeCommand() 或 FireScriptCallback()
    ↓
CommandBus::Execute(...)
```

这里最值得写清楚的是三件事：

1. **UIInputSystem 不直接改业务状态**  
   它只负责把鼠标动作翻译成“某个控件被交互了”。

2. **滑条释放时才真正提交命令**  
   这让拖动过程和最终生效分开了。  
   玩家拖动的是预览态，松手后才是确认态。

3. **命令名是桥梁**  
   比如音量、文字速度、装备页切换这些设置项，最终都可以落到 `CommandBus`。  
   这样 UI 只关心“发什么命令”，不关心“命令最后怎么执行”。

教材里可以把它讲成一句话：

```text
UIInputSystem 负责把鼠标变成命令入口，CommandBus 负责把命令变成游戏动作。
```

如果再往下一层看，滚轮输入也是同一类思路：

```text
OnMouseScrolled()
    ↓
定位鼠标下的 UIScrollView
    ↓
更新 OffsetY
    ↓
ClampOffset()
    ↓
下一帧按新的裁剪和布局重画
```

所以滚动列表并不是“多画几条项”，而是“输入、布局、裁剪、重绘”一起动。

## 3.6.7 动画系统：`UIAnimatorComponent` 怎么让 UI 活起来

很多初学者会把 UI 当成“静态摆件”，但实际项目里 UI 经常需要动画：

- 菜单入场淡入
- 对话框滑入
- 结果页弹出
- 按钮悬停脉冲
- 冷却提示抖一下

Wheatear 里这些效果主要由 `UIAnimatorComponent` 驱动。

### 3.6.7.1 它的思路

UI 动画不是“单独一套动画系统”，而是直接作用于 UI 组件本身。

它会记录运行时基准状态，然后在每帧里根据时间做插值：

- 位置偏移
- 缩放
- 透明度
- 颜色

### 3.6.7.2 常见预设

源码里已经有几种现成预设：

- `fade_in`
- `slide_fade_in`
- `result_pop`
- `pulse`
- `hover_pulse`

这些预设覆盖了大多数 2D 游戏 UI 的常见需求。

### 3.6.7.3 为什么要保存 base state

这是一个很容易讲给面试官听的点。

如果动画直接在原始值上不断叠加，最终会把位置、缩放、颜色越改越歪。  
所以系统会先保存：

- widget 原始位置
- image 原始透明度 / 颜色
- panel 原始颜色
- text 原始颜色
- button 原始颜色
- progress bar 原始颜色

然后每一帧按进度恢复并重算。

这就是“动画驱动状态”，而不是“状态被动画污染”。

### 3.6.7.4 一个典型场景

比如结果页出来时：

```text
Result scene 打开
    ↓
UIAnimatorComponent 触发 result_pop
    ↓
背景淡入
面板弹出
按钮轻微脉冲
标题文字逐渐显现
```

这种效果在 2D 游戏里很常见，也很能体现引擎是否“有生命感”。

## 3.6.8 运行时工具：`UIRuntimeTools` 与 `GameplayUIService`

UI 不应该只靠场景编辑器慢慢拖。

真正的游戏运行时，经常要根据战斗结果、任务状态、设置项、剧情状态去动态改 UI。  
这就是 `UIRuntimeTools` 和 `GameplayUIService` 的价值。

### 3.6.8.1 `UIRuntimeTools` 干什么

它是一个偏底层的运行时操作层，提供这些能力：

- `SetWidgetVisible`
- `SetWidgetTopLeft`
- `SetWidgetCenter`
- `SetWidgetParent`
- `SetText`
- `SetProgress`
- `SetRadialProgress`
- `SetImageAlpha`
- `SetImageColor`
- `SetImageTexture`
- `IsButtonHovered`

这层的意义是：  
上层不用直接摸 component 细节，只要用这些工具函数就能安全地改 UI。

### 3.6.8.2 `GameplayUIService` 干什么

它更偏玩法层接口。

目前能看到的封装主要有：

- `SetVisible`
- `SetHealth`
- `SetResource`
- `SetTooltip`

你可以把它理解成：

```text
玩法代码不要直接碰 UI 组件，先走 GameplayUIService。
```

这是一种很典型的分层习惯。

### 3.6.8.3 一个血条例子

比如角色受伤后，战斗模块不需要知道血条实体叫什么，也不需要知道它挂了什么组件。

它只需要：

```text
GameplayUIService::SetHealth(...)
```

然后内部去更新：

- 进度条数值
- 数字文本
- 可能还有闪红效果

这就是“玩法只管结果，UI 负责表现”的分工。

### 3.6.8.4 一个提示框例子

`SetTooltip()` 更能体现 UI 作为服务层的意义。

通常它会做这些事：

- 打开 tooltip 面板
- 设置文本
- 调整位置到鼠标附近或目标附近
- 避免越界

这就是典型的 runtime UI 需求，不是编辑器里拖个面板就能完全替代的。

## 3.6.9 UI 如何随 Scene 一起存

UI 既然是运行时 Scene 的一部分，那它就必须能被保存和加载。

这就是 `SceneSerializerUIComponents.cpp` 的作用。

### 3.6.9.1 它序列化什么

至少已经能看到这些 UI 组件会被序列化：

- `UICanvasComponent`
- `UIWidgetComponent`
- `UIAnimatorComponent`
- `UIImageComponent`
- `UIRadialCooldownComponent`
- `UICircleComponent`
- `UIPanelComponent`
- `UITextComponent`
- `UIButtonComponent`
- `UIProgressBarComponent`
- `UISliderComponent`

这意味着一张场景文件里，不只是角色和地形，也可以直接包含 UI 布局。

### 3.6.9.2 为什么这样做

好处很直接：

- 场景就是完整内容包
- UI 和场景状态天然同步
- 保存 / 读档时更容易恢复界面
- VN、战斗、结果页都能按场景组合

### 3.6.9.3 常见误区

很多人写 UI 时会把“运行时 UI”做成全局单例，结果：

- 切场景要自己清
- 读档要自己恢复
- 玩法和界面绑死

Wheatear 这里更像是 Scene 驱动 UI。  
这对做 2D 游戏特别顺，因为很多界面本来就是关卡 / 战斗 / 菜单的一部分。

## 3.6.10 具体例子一：战斗 HUD 的血条和资源条

这是最适合入门的例子。

### 3.6.10.1 你会在场景里看到什么

通常会有：

- 背景面板
- 血条 `UIProgressBarComponent`
- 蓝条 / 资源条 `UIProgressBarComponent`
- 数值文本 `UITextComponent`
- 图标 `UIImageComponent`

### 3.6.10.2 运行时链路

战斗数值变化
    ↓

### 3.6.10.3 这个例子说明什么

它说明 UI 不只是“显示信息”，还负责把战斗状态可视化。

对于 2D 游戏来说，这一类 HUD 往往是玩家最常接触的内容，所以你在面试里讲这个例子非常合适。

## 3.6.11 具体例子二：按钮、设置滑条和确认框

## 3.6.12 具体例子三：VN 对话框、滚动列表和技能树

这一组更接近你项目里“剧情 + 玩法 + 工具链”混合的实际情况。

### 3.6.12.1 VN 对话框

这一小节不要只把它看成“一个对话框 UI”，而要把它看成**剧情状态机的可视化层**。

你真正要读的源码主要是这几份：

- `Wheatear/src/Wheatear/Modules/VisualNovel/VisualNovelScript.h`
- `Wheatear/src/Wheatear/Modules/VisualNovel/VisualNovelRuntime.h`
- `Wheatear/src/Wheatear/Modules/VisualNovel/VisualNovelInputService.cpp`
- `Wheatear/src/Wheatear/Modules/VisualNovel/VisualNovelSystem_SceneBindings.cpp`
- `Wheatear/src/Wheatear/Modules/VisualNovel/VisualNovelSystemInternal.h`

这一节最适合用“一个完整场景”来讲。

### 3.6.12.1.1 一段完整 VN 场景长什么样

可以直接拿 `Projects/WheatearDemo/assets/vn/intro.vn` 里的开头来讲：

```vn
# Wheatear 竖切入口 VN。

@label start
@background assets/sandbox/vn/backgrounds/bg_modern_schoolroad_morning.png
@music assets/sandbox/audio/bgm/vn_school_morning.wav "晨路微光"
@speed 42
@character Mira 青梅 assets/sandbox/vn/portraits/aoba_{expression}.png
@character Leo 主角 assets/sandbox/vn/portraits/protag_school_{expression}.png
@show Mira:smile Leo:neutral
Mira: 今天也一起走吧。你要是再赖床，我就把你的早餐拿去喂楼下的猫。
Leo: 你这人说话怎么总像在宣布命令。
@expression Mira worried
Mira: 不过，今天早上有点奇怪。路口那个人，从刚才开始就一直看着我们。
@expression Leo shocked
Leo: 等等，他手里是不是有刀？
@choice 进入第一章假玩法 -> event:go_fake_combat | 先吐槽两句 -> roast
```

这一段已经够把 VN 的核心链路串起来了：

- `@background`：背景切换
- `@music`：BGM 切换和标题提示
- `@speed`：当前对白打字速度
- `@character` / `@show` / `@expression`：立绘和表情
- 普通对白行：名字 + 台词
- `@choice`：分支按钮
- `event:go_fake_combat`：外部命令
- `roast`：脚本内 label 跳转

也就是说，VN 不是“把一段字贴到屏幕上”，而是“剧情脚本在驱动整个场景状态”。

### 3.6.12.1.2 这些命令最后落到哪些 UI 数据

在场景里，`VisualNovelComponent` 已经把需要的 UI 目标都预先命名好了：

- `SpeakerTextEntityName`
- `BodyTextEntityName`
- `AdvanceHintEntityName`
- `BackgroundEntityName`
- `FloorEntityName`
- `CharacterEntityPrefix`
- `ChoiceEntityPrefix`
- `CommandBarEntityName`
- `HistoryPanelEntityName`
- `SettingsPanelEntityName`
- `SaveLoadPanelEntityName`

所以 VN 的绑定方式不是“临时找一个按钮改文本”，而是“通过稳定的实体名，把剧情状态映射到既定 UI 结构”。

这也是为什么 `VisualNovelSystem_SceneBindings.cpp` 里会有：

```text
SetWidgetVisible()
SetText()
SetButtonCommand()
PreloadTextForEntity()
TrySetSpriteTexture()
TryPlaySpriteAnimation()
```

它们不是零散操作，而是一整套绑定层。

### 3.6.12.1.3 `UpdateSceneBindings()` 怎么把当前剧情变成界面

这一段是本小节最关键的源码链。

大致流程是：

1. `state.Runtime.GetCurrentLine()` 先取当前剧情行
2. 算出 `showStoryUi`、`waitingForChoice` 这种全局显示状态
3. 通过 `SetWidgetVisible()` 控制对话框、历史、设置、存读档页面显示
4. 用 `PreloadTextForEntity()` 预热名字和正文
5. 用 `SetText()` 填充 `SpeakerText`、`BodyText`、`AdvanceHint`
6. 用 `CollectVisibleChoiceIndices()` 过滤掉被条件隐藏的选项
7. 用 `SetButtonCommand()` 把可见选项按钮接到命令或 label
8. 用 `TrySetSpriteTexture()` / `TryPlaySpriteAnimation()` 更新背景和角色立绘

这里有两个很适合讲给初学者听的点。

第一，正文不是直接显示整句，而是显示：

```text
state.Runtime.GetVisibleText()
```

也就是说，对话框上的字是“运行时逐字推进”出来的，不是脚本原文一次性全画上去。

第二，角色立绘不是只靠一张固定图，而是会根据表达式、当前角色、是否是说话者来调整：

- 当前说话者更亮
- 非说话者半透明
- 背景图优先走纹理
- 如果没有纹理，就退回颜色块

这就把“剧情场景”从静态画面变成了一个会随着台词变化的动态界面。

### 3.6.12.1.4 输入怎么推进剧情

VN 的输入不是只靠鼠标点按钮。  
`VisualNovelInputService::Sample()` 已经把这几个动作单独采样出来了：

- `vn.advance`
- `vn.auto`
- `vn.history`
- `vn.save`
- `vn.load`
- `1 ~ 9` 的选项键

对应到 runtime，大致就是：

```text
Advance()
Choose(choiceIndex)
SetAutoPlay()
ToggleAutoPlay()
SaveState()
LoadState()
```

这条链路最值得强调的一点是：  
**UI 负责把点击变成命令，VN runtime 负责把命令变成剧情状态变化。**

所以你可以把它理解成：

```text
鼠标 / 键盘输入
    ↓
UIInputSystem / VisualNovelInputService
    ↓
按钮命令 / runtime 操作
    ↓
VisualNovelRuntime::Advance() / Choose()
    ↓
当前行、历史、选项、自动播放状态改变
    ↓
下一帧 UpdateSceneBindings() 再把新状态画回 UI
```

### 3.6.12.1.5 选项分支为什么要单独讲

VN 的选项不是普通按钮列表。  
它有两个很重要的特殊点：

1. 有些选项会被条件隐藏  
   例如 `if flag <id>` 或更完整的条件表达式。

2. 选项按钮的显示顺序不能乱  
   因为隐藏一个选项后，后面的可见选项必须保持稳定编号。

所以代码里会先做：

```text
CollectVisibleChoiceIndices()
```

然后再按可见顺序绑定按钮文本和命令。

这也正好解释了为什么 `@choice` 里有的分支是：

```text
进入第一章假玩法 -> event:go_fake_combat
```

而有的分支只是：

```text
先吐槽两句 -> roast
```

前者会被 `CommandBus` 接走，后者更像是脚本内部跳转。

### 3.6.12.1.6 这一例子最适合怎么在面试里讲

你可以直接这样讲：

```text
VN 这一层不是独立前端，而是剧情状态机的可视化层。
脚本负责描述剧情状态，Runtime 负责逐字推进和分支跳转，
SceneBindings 负责把当前行映射成 UI，InputService 负责把按键和点击翻译成剧情操作。
```

这句话基本就把这节的骨架说清楚了。

一个 VN 对话框常见结构可以再总结成：

- 底板 `UIPanelComponent`
- 角色立绘 `UIImageComponent`
- 名字文本 `UITextComponent`
- 对话文本 `UITextComponent`
- 下一句按钮 `UIButtonComponent`
- 选项按钮若干 `UIButtonComponent`

如果要做入场动画，就再挂 `UIAnimatorComponent`。

它的意义在于：  
对话不是剧情系统自己直接画字，而是剧情系统通过 UI 组件把“当前剧情状态”可视化。

### 3.6.12.2 滚动列表

这一类界面看起来像“很多条目往下排”，但本质上是一个**滚动容器**。

它最常见的用途就是：

- VN 历史回顾
- 存档 / 读档槽位
- 道具列表
- 设置项列表

如果没有滚动容器，长列表只能硬塞在屏幕里，结果通常就是：

- 文字挤爆
- 按钮点不到
- 裁剪混乱
- 输入滚动和拖拽互相打架

所以这部分一定要从“滚动容器”而不是“列表排版”来理解。

### 3.6.12.2.1 这一层到底负责什么

在 Wheatear 里，滚动列表通常由四个东西共同完成：

- `UIScrollViewComponent`：保存滚动状态
- `UIWidgetLayout`：把子元素坐标减去滚动偏移，并做裁剪
- `UIInputSystem`：处理鼠标滚轮和拖拽滑条
- `UIRenderer::DrawUIScrollView()`：把滚动条轨道和滑块画出来

也就是说，它不是一个“单独会滚的控件”，而是**布局、输入、渲染三者一起工作**。

### 3.6.12.2.2 `UIScrollViewComponent` 里存什么

这个组件是滚动容器的状态中心：

- `OffsetY`：当前滚动偏移
- `ContentHeight`：内容总高度
- `WheelStep`：滚轮每次滚动步长
- `ScrollbarWidth`：右侧滚动条宽度
- `EnableWheel`：是否允许滚轮
- `ShowScrollbar`：是否显示滚动条
- `DragScrollbar`：是否允许拖拽滑块
- `ClampToContent`：是否限制在内容范围内

运行时状态还会记录：

- `RuntimeThumbHovered`
- `RuntimeThumbDragging`
- `RuntimeDragStartMouse`
- `RuntimeDragStartOffsetY`

这里最值得记住的一点是：  
**`OffsetY` 不是临时变量，而是 UI 状态的一部分。**

它会被布局系统消费，也会被序列化保存，历史面板和存档页都能复用。

### 3.6.12.2.3 渲染时是怎么画出来的

滚动列表的绘制入口是 `UIRenderer::DrawUIScrollView()`。

它通常会画两部分：

1. 轨道背景
2. 滑块 thumb

thumb 的高度由内容高度决定：

```text
thumbHeight ≈ viewportHeight / ContentHeight
```

内容越长，thumb 越短；内容越少，thumb 越长。  
这就是滚动列表最直观的视觉反馈。

同时，`UIWidgetLayout` 会在算子节点矩形时处理滚动偏移：

```text
如果父节点是 UIScrollViewComponent
    子节点 localRect.Top / Bottom -= OffsetY
```

这意味着真正“滚动”的不是列表项本身，而是**它们在布局里被整体平移了**。

### 3.6.12.2.4 输入是怎么驱动滚动的

`UIInputSystem` 里有两条滚动路径。

第一条是鼠标滚轮：

```text
OnMouseScrolled()
    ↓
找到鼠标下的 UIScrollView
    ↓
OffsetY -= yOffset * WheelStep
    ↓
ClampOffset()
```

第二条是拖拽滑块：

```text
鼠标按下滑块
    ↓
记录 RuntimeDragStartMouse
    ↓
记录 RuntimeDragStartOffsetY
    ↓
拖动时按鼠标位移换算 OffsetY
    ↓
ClampOffset()
```

所以滚动不是“鼠标滚一下就重画一遍列表项”，而是：

**输入改状态，状态改布局，布局再决定重绘结果。**

### 3.6.12.2.5 VN 历史面板是最好的例子

VN 历史面板其实就是一个滚动列表。

`UpdateHistoryScroll()` 这段逻辑非常适合教材讲解：

1. 先把历史文本拼出来
2. 估算总行数
3. 计算 `contentHeight`
4. 写回 `UIScrollViewComponent::ContentHeight`
5. 同时把历史文本实体的 `UIWidgetComponent::Size.y` 改成同样高度

也就是说，它不是只把文字丢进去，而是把“内容总高”和“滚动状态”一起同步了。

这样做的好处是：

- 历史条目再长也不会撑爆面板
- 滚轮能自然工作
- 滑块比例会自动正确
- 文字和滚动条始终一致

这就是一个很典型的“动态内容驱动滚动容器”的例子。

### 3.6.12.2.6 VN 存档 / 读档页也是同一套路

存档页更容易让人看懂滚动列表的价值。

在 `EnsureVNSaveLoadLayout()` 里，滚动容器会包住一串槽位按钮：

- `VN_SaveLoadSlotScroll`
- `VN_SaveLoad_Slot_1`
- `VN_SaveLoad_Slot_2`
- ...

每个槽位按钮的文字来自：

```text
GameProgress::BuildGameSaveSlotButtonText(...)
```

按钮命令则直接绑定成：

- `gamesave:slot_save_N`
- `gamesave:load_N`

如果当前是保存模式，而且该槽位已有存档，还会额外弹出确认面板：

- `VN_SaveLoadConfirmPanel`
- `VN_SaveLoadConfirmText`
- `VN_SaveLoadConfirmYes`
- `VN_SaveLoadConfirmNo`

这说明滚动列表并不只是“装很多按钮”，它还能承接：

- 分页前的槽位浏览
- 覆盖确认
- 保存 / 读取模式切换

`ProgressionSaveLoadPageService::EnsureLayout()` 也是同一种思路：  
它先找到作者摆好的滚动视图，再把槽位、标题、关闭按钮、确认框全部绑定进去。

### 3.6.12.2.7 设置页为什么也该放在这一节里

严格说，当前设置页更像是“纵向控制面板”，不一定总是滚动列表。  
但它和滚动列表用的是同一套思想：**由数据决定条目，由条目决定交互**。

`ProgressionSettingsPageService::UpdateAudioControls()` 做的事情很典型：

- 找到作者摆好的滑条和文字
- 给滑条绑定命令
- 再把 `UserSettings` 里的当前值写回滑条

这说明在你的引擎里，长页面不管最后是滚动容器还是固定控制面板，底层都遵循同一类绑定模式。

### 3.6.12.2.8 面试里可以怎么讲

可以直接说：

```text
滚动列表不是把很多控件堆起来，而是把列表内容、滚动状态、裁剪和输入统一起来。
在 Wheatear 里，UIScrollViewComponent 管状态，UIWidgetLayout 管偏移和裁剪，
UIInputSystem 管滚轮和拖拽，UIRenderer 管滚动条外观。
```

这句话基本就把这一节讲透了。

### 3.6.12.3 技能树

技能树是这套 UI 系统里最适合讲“图状交互”的例子。

它比按钮栏、设置页、对话框都更复杂，因为它同时包含：

- 节点
- 连线
- 选中态
- 锁定态
- 悬停态
- 拖拽平移
- 章节解锁
- 资源消耗

也就是说，它不是一棵“摆在屏幕上的树”，而是一套**可交互的图形化进度图**。

### 3.6.12.3.1 这一页到底是怎么被拼出来的

先看绑定名本身就能知道页面结构：

- `skill_tree.view`
- `skill_tree.subtitle`
- `skill_tree.status`
- `skill_tree.details`
- `skill_tree.materials`
- `skill_tree.learn`
- `skill_tree.magic_sword`

这些名字说明技能树页不只是一个大图，它还配有：

- 说明文字
- 状态面板
- 详情面板
- 材料面板
- 学习按钮
- 进度条

所以它其实是“树图 + 信息面板 + 操作按钮”的组合页。

### 3.6.12.3.2 节点数据从哪来

技能树页面的数据不是手写在渲染器里的，而是从进度定义里同步出来的。

`ProgressionSkillTreePageService::SyncView()` 大致会做这些事：

1. 找到场景里的 `SkillTreeView`
2. 读取 `ProgressionContent::FindSkillNode(...)`
3. 生成或重建 `UISkillTreeNodeView` 列表
4. 把运行时状态同步回组件
5. 更新 `Pan`、`SelectedNodeId`、`CommandPrefix`

每个节点会带上这些关键数据：

- `Id`
- `ParentId`
- `Position`
- `IconPath`
- `Branch`
- `UnlockChapter`
- `Learned`
- `Available`
- `Selected`
- `Locked`

其中最值得讲的是这几个状态：

- `UnlockChapter`：这一节点第几章后可见
- `Learned`：是否已经学会
- `Available`：当前章节是否可点
- `Locked`：未学会时的锁定态
- `Selected`：当前选中的节点

所以技能树不是单纯的“画图”，而是“进度条件驱动的图”。

### 3.6.12.3.3 渲染链路是什么

技能树的渲染入口是 `UIRenderer::DrawUISkillTreeView()`。

它的流程可以拆成四步：

#### 1. 先画背景和底层氛围

- `BackgroundColor`
- 背景同心环
- 中心网格感的装饰圈

这一步是为了让树图不至于像一块白板。

#### 2. 再画连线

连线不是硬直线，而是贝塞尔曲线。

它会根据：

- 父节点位置
- 子节点位置
- `NodeEdgeInset`
- `CurveAmount`
- `LineThickness`
- `LineSegments`

来决定最后的形状。

如果节点已经学会，连线颜色会更亮；如果没学会，就走普通线色。  
如果开启 `DrawLineGlow`，还会先画一层 glow，再画一层主线。

#### 3. 再画节点主体

每个节点会画：

- 外圈
- 内核
- 高亮圈
- 锁定遮罩

不同状态对应不同颜色：

- `NodeColor`
- `LockedNodeColor`
- `HoverNodeColor`
- `SelectedNodeColor`
- `CoreNodeColor`
- `LockColor`

#### 4. 最后叠图标

`IconPath` 会被转成纹理，再画到节点中心。

这就是为什么技能树节点看起来不像“纯几何图”，而是可以承载图标、分支、章节和状态的一整套页面。

### 3.6.12.3.4 输入怎么处理

技能树的输入处理也很有代表性，因为它不是标准的按钮点击。

`UIInputSystem` 里有一段专门的技能树逻辑：

- 先 `HitTestSkillTreeNode()`
- 再判断是不是在拖拽
- 如果只是轻点，就选中节点
- 如果拖动距离太大，就认为是在平移视图

这意味着技能树有两个交互模式：

1. **点节点**  
   选中一个技能，更新详情、材料、学习按钮。

2. **拖画布**  
   平移整张树图，查看别的分支。

拖拽时会把：

- `RuntimeDragStartMouse`
- `RuntimeDragStartPan`
- `RuntimeDragDistance`

都记录下来。  
鼠标松开时，如果拖动距离很小且命中节点，就把它当成一次点击。

这也是技能树比普通列表更适合拿来讲“图状交互”的原因。

### 3.6.12.3.5 它怎么和养成系统连起来

技能树并不是只给你看，它要直接服务养成流程。

在 `ProgressionSkillTreePageService` 里，节点状态会根据进度状态更新：

- 当前章节
- 已解锁技能
- 魔剑等级
- 选中节点

同时，页面还会把：

- `SelectedNodeId`
- `SkillTreePanX`
- `SkillTreePanY`

这类状态同步回 `GameProgress`，这样玩家下次打开页面还能接着看。

这部分非常适合拿来解释“UI 状态为什么要和进度系统连起来”。

因为技能树页不是一次性菜单，它是长期存在的养成面板。  
玩家会反复打开、反复拖动、反复选中，所以这些状态应该被保留。

### 3.6.12.3.6 这一页是怎么存下来的

技能树组件本身也会被序列化。

`SceneSerializerUIComponents.cpp` 里保存了：

- `Pan`
- `MinPan`
- `MaxPan`
- `NodeSize`
- `NodeEdgeInset`
- `LineThickness`
- `CurveAmount`
- `VirtualizationMargin`
- `LineSegments`
- `BackgroundRingCount`
- `DrawLineGlow`
- `CommandPrefix`
- `SelectedNodeId`
- `Nodes`

节点列表 `Nodes` 里面还会存：

- `Id`
- `ParentId`
- `Position`
- `IconPath`
- `Branch`
- `UnlockChapter`
- `Learned`
- `Available`
- `Selected`
- `Locked`

所以这一页不是“运行时才拼出来的临时图”，而是能被 Scene 保存、被编辑器恢复、被运行时继续使用的页面。

### 3.6.12.3.7 一个完整例子

比如魔剑技能树：

```text
核心节点已学会
    ↓
第二层技能在第二章后开放
    ↓
页面同步节点可用状态
    ↓
UIRenderer 画出连线和锁定态
    ↓
玩家点击某个节点
    ↓
UIInputSystem 选中节点
    ↓
CommandPrefix + SelectedNodeId
    ↓
ProgressionSystem 更新学习结果
    ↓
GameProgress 记录当前技能树状态
```

这条链路特别适合面试时讲，因为它把：

- UI
- 养成
- 进度
- 命令驱动

全部串起来了。

### 3.6.12.3.8 面试时可以怎么讲

可以直接说：

```text
技能树不是普通菜单，而是一个图状交互页。
ProgressionSkillTreePageService 负责把养成数据同步成节点，
UIRenderer 负责画节点、连线和锁定态，
UIInputSystem 负责拖拽和平移，点击后再通过 CommandPrefix 回到进度系统。
```

这句话基本就够了。

这也说明 Wheatear 的 UI 不是只够做菜单，而是已经能支撑稍复杂的功能页。

## 3.6.13 和 Unity UGUI、UE UMG、Godot Control 的对照

这部分面试经常会问。

先说结论：Wheatear 的 UI 不是把 Unity、UE、Godot 直接抄一遍，而是更接近一种**“场景内 Retained Mode UI + 命令驱动绑定层”**的混合体。

它有几个很明显的特征：

- 像 Unity / Godot 一样，有明确的控件树和锚点、层级、可见性
- 像 UMG / Slate 一样，页面是从数据和状态同步出来的，不是一次性画死的
- 像自研轻量引擎一样，核心交互最终走的是 `CommandBus`，不是一套庞大的通用事件框架

所以如果面试官问“你这个 UI 更像什么”，最稳妥的回答不是单押某一个，而是：

```text
布局和控件思路上像 UGUI / Control，
页面绑定方式上更像 UMG 的数据驱动，
但运行时更新和业务接入上更偏自研服务层 + CommandBus。
```

### 3.6.13.1 和 Unity UGUI 对照

Unity 里大致可以这样类比：

- `Canvas` ≈ `UICanvasComponent`
- `RectTransform` ≈ `UIWidgetComponent`
- `Image` ≈ `UIImageComponent`
- `Text` ≈ `UITextComponent`
- `Button` ≈ `UIButtonComponent`
- `Slider` ≈ `UISliderComponent`
- `ScrollRect` ≈ `UIScrollViewComponent`
- `EventSystem` ≈ `UIInputSystem`

区别在于：

- Unity 有更完整的组件生态和布局系统
- Wheatear 更偏轻量、直接、服务于当前项目目标
- Unity 更擅长大量通用 UI 玩法；Wheatear 更擅长把少数高频 2D 页面做得可控、可读、可串剧情
- Unity 的运行时 UI 可以较自由地从代码生成；Wheatear 更偏向先在 Scene 里作者化，再由服务层绑定和刷新

### 3.6.13.2 和 UE UMG 对照

UE 的 UMG 更偏 Widget Blueprint + Slate 思路。

你可以把 Wheatear 理解为：

- 数据放在 Scene 里
- 交互由输入系统处理
- 绘制由 `Renderer2D` 完成

它没有 UE 那么重的通用框架，但思路上同样是“UI 是可组合的树状数据结构”。

再进一步说，Wheatear 更接近 UE 里的“设计器里摆好控件，运行时由代码刷新状态”的那部分，而不是完全让 UI 脱离 Scene。

比如：

- VN 对话框是 `VisualNovelSystem_SceneBindings` 负责把运行时状态落到实体名上
- 存档页是 `ProgressionSaveLoadPageService` 把槽位和确认框绑定出来
- 设置页是 `ProgressionSettingsPageService` 把滑条值和按钮命令同步回去

这和 UMG 的“页面结构固定、数据动态刷新”很像，但 Wheatear 的绑定点更轻，也更贴近 Scene 里的实体命名。

### 3.6.13.3 和 Godot Control 对照

Godot 的 `Control` 体系强调：

- anchors
- containers
- signals
- theme

Wheatear 的 `UIWidgetComponent`、`ParentEntity`、`Anchor`、`SortOrder`、`CommandBus` 也能和这个思路对应起来。

进一步看，Godot 很强调 `Container` 自动布局，而 Wheatear 现在更偏“手工布局 + 局部滚动 + 业务服务刷新”。
这意味着：

- 优点是页面形状更可控，和项目 UI 风格更贴
- 缺点是复杂自适应布局要自己设计得更细

所以如果有人问你“为什么不用一个现成 UI 框架”，你可以回答：

```text
因为这个项目的目标不是做通用桌面 UI，而是做 2D 游戏里那几类高频页面，
所以我更看重 Scene 内绑定、命令驱动、可序列化、可和剧情/进度/战斗串起来。
```

### 3.6.13.4 你的引擎有什么特点

Wheatear 的 UI 更偏：

- 轻量
- 组件化
- 场景化
- 命令驱动

它不是“做一个万能 UI 框架”，而是“让 2D 游戏里最常见的界面足够好用，并且能和剧情、战斗、进度、存档串起来”。

如果再说得更具体一点，它的工作方式其实是：

- 场景里先放好作者化的 UI 实体
- 运行时用 `GameplayUILayoutService` / `UIRuntimeTools` 去找到它们
- 再用 `UIInputSystem`、`UIRenderer`、`CommandBus` 这三条链把交互、绘制和业务串起来

这和“纯代码创建 UI”不一样，也和“完全靠编辑器蓝图拼页面”不一样。
它更像一个**介于游戏场景和页面绑定层之间的轻量运行时 UI 架构**。

你可以把 `GameplayUILayoutService` 理解成这件事的中间层：

- `FindAuthoredText()`、`FindAuthoredButton()`、`FindAuthoredScrollView()` 负责确认场景里确实有作者摆好的控件
- `EnsureText()`、`EnsureButton()`、`EnsureSlider()` 负责把业务状态和命令绑回这些控件
- `SetButtonCommand()`、`SetSliderCommand()` 负责把控件输入统一接到命令系统上

所以它的核心并不是“UI 控件类型很多”，而是“控件的绑定关系很清楚”。

## 3.6.14 这一层的优点、缺点和常见误区

### 优点

- UI 直接成为 Scene 的一部分，结构清楚
- 运行时可通过服务层动态更新
- 交互和业务通过命令解耦
- 支持文本、图片、滑条、技能树、滚动视图等常见 2D 需求
- 能和剧情、战斗、菜单自然合流
- 适合 2D 游戏里最常见的 HUD、对话框、设置页、存档页、技能树这些页面
- 作者可以先把页面骨架摆进 Scene，再由运行时把状态填进去，调试时很直观
- 文本、图片、进度条、按钮都走同一套组件和工具层，页面风格统一
- 对于剧情驱动或菜单驱动的项目，命令式绑定很容易和 `CommandBus` 对上
- 结构比较轻，适合你这个主要面向简单 2D 游戏的引擎目标

### 缺点

- 布局系统没有大型引擎那么“全家桶”
- 复杂自适应布局需要更细致地设计
- UI 如果组件堆太多，会让场景更难维护
- 命令名和页面命名如果不统一，很容易变乱
- 运行时 UI 更依赖作者化实体和命名约定，页面结构要先搭好，不能完全靠代码随手长出来
- `FindEntityByName` 这种按名字找控件的方式很直观，但如果滥用在高频路径里，维护和性能都会变差
- 复杂布局、自动吸附、嵌套容器、主题系统这些能力，离成熟商业引擎还差一截
- 一旦页面命名不统一，后期排错会很痛，因为状态、命令、实体名会一起乱
- 命令驱动虽然灵活，但如果没有规范，容易从“解耦”变成“字符串到处飞”

### 常见误区

- 把运行时 UI 和编辑器 ImGui 混为一谈
- 直接在玩法代码里硬改组件，不走服务层
- 忘记预加载字体，导致第一次打开文本卡顿
- 忘记 flush，导致剪裁和 batch 打架
- 过度依赖 `FindEntityByName`，让热路径变慢
- 动画只会改值，不会恢复 base state
- 以为 `UIWidgetComponent` 就等于普通 `Transform`，其实它带的是屏幕空间布局、锚点和层级语义
- 以为 `UIScrollViewComponent` 只是“一个能滚的列表”，其实它管的是容器偏移、裁剪和滑块状态
- 以为按钮点击就是改一个布尔值，实际上它最后是走到 `CommandBus` 或页面服务上的
- 以为 UI 可以完全运行时随手生成，实际上这个架构更偏“场景里先有骨架，服务层再补状态”
- 以为动画只是加个偏移或缩放，结果把 base state 覆盖掉，切换页面后状态就漂了
- 以为文本渲染只要把字符串丢上去就行，结果忽略了字体预热、换行、裁剪和描边

这些坑都很适合拿来做“常见问题”小节。

### 3.6.14.1 这层适不适合你的项目

如果你的目标是：

- 做 2D 游戏
- 页面以 HUD、剧情、设置、存档、技能树为主
- 想让运行时 UI 和进度系统、战斗系统、剧情系统天然接在一起

那这层的设计是挺对路的。

如果你的目标是：

- 做一个通用桌面 UI 框架
- 做复杂响应式布局
- 做完全数据驱动、零作者化的前端式 UI

那这套就不够重，也不够通用。

所以这个引擎的 UI 层，本质上不是“万能”，而是“刚好够用，而且很贴你的游戏类型”。

## 3.6.16 小结

这一章其实是在回答一个很具体的问题：

```text
游戏里的界面，怎么从 Scene 数据变成真正能点、能拖、能滚、能播动画的东西？
```

Wheatear 的答案不是“做一套万能 UI 框架”，而是“把页面做成 Scene 里可组织、可刷新、可保存的一棵数据树”，再由一组服务把它真正跑起来。

你可以把这一章记成一条完整链路：

- 用 `UIComponents` 在 Scene 里描述页面结构
- 用 `UIWidgetLayout` 递归算出位置、层级、裁剪和可见性
- 用 `UISystem` 统一驱动整页更新与排序
- 用 `UIRenderer` 把控件翻译成 `Renderer2D` 的绘制命令
- 用 `UIInputSystem` 处理命中、点击、拖拽和滚动
- 用 `UIRuntimeTools` / `GameplayUIService` 在运行时改页面状态
- 用 `SceneSerializer` 把 UI 和场景一起存下来

如果再往具体场景里看，这套思路最常落在三类页面上：

- VN 对话框，状态来自剧情，UI 只是把当前台词和选项画出来
- 存档页和设置页，页面骨架在 Scene 里，数据刷新由服务层补上
- 技能树和滚动列表，既要能摆得下长内容，又要能响应输入和局部更新

所以这一章真正要记住的，不是某个控件有多少个属性，而是这套 UI 体系怎么把 Scene、输入、渲染和玩法串成一条线。

如果你已经把这一章读顺了，下一步再去看输入、脚本、命令总线、战斗 HUD 或 VN 对话系统，就会非常自然。
