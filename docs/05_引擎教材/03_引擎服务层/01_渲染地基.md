# 第 3 编 01：渲染地基

> 本章所属层级：
> - 引擎服务层：`Renderer`、`RenderCommand`、`Renderer2D`、`Renderer3D`、`Texture`、`Shader`、`Framebuffer`
> - 平台实现层：`OpenGLRendererAPI`、`OpenGLTexture`、`OpenGLShader`、`OpenGLContext`
>
> 本章目标：理解一张图是怎么被画出来的。也就是：
> - 渲染抽象层怎么把 OpenGL 包起来
> - 2D 为什么能合批
> - Scene 里的实体是怎么进入绘制队列的
> - 底层到底会调到哪些 OpenGL API
>
> 这一章会以 2D 为主，因为这是当前引擎最核心、最常用、最能体现结构的渲染地基；3D、阴影、SSAO、IBL 作为延伸部分一起讲清楚大架构。

## 3.1 渲染在整套架构里的位置

```text
应用层
    Editor / Sandbox
        ↓
Scene ECS 层
    Scene / Entity / Components / Systems
        ↓
引擎服务层
    RenderSystem / Renderer2D / Renderer3D / Texture / Shader / Framebuffer
        ↓
平台实现层
    OpenGLRendererAPI / OpenGLTexture / OpenGLShader / OpenGLContext
        ↓
第三方库
    OpenGL / glad / stb_image
```

如果说输入那一章回答的是：

```text
“玩家按了什么？”
```

那这一章回答的就是：

```text
“Scene 里的东西是怎么变成屏幕上的像素的？”
```

渲染章一定要讲得详细，因为它不仅是图像输出，更是把整个引擎的数据模型、资源系统、相机、场景系统和平台 API 全部串起来的一条主线。

## 3.3 先给结论：渲染链路长什么样

Wheatear 的渲染链路可以先记成一句话：

```text
Scene / RenderSystem 负责挑出要画的东西，
Renderer2D / Renderer3D 负责把这些东西攒成批，
RenderCommand / RendererAPI 负责把统一接口落到 OpenGL，
OpenGL 最后把数据画到 framebuffer 上。
```

再把它压成一条更具体的链：

```text
Scene 中的组件数据
    ↓
RenderSystem
    ↓
Renderer2D / Renderer3D
    ↓
RenderBatch / VertexArray / Shader / Texture / UniformBuffer
    ↓
RenderCommand
    ↓
RendererAPI::OpenGL
    ↓
glDrawElements / glDrawArrays / glBindTextureUnit / glViewport / glClear
```

这就是你在面试里可以讲的“从数据到像素”的完整路径。

## 3.4 渲染抽象层：`Renderer`、`RenderCommand`、`RendererAPI`

### 3.4.1 `Renderer` 是门面

`Renderer` 本身很薄：

```cpp
class Renderer
{
public:
    static void Init();
    static void Shutdown();
    static void OnWindowResize(uint32_t width, uint32_t height);
    static RendererAPI::API GetAPI();
};
```

它做的事情很少，但很关键：

```cpp
void Renderer::Init()
{
    RenderCommand::Init();
    Renderer2D::Init();
    Renderer3D::Init();
}
```

也就是说，应用层只要调用一个：

```cpp
Renderer::Init();
```

就能把底层渲染链路准备起来。

### 3.4.2 为什么要有 `RenderCommand`

`RenderCommand` 是一个静态门面：

```cpp
RenderCommand::SetViewport(...)
RenderCommand::SetClearColor(...)
RenderCommand::Clear()
RenderCommand::DrawIndexed(...)
RenderCommand::DrawLines(...)
RenderCommand::DrawArrays(...)
RenderCommand::SetBlend(...)
RenderCommand::SetScissor(...)
RenderCommand::BindFramebuffer(...)
RenderCommand::BindTextureUnit(...)
```

它的意义是：

```text
上层只知道“我要清屏 / 我要画 / 我要切视口”，
不需要知道底层是 OpenGL、Vulkan 还是别的后端。
```

### 3.4.3 `RendererAPI` 是抽象接口

```cpp
class RendererAPI
{
public:
    enum class API
    {
        None = 0,
        OpenGL = 1
    };

    virtual void Init() = 0;
    virtual void SetViewport(...) = 0;
    virtual void SetClearColor(...) = 0;
    virtual void Clear() = 0;
    virtual void DrawIndexed(...) = 0;
    virtual void DrawLines(...) = 0;
    virtual void DrawArrays(...) = 0;
    virtual void SetLineWidth(float width) = 0;
    virtual void SetScissor(...) = 0;
    virtual void SetScissorTest(bool enabled) = 0;
    virtual void EnableDepthTest() = 0;
    virtual void DisableDepthTest() = 0;
    virtual void SetDepthWrite(bool enabled) = 0;
    virtual void SetDepthFunc(DepthFunc func) = 0;
    virtual void SetBlend(bool enabled) = 0;
    virtual uint32_t GetBoundFramebuffer() = 0;
    virtual void BindFramebuffer(uint32_t id) = 0;
    virtual void BindTextureUnit(uint32_t slot, uint32_t textureID) = 0;
};
```

### 3.4.4 现在为什么只有 OpenGL

当前实现只挂了：

```cpp
RendererAPI::API::OpenGL
```

所以真正落地的是 `OpenGLRendererAPI`。

这意味着现在的抽象不是为了多后端并行，而是为了：

- 先把结构分清楚
- 以后如果换后端更容易
- 让上层代码不要直接依赖 GL

## 3.5 渲染资源：Texture、Shader、Camera、Framebuffer

### 3.5.1 `Texture2D`

纹理对象的公共接口是：

```cpp
class Texture
{
public:
    virtual uint32_t GetWidth() const = 0;
    virtual uint32_t GetHeight() const = 0;
    virtual uint32_t GetRendererID() const = 0;
    virtual void SetData(void* data, uint32_t size) = 0;
    virtual void SetSubData(uint32_t x, uint32_t y, uint32_t width, uint32_t height, const void* data) = 0;
    virtual void Bind(uint32_t slot = 0) const = 0;
};

class Texture2D : public Texture
{
public:
    static Ref<Texture2D> Create(uint32_t width, uint32_t height);
    static Ref<Texture2D> Create(const std::string& path);
};
```

纹理分成两类创建方式：

- 纯色 / 空白纹理
- 从路径加载的图片纹理

### 3.5.2 为什么纹理要缓存

`Texture.cpp` 里有一个全局缓存：

```cpp
static std::unordered_map<std::string, TextureCacheEntry> cache;
```

它的目的是：

```text
同一路径 = 同一个 GPU 纹理对象
长期编辑会话不会把所有加载过的图片都留死
```

缓存超预算后会按 LRU 淘汰已经没人引用的纹理。

这在编辑器里非常实用，因为素材浏览和场景预览会加载很多纹理。

### 3.5.3 `Shader`

Shader 抽象很简单：

```cpp
class Shader
{
public:
    virtual void Bind() const = 0;
    virtual void Unbind() const = 0;
    virtual void SetInt(const std::string& name, int value) = 0;
    virtual void SetIntArray(const std::string& name, int* values, uint32_t count) = 0;
    virtual void SetFloat(...) = 0;
    virtual void SetMat4(...) = 0;
    virtual const std::string& GetName() const = 0;
};
```

它的职责是：

```text
把 uniform、矩阵、纹理槽、材质参数传给 GPU。
```

### 3.5.4 `Camera`

渲染时最关键的不是“有一个相机类”，而是：

```text
相机提供 ViewProjection 矩阵，
渲染器把这个矩阵送进 uniform buffer，
所有顶点在同一套投影下被画出来。
```

2D 和 3D 都靠它。

### 3.5.5 `Framebuffer`

Framebuffer 让渲染不一定直接打到默认窗口缓冲。

Wheatear 里它至少承担了三类工作：

- 编辑器视口离屏绘制
- 影子贴图
- SSAO / 后处理

这也是为什么 `RenderCommand` 里要有：

```cpp
GetBoundFramebuffer()
BindFramebuffer(id)
```

### 3.5.6 `VertexArray` / `VertexBuffer` / `IndexBuffer` / `UniformBuffer`

这几个对象属于更底层的渲染骨架：

- `VertexArray` 组织顶点输入布局
- `VertexBuffer` 存顶点
- `IndexBuffer` 存索引
- `UniformBuffer` 存共享常量数据，比如相机矩阵

在 2D 合批里，`RenderBatch` 直接围着它们工作。

## 3.6 `Renderer2D`：2D 渲染的核心

### 3.6.1 为什么先讲 2D

因为这套引擎当前最核心的渲染地基就是 2D：

- 精灵
- 图集
- UI
- 文本
- 圆形
- 线
- 进度条
- 技能图标

这些内容本质上都要落回 2D 批处理。

### 3.6.2 `Renderer2D` 的公开 API

```cpp
Renderer2D::Init()
Renderer2D::Shutdown()
Renderer2D::BeginScene(const Camera&, const glm::mat4&)
Renderer2D::BeginScene(const EditorCamera&)
Renderer2D::EndScene()
Renderer2D::Flush()
Renderer2D::SetViewProjection(const glm::mat4&)

Renderer2D::DrawQuad(...)
Renderer2D::DrawCircle(...)
Renderer2D::DrawRadialCircle(...)
Renderer2D::DrawSprite(...)
Renderer2D::DrawAnimationFrame(...)
Renderer2D::DrawTextGlyph(...)
Renderer2D::DrawLine(...)
Renderer2D::DrawPolyline(...)
Renderer2D::DrawRect(...)
```

这已经说明了它不是“只画图片”的渲染器，而是一个通用的 2D 批渲染层。

### 3.6.3 `Renderer2D::Init()`

初始化时主要做这些事：

1. 生成共享索引缓冲
2. 创建白色纹理
3. 创建四套 batch
4. 给 shader 绑定纹理槽数组
5. 创建相机 uniform buffer

### 3.6.4 共享索引缓冲

四边形的索引模式非常固定：

```text
0,1,2
2,3,0
```

所以 `Renderer2D::Init()` 先把所有 quad 的索引一次性生成出来，再让所有 batch 共享这个 IBO。

这就是“少创建、少绑定、少变化”的渲染思路。

### 3.6.5 白色纹理

Renderer2D 会先创建一个 1x1 的白纹理：

```text
white texture
```

用途是：

- 纯色 quad 的默认纹理
- 纹理为空时的兜底
- 统一 shader 采样逻辑

这样无论画的是纯色还是贴图，shader 的路径都可以统一。

### 3.6.6 四套 batch

Renderer2D 里有四个批：

- `QuadBatch`
- `CircleBatch`
- `LineBatch`
- `TextBatch`

每个 batch 都对应自己的顶点结构和 shader。

### 3.6.7 为什么分 batch

因为不同图元的顶点属性不一样：

- quad 需要位置、颜色、UV、纹理索引、tiling、EntityID
- circle 需要世界位置、局部位置、厚度、fade、progress、startAngle、EntityID
- line 需要位置、颜色、EntityID
- text 需要位置、颜色、UV、纹理索引、outline、softness、EntityID

把它们混在一个顶点结构里会很浪费，也不利于 shader 组织。

## 3.7 `RenderBatch<T>`：真正的合批容器

### 3.7.1 `RenderBatch` 做什么

`RenderBatch<TVertex>` 是 2D 渲染内部真正装顶点和发 draw call 的对象。

它自己负责：

- 分配 CPU 顶点缓冲
- 创建 VAO/VBO/IBO
- 存 shader
- 在 flush 时把数据送进 GPU
- 在需要的时候调用 pre-draw callback

### 3.7.2 典型结构

```cpp
RenderBatch(uint32_t maxVertices,
    Ref<Shader> shader,
    const BufferLayout& layout,
    BatchDrawMode drawMode,
    Ref<IndexBuffer> indexBuffer = nullptr)
```

它内部有：

- `VertexArray`
- `VertexBuffer`
- `IndexBuffer`
- `Shader`
- `TVertex*` CPU 侧缓冲

### 3.7.3 `Flush()` 是什么

```cpp
uint32_t Flush(Renderer2D::Statistics& stats)
```

它会：

1. 把 CPU 顶点数组上传到 VBO
2. 调用 pre-draw callback
3. bind shader
4. 调用 `RenderCommand::DrawIndexed()` 或 `DrawLines()`
5. 增加统计

### 3.7.4 为什么 batch 里要有 pre-draw callback

因为每次真正 draw 之前，要先把当前 batch 用到的纹理都绑好。

Renderer2D 就用这个 callback 做：

```cpp
for (uint32_t i = 0; i < s_Data.TextureSlotIndex; i++)
    s_Data.TextureSlots[i]->Bind(i);
```

这样 shader 里采样器数组 `u_Textures` 才有意义。

### 3.7.5 为什么 batch 要 `Reset()`

因为一帧画完后要重新开始攒下一帧的数据：

```text
Flush -> Reset -> 再积累新一帧
```

这就是典型的帧式批处理。

## 3.8 `BeginScene / EndScene / Flush`

### 3.8.1 `BeginScene()`

`Renderer2D` 里有两种 begin scene：

```cpp
BeginScene(const Camera& camera, const glm::mat4& transform)
BeginScene(const EditorCamera& camera)
```

它们最终都会做同一件事：

```text
把 ViewProjection 上传到 uniform buffer，
把 batch 和纹理槽重置，
为这一帧的绘制做准备。
```

### 3.8.2 `EndScene()`

```cpp
void Renderer2D::EndScene()
{
    Flush();
}
```

这说明 2D 渲染不是“边画边立即发 GL”，而是先攒后刷。

### 3.8.3 `Flush()`

```cpp
s_Data.QuadBatch->Flush(...)
s_Data.TextBatch->Flush(...)
s_Data.CircleBatch->Flush(...)
s_Data.LineBatch->Flush(...)
```

刷新完以后会：

```text
Reset 所有 batch
TextureSlotIndex = 1
```

### 3.8.4 具体例子：一帧里先画 UI，再画精灵吗？

不是。

通常是：

```text
Scene / System 按既定顺序提交绘制
Renderer2D 把不同类型的图元分 batch 攒起来
Flush 时统一发给 GPU
```

这比每个对象自己调一次 GL 高效很多。

## 3.9 `DrawQuad`、`DrawSprite`、`DrawAnimationFrame`

### 3.9.1 纯色 quad

```cpp
DrawQuad(transform, color, entityID)
```

用于：

- 面板底色
- 占位块
- 简单 UI 背景
- 调试网格的基础块

### 3.9.2 贴图 quad

```cpp
DrawQuad(transform, texture, tilingFactor, tintColor, entityID)
```

用于：

- 角色贴图
- 图标
- 背景局部贴图
- 材质上色后的图块

### 3.9.3 `DrawSprite()`

这是真正和 `SpriteRendererComponent` 对接的函数。

它会考虑：

- `DrawOffset`
- `DrawScale`
- `PixelsPerUnit`
- `UVMin / UVMax`
- `FlipX`
- `Texture`

### 3.9.4 为什么 PPU 很重要

如果纹理的实际内容区域不是 1x1，而是某个裁切后的 sprite frame，那么 quad 的显示尺寸应当根据纹理内容实际覆盖的像素数来决定。

这就是 `PixelsPerUnit > 0` 时的逻辑。

它能保证：

```text
图集裁切帧、动画帧、角色倒地帧
不会因为贴图内容大小变化而把视觉比例搞乱
```

### 3.9.5 `DrawAnimationFrame()`

它接受：

- `texture`
- `uvMin`
- `uvMax`
- `flipX`
- `tintColor`

然后把 4 个顶点的 UV 组好，交给 `SubmitQuadVertices()`。

这就是动画帧的最终落点。

### 3.9.6 具体例子：一张角色图是怎么画出来的

假设场景里有一个角色实体，挂了：

- `TransformComponent`
- `SpriteRendererComponent`

运行时：

```text
RenderSystem 遍历实体
    ↓
拿到 Transform + SpriteRenderer
    ↓
Renderer2D::DrawSprite()
    ↓
根据 PPU / UV / FlipX 计算实际 quad
    ↓
写入 QuadBatch
```

最后 `EndScene()` 时才真正发 draw call。

## 3.10 `DrawCircle`、`DrawRadialCircle`、`DrawLine`、`DrawTextGlyph`

### 3.10.1 圆形

`DrawCircle()` 实际上会走 `DrawRadialCircle()` 的路径。

用途：

- 角色技能范围
- 血条装饰
- 进度圆
- 圆形 UI 元素

### 3.10.2 线段和折线

```cpp
DrawLine(p0, p1, color, entityID)
DrawPolyline(points, color, entityID)
```

用途：

- 编辑器网格
- 路径
- 调试线
- UI 装饰线

### 3.10.3 SDF 文字

`DrawTextGlyph()` 把文字的单个字形写入 `TextBatch`。

它带有：

- `fillColor`
- `outlineColor`
- `outlineWidth`
- `edgeSoftness`

所以引擎的文字不是简单贴一张位图，而是用 SDF 风格的 glyph 渲染。

### 3.10.4 为什么文字也能 batch

因为每个 glyph 仍然是四边形，只不过 shader 不同、属性更多。

这样 UI、面板、对话、按钮文字都能在同一帧里走同一套批处理思想。

## 3.11 纹理槽、EntityID 和批溢出

### 3.11.1 纹理槽

Renderer2D 里有：

```cpp
std::array<Ref<Texture2D>, k_MaxTexSlots> TextureSlots;
uint32_t TextureSlotIndex = 1;
```

槽 0 永远给白纹理。

实际贴图会从 1 开始分配。

### 3.11.2 为什么有槽上限

因为 shader 里会拿一个纹理数组去采样。

槽数是有上限的，超了就必须 flush，重新开始下一批。

### 3.11.3 `GetOrAllocTextureSlot()`

它会先检查当前 batch 里有没有已经绑定过的同一纹理。

如果有，就复用旧槽。

如果没有，才分配新槽。

### 3.11.4 具体例子：同一张 UI 图标画很多次

比如同一个按钮图标画 20 次：

```text
不会每次都新绑定一张纹理
而是复用同一个 slot
```

这就是 batch 友好的关键。

### 3.11.5 `EntityID`

每个顶点里都带 `EntityID`。

这在编辑器里特别重要，因为它能支持：

- 视口拾取
- 高亮选中
- 点击实体

也就是那种 `RED_INTEGER` 之类的 picking 玩法。

## 3.12 `RenderSystem`：Scene 如何进入渲染

### 3.12.1 `RenderSystem` 属于哪一层

`RenderSystem` 属于 **Scene ECS 层 / 引擎服务层交界**。

它的职责不是“画什么 API”，而是：

```text
从 Scene 里找出该画的组件，
按正确顺序调用 Renderer2D / Renderer3D / UIRenderer。
```

### 3.12.2 运行时更新

`RenderSystem::OnUpdateRuntime(Scene* scene, Timestep ts)` 里主要做这些事：

1. 找主相机
2. 做阴影 pass
3. 画 2D
4. 画 3D
5. 画 UI

### 3.12.3 先找主相机

它会遍历：

```cpp
view<TransformComponent, CameraComponent>()
```

找到 `Primary` 的那一个。

这说明“主相机”不是全局单例，而是场景组件里的一个约定。

### 3.12.4 2D 渲染顺序

RenderSystem 里的 2D 部分会：

- `DisableDepthTest()`
- 收集 `SpriteRendererComponent`
- 按 Z、Y、EntityID 稳定排序
- 画 sprite
- 画 circle
- 再重新启用深度测试

### 3.12.5 为什么要排序

因为 2D 横板和 UI 很在意遮挡关系。

排序规则大致是：

```text
先比 Z
再比世界 Y
最后比 entity id
```

这样同层角色的前后关系会稳定，不容易出现“偶尔遮挡错乱”。

### 3.12.6 3D 渲染顺序

3D 部分会：

- 开深度测试
- 收集灯光
- 画 mesh shadow
- 画 mesh
- 处理 IBL / SSAO / shadow map

这一章不展开 3D 的所有细节，但你要知道它和 2D 走的是同一套渲染抽象，只是状态更多。

### 3.12.7 Editor 和 Runtime 的区别

编辑器渲染和运行时渲染最大的区别是：

- 编辑器态会尊重 `EditorHiddenComponent`
- 编辑器态用 `EditorCamera`
- 运行时用主相机

所以 `RenderSystem` 的很多函数都有一个参数：

```cpp
bool respectEditorVisibility
```

### 3.12.8 具体例子：场景视口怎么被画出来

在编辑器里：

```text
EditorLayerBase
    ↓
Scene::OnUpdateEditor()
    ↓
RenderSystem::RenderWithEditorCamera()
    ↓
Renderer2D::BeginScene(editorCamera)
    ↓
RenderScene2D()
    ↓
Renderer2D::EndScene()
```

这条链路非常适合拿来解释编辑器视口怎么工作的。

## 3.13 底层 OpenGL 调用

### 3.13.1 `OpenGLRendererAPI::Init()`

初始化时调用：

```cpp
glEnable(GL_BLEND);
glBlendFunc(GL_SRC_ALPHA, GL_ONE_MINUS_SRC_ALPHA);
glEnable(GL_DEPTH_TEST);
glEnable(GL_LINE_SMOOTH);
glDisable(GL_SCISSOR_TEST);
```

这说明引擎默认要支持：

- 透明混合
- 深度测试
- 线平滑
- 默认不启用裁剪

### 3.13.2 清屏和视口

```cpp
glClearColor(...)
glClear(GL_COLOR_BUFFER_BIT | GL_DEPTH_BUFFER_BIT)
glViewport(...)
```

### 3.13.3 真正画图

```cpp
glDrawElements(GL_TRIANGLES, ...)
glDrawArrays(GL_LINES, ...)
glDrawArrays(GL_TRIANGLES, ...)
```

`Renderer2D` 最终就是把 batch 里的顶点上传好，再通过这些调用发出去。

### 3.13.4 剪裁、深度、混合

```cpp
glScissor(...)
glEnable(GL_SCISSOR_TEST)
glDisable(GL_DEPTH_TEST)
glEnable(GL_DEPTH_TEST)
glDepthMask(...)
glDepthFunc(GL_LEQUAL / GL_LESS)
glEnable(GL_BLEND)
glDisable(GL_BLEND)
```

这些是 UI、阴影、天空盒、编辑器视口等功能依赖的基础状态。

### 3.13.5 framebuffer

```cpp
glGetIntegerv(GL_FRAMEBUFFER_BINDING, &id)
glBindFramebuffer(GL_FRAMEBUFFER, id)
```

这在渲染多个 pass 时特别重要，比如：

- Shadow pass 绑定 shadow FBO
- 结束后恢复原来的 framebuffer

### 3.13.6 纹理底层

`OpenGLTexture2D` 用的是现代 DSA 风格：

```cpp
glCreateTextures(GL_TEXTURE_2D, 1, &m_RendererID);
glTextureStorage2D(...)
glTextureSubImage2D(...)
glBindTextureUnit(slot, m_RendererID);
```

这比老式 `glBindTexture` + `glTexImage2D` 的组合更清楚，也更适合讲现代 OpenGL。

### 3.13.7 纹理加载失败怎么办

如果加载失败，会用一个 fallback magenta 纹理。

这个细节很值得在教材里强调，因为它体现了“资源系统宁愿给你一个明显错误图，也不要让整个渲染链路断掉”。

## 3.14 一个完整例子：一个精灵是怎么出现的

假设场景里有一个角色实体，挂了：

- `TransformComponent`
- `SpriteRendererComponent`

完整链路是：

```text
Scene 中的实体
    ↓
RenderSystem 遍历 view<TransformComponent, SpriteRendererComponent>()
    ↓
RenderSystem::RenderScene2D()
    ↓
Renderer2D::DrawSprite()
    ↓
DrawAnimationFrame() 或 DrawQuad()
    ↓
写入 QuadBatch
    ↓
Renderer2D::EndScene()
    ↓
RenderBatch::Flush()
    ↓
RenderCommand::DrawIndexed()
    ↓
OpenGLRendererAPI::DrawIndexed()
    ↓
glDrawElements()
    ↓
屏幕上出现角色
```

你可以把这一段当作面试时最核心的“渲染解释模板”。

## 3.15 再看一个例子：UI 文本 / 血条 / 技能图标

### 3.15.1 UI 为什么也在 2D 渲染里

因为 UI 本质上也是一堆四边形、文字和线条，只不过它有：

- 裁剪
- 层级
- 鼠标交互
- 视口偏移

### 3.15.2 文本

文字一般会经过 SDF glyph 渲染：

```text
font atlas
    ↓
glyph quad
    ↓
TextBatch
    ↓
shader 计算描边和边缘软化
```

### 3.15.3 血条和进度条

其实也还是 quad，只是颜色和比例在变。

### 3.15.4 技能图标

本质上还是纹理 quad + tint + 可能的遮罩。

这就是为什么 2D 批渲染很适合 UI。

## 3.16 渲染的性能取舍

### 3.16.1 批处理的好处

最大好处是减少 draw call。

### 3.16.2 批处理的代价

代价是你要处理：

- batch 满了怎么办
- 纹理槽满了怎么办
- 不同图元类型怎么分 batch
- 不同 pass 怎么切换 framebuffer

### 3.16.3 为什么要稳态排序

因为渲染顺序不稳定会导致：

- z 冲突
- UI 遮挡错乱
- 横板角色前后层级乱跳

### 3.16.4 为什么要有 entityID

因为编辑器拾取和高亮都依赖它。

### 3.16.5 为什么要有 fallback white texture

因为这样 shader 的采样路径统一，纯色和贴图可以共用一套顶点结构和 shader 逻辑。

## 3.17 和 Unity / UE 的渲染做法对照

### 3.17.1 Unity

Unity 的传统渲染更偏：

- Scene / GameObject / Renderer / Material
- Built-in Pipeline 或 SRP
- 批处理和材质系统由引擎框架管理

### 3.17.2 UE

UE 的渲染体系更偏：

- World / Scene / Mesh Pass / RHI / Render Graph
- 材质和渲染阶段都很重
- 后端抽象非常完整

### 3.17.3 Wheatear

Wheatear 则更像一个“教学型但可用”的轻量方案：

- `Renderer` 做门面
- `RenderCommand` 做统一接口
- `Renderer2D` 做批处理
- `OpenGLRendererAPI` 直接落到 GL

它不追求完整的商业级渲染图谱，而是把“你能看懂、能扩展、能做 2D 游戏”放在第一位。

### 3.17.4 面试回答模板

可以这样答：

```text
Unity 和 UE 的渲染体系都比 Wheatear 重得多。
Unity 更偏 GameObject/Renderer/Material 的工作流，
UE 更偏 World/Scene/RHI/Render Graph 的完整体系。
Wheatear 选择了更轻的 Renderer + RenderCommand + Renderer2D + OpenGLRendererAPI 结构，
重点是把 2D 批处理、编辑器视口、UI 和 Scene 渲染先做通，再考虑扩展。
```

## 3.18 本章的优点和代价

### 优点一：结构清楚

从场景到像素的路径非常直观。

### 优点二：适合 2D 游戏

quad、circle、line、text 这些高频图元都能统一处理。

### 优点三：适合编辑器

entityID picking、viewport rendering、FB restore 都是编辑器必需的。

### 代价一：OpenGL 现在是唯一后端

抽象虽然做了，但实际还是 OpenGL。

### 代价二：3D 还不是完整商业引擎级别

目前 3D 够用，但不会像 UE 那样把整个渲染图做得极端完整。

### 代价三：状态切换需要谨慎

depth、blend、scissor、FBO、viewport 一多，顺序就很关键。

## 3.19 面试回答模板

### 问题：你们的渲染链路是怎样的？

```text
Scene / RenderSystem 收集组件数据，
Renderer2D / Renderer3D 把图元和资源攒成批，
RenderCommand / RendererAPI 提供统一后端接口，
OpenGLRendererAPI 最终调用 glDrawElements、glBindTextureUnit、glViewport、glClear 等函数。
```

### 问题：为什么 2D 要 batch？

```text
因为 2D 场景里图元很多，但状态很重复。
批处理能复用 VAO/VBO/IBO、减少纹理切换和 draw call，
特别适合精灵、UI、文字、血条和图标。
```

### 问题：为什么要有 entityID？

```text
为了编辑器拾取和调试。
渲染时把 entityID 写进顶点，视口里能直接知道哪一个像素属于哪个实体。
```

### 问题：为什么要有 RenderCommand？

```text
因为上层不应该直接依赖 OpenGL。
RenderCommand 把 draw、viewport、blend、scissor、framebuffer 这些底层状态封装起来。
```

## 3.21 本章小结

这一章最重要的结论是：

```text
Renderer 负责总门面，
RenderCommand 负责统一后端接口，
Renderer2D 负责 2D 合批，
RenderSystem 负责把 Scene 的数据送进渲染器，
OpenGLRendererAPI 负责落到真正的 GL 调用。
```

你可以把整套渲染链路记成：

```text
Scene 数据
    → RenderSystem
    → Renderer2D / Renderer3D
    → RenderBatch / Texture / Shader / FBO
    → RenderCommand
    → OpenGL
    → 屏幕
```

下一章建议学 **资产系统与图集 / SpriteSheet**，因为渲染讲完以后，最自然的问题就是：

```text
贴图从哪来？
图集怎么切？
动画帧怎么对应到 Renderer2D？
```
