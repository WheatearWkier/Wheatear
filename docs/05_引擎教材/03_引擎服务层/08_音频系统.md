# 第 3 编 08：音频系统

> 本章所属层级：**引擎服务层**
>
> 本章目标：理解 2D 游戏里的音频是怎么从 Scene 组件、全局音量设置和底层播放引擎串起来的；弄清楚 BGM、SFX、播放句柄、音量路由、场景切换清理这些东西怎么落到代码里。
>
> 这一章只讲**运行时音频**。  
> 编辑器 UI 里的 `ImGui` 不属于这里；这里主要是游戏内的 BGM、音效和场景音源。

如果说输入抽象那一章回答的是“玩家想做什么”，那这一章回答的就是：

```text
这个游戏世界里，声音怎么真正响起来、停下来、换音量、换场景以后不漏音？
```

Wheatear 的音频层不是自己手写一套混音器，而是把一个轻量音频引擎接进 Scene / ECS，再由一层服务把它变成适合 2D 游戏的播放流程：

- Scene 里用组件描述音源
- AudioSystem 在运行时拉起和清理场景音频
- AudioEngine 负责真正播放
- GameplayAudioService 负责给玩法层一个更好用的接口
- UserSettings 负责把 master / BGM / SFX 音量持久化

所以这一章的重点不是“音频理论课”，而是“一个成熟的音频库，怎么接成适合项目的引擎服务”。

## 3.8.2 这一层在架构中的位置

音频系统属于**引擎服务层**。  
它不是玩法脚本里随手 `PlaySound` 一下的临时代码，而是一组可以被 Scene、玩法、设置页和运行时统一复用的能力。

```text
应用层
    Editor / Sandbox / Gameplay
        ↓
玩法层
    SideCombat / VN / Progression / Arcade
        ↓
引擎服务层
    AudioEngine / AudioSystem / GameplayAudioService
        ↓
第三方库
    miniaudio
```

这里要分清三件事：

- `AudioEngine` 是底层播放引擎
- `AudioSystem` 是场景生命周期管理器
- `GameplayAudioService` 是玩法层更好用的播放接口

所以音频层不是一坨代码，而是分工明确的三层。

## 3.8.3 先认识音频里的通用概念

这一节先不看 Wheatear，只看音频系统里最常见的概念。

### `clip`

音频素材本身，也就是一个声音文件。  
在这个工程里，它通常不是一个复杂资源对象，而是一个路径字符串，最后交给底层引擎去解析。

### `source`

声音的“播放源”。  
你可以理解成：同一个音频文件可以被多个 source 播放，每个 source 可以有自己的音量、循环和播放状态。

### `handle`

播放句柄。  
一旦播放开始，底层引擎会给你一个可控制的 id，后面可以：

- 停止
- 暂停
- 恢复
- 调整音量
- 查询是否还在播

这也是为什么 BGM 常常需要句柄，而一锤子 SFX 往往不需要。

### `gain` 和 `volume`

很多音频库里会把“最终输出强度”叫 `gain`。  
在这个工程里，UI 上看到的 0-100 音量值，需要先转成更适合底层引擎的增益值。

所以：

- `volume` 更像“人能看懂的百分比”
- `gain` 更像“底层实际用的控制量”

### `stream` 和 `decode`

这是这章非常值得讲清楚的一点。

- `stream` 适合长音乐
- `decode` 适合短音效

直觉上可以理解为：

```text
长 BGM 更适合边播边读，
短 SFX 更适合一次性解码后播放。
```

这也是为什么 loop 的音频和一次性音效在底层播放路径上会有区别。

### `BGM` 和 `SFX`

这两个概念在 2D 游戏里最常见：

- `BGM`：背景音乐
- `SFX`：音效

Wheatear 当前的音频设计基本就是围绕这两类展开的。

## 3.8.4 `AudioEngine`：底层播放引擎

`AudioEngine` 是真正碰到底层库的地方。  
它负责：

- 初始化和关闭音频引擎
- 播放声音
- 管理播放句柄
- 调整音量
- 清理已结束声音

### 3.8.4.1 初始化和关闭

`AudioEngine::Init()` 会创建底层 engine，并初始化 miniaudio。  
`AudioEngine::Shutdown()` 会先停掉所有声音，再释放 engine 本身。

这一点很重要，因为音频资源不像普通内存那么简单：

- 如果先销毁 engine，再销毁 sound，就容易顺序错乱
- 所以关机时要先收尾播放中的声音，再退出底层引擎

### 3.8.4.2 播放 API

`AudioEngine` 提供的播放接口大概分两类：

- `PlaySound()`：播放一个一次性音效，不关心句柄
- `PlaySoundWithHandle()`：播放并返回句柄，后续可以控制

这两个接口背后的差别很实际：

- 打击音效、按钮点击音效，通常用 `PlaySound()`
- BGM、持续环境音、可控过场音，通常用 `PlaySoundWithHandle()`

### 3.8.4.3 句柄控制

有了句柄，就可以做这些事：

- `StopSound()`
- `PauseSound()`
- `ResumeSound()`
- `SetVolume()`
- `IsPlaying()`

这使得播放不是“一锤子买卖”，而是可以被玩法和场景控制的状态对象。

### 3.8.4.4 `PercentToGain()`

这个函数负责把 0-100 的 UI 音量转换成底层增益。

这说明一个很基本但很重要的设计原则：

```text
界面用百分比，底层用增益，二者不要混在一起。
```

### 3.8.4.5 `OnSceneStop()`

这个函数专门给场景切换用。  
它会把当前 scene 里已经开始的声音清掉，并把句柄计数重置。

这很适合 2D 游戏：

- 进战斗时换一首 BGM
- 退出战斗时别让旧场景的音频继续响
- 切场景时把旧句柄回收干净

### 3.8.4.6 一个实现细节：路径解析

`AudioEngine` 不直接拿着原始字符串就播，而是会先做资源路径解析。

这意味着它能兼容：

- 项目资源路径
- 资源别名
- 运行时资源根目录

这对 2D 游戏很实用，因为音频文件经常会被放进项目资源目录里统一管理。

## 3.8.5 `AudioSourceComponent`：Scene 里的音源数据

Wheatear 不是把音频配置藏在系统内部，而是把它放进了 Scene 组件。

```cpp
AudioSourceComponent
    ├─ AudioFilePath
    ├─ Volume
    ├─ Loop
    ├─ PlayOnStart
    └─ RuntimeHandle
```

### 3.8.5.1 这些字段分别是什么意思

- `AudioFilePath`：音频文件路径
- `Volume`：这个音源自己的播放音量
- `Loop`：是否循环
- `PlayOnStart`：运行时开始时是否自动播放
- `RuntimeHandle`：运行时句柄

### 3.8.5.2 为什么 `RuntimeHandle` 不能序列化

因为它不是场景配置，而是当前运行进程里的播放状态。

它和 `RuntimeBody`、`RuntimeFixture` 是同一类东西：

- 它们都属于运行时对象
- 它们都不应该写进 YAML
- 它们都要在运行开始后重新创建

### 3.8.5.3 这个组件怎么存到场景里

`SceneSerializerScriptingComponents.cpp` 负责序列化和反序列化 `AudioSourceComponent`。

会写入的主要字段是：

- `AudioFilePath`
- `Volume`
- `Loop`
- `PlayOnStart`

不会写入的是：

- `RuntimeHandle`

这就把“可保存的数据”和“运行态数据”分开了。

## 3.8.6 `AudioSystem`：场景音频的生命周期管理器

`AudioSystem` 很有意思。  
它不是一个每帧计算的系统，更像是一个**场景音频生命周期管理器**。

### 3.8.6.1 在 Scene 里怎么被注册

`Scene::ConfigureRuntimeSystems()` 会注册 `AudioSystem`，所以它是 runtime scene 的一部分。

这说明它不是 editor 独有的工具，也不是玩法私有对象，而是 Scene 运行时的一环。

### 3.8.6.2 `OnRuntimeStart()`

场景进入运行时后，`AudioSystem` 会遍历所有 `AudioSourceComponent`：

- 先把 `RuntimeHandle` 清零
- 如果 `PlayOnStart` 为真
- 且 `AudioFilePath` 不为空
- 就根据 `UserSettings` 算出最终音量
- 然后调用底层引擎播放

这里有一个很自然的设计：

```text
Scene 负责声明“有哪些声音”
AudioSystem 负责在运行时把它们真正播出来
```

### 3.8.6.3 `OnRuntimeStop()`

场景停止时，`AudioSystem` 不需要挨个手动处理每个 source 的细节，因为 `AudioEngine::OnSceneStop()` 会统一收尾。

这意味着场景切换不会留下旧音频。

### 3.8.6.4 为什么它不需要 `OnUpdateRuntime()`

因为它的重点不是“每帧推进音频模拟”，而是“管理播放生命周期”。

这也是这章要理解的一个点：

```text
不是所有系统都必须每帧算。
有些系统更像启动器、收尾器、路由器。
```

## 3.8.7 `GameplayAudioService`：玩法层的音频门面

如果 `AudioEngine` 是底层播放机器，`GameplayAudioService` 就是给玩法层准备的好入口。

它做的事情很简单，但很实用：

- `MasterGain()`
- `SFXGain()`
- `BGMGain()`
- `PlaySFX()`
- `PlayBGM()`
- `SetBGMVolume()`

### 3.8.7.1 为什么要多包一层

因为玩法层不应该每次都自己算：

- master 音量
- BGM 音量
- SFX 音量
- 单个音效自己的 volume

这一层把这些细节都收拢了，玩法只要告诉它：

```text
播放这段音效
或者播放这段背景音乐
```

### 3.8.7.2 音量是怎么合成的

最终播放音量大致是这样来的：

```text
最终增益 = 单条音源音量 × master 增益 × BGM/SFX 增益
```

这意味着：

- 单个音源能独立调
- 全局 master 可以一刀切
- BGM 和 SFX 又能分开控制

这就是 2D 游戏最常见的音量路由方式。

### 3.8.7.3 SFX 为什么通常是 fire-and-forget

像 `PlaySFX()` 这种函数通常不返回句柄，因为打击音效、按钮音效、跳跃音效大多只需要播一下就行。

而 `PlayBGM()` 通常返回句柄，因为 BGM 往往要：

- 停止
- 切换
- 调音量
- 做淡入淡出

这也是接口设计里很常见的分层：

- 短音效：简单调用
- 长音轨：返回句柄

## 3.8.8 设置页怎么把音量接进来

音频系统不是只在播放时才有意义，它还要和设置页接起来。

### 3.8.8.1 `UserSettings` 里有什么

这工程里保存了三种关键音量：

- `MasterVolume`
- `BGMVolume`
- `SFXVolume`

这些值会写进用户设置文件里，所以下次启动还能保持上次改过的音量。

### 3.8.8.2 设置页怎么绑

`ProgressionSettingsPageService::UpdateAudioControls()` 会把设置页里的音量滑条和按钮绑成命令，并把当前用户设置值同步回控件。

也就是说：

- 页面负责显示
- 命令负责改值
- 用户设置负责持久化

这正好和音频系统形成闭环。

### 3.8.8.3 为什么这很重要

因为音频体验不只是“播出来”，还要“下次打开还记得你改过音量”。

对 2D 游戏来说，这比复杂混音更常见，也更接地气。

## 3.8.9 一个完整例子：BGM 和 SFX 怎么串起来

这一节最适合拿实际场景说。

### 场景里的 BGM

假设某个 Scene 里有一个实体挂着 `AudioSourceComponent`：

- `AudioFilePath = ...`
- `Volume = 0.8`
- `Loop = true`
- `PlayOnStart = true`

运行时开始后：

1. `Scene::ConfigureRuntimeSystems()` 已经注册了 `AudioSystem`
2. `Scene::StartSystems(SceneExecutionMode::Runtime)` 触发 `AudioSystem::OnRuntimeStart()`
3. `AudioSystem` 发现这个源需要自动播放
4. 调用 `AudioEngine::PlaySoundWithHandle()`
5. 因为 `Loop = true`，底层走流式播放
6. 返回句柄存进 `RuntimeHandle`

这条链路很像“场景声明音乐，系统把它启动起来”。

### 战斗里的 SFX

再看战斗。  
当角色出拳、跳跃、命中时，`SideCombatFeedbackService` 会调用 `GameplayAudioService::PlaySFX()`。

然后：

1. 玩法层传入音效路径和音量
2. `GameplayAudioService` 计算 master / SFX 增益
3. `AudioEngine` 播放一次性音效

这条链路的好处是：

- 玩法层不用管底层引擎
- 音量统一按设置页计算
- 音效播放不用自己管理句柄

### 设置页改音量

如果玩家在设置页把 BGM 音量调低：

1. 滑条通过命令更新 `UserSettings`
2. 当前设置写回用户配置
3. 新播放的音乐会自动按新的音量计算
4. 如果以后需要，也可以用 `SetBGMVolume()` 调整正在播放的句柄

这就是一个完整闭环。

## 3.8.10 和 Unity、UE、Godot 的对照

这一节面试常问。

### Unity

Unity 里大致可以类比成：

- `AudioSource` -> `AudioSourceComponent`
- `AudioClip` -> 音频文件路径
- `AudioMixer` / volume settings -> `UserSettings` + `GameplayAudioService`

### UE

UE 里可以类比成：

- `AudioComponent` -> `AudioSourceComponent`
- 播放控制和生命周期 -> `AudioSystem` / `AudioEngine`
- 音量类别控制 -> `GameplayAudioService` + 用户设置

### Godot

Godot 的 `AudioStreamPlayer` / `AudioStreamPlayer2D` 和这里的思路更接近：

- 场景里挂播放器
- 运行时播放
- 场景切换时清理

Wheatear 的风格更轻一些，重点是：

- 够用
- 清晰
- 好接 2D 游戏的 BGM / SFX / 设置页

## 3.8.11 优点、缺点和常见误区

### 优点

- 场景音源和底层播放分层清楚
- BGM 和 SFX 的音量路由明确
- 可以用句柄控制长音轨
- 设置页能直接接进音量体系
- 场景停止时音频能统一清理

### 缺点

- 还不是完整的混音树系统
- 没有复杂空间音频
- 没有一整套音频总线 / bus graph
- 当前更偏 2D 实用播放，不是电影级音频中台

### 常见误区

1. **“AudioSourceComponent 就是播放器本体”**  
   不是，它只是场景里的数据描述。

2. **“RuntimeHandle 可以存进场景”**  
   不行，它是运行时对象句柄。

3. **“所有音效都必须返回句柄”**  
   也不用。短音效 fire-and-forget 就够了。

4. **“音量就是一个数字，直接乘一下就行”**  
   不能混着来。UI 百分比、master gain、单源 volume 要分开理解。

5. **“场景切换时不用管音频”**  
   不对。旧场景音频不清理，体验会很乱。

## 3.8.12 面试时怎么讲

这一节也别背散文，还是分三层最稳。

### 30 秒版

```text
Wheatear 的音频层分成三部分：
AudioEngine 负责底层播放，AudioSystem 负责 Scene 音源生命周期，
GameplayAudioService 负责给玩法层提供 BGM 和 SFX 的统一入口。
Scene 里用 AudioSourceComponent 描述音源，运行时自动播，设置页里再通过 UserSettings 控制 master、BGM 和 SFX 音量。
```

### 1 分钟版

```text
我没有把音频逻辑散落在玩法里，而是做成了分层。
Scene 里的 AudioSourceComponent 只存路径、音量、循环和是否自动播放，
AudioSystem 在 runtime start 时把这些音源真正播出来，runtime stop 时统一清理。
底层 AudioEngine 用 miniaudio 播放声音，播放长音乐时用 handle 和流式路径，
短音效则 fire-and-forget。GameplayAudioService 再把 master、BGM、SFX 音量合成起来，
这样设置页、战斗音效和场景音乐就能共用同一套播放规则。
```

### 追问版

如果面试官继续问“为什么还要多包一层”，你可以接着说：

```text
因为玩法层不该关心底层音频库怎么播，它只需要告诉系统播放什么。
这样 BGM、SFX、设置页和场景音源都能共享同一套音量路由，
后面如果要加淡入淡出、暂停恢复或者更多音频类别，也比较容易扩展。
```

### 最后收口

如果你想把回答收得更稳，就记住这句：

```text
我这个音频层的核心不是“直接调用播放函数”，而是“把 Scene 音源、用户音量和玩法播放统一到一条可控的链路里”。
```

## 3.8.13 小结

这一章真正要记住的，是三层东西：

- `AudioEngine` 负责把声音真正播出来
- `AudioSystem` 负责把 Scene 里的音源在运行时拉起来和收掉
- `GameplayAudioService` 负责把玩法层、设置页和用户音量串成一条路

如果你已经把这一章读顺了，后面再去看：

- BGM 自动播放
- 战斗音效
- 设置页音量控制
- 场景切换清理

就会很自然。  
因为它们其实都在回答同一个问题：

```text
一个 Scene 里的声音，怎么被稳定地播放、控制和收尾？
```
