# 第 3 编 05：输入抽象

> 本章所属层级：**引擎服务层**
>
> 本章目标：理解原始键鼠输入是怎么被抽象成“动作”的，怎么支持重映射，怎么区分连续态和边缘态，最后又怎么被编辑器、VN、战斗和 UI 复用。
>
> 这一章只讲**输入抽象**。  
> 上一编 `02_事件与输入.md` 已经讲过事件路由、`EventBus` 和 `Application` 怎么接收窗口消息，所以这里不重复那一段。

如果说事件层回答的是“发生了什么”，那输入抽象这一章回答的就是：

```text
玩家现在想做什么？
```

Wheatear 的做法不是把所有玩法都绑死在 `KeyCode` 上，而是拆成两条输入通路：

```text
Raw Input
    ↓
Input
    ↓
InputBindingService
    ↓
Gameplay / Editor / UI / VN / Combat
```

这套分法的好处很直接：

- 编辑器相机可以直接读原始键鼠
- 玩法可以只认动作名，不认物理按键
- 同一个动作可以同时绑定键盘和鼠标
- 默认键位可以走数据文件，后续还能在编辑器里改
- 物理按键和命令驱动可以共用一套边缘态逻辑

## 3.5.2 这一层在架构中的位置

输入抽象位于**核心平台层**和**引擎服务层**之间。

```text
应用层
    Editor / Sandbox / Gameplay
        ↓
引擎服务层
    Input / InputBindingService / InputActionCatalog
        ↓
平台实现层
    WindowsInput / GLFW
```

这里要特别注意一件事：

- `Input` 负责“读窗口里的原始状态”
- `InputBindingService` 负责“把原始状态翻译成动作”
- `InputActionCatalog` 负责“动作默认怎么绑”

所以这章不是在讲事件路由。  
事件路由已经在上一章讲过了，这一章讲的是**状态查询和动作语义**。

## 3.5.3 先分清 raw input 和 action input

Wheatear 的输入其实分两种：

### 1. Raw Input

也就是最底层的原始输入：

- 键盘有没有按下
- 鼠标哪个键按着
- 鼠标当前位置
- 鼠标和上一帧相比移动了多少
- 当前光标模式是什么

这类输入适合：

- 编辑器相机
- 视口拖拽
- UI 命中检测
- 工具类操作

### 2. Action Input

也就是语义化动作：

- `move.left`
- `move.right`
- `game.pause`
- `vn.advance`
- `side.jump`
- `arcade.attack`

这类输入适合：

- 玩法逻辑
- UI 按钮绑定
- VN 推进
- 战斗技能
- 命令驱动的动作注入

一句话概括就是：

```text
Raw Input 解决“按了什么”，
Action Input 解决“这代表什么”。
```

## 3.5.4 `Input`：最底层的键鼠读数

`Input` 是这一层最底的接口。  
它本身不关心“这是 VN 还是战斗”，只关心当前窗口里的真实输入状态。

它提供的能力大致有几类：

- `IsKeyPressed()`：键盘按键是否按着
- `IsMouseButtonPressed()`：鼠标按键是否按着
- `GetMousePosition()` / `GetMouseX()` / `GetMouseY()`：鼠标当前位置
- `GetMouseDeltaX()` / `GetMouseDeltaY()`：鼠标相对上一帧的位移
- `SetCursorMode()`：切换光标模式
- `SetMouseInputBounds()` / `ClearMouseInputBounds()`：限制鼠标输入边界

它的 Windows 实现是直接通过 GLFW 去读窗口句柄。  
所以它是典型的“平台实现包在后面、上层统一调用”的写法。

这里最容易被忽略的两个细节是：

### 鼠标 delta 不是系统自带的连续流

`GetMouseDeltaX/Y()` 不是直接读一个“真实物理速度”，而是用当前鼠标位置减去上一帧的位置算出来的。

也就是说：

```text
本帧鼠标位置 - 上帧鼠标位置 = 鼠标位移
```

这就要求每帧结束时要调用 `Input::EndFrame()`，把当前鼠标位置记成下一帧的基准。

### 鼠标输入可以被限定在视口范围内

`SetMouseInputBounds()` 这类接口是为工具和视口场景准备的。  
例如编辑器只想让鼠标在游戏视口里算输入，或者某个界面希望鼠标只在特定矩形区域有效，这时候就能用到它。

这类能力的意义不是“炫技”，而是让输入能和界面区域严格对齐。

## 3.5.5 `InputBindingService`：把键鼠翻译成动作

如果说 `Input` 是“读物理输入”，那 `InputBindingService` 就是“翻译语义动作”。

它解决的核心问题是：

```text
玩家按的是 A、Space、鼠标左键，
但玩法代码真正想问的是 move.left、vn.advance、side.basic。
```

### 3.5.5.1 动作绑定的基本形态

一个动作可以绑定多个物理输入。

例如：

- `move.left` = `A` / `Left`
- `game.pause` = `P` / `Esc`
- `vn.advance` = `Space` / `Enter` / `Right`
- `side.basic` = `J` / `Space` / `Mouse Left`

也就是说，玩法层不需要知道“这个动作到底是哪个键触发的”，只需要知道“这个动作现在是否成立”。

### 3.5.5.2 三种动作语义

`InputBindingService` 里最关键的是三种查询：

- `IsActionDown()`：当前是否按着
- `IsActionPressed()`：这一帧是否刚按下
- `IsActionReleased()`：这一帧是否刚松开

这三个接口不要混。

```text
Down      = 连续态
Pressed   = 边缘态（上帧没按，这帧刚按）
Released  = 边缘态（上帧按着，这帧刚松）
```

这就是为什么：

- 移动、冲刺、持续瞄准通常看 `Down`
- 跳跃、暂停、技能、确认通常看 `Pressed`
- 需要释放瞬间触发的逻辑才看 `Released`

### 3.5.5.3 命令也可以走动作通路

`InjectActionPress()` 是这层很有意思的一个设计。

它的作用是：

```text
把一个“逻辑动作”注入到和物理输入相同的边缘状态机里。
```

这意味着命令驱动和按键驱动可以共用一套入口。

比如战斗系统里，某些 `side:` 命令会先被命令总线取出来，再转成 `InjectActionPress("side.basic")` 这一类动作注入。  
这样一来，不管动作是玩家按键触发的，还是按钮、脚本、自动化流程触发的，后面都能走同一条 `IsActionPressed()` 路径。

这点很适合做复杂项目，因为它能把“输入”和“业务指令”统一起来。

### 3.5.5.4 为什么要有 `GetBindingLabel()`

`GetBindingLabel()` 不是给玩法用的，而是给界面和编辑器用的。

它会把动作绑定显示成类似：

```text
Space / Enter / Right
```

这样的字符串。  
这对于输入绑定面板、设置页、按键提示都很重要。

## 3.5.6 `InputActionCatalog`：数据驱动默认键位

这一层解决的是“默认动作表从哪来”。

Wheatear 不是把所有默认绑定都硬编码在 C++ 里，而是把一份动作目录放进了数据文件：

```text
assets/input/action_bindings.yaml
```

这个文件的 schema 是：

```text
wheatear.input.actions.v1
```

### 3.5.6.1 目录文件能做什么

它可以定义：

- 动作 id
- 显示名
- 默认键位
- 是否禁用

例如：

```yaml
- id: vn.advance
  label: "剧情-推进 / Advance"
  defaults: ["Space", "Enter", "Right"]
```

这类设计的好处是：

- 新动作不一定要改 C++
- 项目可以覆盖引擎默认键位
- 编辑器能直接读出所有动作
- 同一个动作表可以服务多个玩法模块

### 3.5.6.2 加载顺序

`InputActionCatalog::Load()` 的思路是：

1. 先读引擎根目录的默认表
2. 再读项目根目录的覆盖表
3. 项目里的定义覆盖引擎默认值

这意味着：

- 引擎提供基础动作
- 项目可以加自己的动作
- 项目也可以改掉默认绑定

### 3.5.6.3 为什么还有 `UserSettings`

`InputActionCatalog` 负责“默认值”和“动作定义”，  
`UserSettings` 负责“玩家实际改成了什么”。

`InputBindingService::GetKeys()` 的读取顺序大致是：

1. 先看用户当前设置里有没有改过
2. 没有的话看动作目录里的默认值
3. 再不行才退回 C++ 默认表

所以最后真正生效的，不是单一一个数据源，而是一条层层回退的链路。

### 3.5.6.4 鼠标按钮怎么写进表里

这里有个很实用的小设计：  
鼠标按钮并不是单独开一套类型，而是放进同一个整数编码里。

- 正数表示键盘键码
- 负数表示鼠标按钮

这样做的好处是：

- 一个动作的绑定列表可以同时装键盘和鼠标
- `InputBindingService` 只要读一份 `vector<int>` 就够了
- 编辑器里显示和保存也更统一

## 3.5.7 帧边界：为什么一定要 `EndFrame()`

这一章最容易被忽略，但其实最关键的，是**输入帧边界**。

在 `Application::Run()` 里，顺序是这样的：

```text
glfwPollEvents()
FlushEventQueue()
Layer::OnUpdate()
ImGui
InputBindingService::EndFrame()
Input::EndFrame()
m_Window->OnUpdate()
```

这一步很重要，因为：

- `IsActionPressed()` 和 `IsActionReleased()` 都是边缘态
- 边缘态必须知道“上一帧是什么状态”
- `Input::GetMouseDeltaX/Y()` 也依赖上一帧的鼠标位置

所以 `EndFrame()` 的意义不是“收尾动作”，而是：

```text
把这一帧的输入状态封存起来，作为下一帧的比较基准。
```

如果没有这一步，很多按一下才触发的操作就会变得不稳定。

## 3.5.8 一个完整例子：VN 输入

这一章最适合拿 VN 做例子，因为 VN 的输入最能说明“动作语义”这件事。

`VisualNovelInputService::Sample()` 的思路很简单：

- `vn.advance`：推进对话
- `vn.auto`：自动播放
- `vn.history`：历史记录
- `vn.save`：存档
- `vn.load`：读档
- 数字键 `1~9`：选项键

这就形成了一个很清楚的对照：

```text
玩家按下什么
    ↓
动作名或原始按键
    ↓
VN 输入快照
    ↓
剧情系统决定下一步
```

这里有两个很重要的点：

### 全局控制用动作

像 `vn.advance`、`vn.auto`、`vn.save` 这种，不关心玩家到底按的是哪个物理键，只关心“是否发生了这个语义动作”。

这就是 `InputBindingService` 的职责。

### 选项键有时会直接看原始按键

数字选项常常更适合直接看 `1~9` 的物理键。  
因为它更像是一个短时的 UI 选择，而不是长期可重映射的业务动作。

这也说明了一点：  
输入抽象不是要消灭 raw input，而是要让 raw input 和 action input 各自待在最合适的位置。

## 3.5.9 第二个例子：编辑器相机和横版战斗

### 3.5.9.1 编辑器相机为什么读 raw input

`EditorCamera` 的逻辑很直白：

- 右键按住时进入飞行模式
- `W/A/S/D/Q/E` 控制移动
- 鼠标 delta 控制旋转
- `Alt + 鼠标` 做 orbit、pan、zoom

它直接读的是：

- `Input::IsKeyPressed()`
- `Input::IsMouseButtonPressed()`
- `Input::GetMouseDeltaX/Y()`

这很合理，因为编辑器相机更像工具行为，不应该被游戏里的重映射绑住。  
否则用户改了 `move.left`，编辑器里相机也跟着变，这就很别扭。

### 3.5.9.2 横板战斗为什么用动作名

`SideCombatSystem` 和 `SideCombatPlayerService` 这类系统就不一样。  
它们更适合读：

- `move.left`
- `move.right`
- `move.up`
- `move.down`
- `side.jump`
- `side.basic`
- `game.pause`

因为战斗动作本来就应该是语义化的。

比如：

```text
side.jump 不是“按 K”，
而是“角色触发一次跳跃意图”。
```

这样做的好处是：

- 键盘、手柄、鼠标都能映射成同一个动作
- 同一个技能逻辑不需要知道具体按键
- UI 和脚本也可以把动作注入进去

### 3.5.9.3 命令注入怎么和动作接起来

战斗系统里还有一条很值得记住的链路：

```text
CommandBus 收到命令
    ↓
SideCombatSystem 解析命令
    ↓
InputBindingService::InjectActionPress()
    ↓
下游仍然走 IsActionPressed()
```

这说明 Wheatear 不是把“输入”和“命令”割裂开的。  
它们最后会在动作层汇合。

这对教材和面试都很有价值，因为它体现了一个很实用的设计：

```text
把交互入口统一成动作层，业务层就会更干净。
```

## 3.5.10 和别的引擎对照

### 3.5.10.1 Unity Input System

Unity 新输入系统强调：

- Action Map
- Binding
- Rebinding
- 不同设备统一抽象

Wheatear 的思路和它很像，但更轻。

相似点：

- 都是动作驱动
- 都支持一个动作多个绑定
- 都适合把玩法和物理按键解耦

不同点：

- Unity 更完整，设备层和触发器体系更强
- Wheatear 更贴合当前项目的 2D 目标
- Wheatear 更偏数据表 + 用户设置 + 轻量服务层

### 3.5.10.2 UE Enhanced Input

UE 的 Enhanced Input 更强调：

- Mapping Context
- Input Action
- Trigger / Modifier

它的优势是表达力很强。  
Wheatear 现在没有这么重的触发器体系，但核心思路是同一个方向：先把按键变成动作，再让玩法逻辑消费动作。

### 3.5.10.3 Godot InputMap

Godot 的 `InputMap` 和 Wheatear 的输入抽象尤其接近。

因为它也是：

- 动作名
- 动作绑定
- 一个动作多个物理输入

Wheatear 在这个基础上又多了一层：

- YAML 动作目录
- 用户设置持久化
- 编辑器里可改的绑定表

## 3.5.11 优点、缺点和常见误区

### 优点

- 同一个动作可以绑定多个键和鼠标按钮
- 玩法代码不直接依赖 `KeyCode`
- 默认键位可以数据驱动
- 玩家改键可以持久化
- 命令驱动和物理输入可以合流
- 编辑器、VN、战斗、UI 可以共用一套动作语义

### 缺点

- 还不是完整的多设备输入系统
- 触发器、条件组合、上下文切换还比较轻
- 有些工具操作仍然需要 raw input
- 使用者必须记住 `EndFrame()` 的帧边界

### 常见误区

1. **“既然有动作层，就不用 raw input 了”**  
   不是。编辑器相机、拖拽、视口命中都离不开 raw input。

2. **“Pressed 和 Down 没区别”**  
   有区别。一个是边缘态，一个是连续态。

3. **“动作表只是 UI 里面的显示数据”**  
   不是。它会影响默认绑定、编辑器改键、用户设置和玩法语义。

4. **“InjectActionPress 只是临时补丁”**  
   也不是。它是把命令、脚本、UI 和物理按键统一起来的桥。

## 3.5.12 面试时怎么讲

这一节最好别背成一段散文，还是分三层说最稳。

### 3.5.12.1 30 秒版

```text
Wheatear 的输入层分成 raw input 和 action input 两层。
Input 负责读窗口里的键盘、鼠标和 delta，
InputBindingService 负责把物理输入翻译成动作名，
InputActionCatalog 和 UserSettings 负责默认键位和重映射。
这样编辑器、VN、战斗和 UI 都可以共享同一套动作语义。
```

### 3.5.12.2 1 分钟版

```text
我不让玩法直接依赖 KeyCode，而是把输入抽象成动作。
底层 Input 直接读 GLFW 状态，适合编辑器相机和视口拖拽。
上层 InputBindingService 读动作名，比如 move.left、vn.advance、side.jump，
支持多个物理键映射同一个动作，还能区分 Down、Pressed、Released。
默认绑定放在 action_bindings.yaml 里，项目可以覆盖，用户也能在设置里改，
最后 Application 在每帧结束时统一调用 EndFrame，保证边缘态稳定。
```

### 3.5.12.3 追问版

如果面试官继续问“为什么不直接绑键盘”，可以接着说：

```text
因为同一个动作可能同时来自键盘、鼠标、脚本和 UI。
比如 VN 的推进、战斗技能、设置页按钮、命令注入都应该落在同一套动作语义里。
这样玩法只认意图，不认具体按键，后续扩展和改键都会轻很多。
```

### 3.5.12.4 最后收口

如果你想把回答收得更稳，就记住这句：

```text
我这个输入层的核心不是“能不能按键”，而是“怎么把按键翻译成稳定的业务动作”。
```

## 3.5.13 小结

这一章真正要记住的，不是某个 API 的名字，而是整个输入链路的分工：

- `Input` 负责读原始键鼠
- `InputBindingService` 负责把原始输入翻译成动作
- `InputActionCatalog` 负责默认动作表和数据驱动键位
- `UserSettings` 负责玩家改键后的持久化结果
- `Application::Run()` 负责每帧的输入边界

如果你已经把这一章读顺了，后面再去看：

- VN 对话推进
- 战斗技能输入
- 编辑器相机
- UI 点击和拖拽

就会很自然。  
因为它们其实都在回答同一个问题：

```text
玩家这一帧想做的事，最后怎么稳定地落到系统里？
```
