# 第 3 编 02：资产系统

> 本章所属层级：**引擎服务层**
>
> 本章目标：把资源这件事讲成一条真正能落地的链路。也就是：
> - 资源路径怎么找
> - 别名怎么映射
> - 资源对象怎么创建
> - 缓存怎么做
> - 热重载怎么生效
> - Editor / Runtime / 打包后分别怎么拿资源
>
> 这一章很重要，因为 2D 游戏里最常见的资源就是贴图、字体、图集、动画和材质。  
> 如果资源层不稳，后面的 SpriteSheet、Animation、UI、渲染都会跟着乱。

如果说渲染那一章回答的是“怎么画”，那这一章回答的是：

```text
画之前，这些资源从哪来？
名字怎么变成文件路径？
编辑器和运行时怎么走同一套入口？
```

Wheatear 的资产系统不是单一的“加载器”，而是一整套路径和资源语义：

```text
AssetPath
    -> 定义项目根、引擎根、资源根、可写根
AssetAliasRegistry
    -> 把逻辑别名映射到真实内容路径
FileSystem
    -> 处理规范化、目录、复制、写文件
Texture / Shader / Material / Font
    -> 真正把资源变成运行时对象
```

这一章你读完，应该能回答一个最基础但也最常见的问题：

```text
“我在场景、图集、动画、材质、字体里写的那个字符串，到底最后怎么找到文件？” 
```

## 3.2.2 这一层在架构中的位置

```text
应用层
    Editor / Sandbox
        ↓
核心平台层
    Application / Window / EventBus / LayerStack
        ↓
引擎服务层
    AssetPath / AssetAliasRegistry / Texture / Shader / Material / Font
        ↓
Scene ECS 层
    Scene / Components / Systems
        ↓
平台实现层
    OpenGL / stb_image / stb_truetype / yaml-cpp
```

资产系统的作用，不是“帮你少打几个路径”，而是把资源访问统一成一条规范。

这对 2D 游戏特别重要，因为 2D 游戏会反复访问这些资源：

- 图片
- 图集
- 动画帧
- 字体
- UI 图标
- 材质
- 场景文件

如果路径约定不统一，后面 UI、图集、动画、SceneSerializer 都会变成散装字符串地狱。

## 3.2.3 `AssetPath`：统一资源路径的入口

### 3.2.3.1 它解决什么问题

`AssetPath` 解决的是最基础的事：

```text
“这个路径到底该从哪里开始找？” 
```

它把“项目根”“引擎根”“可写根”“资源根”都分开了。

### 3.2.3.2 四类根目录

- `ProjectRoot`：当前项目的根
- `EngineRoot`：引擎内建资源根
- `WritableRoot`：运行时可写数据根
- `AssetRoot` / `ResourceRoot`：项目内的资源和编辑器资源目录

这几个根的意义不一样：

- 项目资源是内容本体
- 引擎资源是内建默认值
- 可写根是存档、设置和运行时生成文件

### 3.2.3.3 `DiscoverProjectRoot()` 怎么找项目根

启动时会从当前目录往上找，检查有没有可用的 `assets` 目录。  
如果没找到，还会尝试 `WheatearEditor` 和 `WheatearSandbox` 子目录。

这个设计很实用，因为你在不同启动方式下，当前工作目录不一定一样。

### 3.2.3.4 `Resolve()` 的思路

`Resolve()` 不是简单拼字符串，它会按优先级试多个候选路径：

1. 绝对路径直接用
2. `assets/...` 和 `resources/...` 优先按项目根找
3. 普通相对路径优先看 asset root
4. 再看项目根和当前工作目录
5. 最后再回退到引擎根

这就保证了：

- 项目里有本地资源时优先用本地资源
- 没有本地 copy 时还能落到引擎自带资源

### 3.2.3.5 `ResolveRuntimeData()` 为什么单独存在

运行时数据和普通资源不完全一样。

它要处理：

- 松散的编辑器文件
- 打包后的内容包
- 运行时生成的存档和配置

所以 `ResolveRuntimeData()` 比 `Resolve()` 更适合运行中找数据。

### 3.2.3.6 `ResolveAsset()` / `ResolveResource()`

这两个接口解决的是语义分工：

- `ResolveAsset()`：内容资源
- `ResolveResource()`：引擎或编辑器内建资源

这让 shader、字体、场景、游戏内容文件的定位更清楚。

### 3.2.3.7 `ToProjectRelative()` 为什么很重要

资源路径在很多地方都会被写回磁盘或做缓存 key。  
这时就不能一直留着绝对路径，而要转成项目相对路径。

这样做的好处是：

- 迁移项目不容易坏
- Git diff 更稳定
- 缓存 key 更统一

### 3.2.3.8 一个最直观的理解

你可以把 `AssetPath` 理解成：

```text
“统一回答所有资源路径问题的地址系统”。
```

## 3.2.4 `AssetAliasRegistry`：逻辑名到真实路径

### 3.2.4.1 为什么还要别名

只靠路径不够。  
因为项目里很多资源会被玩法、UI、剧情、关卡反复引用。

如果每个地方都直接写：

```text
assets/scenes/SaveLoad.wt
assets/gameplay/actions/action_sets.yaml
assets/ui/health_bar.png
```

那维护起来会非常脆。

所以 Wheatear 还加了一层**内容别名**。

### 3.2.4.2 别名文件长什么样

默认会从 `assets/gameplay/content_manifest.yaml` 读。

它本质上是一个别名映射表，比如：

```text
progression.scene.save_load -> assets/scenes/SaveLoad.wt
wao.action_sets -> assets/gameplay/actions/action_sets.yaml
```

### 3.2.4.3 `Resolve()` 和 `Path()`

`Resolve()` 的逻辑是：

- 如果传进来本来就是 asset path，那就直接规范化
- 如果是别名，就查映射
- 查不到就原样返回

`Path(alias, fallback)` 则更像“带默认值的别名读取”。

### 3.2.4.4 为什么别名更适合玩法代码

玩法代码更关心的是：

```text
“我要什么内容”
```

而不是：

```text
“这个文件在磁盘哪一层目录里”。
```

这就是别名层的价值。

### 3.2.4.5 运行时为什么要 `Load()` / `Reload()`

内容表会变，开发过程中也会改。

所以别名表可以重载。  
这对调试流程很友好，尤其是剧情、战斗、进度这种数据驱动内容。

### 3.2.4.6 一个典型链路

```text
ProgressionSystem
  -> AssetAliasRegistry::Path("progression.scene.save_load")
  -> AssetPath::ResolveRuntimeData(...)
  -> SceneSerializer / SceneTransitionService 使用
```

这条链路非常适合在面试里讲。

## 3.2.5 `FileSystem`：资源工具的底盘

### 3.2.5.1 它解决什么

`FileSystem` 负责一些最朴素但最常见的文件操作：

- 路径规范化
- 判断子路径
- 建目录
- 递归拷贝目录
- 写文本文件

### 3.2.5.2 `Normalize()`

资源系统非常依赖路径比较。  
如果你不先规范化，`assets/a/../b` 和 `assets/b` 就可能被当成两条路径。

所以 `Normalize()` 是所有路径逻辑的底座。

### 3.2.5.3 `IsSubPath()`

这个函数的用途很实际：  
它能确保拷贝、导出、打包时，目标仍然在你允许的根目录内。

这类检查在资源工具和打包工具里都很关键。

### 3.2.5.4 `EnsureDirectory()`

资源写入前先保底建目录，这样很多工具链就不需要每个地方重复写一遍创建目录代码。

### 3.2.5.5 `CopyDirectoryRecursive()`

这类接口通常会出现在：

- 打包
- 发布
- 导出工程
- 拷贝运行时内容

它把“目录树整体搬走”这件事统一了。

### 3.2.5.6 `WriteTextFile()`

像材质、图集、动画、场景这类 YAML 资源，最后都要写文本文件。  
有了这个工具，导出逻辑会更统一。

## 3.2.6 纹理：`Texture2D` 怎么创建和缓存

### 3.2.6.1 `Texture2D::Create()` 有两种

一种是按尺寸创建空纹理：

- 给渲染目标
- 给字体图集
- 给动态生成图

另一种是按路径加载：

- 给贴图资源
- 给 UI 图标
- 给图集底图

### 3.2.6.2 路径版创建不是“直接 new”

`Texture2D::Create(path)` 会先查缓存。

它用的是项目相对路径做 cache key，所以同一张图不会被重复加载很多次。

### 3.2.6.3 为什么要做缓存

因为资源系统里最常见的重复问题就是：

```text
同一张贴图被多个实体、多个 UI、多个动画共享。
```

缓存能避免：

- 重复读磁盘
- 重复上传 GPU
- 资源占用膨胀

### 3.2.6.4 缓存淘汰是怎么想的

这里有一个比较典型的 LRU 思路：

- 记录最近使用 tick
- 统计大约占用的 VRAM
- 超过预算时，优先踢掉没人引用的旧纹理

这很适合长时间编辑器会话。

### 3.2.6.5 `SetSubData()` 为什么重要

这个函数对字体特别关键。  
因为字体图集不是一次性全写完的，后面会按需补字。

只上传脏区域，比整张图反复重传更划算。

### 3.2.6.6 一个最直观的链路

```text
SpriteSheet / UI 图标 / 材质贴图
  -> Texture2D::Create(path)
  -> OpenGLTexture2D
  -> 缓存命中则直接复用
```

## 3.2.7 Shader 和 Material：从文件到渲染参数

### 3.2.7.1 `Shader::Create()`

Shader 也分两种创建方式：

- 从文件加载
- 直接从源码字符串创建

这适合两类场景：

- 项目里固定 shader 文件
- 编辑器或测试时临时生成 shader

### 3.2.7.2 `Material` 解决什么

Material 是“把颜色、贴图和 PBR 参数打包起来”的对象。

在当前项目里，它大致包含：

- `Albedo`
- `Metallic`
- `Roughness`
- `FlipNormals`
- `AlbedoMap`
- `NormalMap`
- `RoughnessMap`
- `MetallicMap`

### 3.2.7.3 `Material::Load()`

它会读一个 YAML 文件，把上面的参数和贴图路径读回来。  
贴图路径再继续走 `Texture2D::Create()`。

也就是说，材质并不是孤立资源，它会递归依赖别的资源。

### 3.2.7.4 `Material::Save()`

保存时会把路径转成项目相对路径。  
这样材质文件跟项目更稳定，迁移时不容易断。

### 3.2.7.5 `Dirty` 标记为什么有用

材质常常会在编辑器里被调参。  
有 `Dirty` 标记以后，编辑器就知道这个资源有没有改过、该不该提示保存。

### 3.2.7.6 一个具体例子

一个角色的 3D 预览材质可能会是：

- 背景色偏白
- 金属度接近 0
- 粗糙度中等
- 有法线图
- 有 albedo 贴图

这部分虽然和你主打的 2D 不同，但对预览验证很有价值。

## 3.2.8 字体：`Font` 怎么建 atlas

### 3.2.8.1 字体资源为什么特别

字体不是普通贴图。  
它会不断遇到新字符，需要动态生成字形并上传图集。

### 3.2.8.2 `Font::Create()`

创建时会：

- 读 TTF / OTF 文件
- 初始化 stb_truetype
- 算 ascent / descent / line gap
- 建 atlas 纹理
- 预加载 ASCII 常用字符

### 3.2.8.3 为什么要预加载 ASCII

因为 UI 和菜单最先会遇到的就是这些字符。  
预加载可以避免第一次显示文本时卡顿。

### 3.2.8.4 `PreloadText()`

这个接口很适合在打开某个 UI 页面前先调用。  
它会把即将显示的字符串里还没见过的字形提前塞进 atlas。

### 3.2.8.5 动态 atlas 的关键

`Font` 不是每次都整张重传 atlas。  
它会记录脏区域，只上传新写入的那一块。

这就是 `SetSubData()` 能派上用场的地方。

### 3.2.8.6 `GetKerning()`

字距信息也会缓存。  
这样 `TextRenderer` 在排版时不用每次都回到底层字库查。

### 3.2.8.7 一个具体例子

比如 VN 里的对白：

```text
人物名 + 正文 + 选项文字 + 系统提示
```

这些文本可能第一次显示时就包含中文、英文、标点混排。  
字体系统必须能稳定补字和计算字距，这样 UI 才不会炸。

## 3.2.9 Editor、Runtime、打包后分别怎么拿资源

### 3.2.9.1 Editor

编辑器通常直接走项目目录。  
它更关注：

- 人能看懂路径
- 资源改完能马上看到
- built-in 资源找得到

### 3.2.9.2 Runtime

运行时会更多依赖：

- `ResolveRuntimeData()`
- 别名表
- `WritableRoot`

这样就能兼容：

- 松散开发目录
- 打包运行目录
- 可写的存档和设置

### 3.2.9.3 打包后

打包后资源结构会和开发目录不完全一样。  
这时别名和运行时数据解析就特别重要。

因为你不能假设：

- 文件一定在原开发路径
- 资源一定和源码目录一致
- 存档一定写在项目根下

### 3.2.9.4 为什么这对工具链重要

编辑器、打包器、运行时如果不用同一套路径规则，很容易出现：

- 编辑器能打开，运行时打不开
- 开发目录能跑，打包后找不到资源
- 资源复制到别的机器后路径全断

AssetPath 和 AssetAliasRegistry 就是在避免这种问题。

## 3.2.10 一个完整例子：一张图怎么走到屏幕上

拿 UI 按钮图标举例。

```text
1. 资源表里写别名：ui.button_confirm
2. AssetAliasRegistry 把它映射到真实 png 路径
3. AssetPath 统一把路径规范化
4. Texture2D::Create(path) 查缓存
5. 没命中就加载 OpenGLTexture2D
6. UI / Sprite 系统拿到 Texture2D
7. 最后交给 Renderer2D 画出来
```

如果是字体，就会变成：

```text
1. Font::Create("assets/fonts/xxx.ttf")
2. stb_truetype 生成 glyph
3. atlas 纹理上传
4. TextRenderer / UIRenderer 请求排版
5. 缺字时动态补 glyph 并局部上传
```

如果是材质，就会变成：

```text
1. Material::Load("assets/materials/hero.yaml")
2. 读参数和贴图路径
3. 每张图继续走 Texture2D::Create()
4. Renderer3D 用材质绘制 mesh
```

这就是资源系统最值得讲给面试官听的地方：

```text
它不是一层“文件读写”工具，而是一条把内容变成可运行对象的管线。
```

## 3.2.11 和 Unity、UE、Godot 的对照

### 3.2.11.1 Unity

Unity 里可以对照成：

- `Resources` / `StreamingAssets`
- `Addressables`
- `Texture2D`
- `Material`
- `Font`

Wheatear 的思路更轻量：

- 路径统一
- 别名统一
- 资源对象统一创建
- 缓存和热重载由引擎自己负责

### 3.2.11.2 Unreal

UE 里可对照成：

- 内容路径
- Asset Registry
- `UTexture2D`
- `UMaterial`
- 字体资源和渲染字体 atlas

Wheatear 没有那么重的资产注册框架，但它在项目规模内已经把“可维护路径”和“内容引用”这件事做得比较完整。

### 3.2.11.3 Godot

Godot 里可以对照成：

- `res://`
- `user://`
- ResourceLoader
- Theme / Font / Texture / Material

Wheatear 的 `AssetPath + AssetAliasRegistry` 和这个思路很像：  
一个负责底层路径，一个负责内容逻辑名。

## 3.2.12 这一层的优点、坏处和常见误区

### 优点

- 路径和内容别名分开，逻辑清楚
- 资源对象统一从入口创建，便于缓存
- Editor 和 Runtime 可以共享同一套资源语义
- 字体和贴图都有热重载意识
- 材质、shader、scene、动画都能走统一路径

### 坏处

- 路径层一多，概念容易混
- 别名表维护不好会变成另一种散装配置
- 资源缓存策略需要持续调优
- 运行时数据、编辑器资源、引擎内建资源如果边界不清，后面会很乱

### 常见误区

- 直接在代码里到处写绝对路径
- 把别名当成“可有可无的糖”
- 忘了项目相对路径对缓存 key 的意义
- 忘了字体 atlas 是动态资源，不是静态贴图
- 忘了材质内部还会引用贴图
- 忘了打包后路径环境会变
- 认为资源系统只是 Load，而不是 Resolve + Cache + Hot Reload

## 3.2.13 面试时怎么讲

如果面试官问你“你的资源系统怎么设计的”，你可以这么答：

```text
我把资源系统拆成了几层。
AssetPath 负责项目根、引擎根、资源根和可写根的统一解析；
AssetAliasRegistry 负责把逻辑别名映射到真实内容路径；
Texture、Shader、Material、Font 负责把资源真正创建成运行时对象；
Texture 还做了缓存和 LRU 式淘汰，Font 则做了动态图集和局部上传。
编辑器和运行时都走同一套路径入口，只是运行时会更依赖 ResolveRuntimeData 和可写根。
```

如果继续追问“为什么要这样分”，你就补一句：

```text
因为资源访问如果不统一，后面的图集、动画、UI、场景、材质都会被字符串路径拖乱。
```

## 3.2.14 小结

这一章其实是在讲一件很朴素但很核心的事：

```text
资源不是“文件”，而是“能被统一解析、缓存和复用的内容对象”。
```

Wheatear 的这层做了四件事：

- `AssetPath` 统一找路
- `AssetAliasRegistry` 统一内容名
- `FileSystem` 统一底层文件操作
- `Texture / Shader / Material / Font` 统一资源对象化

把这章看懂后，下一步去看图集和动画，会顺得很多。

## 3.2.15 `SpriteSheetAsset`：图集资源为什么也属于资产系统

虽然图集和动画更像“渲染/玩法内容”，但它们本质上也是资源，只不过它们不是单张图片，而是“图片 + 组织方式 + 额外语义”的组合。

`SpriteSheetAsset` 就是在做这件事。

### 3.2.15.1 `SpriteSheetData` 里存什么

`SpriteSheetData` 不是简单记录一张贴图，它记录的是一整套图集定义：

- `TexturePath`：底图在哪里
- `Columns` / `Rows`：规则网格怎么切
- `Trims`：每个 cell 的裁剪信息
- `Rects`：不规则 named rect

这说明图集资产不是“贴图的附属品”，而是一个独立内容对象。  
后面不管是角色动作帧、UI 图标还是特效帧，只要它们依赖同一张 sheet，都应该通过这个资产定义来拿数据。

### 3.2.15.2 `Load()` / `Save()` 的意义

图集定义一般会写成一个 YAML 文件。  
`Load()` 负责把 YAML 读回 `SpriteSheetData`，`Save()` 负责把编辑器里改过的数据再写回去。

这一步很重要，因为它把“图怎么切”从代码里拿了出来：

- 程序员不用手改硬编码 UV
- 美术或策划可以直接改图集定义
- 编辑器能把修改落回文件

### 3.2.15.3 `GetCachedSheetData()` 为什么要缓存

图集在编辑器里会被反复读：

- 资源浏览器预览
- Inspector 下拉
- 场景里多个实体同时引用

所以 `SpriteSheetAsset` 做了缓存，并且会按文件写入时间做热更新判断。  
它不是每帧盲目读磁盘，而是会节流 probe，避免场景里一堆 sheet 实体把文件系统打爆。

### 3.2.15.4 `ResolveCell()` 到底做了什么

这是这一块最值得读的函数之一。

`ResolveCell()` 的工作可以拆成几步：

1. 先通过 `AssetPath::ResolveRuntimeData()` 找到真实的 sheet 文件。
2. 再拿到 sheet 对应的 `Texture2D`。
3. 根据 cell index 或 named rect 算出内容矩形。
4. 把内容矩形换成 UV 范围。
5. 顺手把 trim 和 collider 也一起解析出来。

最后返回的不是“一个路径”，而是一个完整的 `ResolvedCell`：

- `Texture`
- `UVMin` / `UVMax`
- 内容区像素矩形
- 可选 collider

这就很适合后面的渲染系统直接消费。

### 3.2.15.5 为什么这里要有 trim 和 collider

这是图集章节里会再展开的核心点，但在资产系统这里先点一下。

有些角色帧不是满格的：

- 站立帧和攻击帧大小不同
- 动画帧会有透明边
- 碰撞盒不一定和绘制框一致

所以 `SpriteSheetAsset` 把“视觉内容”和“碰撞内容”都放进定义里。  
这样后面动画、战斗和物理都能从同一份图集定义里拿到一致语义。

### 3.2.15.6 一个最典型的链路

```text
content manifest / 资源路径
    ↓
AssetAliasRegistry / AssetPath
    ↓
SpriteSheetAsset::Load()
    ↓
SpriteSheetAsset::ResolveCell()
    ↓
ResolvedCell(UV + trim + collider)
    ↓
Renderer2D / AnimationSystem / UI
```

你可以把这条链理解成：  
资产系统把“图怎么切”先讲明白，后面的渲染和动画只负责使用。

## 3.2.16 这一章和后面章节的边界

这一章讲到这里，边界其实已经很清楚了：

- `AssetPath` 讲“路径怎么找”
- `AssetAliasRegistry` 讲“逻辑名怎么转真实文件”
- `FileSystem` 讲“文件怎么安全读写和拷贝”
- `Texture / Shader / Material / Font / SpriteSheetAsset` 讲“资源怎么变成对象”

它还**不**负责：

- 图集怎么被批量画出来
- 动画帧怎么按时间推进
- 角色动作怎么接到系统更新里
- UI 怎么把这份资源真正显示到视口里

这些内容，正好就是下一章 `图集与SpriteSheet` 和再下一章 `动画系统` 要继续讲的。
