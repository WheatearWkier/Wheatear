# 第 3 编 04：动画系统

> 本章所属层级：**引擎服务层**
>
> 本章目标：理解 2D 动画是怎么从“帧 + 时间 + 事件 + 属性曲线”组合出来的，怎么和图集系统联动，怎么在运行时驱动实体和 UI，最后又怎么把动画事件接到命令总线里。
>
> 这一章讲的是**时间控制系统**，不是渲染器本身。  
> 渲染器只负责画当前帧，动画系统负责决定“这一帧该是什么”。

如果说图集章回答的是“这一格图是什么”，那这一章回答的是：

```text
这一秒该播哪一帧？
中途要不要触发命令？
颜色、位置、缩放要不要跟着一起变？
```

Wheatear 的动画系统不是单独的“贴图切换器”，而是一个比较完整的 2D 动画编排层：

```text
AnimationClip
    ├─ 帧序列
    ├─ 事件
    └─ 属性轨迹
        ↓
SpriteAnimatorComponent
        ↓
AnimationSystem
    ├─ 推进时间
    ├─ 选择当前帧
    ├─ 应用属性曲线
    ├─ 触发事件命令
    └─ 处理编辑器预览
```

这套结构的好处很直接：

- 2D 角色动作能做得很顺
- VN 立绘可以切表情、切姿势
- UI 图标可以做呼吸、弹出、闪烁
- 战斗技能可以把命中帧、音效、特效点统一编排

## 3.4.2 这一层在架构中的位置

```text
应用层
    Editor / Sandbox
        ↓
引擎服务层
    SpriteSheetAsset / AnimationClip / AnimationSystem / CommandBus
        ↓
Scene ECS 层
    SpriteRendererComponent / SpriteAnimatorComponent / TransformComponent
        ↓
平台实现层
    OpenGLRendererAPI / Texture / Shader
```

动画系统之所以单独拆出来，是因为“动画”不是“渲染”的从属概念。

渲染只管把当前状态画出来；  
动画系统管的是状态如何随时间变化。

这个分层很重要，因为 2D 项目里很多变化并不只是换图：

- 角色攻击时，位置要抖
- 眨眼时，颜色或表情要切
- 技能释放时，某一帧要发命令
- UI 按钮 hover 时，缩放和 alpha 会一起变化

这些都应该归动画系统管，而不是散在玩法代码里。

## 3.4.3 `AnimationClip`：动画数据的核心

### 1. `AnimationFrame`

`AnimationFrame` 表示一帧图像。
它既可以直接存：

- `Texture`
- `TexCoordMin / TexCoordMax`

也可以额外挂上：

- `SpriteSheet`
- `CellIndex`

后者表示“运行时再去图集里解析这帧”。
这点很重要，因为它让动画和图集真正联动起来：

- 早期资产可以直接烘成纹理 + UV
- 后期也可以改成引用 `.wtsheet`
- 图集重排后，动画不必逐帧重做

### 2. `AnimationEvent`

`AnimationEvent` 里存三样东西：

- `Time`
- `Name`
- `Command`

这是动画系统最像“剧情脚本”的地方。  
它允许你把“这一帧发生了什么”写进剪辑里，而不是硬编码在玩法里。

### 3. `AnimatedProperty`

目前源码里支持的属性主要有：

- `SpriteColor`
- `SpriteColorR / G / B / A`
- `PositionX / Y / Z`
- `RotationZ`
- `ScaleX / Y / ScaleUniform`

这说明它不是单纯的“切帧播放器”，而是能顺便控制实体表现的时间轨迹系统。

### 4. `InterpolationMode`

源码里提供了这些曲线：

- `Linear`
- `Step`
- `EaseIn`
- `EaseOut`
- `EaseInOut`

这已经足够支撑大多数 2D 表现了：

- 线性：平稳移动
- Step：一格一格跳变
- EaseIn / EaseOut：进出场更自然

### 5. `PropertyTrack<T>`

`PropertyTrack<T>` 是关键的数据结构。  
它把动画属性写成“关键帧轨迹”：

- 时间点
- 数值
- 插值方式

系统播放时，按照当前时间采样出一个值，再把它写回 `SpriteRendererComponent` 或 `TransformComponent`。

### 6. `AnimationClip`

`AnimationClip` 统一管理：

- `Frames`
- `PropertyTracks`
- `Events`

并提供：

- `AddFrame`
- `AddFramesFromAtlas`
- `AddFloatTrack`
- `AddVec4Track`
- `AddEvent`
- `GetTotalDuration`
- `Clone`

这里最值得记住的一点是：

```text
动画总时长不是只看帧长，而是要同时看帧、轨迹和事件。
```

所以 `GetTotalDuration()` 会取三者中的最大值。

## 3.4.4 `.wtanim`：动画资产怎么保存

`AnimationClipSerializer` 负责把动画剪辑存成 YAML，再从 YAML 读回来。

大体结构是这样：

```yaml
AnimationClip:
  Name: hero_attack
  Looping: false
  Frames:
    - Texture: assets/sprites/hero.png
      UVMin: [0.0, 0.5]
      UVMax: [0.25, 0.75]
      Duration: 0.08
      SpriteSheet: assets/sheets/hero.wtsheet
      CellIndex: 3
  Events:
    - Time: 0.20
      Name: hit
      Command: combat:spawn_hitbox {entity}
  PropertyTracks:
    - Property: 0
      Keyframes:
        - Time: 0.0
          Value: [1.0, 1.0, 1.0, 1.0]
          Mode: 0
```

### 保存时

`Save()` 会把：

- 名称
- 是否循环
- 每帧纹理与 UV
- 事件
- 属性轨迹

全都写回去。

### 读取时

`LoadFromString()` 会先解析 YAML，再按块读：

- `Frames`
- `PropertyTracks`
- `Events`

这里有一个很好的实现细节：  
源码不会只相信 `Property` 枚举值，而是会先判断轨迹真实类型，再做对应转换。  
这样可以避免把错误类型的轨迹强转错对象。

### 当前的落地状态

从代码看，序列化层目前主要落地的是：

- `float`
- `glm::vec4`

接口层已经预留了 `vec2 / vec3` 的扩展位，但实际保存和加载主要还是这两类。

这点写进教材里很合适，因为它既能说明设计余量，也不会把现状说过头。

## 3.4.5 `SpriteAnimatorComponent`：播放状态放哪

动画资产只是“内容”，真正的播放状态要放在实体组件上。

`SpriteAnimatorComponent` 里最重要的字段有：

- `Clips`
- `ExternalClipAssets`
- `DefaultClipName`
- `PlayOnStart`
- `FireEvents`
- `PlaybackSpeed`
- `CurrentClipName`
- `CurrentFrameIndex`
- `ElapsedTime`
- `IsPlaying`
- `IsFinished`

### 1. `Clips`

`Clips` 是实体本地持有的动画剪辑表。
它适合：

- 直接在场景里塞一个小动画
- 编辑器里临时预览
- 调试时快速改一个实体的动作

### 2. `ExternalClipAssets`

这个字段表示“剪辑名 -> `.wtanim` 资产路径”的绑定。

也就是说，一个实体既可以有内联动画，也可以引用外部动画资产。  
运行时启动时，系统会把这些外部资产加载进 `Clips`。

这很适合做复用：

- 一个攻击动作，多个敌人共用
- 一个 UI 过场动画，多个界面共用
- 一个立绘表情动画，多处共用

### 3. `Play()` 和 `GetCurrentFrame()`

`Play()` 会：

- 切当前剪辑
- 重置帧号
- 重置时间
- 开始播放

`GetCurrentFrame()` 则负责安全地取当前帧。  
它会先 clamp 一下索引，防止热重载后剪辑变短，导致越界。

这个小细节很有教材价值，因为它说明了：  
动画系统不是只考虑“理想输入”，还要考虑“资产变了但播放状态还在”的现实情况。

## 3.4.6 `AnimationSystem`：时间怎么推进

动画的主流程都在 `AnimationSystem::UpdateAnimations()` 里。

### 1. 运行时启动

`OnRuntimeStart()` 会先遍历所有 `SpriteAnimatorComponent`，把 `ExternalClipAssets` 里的 `.wtanim` 资产加载进来。

这一步的好处是：

- 资产只写一份
- 多个实体共用
- 场景文件不会被重复塞一堆动画数据

### 2. 更新时间

`OnUpdateRuntime()` 会推进每个正在播放的 animator：

- `ElapsedTime += ts * PlaybackSpeed`
- 根据总时长判断是否循环
- 根据当前时间定位帧

这部分的核心就是一个非常传统但可靠的流程：

```text
当前时间
    ↓
查找帧段
    ↓
确定当前帧
    ↓
应用到 SpriteRendererComponent
```

### 3. 事件触发

`FireAnimationEvents()` 会根据时间区间检查事件。

这里最容易忽略的点是“循环动画的事件边界”：

- 如果动画没循环，按单段区间触发
- 如果动画循环，要考虑跨过一轮后的事件补发

这就是为什么源码里会专门处理：

- `previousTime`
- `currentTime`
- `totalDuration`
- `fmod`
- `floor`

### 4. 为什么事件要延后执行

这是一个很典型、也很值得讲的工程细节。

`AnimationSystem` 会先把事件命令放进 `pendingCommands`，等遍历完再统一执行。  
原因是 `CommandBus::Execute()` 可能会立刻改场景，甚至销毁实体。  
如果在遍历 `entt` 视图时直接执行，就可能让当前迭代失效。

这个设计很像一个成熟引擎该有的姿态：

- 先算状态
- 再统一提交副作用

### 5. `ApplyFrameToSprite()`

这一步把当前帧真正写给 `SpriteRendererComponent`。

如果帧直接引用了 `.wtsheet`：

- 就先走 `SpriteSheetAsset::ResolveCell()`
- 再用解析结果更新纹理和 UV
- 如果该 cell 还带 collider，就顺手同步碰撞体

否则就直接用帧自带的 `Texture / UV`。

这说明动画系统和图集系统不是两套平行体系，而是互相嵌套的：

```text
AnimationClip
    ↓
AnimationFrame
    ↓
SpriteSheetAsset::ResolveCell
    ↓
SpriteRendererComponent / BoxCollider2DComponent
```

## 3.4.7 编辑器预览怎么做

`OnUpdateEditor()` 里会处理编辑器预览。

如果预览模式没开，它会用 `SyncEditorPreviewFrame()` 把实体拉回到可见的第一帧，避免编辑器里看起来卡在一半播放状态。

这件事看起来小，但对工具体验很重要：

- 编辑器里选中实体时更稳定
- 不会因为暂停预览留下奇怪姿态
- 新手更容易看懂当前动画长什么样

## 3.4.8 一个完整例子：角色攻击动画

假设角色有一个 `hero_attack.wtanim`：

- 前 0.1 秒：蓄力
- 0.1 秒左右：出刀
- 0.2 秒：触发命中事件
- 0.3 秒：收刀

它的配置可能是：

- 帧来自 `hero_attack.wtsheet`
- `Event` 的命令是 `combat:spawn_hitbox {entity}`
- 某些帧还会轻微改 `SpriteColor`
- 攻击过程中 `PositionY` 稍微抖一下

完整链路就是：

```text
Scene 里有 SpriteAnimatorComponent
    ↓
AnimationSystem 推进 ElapsedTime
    ↓
采样当前帧
    ↓
帧来自 SpriteSheetAsset::ResolveCell
    ↓
写回 SpriteRendererComponent
    ↓
某个事件命中时间点
    ↓
CommandBus::Execute("combat:spawn_hitbox ...")
```

这样“动画”和“战斗逻辑”之间就不是硬编码 if/else，而是通过事件和命令串起来。

## 3.4.9 一个完整例子：VN 表情与 UI 呼吸

这套系统不只给角色打架用。

它也可以给：

- VN 立绘切表情
- UI 按钮呼吸
- 技能图标闪烁
- 结果页面板弹入

比如一个立绘动画：

- 1 帧：普通脸
- 2 帧：开心
- 3 帧：惊讶

它甚至不需要特别复杂的曲线，只要按时间换帧就够了。  
而一个 UI 呼吸动画，则可以直接在 `PropertyTracks` 里改 `ScaleUniform` 或 `SpriteColorA`。

这就是一个统一动画系统的价值：

- 玩法动画和 UI 动画不用分家
- 图像变化、颜色变化、位置变化可以共用一套时间模型

## 3.4.10 和别的引擎怎么对照

### Unity

Unity 里最像的组合是：

- `AnimationClip`
- `Animator`
- `SpriteAtlas`
- `Animation Event`

Wheatear 的做法和它相近，但更轻：

- 剪辑就是 YAML 资源
- 播放状态就在组件里
- 事件直接转成命令

### Unreal

UE 里可以类比：

- `Animation Montage`
- `Animation Blueprint`
- `PaperFlipbook`
- `Sequencer`

如果从 2D 的角度看，Wheatear 更接近：

- 一个轻量 `Flipbook`
- 再叠一层属性轨迹和事件命令

### Godot

Godot 里更接近：

- `AnimatedSprite2D`
- `SpriteFrames`
- `AnimationPlayer`

其中：

- `AnimatedSprite2D` 对应帧播放
- `AnimationPlayer` 对应属性曲线和事件

Wheatear 其实是把这两种能力揉在了一起。

## 3.4.11 常见误区

- 以为动画系统只是“换贴图”
- 忘了事件命令可能改场景，所以不能在遍历时直接执行
- 忘了总时长还要看事件和属性轨迹
- 只做循环帧，不做属性轨迹，结果表现很僵
- 热重载后当前帧越界
- `ExternalClipAssets` 和内联 `Clips` 的角色混在一起
- 把动画逻辑硬写进玩法分支，导致后面很难复用

## 3.4.12 面试时怎么讲

如果面试官问你“你这个动画系统和普通换图有什么区别”，你可以这样讲：

```text
它不是单纯切帧，而是一个轻量的 2D 时间编排层。
AnimationClip 同时管理帧、事件和属性轨迹；
SpriteAnimatorComponent 负责播放状态；
AnimationSystem 负责推进时间、采样当前帧、触发事件并写回 SpriteRenderer 和 Transform；
如果帧关联了 .wtsheet，还会顺带把碰撞框同步到 BoxCollider2D。
这样角色动作、UI 动效和剧情立绘就能用同一套系统表达。
```

如果面试官继续追问“为什么要把事件做成命令”，你就补一句：

```text
因为动画事件最终会影响剧情、战斗和场景切换；
转成 CommandBus 以后，动画层就不用直接依赖那些上层系统了。
```

## 3.4.13 小结

这一章最核心的结论是：

```text
动画不是渲染的附属，而是把时间、帧、属性和事件统一起来的编排层。
```

Wheatear 的动画系统做了四件事：

- `AnimationClip` 描述内容
- `SpriteAnimatorComponent` 保存播放状态
- `AnimationSystem` 推进时间和触发事件
- `SpriteSheetAsset` / `SpriteSheetSystem` 提供帧与碰撞的实际解析

把这一层看懂以后，后面你再看 VN、战斗动作、UI 动效，都会顺很多。  
因为它们本质上都在问同一件事：

```text
“在某个时间点，应该把什么状态推给世界？” 
```

## 3.4.14 一个完整链路：`.wtsheet -> .wtanim -> AnimationSystem -> CommandBus`

这一节很重要，因为它把前两章的东西真正串起来了。  
很多人看动画系统，只会看到“换帧”，但在 Wheatear 里，动画其实是一个**内容驱动链**。

### 第一步：先有 `.wtsheet`

假设我们先做了一个角色攻击图集：

- `hero_attack.png`
- `hero_attack.wtsheet`

这个图集里有若干格：

- 第 0 格：蓄力
- 第 1 格：起手
- 第 2 格：挥刀
- 第 3 格：命中
- 第 4 格：收招

每一格不仅有 `Texture / UV`，还可能有 collider。

### 第二步：再做 `.wtanim`

然后我们再做一个动画剪辑 `hero_attack.wtanim`。

里面的帧不是只写纹理，而是写：

```yaml
Frames:
  - Texture: assets/sprites/hero_attack.png
    SpriteSheet: assets/sheets/hero_attack.wtsheet
    CellIndex: 0
    Duration: 0.08
  - Texture: assets/sprites/hero_attack.png
    SpriteSheet: assets/sheets/hero_attack.wtsheet
    CellIndex: 1
    Duration: 0.06
  - Texture: assets/sprites/hero_attack.png
    SpriteSheet: assets/sheets/hero_attack.wtsheet
    CellIndex: 2
    Duration: 0.05
  - Texture: assets/sprites/hero_attack.png
    SpriteSheet: assets/sheets/hero_attack.wtsheet
    CellIndex: 3
    Duration: 0.04
```

同时在事件里写一个命令：

```yaml
Events:
  - Time: 0.15
    Name: hit
    Command: combat:spawn_hitbox {entity}
```

这里已经开始出现“数据驱动”的味道了。  
动画本身不直接做伤害，只是在正确时间点发出一个命令信号。

### 第三步：`AnimationSystem` 读取并推进

场景运行起来后，`AnimationSystem::OnRuntimeStart()` 会把外部 `.wtanim` 加载到 `SpriteAnimatorComponent` 里。  
然后在每帧更新里：

1. 累加 `ElapsedTime`
2. 计算当前帧
3. 调用 `ApplyFrameToSprite()`
4. 如果命中事件时间到了，把命令收集到 `pendingCommands`

这时角色屏幕上已经在播动作了，但命令还没执行。

### 第四步：`CommandBus` 真正执行副作用

等这一轮 `entt` 遍历结束后，`AnimationSystem` 才会逐条调用：

```text
CommandBus::Execute(scene, command)
```

这一步才会真正让战斗系统去做事，比如：

- 创建命中判定
- 播放音效
- 触发特效
- 通知剧情系统

### 为什么这样串很重要

因为它把三层职责分清了：

- `.wtsheet` 管图片切块
- `.wtanim` 管时间和事件
- `AnimationSystem` 管播放
- `CommandBus` 管副作用

这就避免了一个常见坏味道：  
把“动画帧播放”和“战斗结算”硬绑在一起。

### 一个更像实战的场景

比如横板格斗里，攻击动作的第 3 帧命中。

你可以让它走这个链：

```text
hero_attack.wtsheet
    ↓
hero_attack.wtanim
    ↓
AnimationSystem 播放到第 3 帧
    ↓
触发 event: hit
    ↓
CommandBus 执行 combat:spawn_hitbox
    ↓
战斗系统创建攻击判定
```

这样“命中帧”不再写死在战斗代码里，而是变成了可编辑资产的一部分。  
这对于面试特别好讲，因为它体现了你不是在堆 if/else，而是在做内容编排。

## 3.4.15 `SceneSerializerAnimationComponents`：动画怎么被存进场景

动画系统之所以适合做成教材，不只是因为它会播帧，还因为它把“可复用资产”和“场景内联数据”同时照顾到了。

### 1. 场景里既能内联，也能外部引用

`SpriteAnimatorComponent` 里有两套来源：

- `Clips`：场景里直接存的动画剪辑
- `ExternalClipAssets`：剪辑名 -> `.wtanim` 资产路径

这意味着一个动画可以有两种生命形式：

1. 作为场景的一部分直接保存
2. 作为独立资产被多个实体复用

这不是重复设计，而是为了兼顾两类需求：

- 原型期和局部调试，内联更快
- 真正的复用内容，外部资产更稳

### 2. 场景序列化会保存什么

`SceneSerializerAnimationComponents.cpp` 里，`SpriteAnimatorComponent` 会保存：

- `DefaultClip`
- `PlayOnStart`
- `FireEvents`
- `PlaybackSpeed`
- `ExternalClipAssets`
- `Clips`

这里最重要的点是：  
**场景不仅保存“现在在播什么”，还保存“这个实体有哪些动画来源”。**

### 3. 为什么 `.wtanim` 资产更适合共享

`AnimationClipSerializer` 的格式和场景内联体是同一套思路，但它更适合独立资产：

- 一个动画剪辑可以在编辑器里单独保存
- 多个实体都能引用同一个 `.wtanim`
- 动画编辑器改完后，不需要把所有场景重新手工改一遍

这就是 `ExternalClipAssets` 存在的原因。

### 4. 一个很实用的理解

你可以这样记：

```text
场景内联动画 = 方便
.wtanim 外部动画 = 复用
SpriteAnimatorComponent = 两者都支持
```

这也是为什么动画系统在结构上比“换图播放器”更完整。

## 3.4.16 编辑器预览：为什么不会把 Inspector 里的实体播乱

编辑器里最讨厌的一类问题是：

> 我只是点了一下实体，为什么它突然停在某一帧？  
> 我只是切到动画面板，为什么场景里的角色看着半播不播？

Wheatear 在这里做了一个很轻但很关键的处理。

### 1. 场景有一个开关

`Scene::SetAnimationEditorPreviewActive(bool active)` 会把开关转给 `AnimationSystem`。

这说明“动画预览”不是一个全局魔法，而是场景级别的状态。

### 2. 预览没开时，系统会把实体拉回静态帧

`AnimationSystem::OnUpdateEditor()` 里有一条很直接的逻辑：

- 如果没有开启预览，就用 `SyncEditorPreviewFrame(scene)` 把实体同步到当前剪辑的第一帧

这件事很重要，因为它能避免编辑器里出现“我什么都没做，但实体一直停在中间帧”的情况。

### 3. 这里可以做一个合理推断

从这段代码能看出来，**开启预览**时，编辑器应该是想让预览链路自己接管播放状态，而不是继续被“强制拉回第一帧”的逻辑覆盖。  
这是一种很常见的编辑器设计：静态检查和实时预览分两套节奏。

### 4. 为什么这对教材很值得讲

因为它说明动画系统不只是 runtime 功能，它也照顾到了编辑器体验。

- 不开预览：看的是稳定静态状态，适合检查资源和姿态
- 开了预览：看的是时间推进结果，适合检查动作节奏

这就是“工具链”和“运行时”共享同一套系统的价值。

## 3.4.17 属性轨迹最适合拿来做什么

`PropertyTrack` 的意义，最好别只停留在“能插值”。

它真正适合的是把那些轻量、持续、可预测的变化都收进来。

### 1. `SpriteColorA`

最适合做：

- 淡入淡出
- 受击闪白
- UI 透明度切换

### 2. `ScaleUniform`

最适合做：

- 按钮 hover 弹一下
- UI 呼吸
- 角色技能释放时的缩放强调

### 3. `PositionY`

最适合做：

- 轻微弹跳
- 立绘浮动
- 过场里的位移动效

### 4. `RotationZ`

最适合做：

- 轻微抖动
- 特效旋转
- 视觉强调

这类轨迹和帧切换配合起来，动画就不再只是“换图”，而是“画面状态跟着时间有规律地变”。

## 3.4.18 再收一层：这一章真正解决的是什么

如果把整章压成一句话，那就是：

```text
动画系统把“图集帧、时间、事件、属性变化、编辑器预览”统一进了一套播放模型。
```

这一层的职责边界也可以再明确一下：

- `AnimationClip` 负责描述内容
- `SceneSerializerAnimationComponents` 负责把内容塞进场景
- `AnimationSystem` 负责按时间推进并触发命令
- `SpriteSheetAsset` / `SpriteSheetSystem` 负责把 sheet cell 变成真正可画的资源

所以动画不是渲染附属，也不是玩法散活。  
它是把“时间上应该发生什么”编排清楚的一层。
