# 第 3 编 07：物理系统

> 本章所属层级：**引擎服务层**
>
> 本章目标：理解 2D 物理是怎么从 Box2D 的通用概念，落到 Wheatear 的 `Scene`、组件、系统和序列化里的；弄清楚 `b2World::Step()` 一帧到底做了什么，以及刚体、碰撞盒、接触回调、动画驱动碰撞盒这些东西怎么串起来。
>
> 这一章只讲**Box2D-backed 的 2D 物理**。  
> 你可以把它理解成：库里的通用物理知识 + 引擎里的接入方式 + 项目里真正的玩法例子。

如果说输入抽象那一章回答的是“玩家想做什么”，那这一章回答的就是：

```text
这个世界里，物体怎么真的撞上去、滑过去、落下来、停住，最后又怎么把结果写回 Scene？
```

Wheatear 的物理层不是自己手写一套求解器，而是把 Box2D 接进 `Scene` / ECS，然后让它负责：

- 刚体的运动
- 碰撞盒的接触
- 重力和约束
- 每帧物理推进
- 运行时状态回写

所以这章的重点不是“我要发明什么物理算法”，而是“我怎么把一个成熟物理库，接成适合 2D 游戏和编辑器的引擎服务”。

## 3.7.2 这一层在架构中的位置

物理系统属于**引擎服务层**。  
它不是编辑器层那种工具 UI，也不是玩法层那种“某个角色专属的战斗逻辑”，而是所有玩法都能复用的底层能力。

```text
应用层
    Editor / Sandbox / Gameplay
        ↓
玩法层
    SideCombat / ArcadeCombat / VN / Progression
        ↓
引擎服务层
    PhysicsSystem / Physics2DComponents / ContactListener
        ↓
第三方库
    Box2D
```

这层和玩法层的区别很重要：

- 玩法层可以决定“谁打谁”
- 物理层负责“它们怎么撞”
- 玩法层可以决定“碰撞后发生什么”
- 物理层负责“碰撞是否成立、刚体怎么移动、结果怎么回写”

所以物理系统的职责不是取代玩法，而是给玩法一个可信的底座。

## 3.7.3 先认识 Box2D 的通用概念

这一节先不看 Wheatear，只看 Box2D 本身。

### `b2World`

`b2World` 是物理世界本体。  
你可以把它理解成一个“统一的模拟容器”：

- 管理所有 body
- 管理所有 fixture
- 负责重力
- 负责碰撞求解
- 负责每帧 `Step()`

一个场景通常对应一个物理世界。  
这很符合游戏引擎的直觉：一个 Scene 里发生的物理，通常在同一个 world 里模拟。

### `b2Body`

`b2Body` 是刚体。  
刚体保存的是“会动的物体状态”，比如：

- 位置
- 旋转
- 线速度
- 角速度
- 质量相关状态
- 睡眠状态

注意一个非常容易混淆的点：

```text
Body 不是形状本身。
Body 是承载运动和约束的对象。
```

### `b2Fixture`

`b2Fixture` 是挂在 body 上的“碰撞附属物”。

它通常负责：

- 把某个 `shape` 挂到 body 上
- 给这个形状提供密度
- 摩擦
- 弹性
- 传感器语义
- 过滤信息

一个 body 可以挂多个 fixture。  
所以更准确地说：

```text
body 负责动，
fixture 负责撞。
```

### `b2Shape`

`b2Shape` 是几何形状描述。

常见的就是：

- `b2PolygonShape`
- `b2CircleShape`

形状只描述“长什么样”，不负责运动。

### `b2Contact` 和 `ContactListener`

当两个 fixture 发生接触时，Box2D 会产生 contact。

这时候你可以：

- 读到接触对
- 得到开始接触 / 结束接触
- 从 fixture 反查到 body
- 再从 body 反查到实体

这是物理和玩法之间最常见的接头点。

### `b2World::Step(timeStep, velocityIterations, positionIterations)`

`Step()` 是这一章最核心的函数。  
它表示“推进一帧物理模拟”。

它不是简单地把位置加一下，而是会做一整套物理解算：

- 读取当前速度和外力
- 做碰撞检测
- 约束求解
- 更新速度
- 更新位置
- 处理接触状态

这也是为什么物理不是“每帧一个 if 碰撞”那么简单。  
真正的物理模拟，本质上是一个“状态推进器”。

## 3.7.4 `Step()` 一帧到底做了什么

这部分最好单独记，因为面试很爱问。

Box2D 的一帧推进可以粗略理解成下面这条链：

```text
输入当前 body / fixture 状态
    ↓
收集外力、重力、速度
    ↓
检测可能接触的对象
    ↓
构建约束
    ↓
做速度求解
    ↓
做位置修正
    ↓
更新 body 的最终姿态
    ↓
触发接触回调
```

### `timeStep`

`timeStep` 是这一帧要推进的时间长度。  
它决定这一帧物理“走多远”。

在游戏里，`timeStep` 常常来自帧时间，也就是 `Timestep ts`。  
Wheatear 当前的做法是直接把 `ts` 传给 `Step()`，这能跑，但要记住一个通用知识点：

```text
物理模拟更偏好稳定的固定时间步。
```

原因很简单：

- 帧率不稳定时，物理步长也会不稳定
- 步长不稳定时，碰撞和约束的数值误差更容易抖

所以教材里你应该记住两件事：

1. 当前工程是直接吃帧 `ts`
2. 更通用、更稳的写法通常会加固定步积累器

### `velocityIterations`

这个参数控制“速度约束求解”反复迭代多少次。  
次数越多，通常速度约束越稳，但也越耗。

### `positionIterations`

这个参数控制“位置修正”迭代多少次。  
它影响穿透修正、接触稳定性和堆叠表现。

这两个参数不是装饰品。  
它们本质上就是在“精度”和“性能”之间找平衡。

### 为什么不是一次算完

因为物理约束是耦合的。

比如：

- 人站在地上
- 地上又叠着箱子
- 箱子之间还有摩擦

这时候每个对象都不是独立的，必须通过多轮迭代去逼近一个稳定解。

所以 `Step()` 的核心不是“算一次”，而是“不断逼近”。

## 3.7.5 `Physics2DComponents` 怎么设计

Wheatear 把物理数据放在 Scene 组件里，而不是藏在系统内部。

### `Rigidbody2DComponent`

这个组件描述的是“刚体的基础属性”：

- `Type`
- `FixedRotation`
- `GravityScale`
- `RuntimeBody`

真正序列化进场景的只有：

- `BodyType`
- `FixedRotation`
- `GravityScale`

而 `RuntimeBody` 只是运行时指针，不能序列化。

原因很简单：

```text
YAML 里存的是配置，
RuntimeBody 指向的是当前进程里的 Box2D 对象。
```

### `BoxCollider2DComponent`

这个组件描述盒形碰撞器：

- `Offset`
- `Size`
- `Density`
- `Friction`
- `Restitution`
- `RestitutionThreshold`
- `FollowAnimation`
- `RuntimeFixture`

这里最值得注意的是 `FollowAnimation`。

它表示这个 collider 不是完全静态的，而是可能跟着图集帧变化，甚至跟着动画每帧调整形状。

### `CircleCollider2DComponent`

圆形碰撞器和盒形碰撞器类似，只是几何形状换成了 circle。

### 为什么运行时指针不能进序列化

这个问题在物理章里特别关键。

像 `RuntimeBody`、`RuntimeFixture` 这种东西：

- 只存在于当前运行进程
- 只对应当前 Box2D world
- 一旦退出运行时就失效
- 重新加载场景后必须重建

所以它们本质上是“缓存状态”，不是“场景配置”。

## 3.7.6 `PhysicsSystem` 的生命周期

`PhysicsSystem` 是物理真正跑起来的地方。

### `OnRuntimeStart()`

启动运行时物理世界：

- 创建 `b2World`
- 设置重力
- 创建 `ContactListener`
- 遍历已有实体，初始化刚体和碰撞盒

### `OnRuntimeStop()`

停止运行时物理：

- 销毁 world
- 销毁 listener
- 清掉 runtime 资源

### `OnUpdateRuntime()`

每帧做这几件事：

1. 先同步动画驱动的碰撞盒
2. 再调用 `m_PhysicsWorld->Step(...)`
3. 再把刚体结果写回 `TransformComponent`

### `OnEntityCreated()`

当 Scene 里新建了实体，并且它带有 `Rigidbody2DComponent` 时，马上给它补上 Box2D body。

### `OnEntityDestroy()`

实体销毁时，把对应的 `b2Body` 也销毁掉，避免泄漏和悬挂指针。

### `InitEntityPhysics()`

这个函数负责把组件数据翻译成 Box2D 对象：

- body type -> `b2BodyType`
- `TransformComponent` -> body 初始位置和角度
- `BoxCollider2DComponent` -> polygon fixture
- `CircleCollider2DComponent` -> circle fixture

这就是“Scene 数据变成物理对象”的真正入口。

---

## 3.7.7 `Scene::OnUpdateRuntime()` 为什么要这个顺序

这段顺序很重要：

```text
SpriteSheetSystem
    ↓
PhysicsSystem
```

在 `Scene::OnUpdateRuntime()` 里，物理不是最先跑的，而是被安排在图集 / 动画系统之后。

原因是：

```text
如果 collider 会跟着动画帧变化，
那物理步进前就必须先把碰撞盒更新到最新形状。
```

所以这不是随便排的顺序，而是为了让 `FollowAnimation` 类型的碰撞盒在物理求解前就是最新的。

这类细节很适合面试时讲，因为它说明你不是只会调用库，而是知道系统之间为什么这么排。

## 3.7.8 动画驱动碰撞盒

这是这章最“引擎味”的地方之一。

有些 2D 角色不是每一帧都用同一个碰撞盒。  
比如：

- 站立
- 跳跃
- 下蹲
- 出招
- 攻击判定

不同帧的图像轮廓不一样，碰撞盒也可能要跟着变。

Wheatear 的做法是：

- 组件里标记 `FollowAnimation`
- `SpriteSheetSystem` 或动画系统先把当前帧状态更新好
- `PhysicsSystem::SyncAnimationDrivenColliders()` 再把 collider 重建或同步

这就把“视觉”和“物理”串起来了。

你可以把它理解成：

```text
动画决定外形，
物理根据外形更新接触盒。
```

这类设计特别适合：

- 角色攻击判定
- 立绘或角色在不同动作中的碰撞范围
- 某些高频变化的 2D 受击盒

## 3.7.9 `ContactListener` 和接触回调

`ContactListener` 是 Box2D 和玩法层之间的桥。

它能把：

- `b2Fixture`
- `b2Body`
- `UUID`
- `Entity`

串起来。

### `GetEntityFromFixture()`

这个函数的核心思路很典型：

1. 从 `fixture` 找到 `body`
2. 从 `body->GetUserData()` 找到实体 UUID
3. 用 Scene 去反查实体

这说明 Box2D 对象本身不认识引擎实体，所以你得自己做一层映射。

### 为什么 `BeginContact` / `EndContact` 现在是空的

这也是一个很好的教材点。

当前工程里，Box2D 的 raw contact 回调还没有直接接到所有玩法规则上，因为很多玩法层已经有自己的判定逻辑。

所以现在它们先保留成空实现，意思是：

- 引擎已经把接入口留好了
- 以后如果要做统一碰撞事件，直接挂上去就行

这属于典型的“先把物理底座搭好，再决定哪些规则从接触回调走”的设计。

## 3.7.10 Play Mode Copy 和 `DuplicateEntity`

这一节特别容易被忽略，但其实很重要。

### `Scene::Copy()`

场景复制时，Wheatear 会把可复制组件拷贝过去，但不会把运行时指针原封不动带过去。

### `DuplicateEntity()`

复制实体时也是一样：

- 先复制可见的组件数据
- 再把 `RuntimeBody` 置空
- 再把 `RuntimeFixture` 置空

### 为什么必须清空

因为这些指针指向的是 Box2D 里的运行时对象。

如果你把它们复制到另一个实体上，就会出现：

- 两个实体共享同一个 body
- 销毁时重复 `DestroyBody`
- runtime 状态串掉

所以这一步不是“小心一点”的问题，而是必须做。

这也是“编辑态数据”和“运行态对象”要分开的最直接证据。

## 3.7.11 一个完整例子：角色刚体怎么跑起来

我们拿一个最常见的例子来说。

假设 Scene 里有一个角色实体，带着：

- `TransformComponent`
- `Rigidbody2DComponent`
- `BoxCollider2DComponent`

### 进入运行时

Scene 开始运行后：

1. `PhysicsSystem::OnRuntimeStart()` 创建 `b2World`
2. `InitEntityPhysics()` 读取组件
3. 创建 `b2Body`
4. 根据 BoxCollider 创建 `b2Fixture`
5. 运行时指针保存到组件里

### 每帧推进

每帧调用 `Step()` 时：

1. Box2D 先处理重力和外力
2. 再处理和地面的接触
3. 再处理速度和位置修正
4. 最后把结果写回 `TransformComponent`

### 撞到地面

角色落地后：

- body 的位置会被修正
- 接触状态会变成“已接触”
- 如果之后接到 `ContactListener`，就能触发更上层的玩法逻辑

### 退出运行时

Scene 停止时：

- world 被销毁
- listener 被销毁
- 实体里的 runtime 指针失效

这个流程就是“物理对象如何从 Scene 数据活起来，又如何干净地退场”。

## 3.7.12 和 Unity、UE、Godot 的对照

这一节面试会经常问。

### Unity

Unity 里大致可以对应成：

- `Rigidbody2D` -> `Rigidbody2DComponent`
- `Collider2D` -> `BoxCollider2DComponent` / `CircleCollider2DComponent`
- `Physics2D` -> `PhysicsSystem`

### UE

UE 里虽然 2D 物理不是最中心的路线，但思路上也能类比：

- 组件持有物理配置
- 系统 / 世界负责推进
- 运行时对象和编辑态数据分离

### Godot

Godot 的 2D 物理也很强调：

- 节点数据
- 运行时世界
- 碰撞回调
- 场景里配置，运行时模拟

Wheatear 的风格更轻一点，核心是：

- Scene 里保存配置
- PhysicsSystem 负责运行
- 玩法自己决定怎么消费接触结果

## 3.7.13 优点、缺点和常见误区

### 优点

- 复用了成熟的 Box2D 物理求解
- 组件数据和运行时对象分离清楚
- 支持动画驱动碰撞盒
- 场景复制和运行时退场都比较干净
- 很适合 2D 游戏和编辑器预览

### 缺点

- 仍然依赖第三方库的模型和术语
- 目前接触回调还比较轻
- 如果直接用帧 `ts`，稳定性不如固定步积累器
- 复杂 3D 物理不在这一章的覆盖范围

### 常见误区

1. **“fixture 就是 body”**  
   不是。body 是刚体，fixture 是挂在 body 上的碰撞附属物。

2. **“Step 就是把位置加一下”**  
   不是。它是完整的碰撞和约束推演。

3. **“运行时指针也应该存进场景”**  
   不行。它们不是配置，是进程内对象。

4. **“碰撞回调一定要立刻驱动所有玩法”**  
   也不一定。很多项目会把物理碰撞和玩法判定分开。

## 3.7.14 面试时怎么讲

### 30 秒版

```text
Wheatear 的物理层是 Box2D-backed 的 2D 物理服务。
Scene 里的 Rigidbody2DComponent、BoxCollider2DComponent、CircleCollider2DComponent
描述静态配置，PhysicsSystem 在运行时创建 b2World、b2Body 和 b2Fixture，
每帧调用 Step 推进物理，再把结果写回 TransformComponent。
```

### 1 分钟版

```text
我把物理配置放在 Scene 组件里，把运行时模拟交给 PhysicsSystem。
Rigidbody2DComponent 只保存 BodyType、FixedRotation、GravityScale，
Collider 组件保存形状和材质参数，RuntimeBody 和 RuntimeFixture 只在运行时存在。
PhysicsSystem 启动时创建 Box2D world，初始化 body 和 fixture，
每帧 Step 后把位置和旋转同步回 Transform。
如果 collider 需要跟动画帧变化，还会先让 SpriteSheetSystem 更新形状，
再让 PhysicsSystem 步进，这样碰撞盒就能跟视觉一致。
```

### 追问版

如果面试官继续问 `Step()`，你可以接着说：

```text
Step 不是一个简单的位移函数，而是一次完整的物理解算。
它会处理重力、速度、碰撞检测、约束求解和位置修正，
velocityIterations 和 positionIterations 决定解算的稳定性和性能。
如果要更稳，通常会再加固定时间步积累器。
```

### 最后收口

如果你想把回答收得更稳，就记住这句：

```text
我这个物理层的核心不是“自己实现碰撞”，而是“把 Box2D 稳稳接进 Scene，并让运行时状态和组件数据分得清清楚楚”。
```

## 3.7.15 小结

这一章真正要记住的，是三层东西：

- Box2D 的通用概念：`b2World`、`b2Body`、`b2Fixture`、`Step()`
- Wheatear 的接入方式：组件保存配置，系统创建运行时对象
- 物理和玩法的关系：物理负责模拟，玩法负责解释

如果你已经把这一章读顺了，后面再去看：

- 动画驱动碰撞盒
- 战斗判定
- 场景复制
- 接触回调

就会很自然。  
因为它们其实都在回答同一个问题：

```text
一个 Scene 里的 2D 物体，怎么在运行时真正动起来、撞起来、再干净地停下来？
```
