# 附录 02：面试高频问题

> 本附录所属层级：**附录**
>
> 本附录目标：把前面正文里最容易被面试官追问的问题，收成一份可以直接背、直接讲、直接回看的问答清单。
>
> 先提醒一句：这不是“把整本书再讲一遍”。  
> 它更像一套**面试答题模板**：先给结论，再给原因，再给一个具体链路，最后补一句取舍。
>
> 如果你现在要准备面试，建议按这个顺序用它：
>
> 1. 先背每题的第一句。
> 2. 再看后面的展开。
> 3. 最后把“具体链路”那一段换成你自己最熟的源码路径。

## 2.1 先怎么答

最稳的答法不是长篇大论，而是四步：

1. 先给结论。
2. 再说为什么这么做。
3. 再举一条具体源码链路。
4. 最后补一句优缺点。

这套顺序几乎适用于所有章节：

- 分层
- ECS
- 渲染
- 输入
- 物理
- CommandBus
- WAO
- Progression
- Editor

## 2.2 项目总览和分层

### Q1：你这个引擎整体怎么分层？

一句话版：  
我把 Wheatear 按“第三方与平台层 -> 核心平台层 -> Scene/ECS 层 -> 引擎服务层 -> 游戏运行服务层 -> 玩法层 -> 应用层”来分。

展开版：  
底层先解决窗口、上下文、平台差异和第三方库；中间层负责主循环、事件、日志和时间；Scene/ECS 层负责世界组织和序列化；引擎服务层提供渲染、输入、物理、音频、UI 等通用能力；游戏运行服务层负责 CommandBus、SceneTransition、GameProgress、ActionSystem、EventScript 这些跨玩法的运行逻辑；玩法层负责 VN、战棋、街机、回合制、Progression 这些具体游戏玩法；应用层负责 Editor 和 Sandbox。

面试追问可以这样接：  
我不是为了“看起来规整”而分层，而是为了让简单 2D 游戏的内容、流程和工具都能各归其位。这样做的代价是文件多一点，但后期维护会清楚很多。

### Q2：为什么不直接把功能都写在场景脚本里？

一句话版：  
因为那样会把玩法、流程、UI、存档、编辑器全部缠在一起，后面很难扩展。

展开版：  
场景脚本适合做局部行为，不适合承载整套游戏循环。Wheatear 现在把“谁在决定流程”“谁在持有状态”“谁在负责展示”拆开了：场景只负责挂组件，服务层负责推进流程，命令和数据负责串起来。这样战斗、剧情、进度、设置都能共用同一套组织方式。

### Q3：你这个项目主要面向什么类型的游戏？

一句话版：  
主要面向简单 2D 游戏，尤其是剧情、战斗、成长和工具链比较完整的那一类。

展开版：  
我不是想做一个商业级全能引擎，而是想把我自己喜欢的 2D 平面游戏，做成一套既能落地 Demo、又能讲清楚架构的项目。它的重点是：2D 渲染、剧情系统、战斗系统、成长系统、编辑器和独立运行端。3D 预览能力是补充验证，不是主线。

## 2.3 核心平台和主循环

### Q4：`main()`、`CreateApplication()`、`Application::Run()` 这条链路怎么讲？

一句话版：  
`main()` 负责启动，`CreateApplication()` 负责创建游戏自己的 Application，`Application::Run()` 负责主循环。

展开版：  
入口先走 `main()`，再由具体工程实现 `CreateApplication()` 返回自己的 `Application` 子类，例如 Editor 或 Sandbox。`Application::Run()` 才是每帧入口，里面会做窗口消息、层更新、渲染提交和退出判断。这样一来，真正的项目差异就不用写死在主函数里，而是由子类决定。

### Q5：为什么要有 `LayerStack` 和 `Overlay`？

一句话版：  
因为很多东西都需要挂在主循环里，但优先级和显示层次不一样。

展开版：  
`Layer` 适合放编辑器层、运行层、调试层、玩法层等逻辑模块；`Overlay` 更像叠在最上面的工具层，比如调试 UI、性能信息、窗口覆盖面板。把两者分开后，更新顺序、输入优先级和渲染顺序都会更清楚。

### Q6：为什么事件要 Queue，而不是窗口回调里直接 Dispatch？

一句话版：  
因为直接在回调里分发很容易把窗口线程、逻辑线程和当前帧状态搅乱。

展开版：  
队列能把“消息来了”与“这一帧什么时候处理”分开。这样层和系统能在固定的更新点消费事件，不会在回调里直接改一半状态。你在面试里可以直接说：队列让系统更新更稳定，也更容易控制优先级和消费边界。

### Q7：`Log` 和 `Timestep` 为什么也算主循环的一部分？

一句话版：  
因为它们决定了调试和帧推进的基本感知。

展开版：  
`Log` 负责把运行状态、错误和调试信息固定下来；`Timestep` 负责把“这一帧过了多久”标准化成所有系统都能用的时间尺度。主循环没有这两样，调试会很痛苦，帧间逻辑也很容易乱。

## 2.4 Scene 和 ECS

### Q8：`Scene`、`Entity`、`Component`、`System` 怎么区分？

一句话版：  
`Scene` 是世界容器，`Entity` 是身份，`Component` 是数据，`System` 是逻辑。

展开版：  
`Scene` 负责承载整个世界和其生命周期；`Entity` 只是一个可查询、可组合的实体标识；`Component` 负责存状态，不负责组织流程；`System` 负责按规则更新一批组件。这个分法的好处是：你可以很容易地把 UI、渲染、战斗、剧情都挂在同一套世界组织上。

### Q9：为什么 `System` 不做成全局单例，而是挂在场景里？

一句话版：  
因为很多系统的生命周期和场景强相关。

展开版：  
战斗场景、编辑器场景、剧情场景的系统不是同一批，也不应该共享同一份运行态。把系统挂在场景里，能让启动、暂停、销毁、切换都更自然。这样在做 Play Mode Copy、场景切换和读档时，也更容易控制哪些状态应该复制、哪些不该复制。

### Q10：`Play Mode Copy`、`Prefab`、`SceneSerializer` 三者是什么关系？

一句话版：  
`SceneSerializer` 负责存取，`Prefab` 负责复用，`Play Mode Copy` 负责编辑态和运行态的隔离。

展开版：  
`SceneSerializer` 把场景写成 YAML；`Prefab` 更像可复用的实体模板；`Play Mode Copy` 则是在编辑器里启动运行时副本，避免运行时状态直接污染编辑态。这样你在编辑器里点 Play，实际跑的是一份可独立销毁的副本。

### Q11：为什么运行时指针、`RuntimeBody`、`RuntimeFixture` 不能直接进序列化？

一句话版：  
因为这些东西是运行时资源，不是资产数据。

展开版：  
序列化应该保存可重建的定义，而不是某一帧里具体的内存句柄。像物理体、碰撞 fixture、运行时指针这类对象，重新加载场景时会重新创建。如果把它们直接写进文件，读出来也没有意义，反而会破坏跨运行时的稳定性。

## 2.5 渲染和资源

### Q12：你的 2D 渲染链路怎么讲？

一句话版：  
大致是 Sprite / Atlas / SpriteSheet 进来，Renderer2D 批处理，再由 UI/HUD 和文本系统一起输出。

展开版：  
我把 2D 渲染看成一条链：资源先变成纹理或图集，再由渲染服务统一提交，最后在场景里表现成角色、背景、UI、HUD、特效和文本。重点不是某个函数有多神，而是整条链从资源到屏幕是清楚的。

### Q13：为什么要有批渲染、纹理槽和 `Flush()`？

一句话版：  
因为 2D 场景里同类图元很多，批量提交能少很多 GPU 状态切换。

展开版：  
批渲染的核心就是尽量把同类绘制合并起来。纹理槽能减少频繁换贴图，`Flush()` 则是在批次满了或状态变化时把当前批提交出去。面试里可以直接说：这不是炫技，是为了让 2D 游戏的渲染更稳、更省调用。

### Q14：`Sprite`、`Atlas`、`SpriteSheet`、`UI/HUD` 这些东西怎么区分？

一句话版：  
Sprite 是单个图元，Atlas 是大图集，SpriteSheet 是按帧组织的序列图，UI/HUD 是它们的使用场景。

展开版：  
Sprite 是最小绘制单元；Atlas 是把很多小图打包进一张图；SpriteSheet 通常强调动画帧序列；UI/HUD 则是这些资源在界面层的实际应用。你在答题时要说清楚：资源类型和使用场景不是一回事。

### Q15：3D 预览为什么会放进一个以 2D 为主的引擎里？

一句话版：  
因为它是验证渲染管线和材质系统的补充能力，不是主业务。

展开版：  
3D 预览能帮助我把 Mesh、Material、Shadow、IBL、SSAO 这些渲染概念在同一套渲染抽象里跑通，方便验证底层 API 和 shader 链路。但它不是这个项目的主卖点。面试时要主动强调这一点，避免别人误以为你的引擎主打 3D 商业渲染。

## 2.6 输入、物理和音频

### Q16：为什么要做输入抽象，而不是直接读 `KeyCode`？

一句话版：  
因为玩法想表达的是“动作”，不是“键盘码”。

展开版：  
输入抽象能把按键、手柄、触屏统一成逻辑动作，例如 `move.left`、`arcade.attack`、`vn.advance`。这样玩法、编辑器和 UI 都不用关心具体键位，而且以后重映射也不会改一堆业务代码。

### Q17：物理系统里为什么要讲 `fixture`、`step()` 这些概念？

一句话版：  
因为它们是物理模拟的基础语义。

展开版：  
`fixture` 不是“某个库专有名词”，它本质上是把几何形状、摩擦、密度、过滤和 sensor 语义挂到刚体上的那层结构。`step()` 则是一帧物理推进的核心：碰撞检测、积分、约束求解都在这里完成。面试时如果被问到物理，你要讲的是“一帧里物理是怎么跑的”，而不是只背 API 名字。

### Q18：音频系统为什么也要单独抽一层？

一句话版：  
因为它和渲染、输入一样，是玩法反复调用的通用能力。

展开版：  
音频系统通常要解决播放、停止、混音、状态管理和 SFX/BGM 的区分。把它独立成服务以后，VN、战斗、街机、结果页都能统一调它，不会每个玩法自己写一套音频逻辑。

## 2.7 运行时服务：CommandBus、EventScript、ActionSystem、SceneTransition、GameProgress

### Q19：为什么要有 `CommandBus`？

一句话版：  
因为很多系统之间不应该直接互相调用，而应该通过命令说话。

展开版：  
`CommandBus` 的作用是把“谁发起动作”和“谁执行动作”分开。这样 UI、脚本、战斗、剧情、进度都能发命令，而不是互相硬连。它的价值就是让跨系统流程更统一，也更容易调试和追踪。

### Q20：`EventScript` 和 `VN` 有什么区别？

一句话版：  
`EventScript` 更像流程编排器，`VN` 更像剧情玩法本体。

展开版：  
`EventScript` 更偏“这一段流程先做什么、再做什么、然后跳哪”；`VN` 更偏“对白、选择、立绘、音乐、分支怎么演”。前者负责导演级编排，后者负责剧情执行。

### Q21：`ActionSystem`、`ActionIntent`、`ActionRecipe`、`ActionResolver`、`EffectLedger` 怎么串起来？

一句话版：  
`ActionIntent` 是意图，`ActionRecipe` 是配方，`ActionResolver` 是解释器，`EffectLedger` 是结果账本。

展开版：  
玩法先发出动作意图，意图里写谁对谁做什么；动作配方描述这个动作本身的参数和效果；解析器把配方变成具体执行；账本负责记录结果，方便调试和回放。你在面试里一定要把这四个词的边界说清楚，这是很容易被追问的点。

### Q22：`SceneTransition` 为什么要记场景路径、前后场景和保存上下文？

一句话版：  
因为读档、切场景和返回页都需要知道“原来在哪里、现在要去哪”。

展开版：  
如果不记录场景上下文，存档后你就不知道该回到哪个场景；如果把过渡页当成目标场景，读档和返回就会乱掉。`SceneTransition` 的职责就是把进入、退出、重进和加载这些流程统一起来。

### Q23：`GameProgress` 为什么不是简单的存档类？

一句话版：  
因为它是全局进度中枢，不只是写文件。

展开版：  
它保存的不只是槽位数据，还包括章节、旗标、材料、装备、技能、地城、关系、结果页数据、当前场景上下文等。它还会生成保存和加载命令，和 VN runtime、场景切换服务联动。也就是说，它管的是“这盘游戏到底进展到哪了”。

### Q24：为什么设置不放进进度槽？

一句话版：  
因为设置属于运行时偏好，不属于长期进度。

展开版：  
音量、文字速度、全屏、震屏这些东西，不应该因为你读了一个存档就被覆盖。Wheatear 把它们单独放到 `UserSettings` 和设置命令服务里，避免进度槽和偏好混在一起。

## 2.8 玩法层：VN、SideCombat、TurnCombat、TacticalCombat、Arcade、Progression

### Q25：`VN` 模块你怎么讲？

一句话版：  
`VN` 不是对话框 UI，而是一套可运行的剧情玩法。

展开版：  
它把脚本、运行时、场景绑定、输入、存读档和编辑器工具串成一条链。脚本负责写什么，运行时负责怎么跑，系统负责接入主循环，编辑器负责能不能改得动。面试时如果被问到剧情系统，直接抓“脚本 -> 运行时 -> 系统 -> UI”的链路讲。

### Q26：`SideCombat` 和 WAO 是什么关系？

一句话版：  
SideCombat 是玩法壳，WAO 是它底层动作表达和结算的公共语言。

展开版：  
SideCombat 会把玩家输入、AI 行为和剧情事件统一成动作意图，再借助 WAO 的动作配方、解析器、状态和结果账本去执行。这样做的好处是，战斗逻辑不会完全写死在玩法里，而是能和其他玩法共用动作语言。

### Q27：`TurnCombat` 最适合怎么讲？

一句话版：  
它是把回合制战斗拆成流程、命令、动作、技能、目标、UI 和视觉七层的样板。

展开版：  
战斗场景里先选单位，再选命令，再选技能，再选目标，接着进入演出和结算，最后交给敌方回合或胜负跳转。`TurnCombat` 最适合拿来讲“玩法层不是一个大函数，而是一组有职责边界的服务”。

### Q28：`TacticalCombat` 适合怎么讲？

一句话版：  
它是把棋盘、单位、命令、技能、AI、UI 和调参串起来的战棋执行系统。

展开版：  
这个模块重点在格子、范围、目标规则、回合阶段和调参。技能从 WAO 动作表生成，AI 按规则走格子和出手，UI 只负责发命令和显示结果。你要让面试官听出来：这不是一堆按钮，是一套状态机。

### Q29：`Arcade` 最适合怎么讲？

一句话版：  
它是一套把输入、动作、子弹、Boss、HUD 和过场统一起来的街机动作系统。

展开版：  
`Arcade` 的重点是实时反馈。玩家输入先进入控制层，再映射到动作配方，动作配方通过 resolver 和 signal 生成投射物；Boss 的入场、跳跃、射击和结果过场也都由独立服务驱动。这个模块很适合拿来讲“动作玩法是怎么被拆开”的。

### Q30：`Progression` 为什么不是菜单页？

一句话版：  
因为它是全局进度中枢，负责长期成长和页面分发。

展开版：  
它把副本结算、结果页、技能树、装备页、存读档页、设置页和编辑器内容都串起来了。它不是单独一个菜单，而是整盘游戏“走到哪、能做什么、下一步去哪”的统一出口。

## 2.9 应用层：Editor 和 Sandbox

### Q31：为什么要分 `Editor` 和 `Sandbox`？

一句话版：  
因为编辑内容和运行游戏是两种不同的工作流。

展开版：  
Editor 偏工具，负责改资源、改场景、改脚本、改调参；Sandbox 偏运行，负责把这些内容加载出来真正跑一遍。把两者分开后，工具链和游戏链不会互相污染，也更符合实际开发。

### Q32：编辑器最值得讲什么？

一句话版：  
最值得讲的是内容编辑器和运行预览怎么联动。

展开版：  
像 `ProgressionContentEditorPanel`、`TacticalCombatTuningEditorPanel`、`ArcadeCombatTuningEditorPanel` 这类窗口，最能体现你的项目不是只写逻辑，而是已经有了能维护内容的工具链。面试时如果时间不够，就优先讲“编辑器改了什么，运行时怎么热更新”。

### Q33：打包发布这块你怎么讲？

一句话版：  
打包不是简单拷文件，而是把内容、配置、启动场景和可写数据一起组织成产物。

展开版：  
这个部分最重要的是产物结构和启动链路。比如 `content.wtpack`、`player.config`、启动场景、预检扫描、依赖报告和 loose runtime data 的关系。面试时要突出一点：我不是只会点一个 Build 按钮，我知道包体里每一层是什么。

## 2.10 和别的引擎怎么对照

### Q34：Unity、UE、Godot 跟你的引擎怎么对应？

一句话版：  
概念上能对应，但我把职责拆得更显式。

展开版：  
比如 Unity/UE 里的场景、组件、存档、设置、UI、DataTable/DataAsset、GameInstance、UMG 这些概念，在 Wheatear 里都能找到对应，但名字不一定一样。我的做法是把内容和状态、运行和编辑、设置和进度分得更清楚。这样更适合讲架构，也更适合简单 2D 游戏。

### Q35：你为什么不直接用 Unity 或 UE？

一句话版：  
因为我想做的是一套能完全理解、能完整讲清楚、并且围绕我自己的 2D 目标收敛的引擎实践。

展开版：  
不是为了替代成熟引擎，而是为了把我真正关心的东西做透：2D 渲染、剧情、战斗、成长、编辑器、调参、存档和命令驱动流程。自研的价值在于，我知道每一层是怎么连起来的。
