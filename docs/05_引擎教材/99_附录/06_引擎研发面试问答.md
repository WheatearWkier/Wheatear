## 0. 自我介绍

### 0.1 60 秒版

## 11–19 问题解决、协作与工程习惯

### 11. 请阐述一次你在项目中解决复杂技术问题的过程，对游戏引擎研发有何借鉴意义？

**答：** 我会先把它变成可复现的最小场景，再沿数据流找断点，最后用架构手段消除同类问题。

具体案例是“动画帧驱动碰撞盒”：角色换帧/倒地后碰撞盒不跟随。排查发现两个原因：Box2D 的 fixture 在创建时拷贝 shape，改组件不会自动更新；同时 `PhysicsSystem` 在 `SpriteSheetSystem` 之前执行，帧数据还没写回。修复分三层：`BoxCollider2DComponent` 增加 `FollowAnimation`；`PhysicsSystem::SyncAnimationDrivenColliders` 每帧比较期望的 half extents/center，变化才销毁重建 fixture；把 `PhysicsSystem` 注册到 `SpriteSheetSystem` 之后。PPU 统一像素到世界单位，`Scene::Copy` 清空 `RuntimeBody/RuntimeFixture`，防止编辑态/运行态互相污染。

**借鉴：** 区分“源数据”和“运行时对象”，同步方向要单向、显式；系统顺序是架构契约；变更检测比每帧重建便宜；修完要有最小回归场景。类似原则也用在 WAO 热重载上：先解析到临时容器，失败就拒绝，成功才原子替换。

### 12. 谈谈你对游戏引擎中渲染机制的理解，以及它在游戏产品中的应用。

**答：** 渲染的核心是“把场景描述压缩成 GPU 能高效消费的批次”，再按管线阶段完成变换、采样、混合和输出。

Wheatear 的 2D 链路：`RenderSystem` 收集 Sprite/Circle，按 `SortingLayer → OrderInLayer → Z → Y → EntityID` 稳定排序；`Renderer2D` 把顶点写进 Quad/Circle/Line/Text 四个批次，纹理通过 32 个槽位去重，槽满或顶点满就 `Flush`；`Flush` 时一次性上传 VBO，再按提交顺序回放 command 段，同类型连续区间合并，共享一个 6 万索引的 IBO。3D 是 forward PBR：方向光 + 8 点光、2048 阴影、IBL、SSAO；3D 角色走骨骼 UBO + GPU 蒙皮。UI 复用 2D 批处理，靠 scissor 裁剪。

**在产品中的应用：** 移动端更怕 overdraw 和带宽，所以要合批、图集、少状态切换、控制半透明层数；PC/主机的大场景更关心可见性裁剪、阴影级联、GI、材质变体；二次元项目强调 NPR、描边、角色头发/布料和特效排序；2D 剧情/横版项目则更依赖图集、UI 合批和文字渲染。不同项目的取舍不同，但“批次、带宽、状态、排序”四个词是共通的。

### 13. 若遇到游戏引擎性能优化的难题，你会采取哪些步骤去分析和解决？

**答：** 先量化，再定位，再只改瓶颈，最后用同一指标回归。

步骤：1）定预算（16.6ms/33ms，CPU/GPU 分开）；2）打点：帧时间、`Renderer2D` draw calls/quads/vertices、场景更新、物理、UI、文件 IO；3）用 RenderDoc/GPU timer 看 GPU 阶段，用 chrono/Profiler 看 CPU；4）找 top cost，提假设；5）做最小实验；6）回归同一场景；7）记录结论和边界。

Wheatear 已做的：纹理 512MiB 预算 + 只淘汰无引用项的 LRU；图集/模型/动画/IBL/Shader 缓存；文件 mtime 轮询降频（sheet 250ms、VN/WAO 500ms）；共享 IBO、一次上传、buffer orphaning、UBO 脏标记、复用排序 vector；字体图集只上传脏区域；skill tree 用 `string_view` 和视口裁剪。不足是 `Instrumentor` 只有宏、没有完整 session，下一步补 GPU timer、采样 profiler 和启动分阶段打点。

### 14. 讲述一下你掌握的脚本语言，以及如何运用它们进行游戏引擎相关开发。

**答：** 这个项目的主语言是 C++20，脚本层是“领域 DSL + 数据文件”，没有引入通用脚本运行时。

具体：C++20 写引擎/编辑器/玩法；GLSL 写着色器；YAML 写场景、Prefab、材质、动画、动作配方、战斗调参、成长内容；`.wts` 事件脚本负责 `event/wait/if` 和 `CommandBus` 流程编排；`.vn` 写视觉小说；`.wtb` 是 WAO 的行为字节码；PowerShell 负责构建/打包；工具侧也可以配合 Python/ComfyUI 做素材处理。

C#/Mono 早期接过后被移除，所以现在没有 C#/Lua 运行时。为什么：单机 2D 项目不需要托管运行时和绑定层，打包简单、资源可 diff、流程集中。代价是每帧逻辑、AI、复杂公式仍然要写 C++ 或 WAO 配方。如果要做 mod 或策划高频改逻辑，我会在 `CommandBus/ActionIntent` 这层边界上嵌 Lua（sol2）或 C#，而不是把脚本塞进渲染/物理热路径。

### 15. 对于业界常用的游戏引擎，你有多少了解以及学习过哪些相关知识？

**答：** 我对 Unity/UE 的机制比较熟，对 Godot、Cocos 和各类自研引擎是“公开资料级”了解，不敢说生产经验。

学习过的：Unity 的 GameObject/Component、C#、Prefab、UGUI、SRP；UE 的 Actor/Component、Blueprint、GAS、Slate/UMG、渲染和资源管线；Godot 的开源场景树和 GDScript；另外通过公开分享/GDC 了解过一些公司自研引擎的定位、工具链和移动端管线。

Wheatear 很多设计是对照它们做的：entt ECS 对应 GameObject/Component 的数据化；`CommandBus + .wts` 对应 Blueprint/GameplayTask 的流程层；WAO 借鉴 GAS 的 Ability/Effect/Cue 思路，但砍掉网络复制和 UObject 反射；ImGui 编辑器对应 Content Browser/Details 面板。**短板要主动说：** 我没有在商业引擎的生产项目里工作过，具体工具链需要上手学；但我能把渲染、资源、工具链和玩法运行层的迁移路径讲清楚。

### 16. 如何确保你所编写的游戏引擎代码具有良好的可维护性和扩展性？

**答：** 用“边界 + 注册表 + 数据化 + 检查”保证可维护性，而不是靠个人记忆。

Wheatear 的做法：分层和依赖方向固定（玩法不直接改渲染/物理，走 `CommandBus` 或服务）；系统统一 `ISystem` 生命周期，玩法通过 `SceneSystemRegistry` 注册，不写进 `Scene` 核心；组件序列化用 `ComponentSerializer<T>` 特化；组件头按 Core/Rendering/Physics/UI/Animation 分主题；编辑器组件/工具用 `EditorComponentRegistry` / `EditorToolRegistry` 注册；调参和内容放 YAML，流程放 `.wts`；`Project Health` 检查缺失引用、场景跳转、资源注册和源码同步；文档和教材覆盖每条链路。

代价：没有反射，新增组件仍有模板样板；大面板拆成多个 partial 文件；编辑器/运行时两套系统需要保持行为一致。扩展点清楚：新人按“组件 + 序列化 + drawer + 系统注册”四步就能加功能。

### 17. 说说你对游戏引擎中物理模拟系统的认识，它对游戏体验有何影响？

**答：** 物理系统不是“让物体动”，而是“用固定时间步和约束求解，给玩法提供可预测的碰撞与力反馈”。

Wheatear 里：每个 Play 会话建一个 `b2World`，重力 `(0, -9.8)`；`Rigidbody2DComponent` 映射 static/dynamic/kinematic，fixture 由 Box/CircleCollider2D 创建，存 `RuntimeBody/RuntimeFixture` 指针；每帧 delta 夹到 0.05，6 次 velocity / 2 次 position 迭代，step 后把 body 位置/角度写回 Transform（单向）。动画驱动的碰撞盒用 `FollowAnimation + 变化检测` 重建 fixture；`PhysicsSystem` 故意排在 `SpriteSheetSystem` 之后。SideCombat 没有用 Box2D，而是自定义 2.5D 运动学（地面/纵深/空中高度、重力 22、hitstun/guard 计时），因为横版手感需要 coyote time 0.08s、jump buffer 0.12s、hit pause 这类可控参数。

**对体验的影响：** 固定步长决定 determinism 和稳定性；迭代次数影响堆叠/穿透；碰撞盒和动画不同步会直接让“打中了却没判定”；hit pause、震屏、击退的时机又决定打击感。所以物理参数和表现参数要分开：前者归物理/玩法，后者归反馈服务。

### 18. 举例说明你如何在团队合作中提升自己的游戏引擎研发能力。

**答：** 团队合作提升引擎能力的关键，是“把隐式知识变成可复用的接口、文档和检查”。

我会做几件事：接口先定契约（谁拥有数据、谁负责生命周期、失败怎么返回），再并行开发；代码评审看边界和回归，不只看风格；把踩坑写成文档/教材和最小复现场景；用 `Project Health`/CI 把“人肉检查”变成自动检查；和美术/策划协作时，先定义资产规范和验收标准，再给工具。

Wheatear 虽然主要是我一个人推进，但我按团队项目的方式组织：90 多份文档、模块化目录、命名规范、CI 构建、资源健康检查、可回滚的打包。这样别人接手时不用从 `main` 开始读。举例：美术给图集，我定义 `.wtsheet` 的网格/trim/碰撞框/PPU，编辑器里可预览和热重载；3D 模型定义 FBX/glTF → `.wtmodel` 的 cook 和导入设置；策划改战斗，走调参 YAML 和 WAO 配方，不需要改 C++。协作成本主要花在“定义清楚”上，而不是事后救火。

### 19. 当面对多个游戏引擎研发任务同时推进时，你会如何进行任务管理？

**答：** 先建依赖图，再按“阻塞/可并行”排，限制同时进行的任务数，给每个任务设验收和回滚点。

我会把任务分成三类：地基（序列化、资源、渲染）、工具（编辑器、调参）、内容（场景、玩法）。地基没稳定前不铺大量内容，避免返工；能并行的按模块拆给不同人；自己同时最多推进 1–2 件，其余排队。每周定里程碑，每天只挑“今天必须完成”的 1–3 件；给集成/调试留 30% buffer；重复性工作优先自动化（打包、健康检查、资源扫描）。

Wheatear 的竖切就是这么排的：先做场景/渲染/输入/音频的地基，再做 VN 和 SideCombat 的竖切，最后补 Progression、存档、打包和调参工具。3D 角色也是先做导入/骨骼/蒙皮的单点验证，再扩到多角色和编辑器。遇到阻塞（比如 shader 工具链、Box2D 同步、FBX 预计算）就先做最小验证，不把整条线堵死。

## 20–29 架构、内容与学习

### 20. 谈谈你对游戏引擎资源管理模块的理解，以及它的重要性。

**答：** 资源管理是引擎的“供应链”，它决定资源能不能找到、包能不能发、内存会不会爆、改资源要不要重编。

Wheatear 的组成：`AssetPath` 统一项目根/资源根/可写根和 loose/packed 两种解析；编辑器侧 `AssetRegistry` 用 `assets/.wheatear/asset_registry.yaml` 记录 UUID、路径、类型、导入设置、引用/反向引用；`AssetDependencyScanner` 从启动场景 BFS 扫场景/Prefab/VN/WTS/YAML/动画/图集/模型/跳转，生成 `content.wtpack`；运行时按指纹解包到缓存，支持补丁、SHA-256 校验、回滚；`Texture/Model/SpriteSheet` 有缓存和 512MiB 纹理预算；`Project Health` 检查缺失引用和未使用资源。

重要性：资源找不到是运行时崩溃的头号来源；包体过大/重复资源影响下载和加载；没有反向引用就不敢删资源；没有热重载，调参迭代会非常慢。当前还没做异步流式加载和 bundle 粒度，3D `.wtmodel` 的打包扫描也需要补强，这是下一步。

### 21. 假如要开发一款新类型游戏，你在游戏引擎选型上会考虑哪些因素？

**答：** 选型先看“游戏需求 + 团队能力 + 内容管线”，而不是先看引擎名气。

我会按这些维度打分：类型和规模（2D/3D、开放世界/关卡制）、目标平台（PC/主机/移动/Web）、渲染上限（NPR/PBR/大场景/光照）、物理和网络（单机/联机/大规模同步）、团队语言和工具经验、编辑器和内容管线、资源生态和插件、源码/授权成本、长期维护和招聘。

举例：2D 剧情 + 横版动作，重内容管线、轻 3D，自研引擎/Unity/Godot 都可；要完全掌控 2D 批处理和专用编辑器，Wheatear 合适，但生态和招聘是风险。3D 开放世界/高品质渲染，UE 更稳。移动休闲/UGC，Unity/Cocos 的生态更成熟。MMO 或强联网，通常要自研/深度改网络层。**选型不是“哪个最强”，而是“哪个风险最低、内容团队最顺手”。**

### 22. 描述你在学习游戏引擎研发知识过程中遇到的最大困难及解决办法。

**答：** 最大的困难不是某个 API，而是“从能跑变成可维护”，也就是把隐式约定显式化。

早期我容易把玩法、UI、流程写在一起，场景一复杂就出现“改 A 坏 B”。后来做了三件事：一是把流程抽到 `CommandBus/.wts`，把规则抽到玩法服务/WAO，把数据抽到 YAML；二是把坐标/UV/PPU/系统顺序这些隐式约定写成文档和最小复现场景；三是加 `Project Health`、断言、日志和回归场景，让问题尽早暴露。比如 UV 翻转曾在纹理、图集、ImGui 缩略图之间不一致，最后统一成“加载时翻转，边界处只翻一次”，而不是到处改符号。

这套方法也让我后来学 entt/Box2D/ImGui docking/骨骼蒙皮快很多：先找边界，再做最小集成，最后写文档。

### 23. 如何将数学知识应用到游戏引擎研发中，特别是在图形处理方面？

**答：** 数学在引擎里主要解决“空间变换、采样、碰撞、排序和数值稳定”五类问题。

Wheatear 的落点：glm 做 vec/mat，`Renderer2D` 用 `projection * inverse(transform)` 把世界坐标送到 NDC；`SceneCamera` 的 ortho 用 `halfWidth = size/2 * aspect`，处理零尺寸；TRS 和 Z 旋转做 2D 变换；UV/PPU 做像素到世界单位；排序用 layer/order/Z/Y；碰撞用 AABB、圆距离、ray-circle；UI 路径用 Bezier，动画用 `fmod/lerp/easing`；`EffectFormula` 用递归下降解析伤害/治疗公式；3D 里 shadow 用 light-space ortho，SSAO 用 hemisphere kernel + TBN，IBL 用预过滤 mip；骨骼用 TRS 层级、四元数 slerp、`world * inverseBind`。

**我比较注意的点：** 坐标约定统一、除零保护、epsilon、clamp、浮点累积误差（动画时间用 `fmod`）、以及公式里的数值范围要有上下界，避免一击秒杀或负数治疗。

### 24. 讲讲你对游戏引擎跨平台开发的认识，以及可能面临的挑战。

**答：** Wheatear 目前是 Windows + OpenGL 的单平台实现，但平台层是按“可替换后端”留的，不是硬编码在玩法里。

已有的基础：GLFW 管窗口/输入；`Window/RendererAPI/Framebuffer/Texture` 都有抽象；`AssetPath` 统一路径；premake 里已经有 Windows/Linux/macOS 的 define 分支；shader 走 ShaderC/SPIRV-Cross 生成 SPIR-V；`wtpack/.wtmodel` 显式小端、版本号。也就是说，玩法层没有直接调 OpenGL。

挑战：1）图形后端：macOS 的 OpenGL 已废弃，要 Metal；Windows 要 D3D12；Linux 要 Vulkan。2）shader 变体和跨编译。3）文件系统大小写/路径分隔符。4）字体回退和中文。5）输入/手柄/触屏。6）音频后端。7）打包和签名。8）CI 测试矩阵。我的做法是先把 RHI 边界做薄，再按目标平台逐个补后端，而不是一次性承诺全平台。

### 25. 对于游戏引擎中动画系统的实现原理，你有怎样的深入理解？

**答：** 动画系统的本质是“按时间采样数据，并把采样结果写回组件；事件只是采样过程中的副作用”。

2D 侧：`AnimationClip` 包含序列帧、属性轨道（颜色/透明度/位置/缩放）和事件；`AnimationSystem` 累加时间，循环用 `fmod`，非循环 clamp；事件按区间触发，命令先收集再交给 `CommandBus`，避免遍历组件时销毁实体。

3D 侧：`ModelBone` 存 Bind TRS 和 `InverseBind`，`ModelAnimation` 在导入时按 30 FPS 烘焙；glTF 采 TRS + slerp，FBX 预计算每帧骨骼矩阵；`BuildBonePalette` 算 `world * inverseBind`；`Renderer3D` 用 256 骨骼 UBO + GPU 蒙皮；阴影 pass 复用同一份 palette。`Animator3D` 支持循环/速度/单 clip，`BlendBonePose` 有 crossfade 代码，但目前没有公开切换 API，FBX 预计算分支也不走 crossfade。

**边界：** 没有状态机、混合树、3D 动画事件、root motion、重定向、压缩和 LOD。2D 和 3D 的共同原则是“动画只负责表现，命中/音效/切场景由命令和玩法模块处理”。

### 26. 举例说明你怎样优化游戏引擎代码以减少内存占用。

**答：** 先消灭重复和常驻大对象，再谈分配器；内存优化要跟帧时间和包体一起看。

Wheatear 的具体例子：纹理 512MiB 预算，只淘汰 `use_count==1` 的 LRU 项；Quad/Circle/Text 共享一个 6 万索引 IBO；per-object 数据走 UBO，不逐物体传 uniform；字体图集 4096²，首次全传，之后只传脏区域；排序 vector 复用；skill tree 用 `string_view` 避免每帧字符串拷贝；1×1 白纹理避免无纹理 quad 单独 shader；Shader/IBL 磁盘缓存避免重复编译/预计算；文件探测降频。

3D 侧：`Model` 按路径缓存，多个角色共享 Mesh/Bone/Animation 数据；但 `.wtmodel` 里保留了 `SourceVertices/SourceIndices`，Samba 165,960 顶点会多占约 10.6MB CPU 内存，这是可以按需丢弃的。还没做的：自定义 allocator/arena、投射物对象池、SoA 重排、纹理压缩/流式；下一步先用内存 profiler 找 top allocation，再做池化和压缩。

### 27. 如何与美术团队协作，确保游戏引擎能完美呈现美术设计效果？

**答：** 和美术协作的关键是“把美术资产规格变成引擎可验证的数据”，而不是口头约定。

2D：美术给 PNG/序列帧；`Sprite Sheet Picker` 里设 columns/rows、trim、碰撞框、命名 rect，保存 `.wtsheet`；实体/动画只存 sheet 路径 + 格子号，运行时 `ResolveCell` 解析；PPU 统一像素到世界单位；`Animation Editor` 里预览、加事件；改 sheet 后热重载；UI 用 1920×1080 参考分辨率和 Canvas 编辑器做吸附/对齐；`Project Health` 检查缺失引用和大文件。

3D：美术给 FBX/glTF；定义单位、Y-up、法线绿通道、材质通道、贴图搜索路径；编辑器 cook 成 `.wtmodel`，自动加 `Animator3D`，可选 clip/调速度；改模型后 Re-Cook 并清缓存；角色缩略图用离屏 FBO 预览。验收时用编辑器直接看，不用等程序打包。这样美术改图/改模型不会变成程序改代码。

### 28. 谈谈你对当前游戏引擎研发技术发展趋势的看法和见解。

**答：** 趋势是“内容管线数据化、渲染 GPU 驱动化、平台移动化、AI 进入生产工具链”，但引擎的竞争力越来越多在工具和迭代速度，而不只是渲染特性。

我关注的：ECS/DOD 和 job system；GPU-driven/indirect draw、Virtual Geometry；实时 GI/软阴影/光线追踪；移动端 TBDR 和能效；跨平台 RHI（D3D12/Vulkan/Metal/WebGPU）；UGC 和热更新；AI 辅助资产生成、对话、测试和调参；开源引擎（Godot）和商业引擎的边界变化。

Wheatear 的定位不是追 AAA：它把 2D 内容生产、数据驱动流程、编辑器调参和打包闭环做深，同时用 3D 角色验证骨骼/蒙皮/PBR/阴影；AI 目前主要用于素材生成和开发辅助。我认为对中小团队，真正的趋势是“策划/美术能自助迭代”，而不是每个改动都找程序。

### 29. 讲述一次你快速学习新的游戏引擎相关技术的经历和收获。

**答：** 我学新技术的方法是“先做最小可运行集成，再补原理和边界，最后写成文档”。

例子：接 Box2D 时，先用最小场景验证 body/fixture/step 和坐标系，再把组件映射进去；遇到动画碰撞盒不跟随，才去读 fixture 拷贝 shape 的语义，最后做 `SyncAnimationDrivenColliders` 和系统排序。接 ShaderC/SPIRV-Cross 时，先跑通一个 quad shader 的 SPIR-V 编译和 `glSpecializeShader`，再加磁盘缓存和损坏回退。接 3D 骨骼时，先用 Fox 验证 glTF skin/joint/weight 和 30 FPS 烘焙，再扩到 Robot 多材质和 Samba 的 FBX 预计算矩阵。

收获：新技术不要一上来铺满全项目；先用最小闭环验证，再抽象；把踩坑写成教材章节，下次就能复用。`docs/05_引擎教材` 就是这么来的。

## 30–39 测试、AI、稳定性与网络

### 30. 在游戏引擎研发中，如何进行有效的代码测试和调试工作？

**答：** 测试和调试要分层：能自动检查的不要靠人眼，能复现的不要靠猜。

Wheatear 现在有：spdlog + 编辑器 Console 的 2048 条环形日志；Debug 断言（`WT_ENABLE_ASSERTS`，失败 `__debugbreak`）；`Renderer2D::GetStats()` 的 draw calls/quads/vertices/indices；WAO `ActionDebugHistory`（256 条环形，Debug 才记录）和 Action Editor 的 Sandbox 预演；Play 模式暂停 F6/单帧 F7；`Project Health` 的缺失引用/场景跳转/资源注册/源码同步检查；`AssetDependencyScanner` 打包预检；`WheatearSandbox --test-wao` 的 28 个自检；GitHub Actions 的 Debug 构建。

不足：没有 gtest/Catch2、没有 CI 跑测试、没有自动化渲染回归。下一步会把 `--test-wao` 扩成测试入口，加关键场景的截图/哈希回归和启动冒烟测试。调试复杂问题时，我的顺序是：最小复现 → 日志/断点 → RenderDoc/帧分析 → 二分定位 → 修复 → 回归场景。

### 31. 说说你对游戏引擎中人工智能系统集成的思路和方法。

**答：** AI 系统要分两层看：游戏 AI 是“感知-决策-动作”，ML/LLM 是“生产工具或对话能力”，两者都不应该直接改游戏状态。

Wheatear 的游戏 AI：SideCombat 是计时器+距离的 FSM（aggro 8、攻击间隔、Boss 血量阈值切招、冲锋/震波）；TurnCombat 是确定性回合选招（`round % 3` / `round % 2`）+ 最低血量比例目标；TacticalCombat 是曼哈顿距离贪心走一格，没有 A*；Arcade Boss 是跳跃/射击计时器 + Lissajous 轨迹；WAO 的 `BehaviorVM` 用字节码描述动作逻辑，AI 只产出 `ActionIntent`，后面交给 `ActionResolver/EffectLedger`。

如果做更强的 AI：感知层用黑板/组件查询，决策层上行为树/效用 AI/GOAP，动作层仍然走 WAO；导航层补 A*/流场。ML/LLM 适合离线生成对话、关卡草稿、调参建议、QA bot，运行时必须有限流、校验、回退和可观测性；不能让模型直接写存档或改战斗数值。引擎侧要提供钩子、遥测和可回放的调试数据。

### 32. 若要改进现有游戏引擎的某个功能模块，你会如何开展工作？

**答：** 改模块先“冻结行为”，再换实现；没有基线就不动结构。

步骤：1）读接口和调用方，画数据流/时序；2）写 3–5 个回归场景或自检，记录基线（帧时间、draw calls、结果）；3）找耦合点和性能热点；4）设计新边界，先加适配层，不改调用方；5）分小步迁移，每步可编译、可回滚；6）对比基线；7）更新文档和编辑器工具。

例子：如果改 `CommandBus`，我会先把 if-chain 包成注册表，保留现有字符串命令和 `CommandResult`；如果改 Tactical AI，会先加 A* 但保留贪心 fallback，用同一关卡对比步数和耗时；如果改 SideCombat，会先拆生命周期/调参/命中服务，避免一次性重写 20 个服务。原则是“行为不变的重构”和“行为变化的改版”分开提交。

### 33. 如何在游戏引擎研发中保证代码的稳定性和兼容性？

**答：** 稳定性靠“边界检查 + 失败可恢复 + 版本兼容”，兼容性靠“默认值 + 迁移 + 回归”。

Wheatear 里：Debug 断言、RAII/智能指针、Scene 延迟销毁、运行时指针不序列化、纹理缺失走 1×1 洋红 fallback、场景写入用 `.tmp + rename` 原子替换、存档/设置带 schema 和版本号、旧字段用 `as<T>(default)` 兼容、热重载先解析到临时容器失败拒绝、`wtpack` 有 magic/version/指纹、补丁有 SHA-256 和回滚、`Project Health` 打包前拦截缺失引用。

兼容性还包括：编辑器保留 `.wts` 未识别行、场景/Prefab 版本号、路径多候选解析、UTF-8 `/utf-8` 编译、Windows 大小写不敏感但代码里不依赖。下一步是 CI 跑自检 + 旧存档/旧场景样本回归。

### 34. 谈谈你对游戏引擎网络通信模块的了解和相关开发经验。

**答：** 当前 Wheatear 没有网络模块，这是明确的边界；如果要做，我会把网络当成“另一套权威数据源”，而不是在玩法里加 socket。

我的理解：传输层 UDP（可靠/不可靠通道）或 QUIC，登录/房间用 TCP/HTTP；序列化用紧凑二进制 + 版本；服务器权威 + 客户端预测/回滚 + 延迟补偿；快照/增量同步、兴趣管理、频控；反作弊、重连、时钟同步、匹配/NAT 穿透。不同品类取舍不同：回合制/战棋可以锁步或服务器回合结算；横版动作/弹幕需要高频 tick + 预测；MMO 要分线/分服和兴趣管理。

Wheatear 的有利条件：固定步长已经有（60Hz 可选）、`CommandBus/ActionIntent` 是天然的网络命令边界、`wtpack` 有版本/指纹。难点：Box2D 跨平台确定性不够，动作战斗的 rollback 成本高；我会先做“服务器权威 + 客户端表现预测”，而不是全量 deterministic lockstep。当前 `Ws2_32` 只是平台链接依赖，没有实际网络代码。

### 35. 描述你在处理游戏引擎复杂逻辑关系时所采用的思维方式。

**答：** 复杂逻辑先拆“状态、事件、数据、所有权”，再用状态机和表格把分支压平。

我会做：1）画状态图/时序图，列出每个状态的进入/退出/合法事件；2）明确“同一事实只有一个 owner”（血量归玩法，表现归反馈，存档归 `GameProgress`）；3）把规则放数据表/配方，把流程放脚本/命令；4）用不变量和断言保护；5）用 ledger/日志让每一步可追踪。

例子：SideCombat 一次攻击是 `Input → ActionIntent → Recipe（startup/hitTime/recovery/cancel 窗口）→ Hitbox → HitResolution → EffectBundle → Ledger → Signal（音效/特效/UI）`。每一段有独立服务，出问题能定位到段。TurnCombat 是 `Intro/AwaitCommand/AwaitTarget/Acting/Victory/Defeat` 的相位机；Tactical 是 `PlayerTurn/AwaitCommand/Targeting/Acting/EnemyTurn`。把“什么时候”与“做什么”分开，复杂逻辑就不会堆成一个巨型 update。

### 36. 举例说明你怎样利用开源游戏引擎资源进行自主学习和开发。

**答：** 开源引擎/库是我主要的学习来源，但我会“读源码 + 包一层 + 写文档”，而不是直接散落调用。

Wheatear 用了：entt（ECS）、GLFW（窗口）、GLAD（GL loader）、ImGui/ImGuizmo（编辑器）、glm（数学）、yaml-cpp（序列化）、Box2D（2D 物理）、spdlog（日志）、miniaudio（音频）、stb（图像/压缩）、tinyobjloader/ufbx/cgltf（模型）、ShaderC/SPIRV-Cross（shader）。用法上都有封装：`Window/RendererAPI/Texture/Framebuffer/AudioEngine`，玩法不直接依赖第三方类型。

学习例子：读 entt 的 sparse set 理解 SoA 和 view；读 Box2D 的 fixture 拷贝语义解决碰撞盒同步；读 ImGui docking 的 DockSpace/Viewport 实现编辑器浮动面板；读 Godot/UE 的源码对照场景树、资源管线和 GAS；读 glTF/FBX 规范理解 skin/joint/weight 和预计算矩阵。注意许可证和版本锁定，vendor 里固定版本，避免“能跑但不可复现”。

### 37. 如何与策划团队沟通，将游戏设计理念转化为游戏引擎可实现的功能？

**答：** 和策划沟通的目标不是“听懂需求”，而是“把需求变成可调、可验证的数据和命令”。

我的做法：先让策划用玩家语言描述体验（什么时候、什么反馈、失败会怎样），再一起拆成状态/事件/数据；能配置的绝不硬编码；先做可玩的灰盒，再调数值；每个功能给验收标准和可调参数。

Wheatear 里对应：Boss 阶段阈值/攻击间隔放 tuning YAML；技能放 WAO 配方（冷却、前后摇、效果、信号）；剧情分支放 `.vn`；流程跳转放 `.wts`；UI 页面放 `.wtuit + CommandBus`；编辑器给他们调参面板和热重载。这样策划改内容不用等程序编译，程序只维护“能力”和“边界”。如果需求超出当前能力，我会明确说“这个要加系统/要改数据结构”，并给替代方案和工期，而不是先答应再返工。

### 38. 讲讲你对游戏引擎性能瓶颈分析和突破方法的理解。

**答：** 瓶颈分析先分 CPU/GPU/IO，再看是“调用次数、数据量、带宽还是同步”的问题；突破往往来自架构，不是微优化。

CPU：draw call 提交、ECS 遍历、物理 step、UI 布局、字符串/分配、文件 stat；GPU：overdraw、纹理带宽、shader 复杂度、阴影/后处理、状态切换；IO：启动解包、纹理解码、YAML 解析。工具：帧时间打点、`Renderer2D` stats、RenderDoc、GPU timer、内存 profiler；Wheatear 的 `Instrumentor` 目前只有宏，还没接采样 profiler。

已经做的突破：2D 合批（1 万 quad/32 纹理/共享 IBO）、纹理/模型/图集/IBL/Shader 缓存、文件轮询降频、UBO 脏标记、字体脏区上传、UI 裁剪与视口虚拟化。下一步如果 2D 还慢，会看 overdraw 和 UI 布局；如果 3D 慢，会看阴影/SSAO 分辨率、角色 draw call 和蒙皮成本；如果启动慢，会做分阶段打点和异步加载。原则：先证明瓶颈，再改；改完用同一场景回归。

### 39. 当游戏引擎研发中出现紧急问题时，你的应急处理流程是怎样的？

**答：** 紧急问题先止损，再定位，再修复，最后补防复发；顺序不能反。

流程：1）确认影响面（是否丢档/崩溃/付费）→ 2）止损（关功能、回滚补丁、切备用场景/资源）→ 3）保留现场（日志、存档、复现步骤）→ 4）最小复现和二分定位 → 5）修复 + 回归 → 6）发版/回滚验证 → 7）复盘和自动检查。

Wheatear 里可用的止损点：热重载解析失败直接拒绝、不替换旧配置；存档先写 `.tmp` 再 rename；`wtpack` 有指纹缓存和补丁回滚/启动健康检查；缺失纹理会走洋红 fallback 而不是崩；`Project Health`/打包预检在发版前拦截缺失引用。原则是“玩家数据 > 稳定性 > 性能 > 新功能”，并且及时同步影响和 ETA，不静默修。

## 40–48 UI、加载、数据、迭代与反问

### 40. 谈谈你对游戏引擎用户界面开发的理解和相关技术掌握情况。

**答：** UI 分两条线：编辑器用 ImGui 即时模式追求工具效率，游戏 UI 用 ECS 组件 + Canvas 追求可控布局和批渲染。

Wheatear 游戏 UI：`UICanvas` 参考 1920×1080，widget 用 0..1 归一化坐标 + anchor + parent 嵌套；`UISystem` 递归算 rect、可见性、clip，按 `SortOrder` 排序；`UIRenderer` 转 NDC，复用 `Renderer2D` 合批，scissor 裁剪；组件有 Image/Panel/Text/Button/Progress/Slider/Pager/ScrollView/Path/SkillTree/Checkbox/RadialCooldown；`UIAnimator` 做 fade/slide/pop/pulse；`.wtuit` 模板复用；按钮点击走 `CommandBus`。

编辑器：ImGui docking、浮动窗口、Viewport、Gizmo、Inspector、Content Browser、UI Canvas Editor（吸附/对齐/分布）、撤销。挑战：分辨率适配、DPI、localization（编辑器中英双语）、焦点/输入穿透、UI 合批和文字图集。当前重点在键鼠/触屏，完整无障碍和手柄导航还不是重点。

### 41. 描述你在优化游戏引擎加载速度方面所做过的尝试和成果。

**答：** 加载优化的核心是“减少小文件 IO、避免重复工作、把能缓存的缓存”，并用启动打点证明。

Wheatear 的做法：打包成单个 `content.wtpack`（zlib 压文本，图片/音频直接 store），避免几千个小文件；运行时按指纹解包到缓存，指纹不变不重复解包；解包先 staging 再原子提交；Shader 编译结果缓存 SPIR-V（`assets/cache/shader/opengl`），IBL 预计算缓存 `.iblcache`；缩略图每帧只渲染一个、失败缓存不重试；文本预加载；文件 mtime 轮询降频。

诚实说：我没有做严格的 A/B 启动基准，当前成果主要是结构性的。下一步会加“启动分阶段打点”（窗口/资源注册/解包/场景反序列化/纹理上传/首帧），再做异步加载和按场景拆 bundle；否则无法判断是解包、YAML 还是纹理上传占大头。

### 42. 说说你对游戏引擎数据存储与读取机制的理解和实践经验。

**答：** Wheatear 的数据层是“文本优先、二进制打包、版本化、可回滚”，牺牲一点读取速度换可读性和可调试性。

具体：场景/Prefab/材质/动画/调参/动作/成长用 YAML；流程用 `.wts`，剧情用 `.vn`；存档 `.wtsave/.vnstate/.wtsettings` 是 key=value 文本，带 schema 和版本（进度 v3、设置 v1）；资源注册表是 YAML；运行时包 `content.wtpack` 是二进制（magic/version/entry/method/size/path/payload）；3D 模型是 `.wtmodel` 二进制，带版本和预计算动画。

读写策略：场景写入 `.tmp + rename` 原子替换；反序列化用 `as<T>(default)` 兼容旧字段；Prefab 有 Version 2 和 UUID 重映射；存档槽 20 个，设置和进度分离；热重载先解析后替换。取舍：YAML 可 diff、可手改、编辑器好接，但大场景解析慢、体积大；下一步会给场景做二进制缓存/压缩，但保留 YAML 作为源格式。

### 43. 若参与游戏引擎更新迭代项目，你会重点关注哪些方面？

**答：** 引擎迭代先保“文件格式/API/行为”三条兼容线，再用回归场景和打包预检验证。

我会重点关注：数据 schema 和版本迁移（场景/Prefab/存档/动作/调参/模型）、编辑器与运行时同版本、旧项目能否打开、关键玩法回归、性能预算、平台/打包、文档和弃用策略。流程：小步提交、CI 构建、旧样例工程回归、打包冒烟、补丁说明；对外 API 尽量加不删，废弃先警告再移除。

Wheatear 已有的基础：场景/Prefab 版本号、存档 schema、`.wtmodel` 版本号、默认值反序列化、`wtpack` 版本/指纹、`RuntimePatchManager` 的 SHA-256/回滚/启动健康检查、`Project Health`。下一步是把“旧场景/旧存档/旧模型”样本纳入自动回归，避免升级时静默坏档。

### 44. 如何在游戏引擎研发中培养和提升自己的创新能力？

**答：** 创新不是凭空造新概念，而是“在约束里发现重复痛点，用更合适的抽象重组”。

我的做法：记录每次重复劳动和踩坑（比如每个玩法都要写一遍动作/命中/表现），找共同语言，做最小抽象，再验证是否真的复用。WAO 就是这么来的：参考 GAS 的 Ability/Effect/Cue，但砍掉网络复制/UObject 反射，只保留 `Intent → Recipe → Resolver → Effect → Ledger → Signal`，适配单机 2D 多玩法。还有 `.wtsheet` 的“引用而非烘焙”、`CommandBus + .wts` 的流程数据化、`Project Health` 的自动检查、Action Editor 的沙盒预演、`.wtmodel` 的 cook。

创新也要克制：抽象过度会比重复更贵。我会先做 2–3 个玩法的垂直验证，再决定是否上升为公共层；每个抽象都写清边界和代价。

### 45. 谈谈你对游戏引擎音频处理模块的认识和相关技术应用。

**答：** 音频模块的目标是“稳定播放、可控混音、和玩法事件对齐”，不是只放一个 PlaySound。

Wheatear 用 miniaudio：`AudioEngine` 包 `ma_engine/ma_sound`；BGM 用流式（`MA_SOUND_FLAG_STREAM`），SFX 用解码（`MA_SOUND_FLAG_DECODE`）；句柄 `uint32_t + map` 管理，播放结束回收；`AudioSourceComponent` 支持 PlayOnStart/循环/音量；`AudioSystem` 把 Master/BGM/SFX 三路增益乘起来；场景停止时统一清理；玩法音效走 `GameplayAudioService/asset alias`，避免硬编码路径。

现状边界：没有解码缓存、3D 空间化、混响、ducking、优先级/voice limit；音量是线性百分比而不是感知曲线。对体验的影响：BGM 切换、打击音、UI 反馈的时机和音量平衡直接决定手感；下一步会补混音总线、压缩/流式、空间音频和音频事件表。

### 46. 讲述你在开发小型游戏项目中运用游戏引擎的完整过程。

**答：** 小项目也要按“竖切”做：先打通一条完整链路，再横向扩内容，最后补发布。

WheatearDemo 的流程就是样板：`主菜单 → VN 剧情 → 弹幕假玩法 → 回合制过渡 → 横版战斗 → Boss → 结算 → 据点 → 技能树/装备/关系/存档 → 后续剧情`。过程：1）定范围和验收；2）搭地基（场景/渲染/输入/音频/资源）；3）做一条竖切（VN 或 SideCombat）；4）补数据/编辑器/热重载；5）接成长/存档/设置；6）打包到干净机器跑；7）修启动/缺失资源/性能；8）写文档和复盘。

关键是早打包、早让非程序的人用编辑器改内容；不要等功能全做完才集成。每加一个玩法，先问“它复用哪些引擎能力、哪些必须私有”，避免把 Demo 写成一次性代码。3D 角色也按同样思路：先做单角色导入/蒙皮，再做多角色和玩法。

### 47. 对于游戏引擎研发中的代码规范，你有怎样的重视程度和实践？

**答：** 代码规范的价值是降低 review 和交接成本；我会把“能自动检查的”交给工具，把“需要判断的”写进 review checklist。

# 第二部分：3D 角色与动画专项（A–H，118 题）

> 这一部分基于当前工作树，覆盖骨骼、GPU 蒙皮、glTF/FBX 动画、`.wtmodel` cook、3D 角色渲染、编辑器工具和 3D 玩法迁移。
>
> 标记说明：★★★ 为看 Demo 后高概率追问；★★ 为深挖；★ 为加分/压力题。

## 0. 先对齐事实

### 0.1 当前已经实现的能力

- **模型导入**：FBX（ufbx）、glTF/GLB（cgltf）、OBJ（tinyobjloader）。
- **模型 Cook**：编辑器 Re-Cook、`WheatearSandbox --cook-model <path>`，生成引擎原生 `.wtmodel` 二进制。
- **骨骼**：`ModelBone`（名称、父级、Bind TRS、InverseBind），支持层级和 Bind Pose。
- **蒙皮**：`MeshVertex` 带 `BoneIndices` / `BoneWeights`，每顶点最多 4 骨骼影响；GPU 蒙皮。
- **动画**：`ModelAnimation`，30 FPS 烘焙；glTF 走 TRS 采样，FBX 走预计算骨骼矩阵；支持循环、播放速度、单 clip 播放。
- **Crossfade**：`Animator3DComponent` + `BlendBonePose` 有代码实现，但当前没有公开的运行时切换 API/调用点。
- **渲染**：`Renderer3D` 的 Bone UBO（`k_MaxBones = 256`）；PBR 和 Shadow shader 都做蒙皮。
- **编辑器**：`MeshRenderer` 指定带骨骼模型后自动添加 `Animator3D`；`Animator3D` 抽屉可选 clip、播放/暂停/重播、调速度、调 crossfade。
- **场景**：`SkeletalTest.wt`（Fox）、`RobotTest.wt`（RobotExpressive）、`SambaTest.wt`（SambaDancing FBX）、`ModelImportTest.wt`（静态 Box/BlenderCube）。
- **剔除/合批**：静态 Mesh 支持视锥剔除和 instancing；蒙皮 Model part 跳过剔除，逐 part 绘制。

### 0.2 演示资产的可量化数据

| 模型 | 骨骼 | Clip 数 | 顶点 | Part | 动画存储 | `.wtmodel` |
| --- | ---: | ---: | ---: | ---: | --- | ---: |
| Fox | 24 | 3（Survey / Walk / Run） | 1,728 | 1 | TRS，30 FPS | 277 KB |
| RobotExpressive | 43 | 14（Dance / Idle / Walk / Run / Punch…） | 7,214 | 19（4 个 skinned） | TRS，30 FPS | 1.5 MB |
| SambaDancing | 104 | 2（Take 001 / mixamo.com） | 165,960 | 2 | FBX 预计算矩阵，30 FPS | 15.1 MB |
| BrainStem | 18 | 1（34.88s） | 34,159 | 59 | TRS，30 FPS | 3.7 MB |

场景默认值：

- Fox：`DefaultClip = Walk`，Transform Scale 0.02。
- Robot：`DefaultClip` 为空 → 运行时取第一个 clip，即 **Dance**。
- Samba：`DefaultClip = mixamo.com`（18.2s），Scale 1。
- 相机：透视 45°，near 0.1 / far 1000；Samba 场景额外有一盏 Point Light 补光。

### 0.3 已知边界（面试前务必心里有数）

1. **编辑 Play 副本不复制 `Animator3DComponent`**：`SceneComponentGroups.h` 的 `AnimationCopyableSceneComponents` 目前只有 `SpriteAnimatorComponent`，`Scene::Copy` / `DuplicateEntity` 会丢掉 3D 动画器。编辑器里点 Play 可能只显示 Bind Pose；Sandbox 直接加载场景则正常。面试前建议验证，必要时把 `Animator3DComponent` 加进复制组。
2. **Crossfade 没有公开调用点**：`NextClipIndex` 只在序列化里被重置，运行时没有 `Play/CrossFade` API 去设置它。代码存在，但演示里基本是单 clip 循环。
3. **FBX 预计算动画不走 crossfade**：`AnimationSystem.cpp` 的 `Precomputed` 分支采样后直接 `continue`，后面的 `BlendBonePose` 只对 TRS 动画生效。
4. **没有 3D 动画事件 / 状态机 / 混合树 / root motion / 重定向 / 压缩 / LOD**。
5. **蒙皮 part 不做视锥剔除**：姿势会改变 AABB，当前选择始终绘制；Robot 19 个 part 会放大 draw call。
6. **Bone UBO 上限 256**：Cook 允许 4096 根骨骼，但 GPU 只上传前 256 根；超过 256 的索引会越界。Samba 104 根是安全的。
7. **Samba 15.1 MB 没有压缩**：165,960 顶点 × 64B ≈ 10.6 MB，加 104 骨骼 × 547 帧 × 64B ≈ 3.6 MB。
8. **3D 角色目前是技术验证场景**：没有接入主玩法、WAO、3D 物理和 3D 角色控制器。
9. **打包注意**：`.wtmodel` 是二进制，依赖扫描不会解析它内部的贴图路径；当前打包可能只收源 `.glb/.fbx`，运行时回退到源文件导入。若要在 Player 里验证 cooked 模型，需检查 `content.wtpack` 是否包含 `.wtmodel` 和贴图。

### 0.4 一句话讲法

> Wheatear 的 3D 角色管线已经打通：glTF/FBX 导入 → 骨骼/权重 → 30 FPS 烘焙 → `.wtmodel` cook → GPU 蒙皮 → PBR/阴影 → 编辑器选 clip 和调参。当前覆盖的是“角色能正确动起来”，下一步才是状态机、动画事件、root motion 和 3D 玩法接入。

## A. 镜头与演示层

### A1 ★★★ 视频里这三个角色分别是什么？为什么选狐狸、机器人、舞者？

**答：** 分别是 `Fox.glb`、`RobotExpressive.glb`、`SambaDancing.fbx`。它们覆盖了三种典型情况：glTF 小骨架（Fox 24 骨骼/3 clip）、glTF 多材质/多 clip（Robot 43 骨骼/14 clip/19 part）、FBX 大骨架 + 预计算矩阵（Samba 104 骨骼/2 clip/165,960 顶点）。选它们是为了同时验证 glTF 与 FBX、TRS 与预计算、单 part 与多 part 三条路径。

### A2 ★★★ 这些是游戏角色还是技术测试？主玩法里有没有真正用到？

**答：** 目前是技术验证场景（`SkeletalTest/RobotTest/SambaTest`），还没有接入主玩法。主流程仍然是 VN、横版战斗、弹幕、回合制、战棋和成长系统；3D 角色验证的是导入、骨骼、蒙皮、动画和渲染管线。诚实的说法是“3D 角色管线已打通，3D 玩法接入是下一步”，不要说成“3D 游戏 Demo”。

### A3 ★★★ 狐狸/机器人/舞者各多少骨骼、多少 clip、多少顶点？为什么差异这么大？

**答：** Fox 24 骨骼/3 clip/1,728 顶点/1 part；Robot 43 骨骼/14 clip/7,214 顶点/19 part；Samba 104 骨骼/2 clip/165,960 顶点/2 part。差异来自资产本身：Fox 是低模四足，Robot 是多材质人形，Samba 是高模 FBX 舞蹈动画。后两者正好用来暴露 draw call、内存和骨骼上限问题。

### A4 ★★ 机器人有 19 个 part、4 个 skinned part，为什么拆这么多？draw call 是多少？

**答：** 导入时按材质/子网格拆 part，Robot 有 19 个材质槽，所以 19 个 `ModelPart`。当前 `RenderSystem::RenderScene3D` 对 `mr.Model` 是逐 part `DrawMesh`，没有走 instancing，因此颜色 pass 最多 19 次 draw；shadow pass 同样逐 part，蒙皮 part 跳过剔除，最多再 19 次。实际 draw call 取决于静态 part 是否被视锥剔除。

### A5 ★★ 舞者的 `.wtmodel` 有 15MB，包体和内存怎么承受？为什么不压缩？

**答：** 15.1MB 主要来自 165,960 顶点 × 64B ≈ 10.6MB，加上 104 骨骼 × 547 帧 × 64B ≈ 3.6MB 的预计算矩阵。当前没有顶点压缩、动画关键帧裁剪/量化、纹理 BC 压缩或 LOD。短期可以用动画压缩、网格量化、BC7/KTX2、LOD 和流式加载；长期应把动画和网格分开 cook，按需加载。

### A6 ★★ 狐狸为什么默认 Walk？机器人为什么默认 Dance？Samba 为什么是 18.2 秒？

**答：** 场景配置里 Fox 的 `DefaultClip = Walk`；Robot 的 `DefaultClip` 为空，运行时取第一个 clip，而 cooked 顺序第一个是 `Dance`；Samba 配的是 `mixamo.com`，时长 18.2s。这样演示里能同时看到短循环、长循环和不同骨架的播放效果。

### A7 ★★ 角色 Scale 分别是 0.02 / 0.1 / 1，为什么差这么多？导入单位怎么处理？

**答：** 三个源资产的单位不同：Fox 偏厘米级、Robot 偏分米级、Samba 是米级，所以场景里用 Transform Scale 把视觉大小拉齐。导入设置里其实有 `Scale` 和 `ConvertToYUp`，但当前演示更多是靠场景 Transform 缩放。更稳的做法是把单位转换烘焙进导入设置，避免每个场景手调 Scale。

### A8 ★★ 角色脚踩在地面上了吗？有没有滑步？没有 root motion 怎么解决？

**答：** 当前动画只驱动骨骼，不驱动实体 Transform；角色是原地动画。如果让实体移动，而动画速度/步幅不匹配，就会出现滑步。现在没有 root motion，位移应由角色控制器驱动；要消除滑步，需要做 root motion 提取、步幅匹配或 foot IK。

### A9 ★★ 角色阴影会跟着骨骼动吗？阴影 pass 怎么拿到骨骼矩阵？

**答：** 会。`RenderSystem::RenderSceneShadow` 取 `Animator3DComponent.BonePalette`，调用 `Renderer3D::DrawMeshShadow(..., bonePalette)`；`DrawMeshShadow` 把 palette 上传到同一个 Bone UBO，Shadow shader 用 `u_Bones` 做蒙皮。阴影贴图 2048，PBR 侧是 3×3 PCF。

### A10 ★★ 角色的材质和贴图从哪来？内嵌纹理怎么提取？

**答：** 导入器会把 glTF/FBX 内嵌贴图提取成 PNG（例如 `Fox_embedded0.png`），把材质路径写进 `ModelPart.Material`。PBR 材质包含 Albedo、Metallic、Roughness、Normal，并支持 Separate / ORM / Metallic-Smoothness 三种通道模式。

### A11 ★★ 3D 角色和 2D 角色/UI 同屏时，渲染顺序怎么排？

**答：** 当前顺序是：2D 场景（depth test 关闭）→ 3D 场景（depth test 打开）→ UI。3D 会覆盖与之重叠的 2D 像素，UI 最后盖在最上面。如果要做“3D 角色站在 2D 背景前/后”的混合场景，需要显式分层、深度或排序策略，不能依赖当前顺序。

### A12 ★★ 3D 角色场景的相机、灯光、地面怎么搭？为什么用透视相机？

**答：** 场景里是透视相机（45°、near 0.1、far 1000）+ 方向光 + 地面 Mesh；Samba 场景额外加了一盏 Point Light 补光。透视相机是为了展示 3D 体积和骨骼动作；正交相机更适合 2.5D 或编辑器俯视。

## B. 资产导入与 Cook

### B1 ★★★ 支持哪些模型格式？FBX/glTF/GLB/OBJ 各用什么库？

**答：** FBX 用 ufbx，glTF/GLB 用 cgltf，OBJ 用 tinyobjloader。FBX/glTF 走 `Model` 管线（可带骨骼/动画），OBJ 也可以走 Mesh/Model 路径；静态 OBJ 在编辑器里通常直接生成 `Mesh`。

### B2 ★★★ 为什么要把 FBX/glTF cook 成 `.wtmodel`？运行时直接读源文件不行吗？

**答：** Cook 的目的是把运行时不需要的源格式复杂度去掉：统一二进制、烘焙动画、避免运行时解析 FBX/glTF、加快加载、方便打包和版本校验。`Model::Create` 会优先找同名 `.wtmodel`；找不到才回退到源文件导入，并打 warning。生产环境应该只带 cooked 文件。

### B3 ★★★ `.wtmodel` 的格式是什么？v1/v2/v3 怎么兼容？

**答：** 魔数 `WTMODEL1`，然后是版本、Part 数；每个 Part 存名称、Transform、是否 Skinned、顶点/索引数、顶点/索引数据、材质和贴图路径；后面是骨骼（名称、父级、Bind TRS、InverseBind）和动画（名称、时长、帧数、FPS、是否预计算、采样数据）。v1 是静态网格，v2 加入骨骼/TRS 动画，v3 加入 `Precomputed` 标志。读取端同时兼容三个版本。

### B4 ★★ cook 什么时候触发？编辑器 Re-Cook 和命令行 `--cook-model` 分别怎么走？

**答：** 三条路径：Content Browser 的模型资产检查器里点 Re-Cook（用注册表里的导入设置，并清 Model cache）；MeshRenderer 拖入 `.fbx/.gltf/.glb` 时会顺带 cook；命令行 `WheatearSandbox.exe --cook-model <path>` 直接调 `Model::Cook`。注意 MeshRenderer 的拖入 cook 路径没有显式 `Model::ClearCache()`，热更新时可能仍拿到旧缓存。

### B5 ★★ 导入设置有哪些？Scale、Y-up、法线绿通道、ORM、纹理搜索路径各自解决什么问题？

**答：** `Scale` 处理单位差；`ConvertToYUp` 处理 Z-up 源（如 Blender/FBX）到引擎 Y-up；`FlipNormalGreen` 处理 DirectX/OpenGL 法线贴图绿通道差异；`ChannelMode` 处理 Separate / ORM / Metallic-Smoothness 三种贴图打包方式；`TextureSearchPath` 处理贴图不在模型同目录的情况。

### B6 ★★ glTF 和 FBX 的坐标系、单位、动画曲线差异怎么处理？

**答：** glTF 规范是右手 Y-up、米；FBX 的轴、单位、旋转顺序、继承模式都更自由。导入器用 ufbx 读 FBX 的变换，按 `ConvertToYUp` 转换；动画上 glTF 直接采 TRS，FBX 则把每帧 `geometry_to_world` 预计算成骨骼矩阵，避免把 FBX 的继承/轴规则压成局部 TRS 后姿态失真。

### B7 ★★★ 骨骼和蒙皮权重怎么导入？每顶点 4 个影响怎么选？超过 4 个怎么办？

**答：** glTF 读 `JOINTS_0` / `WEIGHTS_0`；FBX 读 skin cluster 的权重。顶点结构固定为 `ivec4 + vec4`，所以只保留权重最大的 4 个影响，然后归一化。超过 4 个的来源会丢弃尾部影响；当前没有做“保留 4 个后重新分配误差”的高级处理。

### B8 ★★ 权重归一化怎么做的？零权重/坏权重怎么兜底？

**答：** 导入时把 4 个权重求和，和大于 0 就除以总和；和接近 0 或数据缺失时，退化为 `BoneIndices = {0,0,0,0}`、`BoneWeights = {1,0,0,0}`，保证顶点至少跟一根骨骼走，不会塌到原点。

### B9 ★★ 子网格和材质拆分怎么做的？19 个 part 怎么管理？

**答：** 导入器按 primitive/material 拆 `ModelPart`，每个 part 有自己的 Mesh、Material、Transform、Skinned 和源顶点/索引。Robot 19 个 part 就是 19 个材质槽。管理上目前是逐 part 绘制；后续可以按材质合批、图集合并或把静态 part 合并成一个 Mesh。

### B10 ★★ 内嵌纹理怎么提取？法线/ORM 贴图怎么派生？

**答：** glTF/FBX 内嵌的 image 会写成 PNG（`stb_image_write`），材质里保存相对路径；ORM/Metallic-Smoothness 模式会把不同通道拆成引擎需要的 roughness/metallic 贴图。`FlipNormalGreen` 在导入时处理法线贴图的绿通道。

### B11 ★★ `.wtmodel` 里为什么还存 `SourceVertices/SourceIndices`？

**答：** 为了让编辑器在不重新读源 FBX/glTF 的情况下还能写 cooked 文件、做二次 cook 或后续编辑。代价是 CPU 侧多保留一份顶点/索引；Samba 165,960 顶点会多占约 10.6MB，这是后续可以按需丢弃的优化点。

### B12 ★★★ 模型缓存怎么做？重新 cook 后运行时怎么看到新结果？

**答：** `Model::Create` 用解析后的绝对路径做 key，缓存 `Ref<Model>`；`Model::ClearCache()` 在 Renderer Shutdown 和 Content Browser Re-Cook 后调用。运行时没有文件监听，所以重新 cook 后要清缓存或重启；编辑器里从 MeshRenderer 拖入触发的 cook 没有清缓存，这一点要特别注意。

### B13 ★★ 资源 UUID/路径迁移怎么处理？模型移动后场景引用怎么保持？

**答：** 场景同时存 `ModelPath` 和 `ModelAsset`（UUID）；`AssetRegistry` 维护 UUID → 路径映射，路径变了 UUID 不变，引用还能找到。跨路径移动资产的自动 ID 迁移（`.meta`）还没接，UUID 缺失时会回退到旧路径字段。

### B14 ★★ `.wtmodel` 怎么进 `content.wtpack`？依赖扫描怎么找到它？

**答：** 依赖扫描从启动场景 BFS，遇到场景里的 `assets/models/*.glb|fbx` 会收录源文件；但 `.wtmodel` 是二进制，扫描器不解析它内部的贴图路径。当前更可能把源 `.glb/.fbx` 打进包，运行时再回退导入；要让 cooked 模型和贴图稳定进包，需要补 `.wtmodel` 及其材质贴图的扫描规则。面试前建议实际打包 3D 场景验证。

### B15 ★★ 美术重新导出 FBX 后，旧动画、旧材质、旧 UUID 会怎样？

**答：** 重新 cook 会覆盖 `.wtmodel`，动画和网格以新文件为准；场景里的 `ModelAsset` UUID 如果没变，引用还在。材质如果按子网格名称匹配，改名会丢；UUID 迁移没接时，移动路径也可能断。实际流程应让美术保持节点/材质命名，cook 后清缓存并回归场景。

### B16 ★★ cook 失败时编辑器/运行时怎么提示和回退？

**答：** 编辑器 Content Browser 会显示 `Cook failed: <error>`；MeshRenderer 路径打 `WT_CORE_ERROR`。运行时 `Model::Create` 若 cooked 读取失败会返回 `nullptr` 并打错误；如果只是没有 cooked 文件，会回退到源文件导入。没有自动备份/原子替换，cook 中断可能留下半个 `.wtmodel`，这是后续要补的。

## C. 骨骼/蒙皮数学

### C1 ★★★ 骨骼层级、Bind Pose、Inverse Bind 分别是什么？

**答：** Bind Pose 是模型导入时的默认姿态；每根骨骼存 Bind Translation/Rotation/Scale 和 `InverseBind`。`InverseBind` 把网格顶点从模型空间变换到该骨骼的局部空间，是蒙皮公式的一部分。骨骼层级用 `Parent` 索引表示，根骨骼 Parent = -1。

### C2 ★★★ 世界骨骼矩阵怎么算？为什么 palette = world × inverseBind？

**答：** `BuildBonePalette` 先算每根骨骼的局部矩阵 `T * R * S`，再沿父级递归乘出世界矩阵，最后 `palette = world * InverseBind`。这个矩阵把 Bind Pose 下的顶点变换到当前姿态：先回到骨骼局部空间，再跟当前世界骨骼走。

### C3 ★★★ 顶点里的 bone indices/weights 怎么用？Shader 里的 skin 矩阵怎么算？

**答：** 顶点着色器读 `a_BoneIndices`（ivec4）和 `a_BoneWeights`（vec4），计算 `skin = Σ(u_Bones[index_i] * weight_i)`；然后 `localPos = skin * localPos`，法线用 `mat3(skin) * localNormal` 后再乘模型/法线矩阵。

### C4 ★★★ 为什么选 GPU 蒙皮？什么情况下 CPU 蒙皮更合适？

**答：** GPU 蒙皮把每顶点 4 次矩阵乘放到顶点着色器，CPU 只上传骨骼 palette，省掉大量 CPU 顶点变换和动态 VBO 上传。CPU 蒙皮更适合需要 CPU 侧碰撞/布娃娃/导出变形网格、或目标平台不支持顶点纹理/UBO 的情况。

### C5 ★★ 4 个骨骼影响怎么选？权重不归一化会怎样？

**答：** 导入时按权重排序取前 4，并归一化。权重不归一化会导致顶点被放大/缩小或偏离骨骼；如果总和小于 1，模型会向原点收缩；大于 1 会膨胀。当前导入端做了归一化和零权重兜底。

### C6 ★★ 法线怎么蒙皮？为什么不能直接用 mat4 变换法线？

**答：** 法线是方向向量，不应该受平移影响；严格做法是用蒙皮矩阵的逆转置（或每根骨骼的逆转置加权）。当前 shader 用 `mat3(skin) * localNormal`，在均匀缩放/刚体旋转下够用；遇到非均匀缩放会有偏差，后续可以改成逆转置或每骨骼法线矩阵。

### C7 ★★ 法线贴图/TBN 在蒙皮后怎么处理？

**答：** 当前没有顶点切线属性，`CalcNormal` 用屏幕空间导数从世界位置和 UV 重建 TBN：`dp1/dp2` 求切线，再正交化、叉乘出副切线。蒙皮后的世界位置和 UV 已经包含变形结果，所以法线贴图能跟着角色动；但屏幕空间 TBN 在极端拉伸/低模上会有误差。

### C8 ★★ 骨骼数上限 256 怎么来的？超过 256 会怎样？

**答：** `Renderer3D.h` 里 `k_MaxBones = 256`，对应 Bone UBO 的 `mat4 u_Bones[256]`。Cook 端允许 4096 根骨骼，但 `DrawMesh` 只上传前 256 根；如果顶点索引超过 255，shader 会越界访问 UBO。Samba 104 根是安全的；超过 256 需要改骨骼纹理/SSBO 或分块绘制。

### C9 ★★ 为什么用 UBO 传骨骼？每帧上传 16KB 的代价是什么？

**答：** UBO 比逐骨骼 `glUniformMatrix4fv` 调用便宜，适合 256 根这种数组；但当前每个蒙皮 part 都会 `SetData` 一次 16KB 的 BoneBuffer，Robot 19 个 part 就是 19 次重复上传。更好的做法是按实体缓存 palette，palette 不变就不重传，或者用 SSBO/纹理。

### C10 ★★ 骨骼矩阵用 mat4 还是 dual quaternion？精度/性能怎么取舍？

**答：** 当前是线性混合蒙皮（LBS），用 mat4 加权，简单、兼容性好；缺点是关节大角度扭转会出现“糖纸”收缩。Dual Quaternion Skinning 能改善扭转，但需要额外的双四元数混合和法线处理，成本和复杂度更高。当前项目用 LBS 是合理的第一版。

### C11 ★★ 蒙皮后的 AABB 怎么算？为什么现在跳过视锥剔除？

**答：** Mesh 的 AABB 是 Bind Pose 下算的，蒙皮后姿势会变，直接用旧 AABB 剔除会 pop。所以 `RenderSystem` 对 `part.Skinned` 跳过视锥剔除，始终绘制；代价是屏幕外角色仍然消耗顶点蒙皮和 draw call。后续可以用骨骼位置估算动态 AABB，或低频更新。

### C12 ★★ 蒙皮角色怎么投阴影？阴影 pass 需要哪些数据？

**答：** Shadow pass 走 `DrawMeshShadow`，需要同一个 `bonePalette` 和 `LightSpaceMatrix`；它把 palette 上传到 Bone UBO，Shadow shader 做和 PBR 一样的 `skin` 计算，再乘 light-space 矩阵写深度。颜色 pass 和阴影 pass 共用 palette，避免重复采样。

### C13 ★★ 蒙皮角色怎么做 instancing？为什么现在只对静态网格 instancing？

**答：** 当前 `DrawMeshInstanced` 只支持 `mr.Mesh` 的静态网格，`mr.Model` 逐 part 绘制。蒙皮 instancing 需要每实例的骨骼 palette（骨骼纹理/SSBO），现在的 Bone UBO 是全局一份，无法同时容纳多个角色的骨骼。要做需要改数据布局。

### C14 ★★ 1000 根骨骼/100 个角色怎么办？骨骼纹理、compute skinning 了解吗？

**答：** 256 根 UBO 不够时，可以把骨骼矩阵放进 Texture Buffer/SSBO，shader 按 `boneIndex` 采样；角色多时用 compute shader 做 GPU skinning，把结果写到输出顶点缓冲/纹理，再走普通绘制。还可以做动画 LOD、更新频率 LOD、骨骼裁剪。当前都没实现。

### C15 ★★ 蒙皮角色 LOD 怎么做？

**答：** 三层：网格 LOD（高模/中模/低模）、骨骼 LOD（远处合并/裁剪手指/面部骨骼）、更新 LOD（远处 15/30Hz 更新动画）。再加阴影 LOD 和 impostor。当前只有单套网格和每帧全骨骼更新。

### C16 ★ 布料、头发、表情、IK 怎么接？

**答：** 这些都需要额外的骨骼/约束/形变数据：布料可用骨骼链或专用 cloth solver；头发可用发片/条带 + 骨骼；表情可用 morph target 或面部骨骼；IK 需要双骨骼/多骨骼解算器。当前 `.wtmodel` 没有 morph target、IK、cloth 数据，属于后续扩展。

### C17 ★ 2D 骨骼和 3D 骨骼的本质区别是什么？

**答：** 2D 骨骼通常只在 XY 平面内做 2×3/3×3 变换，权重和层级更简单；3D 骨骼是完整的 TRS 层级，涉及四元数、法线、切线、蒙皮矩阵和更复杂的 Bind Pose。Wheatear 当前 2D 是序列帧 + 属性轨道，3D 才是真正的骨骼蒙皮。

### C18 ★ 如果让你从零写一个蒙皮系统，模块怎么分？

**答：** 导入/骨骼构建、Bind Pose/InverseBind、动画采样、姿态混合、骨骼世界矩阵求解、蒙皮矩阵生成、顶点蒙皮（CPU/GPU）、阴影/法线处理、LOD/压缩、调试可视化。Wheatear 的 `Model`、`AnimationSystem`、`Renderer3D` 大致对应这条链。

## D. 动画运行时

### D1 ★★★ `Animator3D` 的状态和字段怎么用？

**答：** `DefaultClip` 指定默认片段，`PlayOnStart` 决定启动是否播放，`Loop` 控制循环，`PlaybackSpeed` 控制速度，`FadeDuration` 是交叉淡化时长；运行时字段 `CurrentClipIndex/NextClipIndex/Time/NextTime/FadeElapsed/IsPlaying/BonePalette` 由 `AnimationSystem` 维护。

### D2 ★★★ 动画采样怎么做？30 FPS 烘焙 + lerp/slerp，为什么？

**答：** 导入时把动画按 30 FPS 烘焙成逐帧 TRS；运行时 `framePosition = time * fps`，取前后两帧，平移/缩放用 `glm::mix`，旋转用 `glm::slerp` 并归一化。30 FPS 是精度/内存/性能的折中，足以覆盖大多数角色动作；更复杂的情况可以 60 FPS 或保留原始曲线。

### D3 ★★★ 为什么 FBX 要预计算 bone matrices，而 glTF 用 TRS？

**答：** FBX 的继承模式、旋转顺序、轴和单位规则很复杂，把动画压成局部 TRS 再重建世界矩阵，可能和原 DCC 的姿态不一致；所以 FBX 直接烘焙每帧 `geometry_to_world` 骨骼矩阵，保证姿态正确。glTF 的节点 TRS/动画通道更规范，可以直接采样 TRS 再乘出世界矩阵。

### D4 ★★★ FBX 的继承/轴/单位规则具体会带来什么问题？

**答：** 例如 Pre/Post Rotation、Rotation Order、Inherit Type、Pivot、Unit Scale、Y-up/Z-up 混用；同一段动画在不同 DCC 里导出后，局部旋转可能看起来一样，但世界姿态不同。预计算矩阵绕开了这些规则，代价是数据量大、不能直接做 TRS 混合。

### D5 ★★ 预计算矩阵怎么采样？为什么逐帧取整而不是插值？

**答：** `frame = llround(time * fps)`，然后直接取该帧的 `BoneMatrices[bone][frame]`。矩阵插值会引入剪切/缩放伪影，且需要分解/重建；当前选择最近帧，30 FPS 下视觉上可接受，但快速动作会有轻微阶梯感。

### D6 ★★ 交叉淡化怎么实现的？alpha 和 slerp 怎么算？

**答：** `AnimationSystem` 同时采样当前 clip 和 `NextClipIndex` 的 clip，`FadeElapsed += dt`，`alpha = clamp(FadeElapsed / FadeDuration, 0, 1)`，用 `BlendBonePose` 对平移/缩放 lerp、旋转 slerp；alpha 到 1 后把 `CurrentClipIndex` 切到 `NextClipIndex`，清空过渡状态。

### D7 ★★★ FBX precomputed 动画能 crossfade 吗？代码路径怎么走？

**答：** 不能。`AnimationSystem` 里 `if (currentAnimation.Precomputed) { ...; continue; }`，在进入 crossfade 逻辑之前就跳过了。也就是说 Samba 这类 FBX 预计算动画目前只支持单 clip 播放；要做 crossfade，需要在矩阵层面混合（或分解成 TRS 再混合），成本和伪影都要处理。

### D8 ★★ 运行时怎么切 clip？有没有公开的 Play/CrossFade API？

**答：** 没有公开 API。当前只能直接改 `Animator3DComponent.DefaultClip` 并重置 `CurrentClipIndex`，或者手动设置 `NextClipIndex/NextTime`；编辑器抽屉也只做“选默认 clip + 重置”。面试时不要声称“支持运行时 crossfade 切换”，除非现场补了 `Play/CrossFade` 方法。

### D9 ★★ 循环/非循环/播放速度/暂停怎么处理？

**答：** `Loop` 为真时 `Time = fmod(Time, duration)`；为假时 `Time >= duration` 就 clamp 并 `IsPlaying = false`。`PlaybackSpeed` 取 `max(0, speed)`，0 等于暂停；`IsPlaying` 也可以单独暂停/恢复。

### D10 ★★★ 3D 动画事件有吗？攻击第 12 帧生成 hitbox 怎么做？

**答：** 当前没有 3D 动画事件。2D 的 `AnimationClip` 有事件轨道，3D 的 `ModelAnimation` 没有。要做的话，可以在 `ModelAnimation` 里加事件时间/名称，`AnimationSystem` 在采样时派发 `CommandBus`；或者由 WAO 按动作时间窗口生成 hitbox。后者更符合现有“动画只做表现、规则走玩法服务”的边界。

### D11 ★★★ 动画状态机有吗？Idle/Walk/Run/Jump 怎么切？

**答：** 没有状态机。`Animator3D` 只有当前 clip 和 next clip，没有参数、条件、过渡图。Idle/Walk/Run 需要外部系统根据速度/输入去设置 clip；复杂角色要补 AnimatorController（状态、参数、transition、interrupt、exit time）。

### D12 ★★ 混合树/上下半身分层/遮罩有吗？

**答：** 没有。当前只有整骨架的简单 crossfade，没有 1D/2D blend tree、没有 bone mask、没有 additive layer。要做“上半身攻击 + 下半身跑”，需要分层采样和按骨骼遮罩混合。

### D13 ★★★ root motion 有吗？没有的话位移怎么驱动？

**答：** 没有 root motion。动画只改骨骼，`TransformComponent` 不由动画驱动；角色位移要由控制器/玩法服务写 Transform。代价是容易滑步，尤其是 Walk/Run 的步幅和移动速度不匹配时。

### D14 ★★ 动画重定向/retargeting 了解吗？

**答：** Retargeting 是把一套骨架的动画映射到另一套骨架，需要按骨骼名称/层级建立映射，并处理 Bind Pose、比例、朝向差异。当前没有实现；`ModelBone` 只有名称/父级，没有重定向映射表。

### D15 ★★ 动画压缩/关键帧裁剪/曲线简化了解吗？

**答：** 常见做法：去掉线性段中间帧、量化时间/数值、只存变化骨骼、用半精度/16 位、曲线拟合；FBX 预计算矩阵还可以按误差阈值抽帧。当前全部 float32 逐帧存，Samba 15MB 就是没压缩的结果。

### D16 ★★ 动画内存怎么估？Samba 18.2s/104 骨骼/547 帧占多少？

**答：** 预计算矩阵：104 × 547 × 64B ≈ 3.64MB；TRS 动画则是 104 × 547 × (12+16+12)B ≈ 2.28MB。Samba 总文件 15.1MB，大头是 165,960 顶点 × 64B ≈ 10.6MB，再加索引和材质。面试时能把这两块拆开讲，比只说“15MB”更有说服力。

### D17 ★★ 多角色共享 Model/Animation 数据吗？BonePalette 是每实体一份吗？

**答：** `Model` 按路径缓存，多个实体共享同一份 Mesh/Bone/Animation 数据；`BonePalette` 在 `Animator3DComponent` 里，每个实体一份，因为每个角色的播放时间/姿态不同。共享模型数据是省内存的关键；每个角色一份 palette 是正确性要求。

### D18 ★★ 动画更新在哪个系统/顺序？和物理/渲染/命令的关系？

**答：** 3D 动画在 `AnimationSystem::OnUpdateRuntime` 里更新，位于 2D 动画之后、`RenderSystem` 之前；它只写 `BonePalette`，渲染阶段读取。物理不依赖 3D 动画；如果以后要做动画驱动碰撞，需要像 2D 的 `FollowAnimation` 一样加同步点。

### D19 ★★ 动画和 gameplay 的边界在哪？哪些逻辑不该写进动画？

**答：** 动画负责姿态、时间采样和表现事件；伤害、命中、状态、冷却、AI 决策属于玩法/WAO。动画可以发事件（2D 已有），但不应该直接改血量/规则。这样换动画、换模型不会改坏战斗逻辑。

### D20 ★★ 如果要做 3D 动作游戏，动画层还缺什么？

**答：** 状态机、混合树/分层、动画事件、root motion、IK、动画压缩/LOD、重定向、3D 命中盒/骨骼插槽、网络同步、动画调试器。当前只完成了“骨架 + 蒙皮 + 单 clip 播放”这一层。

## E. 渲染与性能

### E1 ★★★ 3D 角色 draw call 怎么算？19 个 part 是不是 19 次？

**答：** 颜色 pass 对每个 `ModelPart` 调一次 `DrawMesh`，所以 Robot 最多 19 次；shadow pass 也逐 part，最多再 19 次。静态 part 可以被视锥剔除，skinned part 跳过剔除，所以 4 个 skinned part 基本一定会画。没有对 Model part 做 instancing。

### E2 ★★★ 角色阴影/IBL/SSAO 都生效吗？开了哪些 pass？

**答：** 阴影和 IBL 在运行时/编辑器都生效；SSAO 目前只在 `EditorLayer3D` 里 `InitSSAO` 并 `ComputeSSAO`，Sandbox 运行时不计算。PBR shader 会读 shadow map、IBL irradiance/prefilter/BRDF LUT；SSAO 通过 `u_HasSSAO` 控制。

### E3 ★★ 角色材质是 PBR 吗？金属/粗糙度/法线怎么用？

**答：** 是 metallic-roughness PBR。`Material` 有 Albedo、Metallic、Roughness、NormalMap，shader 用 GGX/Smith/Schlick，IBL 用 irradiance + prefilter + BRDF LUT，法线贴图用屏幕空间 TBN 重建。

### E4 ★★ 角色贴图格式/压缩？BC/DDS/KTX 有吗？

**答：** 当前主要用 PNG/JPG 经 stb_image 解码成 RGBA8，没有 BC/DDS/KTX 压缩。165,960 顶点的角色贴图如果多张 2K/4K，显存会很快上去；README 也把 DDS/KTX/BC 列为后续。

### E5 ★★ 角色渲染的 overdraw/透明/排序怎么处理？

**答：** 角色大多是不透明，开深度测试，顺序影响较小；透明部件/特效会走 alpha blend，当前没有专门的 3D 透明排序。大量半透明叠加时 overdraw 和排序会变成问题。

### E6 ★★ 角色和 2D 场景/UI 的渲染顺序？

**答：** 2D → 3D → UI。2D 关深度，3D 开深度，UI 最后。角色会盖住 2D；如果角色应该被 2D 前景遮挡，需要额外的深度/层级方案。

### E7 ★★★ 角色动画的性能瓶颈在哪？CPU 采样、骨骼计算、UBO 上传、GPU 蒙皮？

**答：** 当前小场景主要成本在 CPU 采样 + `BuildBonePalette`（每帧分配 local/world 数组、递归求父级）+ 每个 part 一次 16KB Bone UBO 上传；GPU 侧是每顶点 4 次矩阵乘。Samba 165,960 顶点、104 骨骼，GPU 蒙皮和顶点带宽更明显。

### E8 ★★★ 同屏 100 个角色怎么办？instancing、骨骼纹理、Job System？

**答：** 当前架构会退化：100 个角色 × 每个角色每帧采样/建 palette/上传 UBO/逐 part draw。要扩展需要：动画 LOD/更新频率、骨骼纹理/SSBO、compute skinning、按材质/网格合批、视锥/遮挡剔除、Job System 并行采样。当前没有这些。

### E9 ★★★ 蒙皮角色为什么不做剔除？代价是什么？

**答：** Bind Pose AABB 会随姿势变化，直接剔除会 pop，所以代码对 `part.Skinned` 跳过剔除。代价是屏幕外角色仍要蒙皮/绘制；角色多时这是主要浪费。可以每 N 帧用骨骼位置更新动态 AABB。

### E10 ★★ 阴影贴图分辨率/PCF 对角色性能的影响？

**答：** 阴影是 2048×2048，PBR 侧 3×3 PCF；角色每个 part 都要进 shadow pass，蒙皮 part 还会重复做骨骼蒙皮。角色越多，shadow pass 的顶点/绘制成本越高；可以考虑阴影 LOD、只让近处角色投影、降低更新频率。

### E11 ★★ 移动端 TBDR 上角色渲染要注意什么？

**答：** TBDR 怕 overdraw、带宽和 Render Pass 切换；角色渲染要控制透明层数、贴图带宽、骨骼数量、顶点数，尽量在同一个 pass 里完成不透明绘制；蒙皮可以放 vertex shader，但要避免每 draw 大 UBO 上传。当前没有移动端优化。

### E12 ★★ 角色渲染怎么做 LOD/阴影 LOD/更新频率 LOD？

**答：** 网格 LOD（多套 Mesh）、骨骼 LOD（远处裁剪手指/面部）、动画更新 LOD（15/30Hz）、阴影 LOD（远处不投影或低分辨率）、材质 LOD。当前都没有。

### E13 ★★ 角色渲染和 UE/Unity 的 SkinnedMeshRenderer 比差在哪？

**答：** UE/Unity 有完整的骨骼动画状态机、混合树、事件、root motion、重定向、LOD、压缩、GPU skinning、布料/IK、材质变体和移动端优化；Wheatear 目前只有核心的导入/骨骼/蒙皮/单 clip 播放，差距主要在动画系统和规模化。

### E14 ★★ 如果角色进入主玩法，渲染层最先要改什么？

**答：** 动态 AABB/剔除、draw call 合批、动画 LOD、骨骼 UBO 复用、贴图压缩、透明排序、阴影策略；如果要做 3D 动作游戏，还要接 3D 物理/命中盒和相机。

## F. 编辑器/工具链

### F1 ★★★ 怎么给实体指定模型？`MeshRenderer` 的 `Model` 字段怎么工作？

**答：** Content Browser 把 `.fbx/.gltf/.glb` 拖到 MeshRenderer 上，编辑器会 cook 成 `.wtmodel`、设置 `Model`/`ModelAsset`、清空旧的 Mesh/Material，并在有骨骼时自动加 `Animator3D`。`.obj` 走 `Mesh` 字段。

### F2 ★★★ 指定带骨骼模型后为什么自动加 `Animator3D`？

**答：** `Mesh3DDrawers` 在设置 `c.Model` 后检查 `Model->HasSkin()`；如果有骨骼且实体没有 `Animator3DComponent`，就自动添加并把 `DefaultClip` 设为第一个动画。这样拖入模型就能直接播放，不用手动加组件。

### F3 ★★ 编辑器怎么列 clip、播放/暂停/重播、调速度、调 crossfade？

**答：** `SpriteAnimatorDrawer.cpp` 的 `DrawAnimator3DComponent` 从 `Model->GetAnimations()` 列 clip，提供 Play/Pause、Restart、Loop、PlayOnStart、Speed、Crossfade 控件，并显示当前 clip、时间、骨骼数、clip 数。

### F4 ★★ Re-Cook 做了什么？失败怎么提示？

**答：** Content Browser 的 Re-Cook 用注册表里的 `ModelImportSettings` 调 `ModelImporter::Cook`，写同名 `.wtmodel`，成功后 `Model::ClearCache()` 并显示“Model cooked”；失败显示“Cook failed: <error>”。MeshRenderer 拖入路径也会 cook，但没有清缓存。

### F5 ★★ 模型缩略图怎么渲染？能显示骨骼/动画吗？

**答：** Content Browser 的缩略图用 128×128 离屏 FBO + 临时场景，把模型按 Bind Pose 渲染一帧再读回纹理；动画 clip 缩略图取第一帧。它不播放骨骼动画，也不显示骨骼线框。

### F6 ★★ 动画编辑器支持 3D clip 吗？还是只支持 2D 序列帧？

**答：** Animation Editor 目前只编辑 `SpriteAnimatorComponent` 的 2D 序列帧、属性轨道和事件；3D clip 只能在 `Animator3D` 抽屉里选择/播放，没有时间线、事件轨道或关键帧编辑。

### F7 ★★ 如果要做 3D 动画状态机编辑器，怎么设计？

**答：** 节点是状态（clip/混合树），边是 transition（条件、exit time、duration、interrupt），参数面板是 float/bool/trigger，预览用当前场景角色；底层需要 AnimatorController 资产和运行时状态机。当前没有。

### F8 ★★ 模型导入设置面板在哪？改完怎么重新 cook？

**答：** Content Browser 选中模型后在检查器里改 Scale、Convert To Y-Up、Flip Normal Green、Material Channels、Texture Search Path，然后点 Re-Cook Model。改设置不会自动重 cook，需要手动触发。

### F9 ★★ 资源浏览器怎么识别 `.wtmodel/.glb/.fbx`？

**答：** `AssetRegistry` 把模型扩展名归到 `EditorAssetKind::Model`，Content Browser 用类型过滤和缩略图展示；`.wtmodel` 是 cooked 产物，源 `.glb/.fbx` 是导入源。

### F10 ★★ 美术重新导出 FBX，运行时怎么热重载？

**答：** 当前没有文件监听。流程是重新 cook → `Model::ClearCache()` → 重新加载场景/重启；Content Browser Re-Cook 会清缓存，MeshRenderer 拖入路径不会。要做到真正的热重载，需要监听 `.wtmodel` 时间戳并替换 `Ref<Model>`。

### F11 ★★ 3D 角色的 picking/选中怎么做？

**答：** PBR shader 把 `EntityID` 写到 fragment output location 2，编辑器 viewport 的 `RED_INTEGER` attachment 2 读出像素值，再转成 entt entity。3D 这条链是通的；2D 的 attachment 编号另有已知不一致，不要混着讲。

### F12 ★★ 3D 角色的 Gizmo/Transform 和 2D 有什么不同？

**答：** 3D 用 ImGuizmo 的 LOCAL 模式做平移/旋转/缩放，支持 0.5 单位吸附和 45° 旋转吸附；2D 主要是 XY 平移/Z 旋转。3D 相机是 `EditorCamera`，支持 Orbit/Fly。

## G. 3D 玩法与岗位匹配

### G1 ★★★ 3D 角色能接入现有 WAO/战斗系统吗？怎么接？

**答：** 可以复用 WAO 的 Intent/Recipe/Effect/Signal 语义，但需要补 3D 的表现和判定：3D 动作解析器、骨骼插槽/动画事件、3D hitbox、3D 位移/受击。当前 WAO 主要服务 2D 玩法，3D 角色还没有接。

### G2 ★★★ 3D 动作战斗的 hitbox、骨骼插槽、动画通知怎么设计？

**答：** 常见做法是动画里标 notify（时间/事件），运行时在指定帧从骨骼 socket 生成 capsule/sphere hitbox，交给命中服务；表现（特效/音效）走信号。Wheatear 目前没有 3D 动画事件和 socket，需要先补这两块。

### G3 ★★★ 3D 角色的移动/跳跃/碰撞用什么？Box2D 还是 3D 物理？

**答：** 当前 3D 角色只做渲染，没有 3D 物理；Box2D 是 2D，不能直接用于 3D 角色。要做 3D 角色控制器，需要 3D 碰撞查询（胶囊/球/射线）和运动学控制器，或者引入 Jolt/PhysX 这类 3D 物理。

### G4 ★★★ 如果要做 3D 角色控制器，需要哪些模块？

**答：** 输入映射、角色运动学（速度/重力/跳跃/地面检测/斜坡/台阶）、3D 碰撞查询、相机（第三人称/锁定）、动画状态机、root motion、命中/受击、网络同步。当前只有输入和相机的一部分。

### G5 ★★ 3D 角色和 2D 横版战斗的“手感”参数怎么迁移？

**答：** coyote time、jump buffer、hit pause、震屏、击退这些概念可以迁移；但 3D 要多考虑摄像机、锁定、转向、斜坡和 3D 命中体积。2D 的 “lane + air height” 在 3D 里变成完整的 XYZ 运动。

### G6 ★★ 如果要做 3D 开放世界，角色/动画/渲染/资源哪里先崩？

**答：** 先崩的通常是资源流式加载、draw call/骨骼数量、阴影/GI 和动画 LOD；角色本身不是最难的，难的是大规模场景的可见性、内存和加载。当前引擎没有流式加载、地形 LOD、虚拟纹理和 3D 物理。

### G7 ★★ 3D 角色的 GI/阴影/大世界 LOD 怎么接？

**答：** 阴影要从单方向光 shadow map 扩到级联/多光源；GI 可以用光照探针/DDGI/Lumen 类方案；角色要参与探针采样和间接光。大世界还要角色 LOD、阴影 LOD、动画 LOD。当前只有单方向光 2048 阴影 + IBL。

### G8 ★★ 3D 角色的网络同步怎么做？骨骼/动画状态还是根节点？

**答：** 通常同步根 Transform + 动画状态/归一化时间 + 关键参数，骨骼姿态在客户端本地采样；不需要每帧同步每根骨骼。服务器权威 + 客户端预测/回滚，或状态同步 + 插值。当前没有网络层。

### G9 ★★ 3D 角色多人同屏怎么优化？

**答：** 动画 LOD、骨骼纹理/SSBO、GPU skinning、instance/合批、动态剔除、更新频率 LOD、材质/贴图合批。当前逐角色逐 part 绘制，扩展性有限。

### G10 ★★ 3D 角色资产怎么和 2D 管线共存？

**答：** 共用 Scene/ECS/Asset/Editor，渲染上 2D 和 3D 各走一条 pass，UI 最后；资源上 `.wtmodel` 和 `.wtsheet/.wtanim` 并存。关键是明确 2D/3D 的深度和层级关系。

### G11 ★★ 如果要把引擎改成 3D 主引擎，路线是什么？

**答：** 3D 物理/控制器 → 动画状态机/事件/root motion → LOD/流式/大世界 → GI/阴影/后处理 → 材质/贴图压缩 → RHI/多平台 → 3D 编辑器工具。当前完成的是渲染和角色动画的基础段。

### G12 ★★★ 3D 角色支持对岗位匹配度有多大帮助？

**答：** 帮助很大：它证明你不仅会 2D 批处理，还碰过骨骼、蒙皮、动画烘焙、GPU UBO、PBR/阴影和资产 cook。但要诚实说明边界：状态机、事件、root motion、3D 物理、大世界还没做。岗位是 3D 引擎底层，这些“下一步”要能讲出清晰路线。

### G13 ★★ 你了解 UE/Unity 的骨骼动画管线吗？和你的差在哪？

**答：** UE 有 Skeletal Mesh、Animation Blueprint、Montage、Notify、Root Motion、LOD、Retargeting；Unity 有 SkinnedMeshRenderer、Animator/State Machine、Avatar、Humanoid Retargeting、Animation Events。Wheatear 目前相当于“Skeletal Mesh + 单 clip 采样 + GPU skinning”，动画系统和工具链差距最大。

### G14 ★★ 你了解 3A 角色渲染吗？皮肤/头发/布料/眼睛/表情。

**答：** 3A 角色通常有 SSS/预积分皮肤、发丝/发片、布料模拟、眼球折射/高光、面部 blendshape/骨骼、皱纹/汗毛/次表面散射。Wheatear 目前是标准 PBR，没有这些专用模型。

### G15 ★★ 你了解实时 GI 对角色/大世界的影响吗？

**答：** GI 决定角色在环境里的间接光、接触阴影和色调统一；大世界需要探针/DDGI/虚拟纹理。角色如果没有正确的环境光，会像“贴上去的”。当前只有 IBL，没有动态 GI。

### G16 ★★ 如果让你做 3D 引擎的动画模块，你会先做什么？

**答：** 先把“能正确动”做扎实：骨骼/蒙皮/采样/阴影一致；然后做状态机 + 动画事件 + root motion，这是动作游戏的地基；再做压缩/LOD/重定向和调试工具。当前项目已经完成了第一层。

## H. 风险/现场题

### H1 ★★★ 你的 crossfade 代码路径真的被调用了吗？怎么证明？

**答：** 目前不能证明。`NextClipIndex` 只在 `SceneSerializerAnimationComponents.cpp` 里被重置，代码库里没有运行时设置它的 `Play/CrossFade` API。要证明，需要补一个公开方法并在编辑器/输入里调用，然后打日志或看骨骼过渡。

### H2 ★★★ FBX precomputed 动画能 crossfade 吗？

**答：** 不能。`Precomputed` 分支采样后直接 `continue`，crossfade 只在 TRS 分支执行。Samba 这类 FBX 角色目前只能硬切或单 clip 播放；要 crossfade 需要矩阵混合/分解。

### H3 ★★★ 骨骼数超过 256 会怎样？

**答：** `DrawMesh` 只把前 256 根 palette 上传到 Bone UBO，shader 的 `u_Bones[256]` 只有 256 项；顶点索引超过 255 会越界，表现为模型爆炸/错位/未定义。Cook 端允许 4096，但 GPU 端没有跟上；Samba 104 根安全。

### H4 ★★★ 蒙皮角色为什么不做视锥剔除？代价是什么？

**答：** Bind Pose AABB 会随姿势变化，直接剔除会 pop；当前对 `part.Skinned` 跳过剔除，始终绘制。代价是屏幕外角色也消耗蒙皮/draw call，角色多时浪费明显。后续用动态 AABB/骨骼包围盒或低频更新。

### H5 ★★ 15MB 的 Samba 模型，包体/内存怎么优化？

**答：** 动画关键帧裁剪/量化、矩阵压缩、顶点量化/网格压缩、贴图 BC/KTX2、LOD、按需流式加载；还可以把动画和网格拆成独立资产，只加载需要的 clip。当前都没做。

### H6 ★★★ 3D 动画没有事件，战斗怎么同步？

**答：** 目前只能由玩法服务按时间窗口算（例如 WAO recipe 的 startup/hitTime），或者后续给 `ModelAnimation` 加事件轨道，在采样时发 `CommandBus`。没有事件时，动画和战斗的耦合会更依赖固定时间参数。

### H7 ★★ 没有 root motion，角色位移怎么处理？

**答：** 由控制器/玩法服务写 Transform；动画只做原地循环。要减少滑步，需要让移动速度和动画步幅匹配，或做 root motion 提取/foot IK。

### H8 ★★ 没有状态机，复杂角色怎么办？

**答：** 需要补 AnimatorController：状态、参数、transition、exit time、interrupt、blend tree；否则 Idle/Walk/Run/Jump/Attack 的切换只能散落在玩法代码里，难维护。当前只有 current/next clip。

### H9 ★★ 3D 角色只是测试场景，怎么证明能进玩法？

**答：** 做一条最小竖切：3D 角色 + 控制器 + 相机 + 一个攻击动作 + 一个 hitbox + 一个敌人 + UI + 打包运行。当前只有 `SkeletalTest/RobotTest/SambaTest`，没有玩法闭环；面试时把它讲成“管线验证”，不要讲成“3D 玩法已完成”。

### H10 ★★ 现场让你加“按 1 切 Idle、按 2 切 Walk”，你怎么改？

**答：** 先给 `Animator3DComponent` 加 `PlayClip(name)`/`CrossFadeTo(name, duration)`，设置 `NextClipIndex`/`NextTime`/`FadeElapsed`；在输入系统或一个临时 System 里按键调用；FBX 预计算 clip 先做硬切，glTF TRS clip 走现有 `BlendBonePose`；最后用 Fox/Robot 场景验证。注意编辑器 Play 副本要先把 `Animator3DComponent` 加进 `SceneComponentGroup`，否则运行时副本没有动画器。

## 2.2 项目总览和分层

### Q1：你这个引擎整体怎么分层？

一句话版：  
我把 Wheatear 按“第三方与平台层 -> 核心平台层 -> Scene/ECS 层 -> 引擎服务层 -> 游戏运行服务层 -> 玩法层 -> 应用层”来分。

展开版：  
底层先解决窗口、上下文、平台差异和第三方库；中间层负责主循环、事件、日志和时间；Scene/ECS 层负责世界组织和序列化；引擎服务层提供渲染、输入、物理、音频、UI 等通用能力；游戏运行服务层负责 CommandBus、SceneTransition、GameProgress、ActionSystem、EventScript 这些跨玩法的运行逻辑；玩法层负责 VN、战棋、街机、回合制、Progression 这些具体游戏玩法；应用层负责 Editor 和 Sandbox。

面试追问可以这样接：  
我不是为了“看起来规整”而分层，而是为了让简单 2D 游戏的内容、流程和工具都能各归其位。这样做的代价是文件多一点，但后期维护会清楚很多。

### Q2：为什么不直接把功能都写在场景脚本里？

一句话版：  
因为那样会把玩法、流程、UI、存档、编辑器全部缠在一起，后面很难扩展。

展开版：  
场景脚本适合做局部行为，不适合承载整套游戏循环。Wheatear 现在把“谁在决定流程”“谁在持有状态”“谁在负责展示”拆开了：场景只负责挂组件，服务层负责推进流程，命令和数据负责串起来。这样战斗、剧情、进度、设置都能共用同一套组织方式。

### Q3：你这个项目主要面向什么类型的游戏？

一句话版：  
主要面向简单 2D 游戏，尤其是剧情、战斗、成长和工具链比较完整的那一类。

展开版：  
我不是想做一个商业级全能引擎，而是想把我自己喜欢的 2D 平面游戏，做成一套既能落地 Demo、又能讲清楚架构的项目。它的重点是：2D 渲染、剧情系统、战斗系统、成长系统、编辑器和独立运行端。3D 预览能力是补充验证，不是主线。

## 2.3 核心平台和主循环

### Q4：`main()`、`CreateApplication()`、`Application::Run()` 这条链路怎么讲？

一句话版：  
`main()` 负责启动，`CreateApplication()` 负责创建游戏自己的 Application，`Application::Run()` 负责主循环。

展开版：  
入口先走 `main()`，再由具体工程实现 `CreateApplication()` 返回自己的 `Application` 子类，例如 Editor 或 Sandbox。`Application::Run()` 才是每帧入口，里面会做窗口消息、层更新、渲染提交和退出判断。这样一来，真正的项目差异就不用写死在主函数里，而是由子类决定。

### Q5：为什么要有 `LayerStack` 和 `Overlay`？

一句话版：  
因为很多东西都需要挂在主循环里，但优先级和显示层次不一样。

展开版：  
`Layer` 适合放编辑器层、运行层、调试层、玩法层等逻辑模块；`Overlay` 更像叠在最上面的工具层，比如调试 UI、性能信息、窗口覆盖面板。把两者分开后，更新顺序、输入优先级和渲染顺序都会更清楚。

### Q6：为什么事件要 Queue，而不是窗口回调里直接 Dispatch？

一句话版：  
因为直接在回调里分发很容易把窗口线程、逻辑线程和当前帧状态搅乱。

展开版：  
队列能把“消息来了”与“这一帧什么时候处理”分开。这样层和系统能在固定的更新点消费事件，不会在回调里直接改一半状态。你在面试里可以直接说：队列让系统更新更稳定，也更容易控制优先级和消费边界。

### Q7：`Log` 和 `Timestep` 为什么也算主循环的一部分？

一句话版：  
因为它们决定了调试和帧推进的基本感知。

展开版：  
`Log` 负责把运行状态、错误和调试信息固定下来；`Timestep` 负责把“这一帧过了多久”标准化成所有系统都能用的时间尺度。主循环没有这两样，调试会很痛苦，帧间逻辑也很容易乱。

## 2.4 Scene 和 ECS

### Q8：`Scene`、`Entity`、`Component`、`System` 怎么区分？

一句话版：  
`Scene` 是世界容器，`Entity` 是身份，`Component` 是数据，`System` 是逻辑。

展开版：  
`Scene` 负责承载整个世界和其生命周期；`Entity` 只是一个可查询、可组合的实体标识；`Component` 负责存状态，不负责组织流程；`System` 负责按规则更新一批组件。这个分法的好处是：你可以很容易地把 UI、渲染、战斗、剧情都挂在同一套世界组织上。

### Q9：为什么 `System` 不做成全局单例，而是挂在场景里？

一句话版：  
因为很多系统的生命周期和场景强相关。

展开版：  
战斗场景、编辑器场景、剧情场景的系统不是同一批，也不应该共享同一份运行态。把系统挂在场景里，能让启动、暂停、销毁、切换都更自然。这样在做 Play Mode Copy、场景切换和读档时，也更容易控制哪些状态应该复制、哪些不该复制。

### Q10：`Play Mode Copy`、`Prefab`、`SceneSerializer` 三者是什么关系？

一句话版：  
`SceneSerializer` 负责存取，`Prefab` 负责复用，`Play Mode Copy` 负责编辑态和运行态的隔离。

展开版：  
`SceneSerializer` 把场景写成 YAML；`Prefab` 更像可复用的实体模板；`Play Mode Copy` 则是在编辑器里启动运行时副本，避免运行时状态直接污染编辑态。这样你在编辑器里点 Play，实际跑的是一份可独立销毁的副本。

### Q11：为什么运行时指针、`RuntimeBody`、`RuntimeFixture` 不能直接进序列化？

一句话版：  
因为这些东西是运行时资源，不是资产数据。

展开版：  
序列化应该保存可重建的定义，而不是某一帧里具体的内存句柄。像物理体、碰撞 fixture、运行时指针这类对象，重新加载场景时会重新创建。如果把它们直接写进文件，读出来也没有意义，反而会破坏跨运行时的稳定性。

## 2.5 渲染和资源

### Q12：你的 2D 渲染链路怎么讲？

一句话版：  
大致是 Sprite / Atlas / SpriteSheet 进来，Renderer2D 批处理，再由 UI/HUD 和文本系统一起输出。

展开版：  
我把 2D 渲染看成一条链：资源先变成纹理或图集，再由渲染服务统一提交，最后在场景里表现成角色、背景、UI、HUD、特效和文本。重点不是某个函数有多神，而是整条链从资源到屏幕是清楚的。

### Q13：为什么要有批渲染、纹理槽和 `Flush()`？

一句话版：  
因为 2D 场景里同类图元很多，批量提交能少很多 GPU 状态切换。

展开版：  
批渲染的核心就是尽量把同类绘制合并起来。纹理槽能减少频繁换贴图，`Flush()` 则是在批次满了或状态变化时把当前批提交出去。面试里可以直接说：这不是炫技，是为了让 2D 游戏的渲染更稳、更省调用。

### Q14：`Sprite`、`Atlas`、`SpriteSheet`、`UI/HUD` 这些东西怎么区分？

一句话版：  
Sprite 是单个图元，Atlas 是大图集，SpriteSheet 是按帧组织的序列图，UI/HUD 是它们的使用场景。

展开版：  
Sprite 是最小绘制单元；Atlas 是把很多小图打包进一张图；SpriteSheet 通常强调动画帧序列；UI/HUD 则是这些资源在界面层的实际应用。你在答题时要说清楚：资源类型和使用场景不是一回事。

### Q15：3D 预览为什么会放进一个以 2D 为主的引擎里？

一句话版：  
因为它是验证渲染管线和材质系统的补充能力，不是主业务。

展开版：  
3D 预览能帮助我把 Mesh、Material、Shadow、IBL、SSAO 这些渲染概念在同一套渲染抽象里跑通，方便验证底层 API 和 shader 链路。但它不是这个项目的主卖点。面试时要主动强调这一点，避免别人误以为你的引擎主打 3D 商业渲染。

## 2.6 输入、物理和音频

### Q16：为什么要做输入抽象，而不是直接读 `KeyCode`？

一句话版：  
因为玩法想表达的是“动作”，不是“键盘码”。

展开版：  
输入抽象能把按键、手柄、触屏统一成逻辑动作，例如 `move.left`、`arcade.attack`、`vn.advance`。这样玩法、编辑器和 UI 都不用关心具体键位，而且以后重映射也不会改一堆业务代码。

### Q17：物理系统里为什么要讲 `fixture`、`step()` 这些概念？

一句话版：  
因为它们是物理模拟的基础语义。

展开版：  
`fixture` 不是“某个库专有名词”，它本质上是把几何形状、摩擦、密度、过滤和 sensor 语义挂到刚体上的那层结构。`step()` 则是一帧物理推进的核心：碰撞检测、积分、约束求解都在这里完成。面试时如果被问到物理，你要讲的是“一帧里物理是怎么跑的”，而不是只背 API 名字。

### Q18：音频系统为什么也要单独抽一层？

一句话版：  
因为它和渲染、输入一样，是玩法反复调用的通用能力。

展开版：  
音频系统通常要解决播放、停止、混音、状态管理和 SFX/BGM 的区分。把它独立成服务以后，VN、战斗、街机、结果页都能统一调它，不会每个玩法自己写一套音频逻辑。

## 2.7 运行时服务：CommandBus、EventScript、ActionSystem、SceneTransition、GameProgress

### Q19：为什么要有 `CommandBus`？

一句话版：  
因为很多系统之间不应该直接互相调用，而应该通过命令说话。

展开版：  
`CommandBus` 的作用是把“谁发起动作”和“谁执行动作”分开。这样 UI、脚本、战斗、剧情、进度都能发命令，而不是互相硬连。它的价值就是让跨系统流程更统一，也更容易调试和追踪。

### Q20：`EventScript` 和 `VN` 有什么区别？

一句话版：  
`EventScript` 更像流程编排器，`VN` 更像剧情玩法本体。

展开版：  
`EventScript` 更偏“这一段流程先做什么、再做什么、然后跳哪”；`VN` 更偏“对白、选择、立绘、音乐、分支怎么演”。前者负责导演级编排，后者负责剧情执行。

### Q21：`ActionSystem`、`ActionIntent`、`ActionRecipe`、`ActionResolver`、`EffectLedger` 怎么串起来？

一句话版：  
`ActionIntent` 是意图，`ActionRecipe` 是配方，`ActionResolver` 是解释器，`EffectLedger` 是结果账本。

展开版：  
玩法先发出动作意图，意图里写谁对谁做什么；动作配方描述这个动作本身的参数和效果；解析器把配方变成具体执行；账本负责记录结果，方便调试和回放。你在面试里一定要把这四个词的边界说清楚，这是很容易被追问的点。

### Q22：`SceneTransition` 为什么要记场景路径、前后场景和保存上下文？

一句话版：  
因为读档、切场景和返回页都需要知道“原来在哪里、现在要去哪”。

展开版：  
如果不记录场景上下文，存档后你就不知道该回到哪个场景；如果把过渡页当成目标场景，读档和返回就会乱掉。`SceneTransition` 的职责就是把进入、退出、重进和加载这些流程统一起来。

### Q23：`GameProgress` 为什么不是简单的存档类？

一句话版：  
因为它是全局进度中枢，不只是写文件。

展开版：  
它保存的不只是槽位数据，还包括章节、旗标、材料、装备、技能、地城、关系、结果页数据、当前场景上下文等。它还会生成保存和加载命令，和 VN runtime、场景切换服务联动。也就是说，它管的是“这盘游戏到底进展到哪了”。

### Q24：为什么设置不放进进度槽？

一句话版：  
因为设置属于运行时偏好，不属于长期进度。

展开版：  
音量、文字速度、全屏、震屏这些东西，不应该因为你读了一个存档就被覆盖。Wheatear 把它们单独放到 `UserSettings` 和设置命令服务里，避免进度槽和偏好混在一起。

## 2.8 玩法层：VN、SideCombat、TurnCombat、TacticalCombat、Arcade、Progression

### Q25：`VN` 模块你怎么讲？

一句话版：  
`VN` 不是对话框 UI，而是一套可运行的剧情玩法。

展开版：  
它把脚本、运行时、场景绑定、输入、存读档和编辑器工具串成一条链。脚本负责写什么，运行时负责怎么跑，系统负责接入主循环，编辑器负责能不能改得动。面试时如果被问到剧情系统，直接抓“脚本 -> 运行时 -> 系统 -> UI”的链路讲。

### Q26：`SideCombat` 和 WAO 是什么关系？

一句话版：  
SideCombat 是玩法壳，WAO 是它底层动作表达和结算的公共语言。

展开版：  
SideCombat 会把玩家输入、AI 行为和剧情事件统一成动作意图，再借助 WAO 的动作配方、解析器、状态和结果账本去执行。这样做的好处是，战斗逻辑不会完全写死在玩法里，而是能和其他玩法共用动作语言。

### Q27：`TurnCombat` 最适合怎么讲？

一句话版：  
它是把回合制战斗拆成流程、命令、动作、技能、目标、UI 和视觉七层的样板。

展开版：  
战斗场景里先选单位，再选命令，再选技能，再选目标，接着进入演出和结算，最后交给敌方回合或胜负跳转。`TurnCombat` 最适合拿来讲“玩法层不是一个大函数，而是一组有职责边界的服务”。

### Q28：`TacticalCombat` 适合怎么讲？

一句话版：  
它是把棋盘、单位、命令、技能、AI、UI 和调参串起来的战棋执行系统。

展开版：  
这个模块重点在格子、范围、目标规则、回合阶段和调参。技能从 WAO 动作表生成，AI 按规则走格子和出手，UI 只负责发命令和显示结果。你要让面试官听出来：这不是一堆按钮，是一套状态机。

### Q29：`Arcade` 最适合怎么讲？

一句话版：  
它是一套把输入、动作、子弹、Boss、HUD 和过场统一起来的街机动作系统。

展开版：  
`Arcade` 的重点是实时反馈。玩家输入先进入控制层，再映射到动作配方，动作配方通过 resolver 和 signal 生成投射物；Boss 的入场、跳跃、射击和结果过场也都由独立服务驱动。这个模块很适合拿来讲“动作玩法是怎么被拆开”的。

### Q30：`Progression` 为什么不是菜单页？

一句话版：  
因为它是全局进度中枢，负责长期成长和页面分发。

展开版：  
它把副本结算、结果页、技能树、装备页、存读档页、设置页和编辑器内容都串起来了。它不是单独一个菜单，而是整盘游戏“走到哪、能做什么、下一步去哪”的统一出口。

## 2.9 应用层：Editor 和 Sandbox

### Q31：为什么要分 `Editor` 和 `Sandbox`？

一句话版：  
因为编辑内容和运行游戏是两种不同的工作流。

展开版：  
Editor 偏工具，负责改资源、改场景、改脚本、改调参；Sandbox 偏运行，负责把这些内容加载出来真正跑一遍。把两者分开后，工具链和游戏链不会互相污染，也更符合实际开发。

### Q32：编辑器最值得讲什么？

一句话版：  
最值得讲的是内容编辑器和运行预览怎么联动。

展开版：  
像 `ProgressionContentEditorPanel`、`TacticalCombatTuningEditorPanel`、`ArcadeCombatTuningEditorPanel` 这类窗口，最能体现你的项目不是只写逻辑，而是已经有了能维护内容的工具链。面试时如果时间不够，就优先讲“编辑器改了什么，运行时怎么热更新”。

### Q33：打包发布这块你怎么讲？

一句话版：  
打包不是简单拷文件，而是把内容、配置、启动场景和可写数据一起组织成产物。

展开版：  
这个部分最重要的是产物结构和启动链路。比如 `content.wtpack`、`player.config`、启动场景、预检扫描、依赖报告和 loose runtime data 的关系。面试时要突出一点：我不是只会点一个 Build 按钮，我知道包体里每一层是什么。

## 2.10 和别的引擎怎么对照

### Q34：Unity、UE、Godot 跟你的引擎怎么对应？

一句话版：  
概念上能对应，但我把职责拆得更显式。

展开版：  
比如 Unity/UE 里的场景、组件、存档、设置、UI、DataTable/DataAsset、GameInstance、UMG 这些概念，在 Wheatear 里都能找到对应，但名字不一定一样。我的做法是把内容和状态、运行和编辑、设置和进度分得更清楚。这样更适合讲架构，也更适合简单 2D 游戏。

### Q35：你为什么不直接用 Unity 或 UE？

一句话版：  
因为我想做的是一套能完全理解、能完整讲清楚、并且围绕我自己的 2D 目标收敛的引擎实践。

展开版：  
不是为了替代成熟引擎，而是为了把我真正关心的东西做透：2D 渲染、剧情、战斗、成长、编辑器、调参、存档和命令驱动流程。自研的价值在于，我知道每一层是怎么连起来的。

# 第四部分：项目速答卡

> 由原《03_引擎架构/面试准备_高频问答》合并而来，适合面试前快速过一遍。

> 用途：针对 Wheatear 引擎项目，面试官可能追问的底层知识与设计动机。
> 每个问题给出「怎么答」要点与代码位置，答的时候先讲设计动机，再讲实现细节。

## 一、渲染

### Q1：2D 渲染是怎么合批的？为什么不用逐物体 draw call？

**怎么答：**

- 自研 `Renderer2D`：单一大 VBO（`RenderBatch`），每帧把所有 quad/circle/line/text 顶点攒进批，`EndScene` 时一次提交。
- 顶点带 `TexIndex`（纹理槽）+ `EntityID`（用于编辑器 picking），纹理切换通过 `GetOrAllocTextureSlot` 分配槽位，槽满或纹理数超上限时 `Flush`。
- 相同纹理的物体自动合批；同帧超过 32 种纹理才强制刷批（配合全局纹理缓存 dedup，同一路径共享同一个 GL 纹理，所以同图多实体不会碎批）。
- 文本（SDF）、UI 走同一套批渲染。

**代码位置：** `Wheatear/src/Wheatear/Renderer/Renderer2D.cpp`、`RenderBatch.h`。

### Q2：纹理缓存为什么存在？怎么管理生命周期？

**怎么答：**

- `Texture2D::Create(path)` 有全局 LRU 缓存：同一路径返回同一对象（GPU 纹理只建一份，也是合批的前提）。
- 512MB VRAM 预算，超出后淘汰「无人引用（use_count==1）」的最久未用项，防止编辑器长会话累积纹理。
- 缓存持有 `shared_ptr`，业务侧也持引用，卸载是引用计数自然完成。

**代码位置：** `Wheatear/src/Wheatear/Renderer/Texture.cpp`。

### Q3：SpriteSheet 的 UV 坐标系约定？

**怎么答：**

- 引擎纹理加载 `stbi_set_flip_vertically_on_load(1)`，因此 GL 纹理 v=0 是图像底部；组件/动画链路统一使用该约定（旧实现曾是 top-left 约定导致渲染颠倒，已统一修复）。
- `.wtsheet` 格子索引行主序（row 0 = 图像顶部），`ResolveCell` 输出内容框的 GL UV；ContentBrowser 缩略图按 ImGui 约定再翻转一次。
- 面试加分：讲「统一约定 + 在边界翻转」而不是到处改符号。

### Q4：PPU（Pixels Per Unit）解决了什么问题？

**怎么答：**

- 传统 quad 是 1×1×scale，非方形纹理会被拉伸；动画帧内容尺寸变化（站立→躺下）时更明显。
- `PixelsPerUnit > 0` 时渲染尺寸 = UV 覆盖的像素数 ÷ PPU，quad 保持真实宽高比；动画播放时每帧尺寸自动跟随内容。
- 同一 PPU 也是碰撞盒像素→世界单位的换算基准，渲染与物理共用一套尺度。

## 二、Scene / ECS

### Q5：为什么用 entt？组件系统怎么组织的？

**怎么答：**

- entt 是 header-only 的 ECS：组件是 POD 结构体，存储是 SoA 的 sparse set，遍历快、缓存友好。
- 主题化组件头文件（Core/Physics2D/Rendering/UI/Animation...）而非单一大头，减少 include 面。
- 场景序列化用模板特化 `ComponentSerializer<T>`，YAML 键名与组件一一对应，新增组件只需加一个特化。

**代码位置：** `Wheatear/src/Wheatear/Scene/`、`Scene/Serialization/`。

### Q6：系统（System）是怎么组织的？编辑器和运行时共用吗？

**怎么答：**

- 每个系统实现 `ISystem`（OnRuntimeStart/OnUpdateRuntime/OnUpdateEditor/OnEntityCreated...），场景在 `ConfigureRuntimeSystems` / `ConfigureEditorSystems` 注册。
- 编辑器里跑的是「编辑系统集」（SpriteSheet 解析、动画预览帧同步、编辑器相机等），进入 Play 切换为运行时系统集——同一份场景数据，两套行为。
- 好处：编辑器所见即所得（预览帧、碰撞框跟随都在编辑态生效）。

### Q7：运行时和编辑器之间怎么切换状态？

**怎么答：**

- `SceneState`（Edit/Play）由 EditorLayer 管理，切换时序列化场景为临时内存副本（或直接深拷贝场景），运行时改动不影响编辑场景。
- 实体激活（activate/deactivate）、延迟操作（拖放资产落地）走队列，避免渲染循环中修改 ECS。

## 三、事件脚本 / CommandBus

### Q8：.wts 事件脚本是什么？为什么要做？

**怎么答：**

- 流程不硬编码：`CommandBus` 统一命令入口，`.wts` 用**自定义文本脚本格式**描述「什么时候做什么」（场景切换、剧情节点、UI、存读档、战斗结算），支持 `event` 块、`wait` 等待、`if` 条件。
- 引擎只提供命令原语，玩法流程是数据——策划/编辑器可直接改文本资源，不用重编。
- 编辑器有事件脚本图面板（可视化组织），运行时 500ms 热重载，改脚本即生效。

**代码位置：** `Wheatear/src/Wheatear/Runtime/CommandBus.h`、`assets/events/*.wts`。

### Q9：动画事件和 .wts 的关系？

**怎么答：**

- 动画事件在指定时间发 `Command`（带 `{entity}/{clip}/{event}` 占位符），动画系统不关心命令含义。
- 命令落到 CommandBus 后被各模块消费（伤害结算、音效、镜头、切场景）——动画系统与玩法解耦。

## 四、WAO 动作系统

### Q10：WAO 是什么？和 GAS 有什么区别？

**怎么答：**

- WAO（Wheatear Action Orchestration）是动作编排层：`ActionIntent（意图）-> ActionRecipe（配方）-> RuleResolver（规则）-> EffectBundle（效果束）-> EffectLedger（结算账本）-> SignalRouter（信号路由）`。
- 输入、AI、事件脚本都能产生 Intent，进入同一套动作入口；技能、冷却、资源、效果、表现分层。
- 相比 GAS：不做网络/预测/属性集那一套，聚焦单机 2D 多玩法复用；配 `Action Debugger` 编辑器追踪动作结果。

**代码位置：** `Wheatear/src/Wheatear/Gameplay/Action/`。

## 五、资产系统

### Q11：.wtsheet 为什么设计成「引用」而不是「烘焙」？

**怎么答：**

- 组件/动画帧存 (sheet 路径 + 格子号)，运行时 `ResolveCell` 统一解析，sheet 文件 mtime 变化即热重载——改网格/裁切，所有引用方下一帧更新，无需重新导出资源。
- 同一份网格定义被实体、动画、碰撞复用，不会出现「改一次图集要重导 N 份」。
- 打包：`ResolveRuntimeData` 兼容 loose 文件与 `content.wtpack`，同一套代码两条路径。

**代码位置：** `Wheatear/src/Wheatear/Assets/SpriteSheetAsset.cpp`、`AssetPath.cpp`。

### Q12：热重载怎么做的？性能考虑？

**怎么答：**

- 轮询 `last_write_time`，与缓存记录比较，变了才重读（不是每帧解析文件）。
- 探测频率按场景分级：VN/战斗脚本 500ms；sheet 解析在热路径上加 250ms 闸，避免大量实体每帧做文件系统调用。
- 编辑器资产浏览器目录扫描同样做了 (目录, 搜索词) 键控缓存 + 250ms 闸。

## 六、输入

### Q13：输入系统分几层？

**怎么答：**

- 底层：GLFW 回调 → 事件分发（KeyEvent/MouseEvent）。
- 中间：`Input` 静态查询（IsKeyPressed 等，带边沿检测状态机）。
- 上层：`InputBindingService` 动作绑定（action → 键/鼠标/组合），支持重映射 UI（Input Bindings 面板）、命令注入（AI/脚本模拟输入）、EndFrame 状态同步。

**代码位置：** `Wheatear/src/Wheatear/Input/`。

## 七、物理

### Q14：Box2D 怎么和 ECS 集成？动画驱动的碰撞怎么实现？

**怎么答：**

- 运行时会话创建 b2World，`OnRuntimeStart` 从组件数据建 body/fixture（组件存 RuntimeBody/RuntimeFixture 指针）。
- 每帧 Step 后 body 位置写回 Transform（单向：body → Transform）；fixture 在创建时拷贝 shape，之后组件数据变化不会自动同步——只有 `FollowAnimation` 的碰撞（`SyncAnimationDrivenColliders`）每帧比对组件数据与 fixture shape，**变化才重建**。
- `BoxCollider2DComponent.FollowAnimation`：精灵系统/动画系统每帧按格子碰撞框（像素）÷ PPU 写 Offset/Size，物理系统检测变化重建 fixture——人倒下碰撞盒跟着变。

**代码位置：** `Wheatear/src/Wheatear/Systems/PhysicsSystem.cpp`、`SpriteSheetSystem.cpp`。

## 八、编辑器架构

### Q15：编辑器为什么是面板体系？浮动窗口怎么做？

**怎么答：**

- 全部 ImGui：SceneHierarchy/Inspector/ContentBrowser/AnimationEditor 等面板，EditorLayer 统一调度。
- 浮动窗口通过 `EditorFloatingWindow`（可停靠/分离），面板内容与窗口框架解耦，同一面板可浮动可嵌入。
- ContentBrowser 支持 UE 式抽屉模式（底部折叠栏）。

### Q16：编辑器「离屏缩略图」怎么实现的？

**怎么答：**

- 非图片资产（场景/Prefab/UI 模板/Mesh/动画）排队进 `RenderThumbnail`：建临时场景 → 离屏 FBO（128×128）→ `ReadPixels` → 上传为缩略图纹理 → 缓存。
- 每帧只渲染队列中的一个，避免卡顿；结果缓存到 `m_ThumbnailCache`。

## 九、工程实践

### Q17：编译速度怎么优化的？

**怎么答：**

- 预编译头：glm/entt/imgui 等稳定大头进 PCH（引擎与编辑器各一份），单文件增量编译约 3 秒。
- MSBuild 并行编译（/m）。
- include 治理：主题化组件头、模块内聚、避免模块间交叉 include。

### Q18：性能上做过哪些实测优化？

**怎么答：**

- 纹理 LRU 缓存（dedup，合批前提 + VRAM 预算）。
- 文件系统探测降频（sheet 解析 250ms 闸、目录扫描缓存）。
- 音频解码缓存；热路径避免重复分配（如 animator 绑定缓存避免每帧重建属性轨道 writer）。
- 上述都是「先定位热路径再优化」，不是盲目微优化。

## 十、可以主动展示的亮点

1. **SpriteSheet 引用式资产闭环**：资产化 → 热更新 → trim → PPU → 碰撞联动 → 编辑器拖放，一条链。
2. **编辑器/运行时同一场景两套系统**：编辑态预览与运行时行为一致。
3. **数据驱动流程**：.wts + CommandBus + 数据表，玩法逻辑可编辑。
4. **WAO 动作编排**：多玩法复用的动作语义层。
5. **工程习惯**：PCH/增量编译、主题化头文件、模板序列化器、提交粒度清晰。
