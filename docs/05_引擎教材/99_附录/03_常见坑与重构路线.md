# 附录 03：常见坑与重构路线

> 本附录所属层级：**附录**
>
> 本附录目标：把 Wheatear 这套架构里最容易踩坑、最值得提前警惕、也最适合后续重构的地方收成一份工程复盘。
>
> 先提醒一句：这不是“挑毛病”文档。  
> 它更像是把经验摊开，让你知道：
> - 哪些地方已经做对了
> - 哪些地方以后最容易乱
> - 真要重构时应该从哪里下手
>
> 这份附录最好和前面正文一起看，因为很多坑并不是“代码坏了”，而是**边界没说清楚**。

## 3.1 这份附录的读法

你可以把常见坑分成四类：

1. **状态边界**：内容、进度、设置、运行时状态有没有混在一起。
2. **流程边界**：命令、事件、场景切换、保存读取有没有互相串线。
3. **表现边界**：UI、渲染、编辑器是不是直接改了业务状态。
4. **扩展边界**：模块越来越多时，职责会不会膨胀。

如果你后面要重构，最有价值的不是一下子改所有东西，而是先把这四类边界理顺。

## 3.2 最常见的坑

### 3.2.1 把内容和状态混在一起

#### 表现

- YAML 内容表里夹运行时字段
- 存档对象里放太多静态定义
- 编辑器保存一次，运行态也被一起污染

#### 为什么会出问题

因为内容、进度、设置的生命周期不同。

- 内容是项目资产
- 进度是玩家局势
- 设置是运行时偏好

混在一起以后，改配置会影响存档，读档会覆盖设置，运行时还可能把编辑态一起写坏。

#### 现在的做法

Wheatear 现在把它们分成了三块：

- `ProgressionContent`
- `GameProgress`
- `UserSettings`

#### 后续建议

- 保持内容文件只存定义，不存运行时结果
- 保持存档只存玩家进度，不存编辑器临时态
- 保持设置独立于进度槽

### 3.2.2 让 UI 直接改业务状态

#### 表现

- 按钮回调里直接改数值
- 面板里直接写全局变量
- 选中状态和业务状态缠在一起

#### 为什么会出问题

因为 UI 会变得特别脆，面板一多，所有修改逻辑都会散掉。

#### 现在的做法

Wheatear 倾向于：

- UI 只发命令
- `CommandBus` 收消息
- 具体系统去改状态

#### 后续建议

- 继续坚持“UI -> 命令 -> 服务 -> 状态”的链路
- 如果以后新增面板，优先复用命令命名规则

### 3.2.3 命令边界不清

#### 表现

- `scene:`、`event:`、`progression:`、`vn:`、`tactic:`、`arcade:` 混着用
- 一个模块既发命令又解释命令
- 命令前缀不统一，后期很难排查

#### 为什么会出问题

命令一旦变成“随手字符串”，就很容易失控。

#### 现在的做法

Wheatear 里每个大玩法都尽量有自己的命令风格，并由对应服务消费：

- VN 有自己的剧情命令
- Progression 有自己的进度命令
- TacticalCombat 用 `tactic:`
- Arcade 用动作和信号接子弹生成

#### 后续建议

- 给每个大模块保留自己的命令前缀
- 命令尽量短、稳定、可读
- 不要让 UI 直接拼出一堆语义过重的字符串

### 3.2.4 保存、切场景、返回页混成一团

#### 表现

- 读档不知道回哪个场景
- `SaveLoad` 页关闭后回错地方
- 结果页、剧情页、据点页互相跳乱

#### 为什么会出问题

因为“当前在哪”不是一个可省略的细节。

#### 现在的做法

Wheatear 里已经很明确地做了：

- `SceneTransition` 负责场景迁移
- `GameProgress` 保存场景上下文
- `BuildLoadGameCommand()` 带场景路径

#### 后续建议

- 保存槽一定要记场景上下文
- 返回逻辑不要只靠“上一个按钮是谁”
- 过渡页要当作过渡页，不要当目标场景

### 3.2.5 运行时对象直接序列化

#### 表现

- 把物理指针、运行时句柄、临时对象直接写进文件
- 读档后发现对象已经失效

#### 为什么会出问题

因为运行时对象不是持久化定义。

#### 现在的做法

Wheatear 已经把很多运行时对象看成“重建对象”：

- 物理体
- fixture
- 临时运行句柄
- 部分视觉临时状态

#### 后续建议

- 序列化保存“可重建的数据”
- 不保存“当前内存地址”
- 运行时缓存要么重建，要么明确清空

### 3.2.6 绑定名过多但不统一

#### 表现

- 同一个页面里有很多实体名
- 改一个名字会连带改一堆脚本
- 排查 UI 时很费劲

#### 为什么会出问题

因为绑定名就是隐性的 API。

#### 现在的做法

Wheatear 用 `SystemBindings` 和一批命名约定来缓解这个问题，但依然需要强约束。

#### 后续建议

- 绑定名尽量统一前缀
- 页面级控件尽量集中命名
- 重要绑定点要有文档

### 3.2.7 服务越来越多

#### 表现

- 每个页面、每个玩法、每个调参都拆成一个服务
- 文件很多，初学者容易迷路

#### 为什么会出问题

因为职责拆细以后，查起来会绕一点。

#### 这其实不是坏事

对这类项目来说，服务多不一定是问题，**边界不清**才是问题。

#### 后续建议

- 保持服务单一职责
- 给每个服务写清楚“只负责什么”
- 文档里固定一条主链路，让人有入口

### 3.2.8 热重载和缓存失效

#### 表现

- 改了 YAML 但运行时没立刻生效
- 资源缓存和文件变更不同步

#### 为什么会出问题

因为热重载一旦做起来，缓存策略就必须明确。

#### 现在的做法

Wheatear 的调参服务已经在做：

- 文件时间检查
- 缓存刷新
- 编辑器保存后 Reload

#### 后续建议

- 把热重载和缓存策略写进文档
- 明确哪些文件支持热更，哪些不支持
- 编辑器保存后最好立刻给出状态反馈

## 3.3 现在最值得重构的不是功能，而是边界

### 3.3.1 第一步：固定“状态归属”

先把三类东西再钉死一次：

- 内容资产
- 运行时进度
- 用户设置

只要这三类边界稳了，后面重构就不会乱。

### 3.3.2 第二步：统一命令命名和消费方式

建议保持：

- `scene:`
- `event:`
- `progression:`
- `vn:`
- `tactic:`
- `arcade:`

这类前缀的统一风格。

这样后面排查日志、回放流程、做文档都更轻松。

### 3.3.3 第三步：继续抽公共页面模式

你现在已经有很多 PageService 了。

下一步如果要重构，优先考虑的是：

- 有没有重复的“同步状态 -> 更新文本 -> 设置按钮命令”
- 有没有重复的“分页 / 选中项 / 详情面板”
- 有没有重复的“保存 / 读回 / 状态条”

这些地方适合抽公共模式，但不要一下子抽太大。

### 3.3.4 第四步：把编辑器工具链统一成同一种文档体验

现在你已经有很多调参和内容编辑器了：

- Progression
- TacticalCombat
- ArcadeCombat
- 资源编辑器
- 场景 / Inspector / 预览

下一步比较值得做的是把它们的文档状态、保存状态、错误提示和热重载反馈统一一点。

## 3.4 不建议现在就重构的地方

### 3.4.1 不要把所有服务合回一个大管理器

这样会重新回到“一个巨型对象负责一切”的老路。

### 3.4.2 不要为了少文件而合并边界

文件多不等于设计差。
很多时候文件多只是因为你把职责拆对了。

### 3.4.3 不要为了泛化而过早抽象

有些页面逻辑现在看起来像重复，但它们的状态语义其实不同。  
如果过早抽一个大基类，反而会让后续修改变得更绕。

### 3.4.4 不要把“能跑”当成“边界已清楚”

很多坑在小 Demo 阶段不会立刻爆，但在：

- 多玩法共存
- 编辑器维护
- 读档
- 热重载
- 面试讲解

这些场景下会暴露出来。

## 3.5 如果真要重构，建议怎么走

### 路线 A：保行为，先收边界

目标：

- 不改外部行为
- 先把状态归属、命令边界、保存边界写稳

适合场景：

- 你现在还在不断补文档和补功能
- 还不想让项目进入大面积改动

### 路线 B：抽共性页面模式

目标：

- 把多个 PageService 的共同结构提出来
- 但不强行合并语义不同的页面

适合场景：

- Progression 页面越来越多
- Editor 面板越来越多

### 路线 C：统一调参与编辑器文档模型

目标：

- 让 YAML、Manifest、结构化编辑器和热重载都走同一套体验

适合场景：

- 你后面还会继续增加战斗玩法和成长系统

### 路线 D：再考虑更大的体系化抽象

目标：

- 如果以后玩法数量更多，再考虑更通用的页面架构、战斗框架或内容系统

适合场景：

- 当前这套教材已经稳定
- 你开始考虑下一版引擎设计

## 3.6 面试时怎么把坑讲成亮点

如果面试官问“你项目里有什么不足”，你可以这样讲：

> 我觉得这套引擎现在最值得继续打磨的地方，不是功能本身，而是边界和文档化。  
> 比如内容和状态、进度和设置、命令和 UI、场景和过渡页这些边界，我已经在架构上做了拆分，但后面还可以继续把命令命名、页面模式和编辑器体验统一得更强。  
> 我不会为了少文件去合并职责，因为我更看重后期维护和讲解清晰度。下一步如果要重构，我会先固定边界，再抽公共模式，最后再考虑更大的统一抽象。

这样讲的好处是：

- 不会显得你回避问题
- 也不会显得你把项目说得太满
- 更像一个真的做过工程的人

## 3.7 小结

这一份附录最重要的意义是：

**提前知道哪里会乱，后面你就不容易乱。**

如果说正文是在讲“现在是什么”，那这份附录就在讲：

- 以后最可能坏在哪里
- 为什么会坏
- 坏了以后怎么修

这对一个还在持续成长的项目来说，比盲目重构更有价值。
