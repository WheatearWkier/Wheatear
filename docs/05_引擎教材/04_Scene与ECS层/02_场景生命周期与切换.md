# 第 4 编 02：场景生命周期与切换

> 本章所属层级：**Scene ECS 层**
>
> 本章目标：把 `Scene` 这层真正“跑起来”的全过程讲清楚。也就是：
> - `Scene` 什么时候创建，什么时候启动，什么时候停止，什么时候销毁
> - Edit / Runtime 两种模式到底差在哪
> - 场景切换为什么不是“点一下立刻换”
> - `SceneSystemRegistry` 怎么给运行时注入模块系统
> - 视口、保存策略、实体销毁队列这些状态为什么都得挂在 `Scene` 上
>
> 这一章先讲**场景怎么活**，下一章再讲**场景怎么存、怎么复制、怎么做 Prefab 和 Play Mode Copy**。

如果说上一章已经回答了“`Scene` 里有什么”，那这一章回答的是：

```text
这个世界什么时候开始工作？
什么时候停？
谁来切换它？
切换时哪些状态要保留，哪些状态要清掉？
```

Wheatear 的 `Scene` 不是一个静态容器，它更像一个有生命周期的运行世界：

```text
Scene
  ├─ entt::registry
  ├─ Systems
  ├─ Viewport / Camera state
  ├─ SavePolicy
  ├─ Destroy queue
  └─ Entity lookup caches
```

Scene 层最重要的一点是：  
**它自己既管数据，也管这些数据在什么阶段被谁更新。**

## 4.2.2 这一层在架构中的位置

```text
应用层
    Editor / Sandbox
        ↓
核心平台层
    Application / Window / EventBus / LayerStack
        ↓
引擎服务层
    Input / Renderer / UI / Audio / Physics
        ↓
Scene ECS 层
    Scene / Entity / Components / Systems / Serializer
        ↓
平台实现层
    GLFW / OpenGL / entt / Box2D / YAML
```

`Scene` 的位置很关键。  
它不是最底层，但它是“游戏世界”的承载点。

你可以把它理解成：

- 上面一层负责“谁在用它”
- 下面一层负责“它怎么被实现”
- `Scene` 自己负责“这个世界怎么被组织、怎么被启动、怎么被关闭”

这一层和前面几层的关系，可以压成一句话：

```text
Application 把窗口和事件带起来，
Scene 把游戏世界带起来，
Systems 再把这个世界每帧更新起来。
```

## 4.2.3 `Scene` 先天带着什么

先看 `Scene.h`，你会发现它不是只有一个 registry。

它还带着这些状态：

- `entt::registry m_Registry`
- `std::vector<Scope<ISystem>> m_Systems`
- `SceneExecutionMode m_ExecutionMode`
- `SavePolicy m_SavePolicy`
- `std::vector<SavePolicy> m_SavePolicyOverrides`
- `std::vector<entt::entity> m_DestroyQueue`
- 视口宽高和偏移
- 实体名 / UUID 查找缓存
- 系统 type-index 缓存

这说明 `Scene` 不只是“装实体”，它还管理：

```text
世界状态
系统集合
运行模式
销毁调度
保存约束
查找性能
```

### 4.2.3.1 构造和析构

`Scene` 构造时会注册组件生命周期，析构时会解绑。

这件事的意义很简单：

```text
Scene 一出生，就把组件生命周期挂到自己身上；
Scene 一死掉，就把这些绑定解除掉。
```

这样不会出现“组件回调还指向一个已经销毁的世界”的问题。

### 4.2.3.2 执行模式

`SceneExecutionMode` 只有三个值：

- `None`
- `Edit`
- `Runtime`

这三个值非常值得记住，因为后面几乎所有生命周期函数都围着它转。

你可以把它理解成：

- `None`：还没真正进入任何状态
- `Edit`：给编辑器用，强调可视化和可修改
- `Runtime`：给实际游戏用，强调玩法、输入、物理、音频、UI、渲染

### 4.2.3.3 保存策略

`SavePolicy` 是 `Scene` 自带的运行约束，而不是全局常量：

- `CanSave`
- `CanLoad`
- `SaveDirectory`
- `AutoLoadSlot`

这个设计很实用。  
因为有些场景可以保存，有些场景不允许读档；有些场景进来后要自动读某个槽位。

`GetEffectiveSavePolicy()` 还支持覆盖栈，这意味着 Scene 在某些时刻可以临时换一套规则，而不是把规则写死。

## 4.2.4 `Scene` 的启动与停止

这一节是本章最核心的部分。

### 4.2.4.1 `OnRuntimeStart()`

运行时启动时，Scene 会做这几件事：

1. 停掉旧系统
2. 清空保存策略覆盖
3. 配置运行时系统
4. 启动这些系统

可以压成一条链：

```text
OnRuntimeStart
  -> StopSystems
  -> ClearSavePolicyOverrides
  -> ConfigureRuntimeSystems
  -> StartSystems(Runtime)
```

它的语义很明确：

```text
“我要开始真正的游戏运行了，请把运行时需要的系统都挂上来。” 
```

### 4.2.4.2 `OnRuntimeStop()`

停止运行时会做反过来的事情：

```text
OnRuntimeStop
  -> StopSystems
  -> ClearSavePolicyOverrides
  -> Clear DestroyQueue
```

这里要注意两点：

- 运行时停掉后，销毁队列也要清空
- 运行时用过的系统也要清掉，避免下一次进入时残留状态

### 4.2.4.3 `OnEditorStart()`

编辑器模式启动时，Scene 不会挂那些完整的运行时系统，而是挂一套更偏编辑器预览的系统：

```text
OnEditorStart
  -> StopSystems
  -> ConfigureEditorSystems
  -> StartSystems(Edit)
```

这一点很重要。  
编辑器模式不是“运行时缩小版”，它有自己的一套目标：

- 能预览
- 能选中
- 能拖拽
- 能调参
- 不能让运行时资源乱跑

### 4.2.4.4 `OnEditorStop()`

编辑器停止时：

```text
OnEditorStop
  -> StopSystems
  -> Clear DestroyQueue
```

编辑器退出时，最重要的是把状态收干净。  
这能避免你从 Edit 切到 Play、再切回 Edit 时，系统状态互相污染。

### 4.2.4.5 `StartSystems()` 和 `StopSystems()`

`StartSystems()` 会根据当前模式调用：

- `OnEditorStart(this)`
- `OnRuntimeStart(this)`

`StopSystems()` 则反过来调用：

- `OnEditorStop(this)`
- `OnRuntimeStop(this)`

并且它是**逆序停止**。

这不是小细节，而是很典型的资源释放顺序：

```text
后注册的系统先停，
先注册的系统后停。
```

这样更容易保证依赖关系正确。

## 4.2.5 更新时 Scene 里发生什么

### 4.2.5.1 `OnUpdateRuntime()`

运行时每帧更新的顺序是：

1. 先处理销毁队列
2. 再更新系统
3. 物理系统放在一个稍微特殊的位置

为什么要先处理销毁队列？

因为有些实体已经被标记销毁了，不先清掉，后面的系统还可能碰到脏句柄。

为什么物理系统要特殊处理？

因为当前实现里，物理希望在动画 / 图集状态更新之后再 step，这样 `FollowAnimation` 一类的碰撞体数据是最新的。

这条更新逻辑可以概括成：

```text
OnUpdateRuntime
  -> FlushDestroyQueue
  -> 更新动画 / 图集 / 音频 / UI / 玩法模块 / 渲染
  -> 在合适的位置插入 PhysicsSystem
```

这里最值得记住的是：

```text
Scene 不只是“按顺序叫系统更新”，它还会主动安排某些系统的相对时序。
```

### 4.2.5.2 `OnUpdateEditor()`

编辑器更新也会先清理销毁队列，但它走的是编辑器路径：

```text
OnUpdateEditor
  -> FlushDestroyQueueEditor
  -> 更新编辑器态系统
  -> 用 EditorCamera 画出场景
```

这和 Runtime 的差异很明显：

- Runtime 关心玩法是否正确
- Editor 关心编辑和预览是否顺手

### 4.2.5.3 `RenderWithSceneCamera()`

这个函数是给外层调用的。

如果场景当前有一个可用相机，就让 `RenderSystem` 用那台相机去画。

这也是 Scene 层的一个典型设计：

```text
Scene 不自己直接画，
它只是把“该用什么相机画”这件事交给 RenderSystem。
```

## 4.2.6 实体的创建和销毁

这一节能帮助你理解为什么 Scene 生命周期不是“只有开始和结束”。

### 4.2.6.1 创建实体

`CreateEntity()` 最终会走到 `CreateEntityWithUUID()`。

创建一个新实体时，Scene 会默认给它加上：

- `IDComponent`
- `TransformComponent`
- `TagComponent`

也就是说，实体刚出生就有三个最基础的身份信息：

```text
唯一 ID
位置变换
名字
```

这三个东西是后面查找、保存、复制、绑定的基础。

### 4.2.6.2 立即销毁

`DestroyEntityImmediate()` 是直接销毁。

它会先检查句柄是不是还有效，再通知所有系统 `OnEntityDestroy`，最后真的把实体从 registry 里删掉。

这个接口适合：

- 编辑器里的立即删除
- 撤销 / 重做
- 某些必须同步收尾的场景

### 4.2.6.3 延迟销毁

`DestroyEntity()` 不会马上删，它只是把实体丢进 `m_DestroyQueue`。

下一帧统一清理。

这样做的好处非常明显：

- 避免在遍历实体时直接修改 registry
- 避免系统回调里套系统回调，导致迭代器失效
- 避免一边更新一边把世界结构撕掉

### 4.2.6.4 为什么销毁队列要排序和去重

真正执行销毁时，Scene 会先把队列 swap 出来，再排序、去重，然后再处理。

这么做是为了：

- 销毁顺序可重复
- 系统在销毁回调里再次请求销毁时不会把当前队列搞乱

这属于非常典型的引擎写法：

```text
先收集，
再统一处理，
不要边走边拆。
```

### 4.2.6.5 `FlushDestroyQueue()` 和 `FlushDestroyQueueEditor()`

这两个函数名字很像，但目的不完全一样。

- Runtime 版会通知系统做资源收尾
- Editor 版更偏向把 registry 结构清掉

这反映出一个很实际的设计取舍：

```text
运行时要照顾物理、音频、UI、脚本等资源收尾；
编辑器态更重视稳定和简单。
```

### 4.2.6.6 prefab / duplicate 先放一边

`InstantiateFromPrefab()` 和 `DuplicateEntity()` 也属于实体生命周期，但它们更偏“复制”和“实例化”，
具体的序列化和拷贝规则放到下一章再详细展开。

这一章先记住一句话就够了：

```text
Scene 不只是“创建和删除实体”，它还负责把实体的生命周期和系统生命周期对齐。
```

## 4.2.7 视口、相机和保存策略

### 4.2.7.1 视口为什么属于 Scene

`Scene` 保存了：

- 视口宽度
- 视口高度
- 视口偏移

这是因为场景并不是脱离窗口存在的。  
它要知道自己当前应该在多大的区域里运行。

`OnViewportResize()` 会把新尺寸同步到非固定宽高比的相机组件上。

### 4.2.7.2 为什么有 `ViewportOffset`

编辑器里，场景窗口只是主界面中的一个区域，不是整个屏幕。

所以 `SetViewportOffset()` 很重要：

```text
它让 Scene 知道“可视区域从哪里开始”。
```

这对鼠标命中、UI 输入、视口内拾取都很关键。

`UISystem` 也会从这里拿到偏移，保证点击命中的是视口内部，而不是整个编辑器窗口。

### 4.2.7.3 `SavePolicy` 为什么也在 Scene 里

这不是全局配置，而是场景自己的规则。

比如：

- 某些剧情场景不允许读档
- 某些结果页只允许返回上一场景
- 某些关卡切入后要自动加载某个存档槽

`GetEffectiveSavePolicy()` 还能看覆盖栈，所以外层可以临时改规则，而不用改原始 Scene 配置。

### 4.2.7.4 读档为什么要看当前场景

`GameProgress` 里会记录当前场景和上一个场景。

这不是装饰字段，它是场景切换和存档逻辑的一部分。

比如读档时，你需要知道：

- 从哪个场景来的
- 现在要回到哪个场景
- 当前场景允不允许 load

所以场景状态不只是“画面状态”，也是“流程状态”。

## 4.2.8 系统怎么挂进 Scene

这一节是 Scene ECS 层真正“能跑”的核心。

### 4.2.8.1 `ISystem` 的统一接口

`ISystem` 提供了这几个回调：

- `OnRuntimeStart`
- `OnRuntimeStop`
- `OnEditorStart`
- `OnEditorStop`
- `OnUpdateRuntime`
- `OnUpdateEditor`
- `OnEntityCreated`
- `OnEntityDestroy`

这意味着系统不是靠某个全局单例硬撑着，而是直接挂在 Scene 上。

### 4.2.8.2 `RegisterSystem<T>()`

Scene 内部有一个模板注册接口。

它会创建系统对象、塞进 `m_Systems`，然后把系统缓存标记为脏。

这也是为什么 `GetSystem<T>()` 要做一次懒缓存：

```text
注册之后，下一次按类型找系统，不用每次都动态扫描整列表。
```

### 4.2.8.3 为什么要有 `GetSystem<T>()` 缓存

Scene 里有很多地方会频繁找系统，比如：

- `SetViewportOffset()` -> 找 `UISystem`
- `SetAnimationEditorPreviewActive()` -> 找 `AnimationSystem`
- `RenderWithSceneCamera()` -> 找 `RenderSystem`

如果每次都线性遍历和 `dynamic_cast`，虽然代码能跑，但不够干净。

所以这里用了 type-index 缓存，减少重复扫描。

### 4.2.8.4 运行时系统怎么配置

`ConfigureRuntimeSystems()` 大致会装上：

- `PhysicsSystem`
- `AnimationSystem`
- `SpriteSheetSystem`
- `AudioSystem`
- `UISystem`
- `SceneSystemRegistry` 注入的模块系统
- `RenderSystem`

这说明运行时不是只有引擎内建系统，还可以被模块扩展。

### 4.2.8.5 编辑器系统怎么配置

编辑器态则更轻一些：

- `AnimationSystem`
- `SpriteSheetSystem`
- `UISystem`
- `RenderSystem`

这样做很合理，因为编辑器里不一定需要完整的物理和玩法链路。

### 4.2.8.6 `SceneSystemRegistry` 为什么存在

`SceneSystemRegistry` 的作用就是：  
**让模块在不改 Scene 核心代码的情况下，把自己的运行时系统挂进来。**

在 `ModuleBootstrap.cpp` 里，你可以看到这些系统被注册进去：

- `VisualNovel`
- `ArcadeCombat`
- `SideCombat`
- `TurnCombat`
- `TacticalCombat`
- `Progression`
- `EventScript`

这件事很适合面试时讲：

```text
Scene 核心只知道“我要有一批 runtime systems”；
具体有哪些玩法系统，由模块注册进来。
```

### 4.2.8.7 为什么停止时要逆序

系统启动是正序，停止是逆序。

这是非常标准的资源生命周期处理方式。

举个直觉例子：

- 后挂上的 UI 或玩法系统，可能依赖前面的物理、动画、资源系统
- 停止时应该先让高层系统收尾，再收底层资源

这样更不容易在销毁时留下悬挂引用。

## 4.2.9 场景切换到底是怎么发生的

这一节是很多人面试时最容易卡住的地方。

### 4.2.9.1 为什么不能在按钮回调里直接切场景

因为按钮回调发生时，当前帧可能还在：

- 更新系统
- 遍历实体
- 处理输入
- 执行脚本

如果你在这个时候直接把 Scene 换掉，很容易把当前帧的状态撕开。

所以 Wheatear 用的是**请求队列**：

```text
按钮 / 命令
    ↓
SceneTransitionService
    ↓
外层 Layer / Editor 在帧末统一消费
    ↓
真正执行 LoadScene / NewGame / LoadGame
```

### 4.2.9.2 `SceneTransitionService` 的角色

它只是把切换请求排队，不直接换。

请求类型有三种：

- `LoadScene`
- `NewGame`
- `LoadGame`

这三个名字已经把常见流程都覆盖了。

### 4.2.9.3 Runtime 下谁来消费请求

在 `RuntimeSceneLayer` 里，运行时每帧会：

1. 更新场景
2. 收集游戏运行命令
3. 收集 `SceneTransitionService` 请求
4. 执行最后一个请求

也就是说，真正换场景是在帧末完成的。

### 4.2.9.4 RuntimeSceneLayer 的加载流程

`RuntimeSceneLayer::LoadScene()` 大致是这样：

```text
Reset UI input
Clear queued commands
Stop old scene if needed
Create new Scene
Deserialize YAML
Set GameProgress transition context
Apply pending auto-load slot
Push viewport size to the new scene
OnRuntimeStart
```

这条链路很重要，因为它告诉你：  
**切场景不是只换一份场景数据，还是一整套输入、命令、进度、视口、系统状态的收口。**

### 4.2.9.5 `NewGame` 和 `LoadGame`

在请求执行时，`NewGame` 会先：

- `GameProgress::ResetForNewGame()`
- 清掉 pending auto-load slot
- 再加载目标场景

`LoadGame` 则会：

- 先检查当前场景是否允许读取
- 记录要自动加载的槽位
- `GameProgress::LoadSlot(slot)`
- 再加载场景

所以 `Scene` 的生命周期，已经和进度系统绑在一起了。

### 4.2.9.6 编辑器 Play Mode 的切换

编辑器里最典型的切换是：

```text
编辑态 Scene
  -> Scene::Copy()
  -> Play Scene
  -> OnEditorStop()
  -> OnRuntimeStart()
```

停止 Play Mode 时再反过来：

```text
Play Scene
  -> OnRuntimeStop()
  -> 回到 Editor Scene
  -> OnEditorStart()
```

这个设计的重点是：

```text
编辑器态 Scene 和运行态 Scene 不是同一个对象。
```

也就是说，你在编辑器里调试，实际上是在一份复制出来的运行时场景上跑。

### 4.2.9.7 为什么要在新场景后强制推一次视口

RuntimeSceneLayer 里有一个很细的处理：

加载新场景后，会把视口宽高先置 0，再强制推一次 resize。

这样做是为了让新场景拿到最新的相机参数，不会沿用旧场景的残留状态。

这类细节很值得记住，因为它非常像真实引擎里会遇到的坑：

```text
换了一个场景，但窗口没变；
如果你不主动推一次 resize，新场景相机可能以为自己没变。
```

## 4.2.10 一个完整例子：从菜单进游戏，再到读档

这一节把上面的碎点串成一条真正能讲给面试官听的链路。

### 4.2.10.1 新游戏

比如主菜单里点“开始游戏”。

链路大概是：

```text
UIButton
  -> UIInputSystem 命中点击
  -> CommandBus::Execute(scene, "newgame:xxx")
  -> SceneTransitionService::RequestNewGame(...)
  -> RuntimeSceneLayer / Editor Play Mode 在帧末消费请求
  -> GameProgress::ResetForNewGame()
  -> LoadScene(...)
  -> Scene::OnRuntimeStart()
```

这条链路体现了几个设计点：

- UI 只负责发命令
- 命令总线负责把字符串变成动作
- 场景切换服务负责排队
- 外层 Layer 负责真正执行

### 4.2.10.2 读档

读档链路会多一层保存策略判断：

```text
UI / 命令
  -> SceneTransitionService::RequestLoadGame(...)
  -> 外层消费请求
  -> 检查当前 Scene 的 GetEffectiveSavePolicy().CanLoad
  -> GameProgress::LoadSlot(slot)
  -> LoadScene(...)
  -> Scene::OnRuntimeStart()
```

如果当前场景不允许读取，系统会给出结果信息，而不会硬切。

这也是为什么 `SavePolicy` 必须挂在 Scene 上。

### 4.2.10.3 返回上一场景

游戏里很多时候不是“绝对去某个固定 Scene”，而是“回到之前那一个”。

这时 `GameProgress::SetSceneTransitionContext(previous, current)` 就很关键了。  
它会记录当前场景与上一个场景，为后面返回、读档、结果页跳转提供依据。

## 4.2.11 和 Unity、UE、Godot 的对照

面试里这个问题几乎跑不掉。

### 4.2.11.1 Unity

Unity 里你会想到：

- `SceneManager.LoadScene`
- Play Mode
- 编辑器里的场景复制和运行

你可以把 Wheatear 的这条线类比成：

```text
编辑态 Scene -> Copy -> 运行态 Scene -> OnRuntimeStart()
```

区别在于 Wheatear 更明确地把 Scene 和 ECS / Systems 挂在一起了。

### 4.2.11.2 Unreal

UE 里你会想到：

- `OpenLevel`
- PIE（Play In Editor）
- `UWorld` / `Level` / `GameInstance`
- `Subsystem`

Wheatear 的思路和它们很像，但更轻：

- 世界容器就是 `Scene`
- 系统就挂在 `Scene` 下面
- Play Mode 就是复制一份编辑场景来跑

### 4.2.11.3 Godot

Godot 里常见的是：

- `SceneTree`
- `change_scene_to_file`
- `PackedScene`

Wheatear 的 `Scene + Serializer + Prefab` 路线，和 Godot 的“场景即内容单位”也能对上。

### 4.2.11.4 你的引擎特点

Wheatear 的特点不是“把这些引擎原样重做一遍”，而是：

- Scene 更明确地承载 ECS
- 系统更明确地跟着 Scene 生命周期走
- 切场景更明确地通过请求队列完成
- 编辑器 Play Mode 更明确地分成复制态和编辑态

这就是一个比较适合 2D 游戏、又便于讲清楚架构的方案。

## 4.2.12 这一层的好处、坏处和常见误区

### 好处

- 生命周期清楚，启动和停止入口统一
- 编辑态和运行态分离，调试更安全
- Destroy queue 让实体销毁更稳
- `SceneSystemRegistry` 让模块能注入自己的系统
- 视口、保存策略、进度上下文都能跟场景绑定
- 很适合做“从菜单到剧情到战斗”的 2D 游戏流程

### 坏处

- 逻辑比“全局单例 + 一堆脚本”更重
- 需要自己管理系统顺序
- 切换流程一多，状态收口点也会多
- 如果命名和职责不统一，Scene 会很快变得很杂

### 常见误区

- 在按钮回调里直接销毁 / 载入 Scene
- 忘记清 UI 输入和命令队列
- 把编辑器态和运行时态混在一起
- 忘记 `OnRuntimeStop()`，导致旧系统残留
- 切场景时不重推视口，导致新场景相机状态不对
- 直接依赖字符串找实体而不关心缓存失效

这些坑都很适合写到后面的“常见问题”附录里。

## 4.2.13 面试时怎么讲

如果面试官问你“你的 Scene 生命周期是怎么设计的”，可以这么答：

```text
Scene 是游戏世界容器，内部持有 entt registry 和一组系统。
它有 Edit / Runtime 两种执行模式。
启动时会按模式装配对应系统，停止时逆序释放。
每帧会先处理销毁队列，再更新系统。
场景切换不是立即执行，而是通过 SceneTransitionService 排队，
由 RuntimeSceneLayer 或 Editor Play Mode 在帧末统一消费。
编辑器 Play Mode 会先复制一份 Scene，再切到 Runtime，这样编辑态和运行态互不污染。
```

如果继续追问“为什么要这样做”，你就补一句：

```text
因为这样能把输入、命令、系统更新、保存策略、视口和进度状态都收束到一条可控的生命周期里。
```

这句很适合面试。

Scene 不是文件名，也不是一堆实体的集合；

- `Scene` 什么时候开始工作

- 系统怎么挂上去
- 为什么要有销毁队列
- 为什么切场景要排队
- 为什么 Edit 和 Runtime 不能混
