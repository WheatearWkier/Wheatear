# 第 4 编 04：系统接入渲染、物理、动画

> 本章所属层级：**Scene ECS 层**
>
> 本章目标：把“系统”这个词在 Wheatear 里真正落地。
> - `ISystem` 是什么
> - 系统为什么挂在 `Scene` 上，而不是挂成全局单例
> - `RenderSystem`、`PhysicsSystem`、`AnimationSystem`、`SpriteSheetSystem`、`AudioSystem`、`UISystem` 分别负责什么
> - `OnRuntimeStart / OnUpdateRuntime / OnEntityCreated / OnEntityDestroy` 是怎么接起来的
> - 为什么系统顺序会影响最终结果
>
> 这一章是 Scene ECS 层的最后一块骨架。  
> 前两章讲了 Scene 怎么活、怎么存；这一章讲 Scene 里的“器官”怎么接上去。

如果说前两章是在回答：

```text
世界怎么存在？
世界怎么被保存和复制？
```

那这一章回答的是：

```text
世界里的渲染、物理、动画、图集、音频、UI，是怎么被接上来的？
```

Wheatear 的系统不是那种“全局跑一堆单例更新”的写法，而是：

```text
Scene
  -> 一组 ISystem
  -> 每帧按生命周期回调运行
  -> 需要时还能接收实体创建 / 销毁通知
```

这套结构的意义在于，系统不是漂在外面的服务，而是**跟着场景生命周期一起生灭**。

## 4.4.2 这一层在架构中的位置

```text
应用层
    Editor / Sandbox
        ↓
核心平台层
    Application / EventBus / LayerStack
        ↓
引擎服务层
    Renderer / Input / UI / Audio / Physics
        ↓
Scene ECS 层
    Scene / Entity / Components / Systems / Serializer
        ↓
平台实现层
    OpenGL / Box2D / SDL / GLFW / entt
```

系统层的职责很明确：

- Scene 提供世界和实体
- System 提供更新逻辑
- Component 提供数据

三者合起来，就是典型的 ECS 运行结构。

但 Wheatear 的实现不是教科书式“纯逻辑 ECS”，而是更务实：

- 渲染系统负责整帧画面
- 物理系统负责 Box2D 世界
- 动画系统负责 clip / frame / property track
- 图集系统负责把 sheet 和 cell 解析成纹理和 UV
- 音频系统负责场景音效启动和停止
- UI 系统负责运行时界面更新和绘制

这非常适合做 2D 游戏，也很适合拿来面试讲清楚“我怎么把几类常见玩法能力接进 Scene”。

## 4.4.3 `ISystem`：统一的系统接口

### 4.4.3.1 它长什么样

`ISystem` 提供了这几个虚函数：

- `OnRuntimeStart(Scene* scene)`
- `OnRuntimeStop(Scene* scene)`
- `OnEditorStart(Scene* scene)`
- `OnEditorStop(Scene* scene)`
- `OnUpdateRuntime(Scene* scene, Timestep ts)`
- `OnUpdateEditor(Scene* scene, Timestep ts)`
- `OnEntityCreated(Scene* scene, Entity& entity)`
- `OnEntityDestroy(Scene* scene, Entity& entity)`

这套接口已经把系统生命周期讲得很完整了：

```text
启动
停止
运行时更新
编辑器更新
实体创建通知
实体销毁通知
```

### 4.4.3.2 为什么 `OnEditorStart/Stop` 默认转发到 Runtime

`ISystem` 里默认实现是：

```text
OnEditorStart -> OnRuntimeStart
OnEditorStop  -> OnRuntimeStop
```

这表示很多系统在编辑器态和运行态其实共用初始化和收尾逻辑。  
如果某个系统需要特殊编辑器行为，再自己 override 就行。

这比强行写两套接口更实用。

### 4.4.3.3 为什么有实体生命周期回调

因为有些系统不能只靠每帧扫描。

比如：

- 物理系统要在实体创建时立刻建 body
- 物理系统要在实体销毁时销 body
- 某些未来的系统也可能要在实体创建时做预热

所以 `OnEntityCreated/Destroy` 是为了处理那些“不是纯轮询就能干净完成”的工作。

## 4.4.4 `Scene` 怎么挂系统

### 4.4.4.1 `Scene` 自己持有什么

Scene 里有：

- `std::vector<Scope<ISystem>> m_Systems`
- `std::unordered_map<std::type_index, ISystem*> m_SystemCache`
- `bool m_SystemCacheDirty`

这说明系统是 Scene 的成员，不是全局静态对象。

### 4.4.4.2 `RegisterSystem<T>()`

`Scene` 里面有模板注册函数，会把系统创建出来并塞进 `m_Systems`。

这有两个意义：

1. 系统的生命周期由 Scene 统一管理
2. 系统不需要自己决定什么时候销毁

### 4.4.4.3 `GetSystem<T>()`

有些地方需要按类型回头找系统，比如：

- `SetViewportOffset()` 要找 `UISystem`
- `SetAnimationEditorPreviewActive()` 要找 `AnimationSystem`
- `RenderWithSceneCamera()` 要找 `RenderSystem`

所以 Scene 维护了一个 type-index 缓存。  
这是很典型的“按类型找系统，但不要每帧都线性扫”的做法。

### 4.4.4.4 `ConfigureRuntimeSystems()`

运行时会挂这些系统：

- `PhysicsSystem`
- `AnimationSystem`
- `SpriteSheetSystem`
- `AudioSystem`
- `UISystem`
- `SceneSystemRegistry` 注入的模块系统
- `RenderSystem`

### 4.4.4.5 `ConfigureEditorSystems()`

编辑器态会挂：

- `AnimationSystem`
- `SpriteSheetSystem`
- `UISystem`
- `RenderSystem`

可以看到，编辑器不一定需要完整物理和玩法链路，但还是需要预览、动画、图集和 UI。

## 4.4.5 系统顺序为什么重要

Scene 的运行时更新顺序不是随机的。

### 4.4.5.1 `OnUpdateRuntime()` 的大结构

```text
FlushDestroyQueue
for each system in m_Systems:
    if system is PhysicsSystem:
        延后执行
    else:
        system->OnUpdateRuntime(...)
        if 当前是 SpriteSheetSystem 且 Physics 被延后:
            立刻跑 Physics
loop 结束后如果还有 Physics:
    再跑一次 Physics
```

### 4.4.5.2 为什么 Physics 要延后

因为当前实现里，物理要等动画 / 图集先把碰撞盒同步好。

比如：

- 动画帧变了
- 图集 cell 变了
- `FollowAnimation` 的 collider 变形了

那物理 step 就应该看到更新后的 collider。

所以系统顺序不是摆设，它真的会影响结果。

### 4.4.5.3 为什么 RenderSystem 放最后

因为渲染应该读取已经更新过的：

- 动画状态
- 物理位置
- UI 状态
- 战斗状态
- 脚本状态

这就是为什么 RenderSystem 通常是最后一环：  
它负责把前面系统更新出来的世界“拍成画面”。

## 4.4.6 渲染系统：`RenderSystem`

### 4.4.6.1 它在干什么

`RenderSystem` 是 Scene 里的总渲染调度器。

它不是只画一张图，而是按 pass 把整帧都组织起来：

- Shadow pass
- 2D pass
- 3D pass
- UI pass

### 4.4.6.2 Runtime 里怎么画

`OnUpdateRuntime()` 的链路大概是：

```text
找主相机
-> 计算相机矩阵
-> Shadow pass
-> 2D pass
-> 3D pass
-> UI pass
```

这个系统的价值，不只是“会画”，而是把整帧画面的顺序固定住。

### 4.4.6.3 它为什么还负责 UI pass

因为在 Wheatear 里，UI 也是运行时场景的一部分。

所以最终会走到：

```text
RenderSystem
  -> UIRenderer::BeginUIPass
  -> UISystem::RenderUI
  -> UIRenderer::EndUIPass
```

这让 UI 和主画面共享同一帧更新结果。

### 4.4.6.4 Editor 里怎么画

编辑器态会走 `RenderWithEditorCamera()`。

这说明同一个 Scene，既能被游戏相机画，也能被编辑器相机画。  
这在讲教材时很好用，因为它把“场景渲染”和“编辑器预览”分开了。

### 4.4.6.5 它依赖哪些底层系统

渲染系统真正依赖的是：

- `Renderer2D`
- `Renderer3D`
- `RenderCommand`
- `Framebuffer`
- `UISystem`

也就是说，RenderSystem 是 Scene 层的“总导演”，不是最低层 API。

## 4.4.7 物理系统：`PhysicsSystem`

### 4.4.7.1 它在干什么

`PhysicsSystem` 负责 Box2D 世界：

- 创建 `b2World`
- 绑定 `ContactListener`
- 给带刚体的实体初始化 body / fixture
- 每帧 step
- 把物理结果同步回 `TransformComponent`

### 4.4.7.2 启动时做什么

`OnRuntimeStart()` 会：

1. 创建物理世界
2. 创建 contact listener
3. 给场景里现有的 `Rigidbody2DComponent` 实体做物理初始化

这很重要，因为运行时开始时，场景里可能已经有一批实体了。

### 4.4.7.3 更新时做什么

`OnUpdateRuntime()` 会：

- 先同步动画驱动的 collider
- 再 `Step`
- 再把 body 的位置和角度写回 `TransformComponent`

这说明物理不是单向的，它会把结果回写给场景数据。

### 4.4.7.4 为什么要先同步动画驱动碰撞盒

因为有些 2D 动画角色的碰撞盒会跟帧变化。

比如某个攻击动作：

- 起手帧碰撞盒小
- 出招帧碰撞盒大
- 收招帧恢复正常

如果不先同步，物理 step 就会拿到过期的 fixture。

### 4.4.7.5 `OnEntityCreated` 和 `OnEntityDestroy`

这两个回调是物理系统非常核心的一块：

- 实体创建时，如果有刚体，就立即建 body
- 实体销毁时，如果 body 存在，就立即销 body

这就是为什么系统要能接实体生命周期通知。  
否则物理资源会越来越乱。

### 4.4.7.6 为什么复制实体时要清运行时指针

这个点跟上一章也能连起来。

`Scene::DuplicateEntity()` 会把：

- `RuntimeBody`
- `RuntimeFixture`

都清掉。

原因很简单：

```text
复制的是数据，不是 Box2D 的运行时对象。
```

## 4.4.8 动画系统：`AnimationSystem`

### 4.4.8.1 它在干什么

动画系统负责：

- 运行时加载外部 `*.wtanim`
- 播放 clip
- 切帧
- 触发动画事件
- 驱动属性轨道
- 编辑器预览某一帧

### 4.4.8.2 启动时做什么

`OnRuntimeStart()` 会遍历所有 `SpriteAnimatorComponent`，把外部动画 clip 读进来。

这意味着动画不是只能埋在场景里，也可以从外部资产加载。

### 4.4.8.3 更新时做什么

`OnUpdateRuntime()` 最核心的工作就是 `UpdateAnimations()`。

它会：

- 累加播放时间
- 找当前帧
- 应用帧的纹理 / UV
- 应用属性轨道
- 收集动画事件命令
- 统一在循环后执行这些命令

### 4.4.8.4 为什么动画事件不能边遍历边执行

因为动画事件可能触发：

- 命令总线
- 实体销毁
- 状态切换

如果你在遍历 view 的时候直接执行，很容易把迭代器弄坏。  
所以它先收集命令，再统一执行。

这也是引擎里非常标准的“先收集，后提交”思路。

### 4.4.8.5 动画和 sprite / collider 的关系

动画帧变了，不只是换图片，还可能：

- 换 atlas cell
- 驱动 collider
- 改 sprite 的颜色 / 位置 / 缩放

所以动画系统和 SpriteSheetSystem 不是孤立的。

---

## 4.4.9 图集系统：`SpriteSheetSystem`

### 4.4.9.1 它在干什么

图集系统负责把：

- `SpriteRendererComponent`
- `UIImageComponent`

里写的 `.wtsheet + CellIndex / SubRect`

解析成真正可画的：

- Texture
- UVMin
- UVMax

### 4.4.9.2 为什么这个系统重要

因为如果没有它，场景里就只能存“资源引用”，不能稳定地把图集 cell 转成渲染数据。

它等于把“内容数据”翻译成“渲染数据”。

### 4.4.9.3 为什么它要和动画配合

动画帧也可能引用图集 cell。  
一旦当前帧切换，SpriteSheetSystem 就能把 collider 一起更新掉。

这正是这个系统存在的价值：

```text
图集不是死的资源名，
它是会驱动渲染和碰撞的实时数据。
```

### 4.4.9.4 热重载意味着什么

图集定义文件改了，系统能重新解析。

这对于做 2D 游戏非常实用，因为：

- UI 图
- 角色帧动画
- 技能图标

都经常会反复调。

## 4.4.10 音频系统：`AudioSystem`

### 4.4.10.1 它在干什么

音频系统在这里比较轻，但职责清楚：

- Runtime Start 时启动需要自动播放的音源
- Runtime Stop 时统一收尾

### 4.4.10.2 为什么它属于 Scene 系统

因为很多音效是场景内容的一部分，而不是全局常驻。

例如：

- 某个剧情场景的 BGM
- 某个战斗场景的提示音
- 某个 UI 场景的开场音效

### 4.4.10.3 为什么启动时要看音量设置

因为 `AudioSystem` 会读取用户设置，再决定播放增益。

这说明它不是单纯“发声”，而是和配置系统一起工作的。

---

## 4.4.11 UI 系统：`UISystem`

### 4.4.11.1 它在干什么

UI 系统负责：

- Runtime Start 时重置 animator
- 预加载字体文本
- 每帧处理 UI 输入
- 每帧更新 UI animator
- 按排序和裁剪规则把 UI 画出来

### 4.4.11.2 为什么它和 Scene 绑定

因为运行时 UI 本来就是场景的一部分：

- 血条
- 对话框
- 设置页
- 滑条
- 技能树

都不是编辑器外面的独立窗口。

### 4.4.11.3 它为什么要先做输入，再做动画

因为输入会改变 hover、pressed、dragging 状态，
动画会基于这些状态做表现变化。

所以顺序要对。

### 4.4.11.4 它为什么最终要和 RenderSystem 合作

因为 UI 的渲染不是单独跑 OpenGL，而是走：

```text
UISystem -> UIRenderer -> Renderer2D
```

这使得 UI 也纳入了统一的渲染栈。

## 4.4.12 `ComponentLifecycleRegistry`：组件生命周期和系统接手

这一节是很多人会漏掉的，但它很关键。

### 4.4.12.1 它不是系统本身

`ComponentLifecycleRegistry` 不是一个系统，而是一个**组件生命周期分发器**。

它负责把 entt 的：

- `on_construct`
- `on_update`
- `on_destroy`

信号接到注册过的回调上。

### 4.4.12.2 它为什么属于这一章

因为有些系统不是只靠每帧扫描才知道状态变化的。  
它们还需要在组件加上去、改掉、删掉时立刻做反应。

例如 `CameraComponent`：

- 加上去时，立刻按 Scene viewport 同步相机尺寸
- 更新时，也要再次同步

这就是 `RegisterCoreComponentLifecycles()` 的意义。

### 4.4.12.3 它和 Scene 的关系

Scene 构造时会把自己绑定给这个 registry。  
Scene 析构时会解绑。

所以组件生命周期回调始终知道自己属于哪个 Scene。

### 4.4.12.4 为什么这很适合编辑器

因为编辑器里实体和组件经常被不断改动。

有了这个层，某些状态可以在组件变化时即时更新，而不是等下一帧再补。

## 4.4.13 系统之间怎么串起来

这一章最重要的不是单个系统，而是系统之间的链路。

### 4.4.13.1 典型运行时链路

```text
Scene::OnUpdateRuntime
  -> AnimationSystem 更新动画
  -> SpriteSheetSystem 解析图集
  -> PhysicsSystem step，并同步 transform
  -> AudioSystem 维持场景音频
  -> UISystem 处理 UI 输入和 UI 动画
  -> RenderSystem 组织渲染 pass
```

### 4.4.13.2 为什么这条链是顺的

因为它遵循了现实游戏里比较自然的数据流：

- 先更新内容状态
- 再更新物理状态
- 再更新 UI / 音频 / 玩法
- 最后统一渲染

### 4.4.13.3 一个非常具体的例子

比如 VN 场景里的一句台词：

```text
动画系统触发对白事件
-> CommandBus 发命令
-> VN 模块改立绘和文本
-> UISystem 更新对话框内容
-> RenderSystem 把 UI 和背景画出来
```

或者战斗场景里一个角色受击：

```text
动画事件命中帧
-> CommandBus 发伤害命令
-> 物理/状态更新
-> UI 血条变化
-> RenderSystem 画出新一帧
```

这就是“系统接入”的真正含义。

---

## 4.4.14 模块系统怎么注入 Scene

### 4.4.14.1 为什么有 `SceneSystemRegistry`

因为 Scene 核心不应该知道所有玩法模块的细节。

`SceneSystemRegistry` 让模块自己注册运行时系统：

- VisualNovel
- ArcadeCombat
- SideCombat
- TurnCombat
- TacticalCombat
- Progression
- EventScript

### 4.4.14.2 这说明什么

说明 Scene 核心只提供“装系统”的位置，
真正的玩法系统可以按项目需求插进来。

这非常适合你的项目，因为你有很多 Demo：

- VN
- 横板格斗
- 弹幕
- 回合制
- 战棋

这些玩法系统不需要写死在 Scene 核心里。

### 4.4.14.3 为什么这在面试里很加分

因为你可以清楚地说明：

```text
引擎核心只管通用能力，
玩法模块通过注册机制接入 Scene。
```

这不是“把所有东西写进一个大类”，而是很清楚的分层思路。

## 4.4.15 和 Unity、UE、Godot 的对照

### 4.4.15.1 Unity

Unity 里可以类比成：

- `Scene` + `MonoBehaviour` 生命周期
- `Update`
- `OnEnable/OnDisable`

Wheatear 的区别在于：

- 系统是挂在 Scene 上的
- 生命周期更明确地分成 Runtime / Editor
- 系统之间的顺序是显式控制的

### 4.4.15.2 Unreal

UE 里可以类比成：

- `UWorld`
- `Subsystem`
- 各类 Actor / Component 生命周期

Wheatear 的相似点是：

- 世界有自己的生命周期
- 系统挂在世界下
- 不同场景有不同的运行语义

### 4.4.15.3 Godot

Godot 更像：

- SceneTree
- Node 生命周期

Wheatear 的区别是它更偏 ECS：

- 数据放组件
- 逻辑放系统
- 场景负责调度

### 4.4.15.4 你的引擎特点

Wheatear 的系统层特点可以概括成：

- 够轻
- 够清楚
- 够贴合 2D 游戏
- 够适合把玩法模块接进来

## 4.4.16 这一层的优点、坏处和常见误区

### 优点

- 系统生命周期统一
- 运行时 / 编辑器态都能复用系统框架
- 实体创建、销毁可以让系统及时接手
- 渲染、物理、动画、UI、音频、图集能分工明确
- 模块系统可以注入，不用改 Scene 核心
- 系统顺序可控，适合做复杂 2D 游戏

### 坏处

- 系统很多时，顺序管理要非常小心
- 某些系统之间会有隐式依赖
- 如果把职责划太细，调用链会长
- 如果把职责划太粗，Scene 又会变得臃肿

### 常见误区

- 以为系统就是“每帧扫一遍组件”
- 忘了物理 / 动画 / 图集之间有时序关系
- 把渲染系统当成纯绘图工具，忽略它其实是整帧调度器
- 直接把模块系统写死进 Scene 核心
- 忘了实体创建 / 销毁要通知系统
- 以为编辑器态和运行态可以共用同一套资源状态

---

## 4.4.17 面试时怎么讲

如果面试官问你“你的系统是怎么挂进 Scene 的”，可以这么答：

```text
Scene 持有一组 ISystem，启动时根据 Edit / Runtime 模式装配不同系统。
系统通过 OnRuntimeStart / OnUpdateRuntime / OnEntityCreated / OnEntityDestroy 接收场景生命周期和实体生命周期回调。
渲染、物理、动画、图集、音频、UI 都是独立系统，但它们按照 Scene 统一的顺序更新。
模块系统则通过 SceneSystemRegistry 注入，不需要改 Scene 核心代码。
```

如果追问“为什么要这样设计”，你就补一句：

```text
因为这样既能保证通用引擎能力清晰，又能让 VN、战斗、进度这些玩法模块自然挂进来。
```

## 4.4.18 小结

这一章其实在讲一个很朴素但很核心的事实：

```text
Scene 不是只存数据，它还负责把一组系统按正确顺序接起来。
```

Wheatear 的系统层最后可以归纳成一句话：

- `PhysicsSystem` 管身体
- `AnimationSystem` 管动作
- `SpriteSheetSystem` 管图集解析
- `AudioSystem` 管场景音频
- `UISystem` 管运行时 UI
- `RenderSystem` 管整帧画面
- `SceneSystemRegistry` 管模块注入

你把这一章读懂，Scene ECS 层就基本通了。
