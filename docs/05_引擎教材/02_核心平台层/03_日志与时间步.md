# 第 2 编 03：日志与时间步

> 本章所属层级：核心平台层  
> 本章学习目标：理解 Wheatear 的日志系统为什么要在最早期初始化，为什么要区分 Core Logger 和 Client Logger，编辑器控制台里的日志是怎么来的，以及 `Timestep` 为什么不是一个普通 `float`。
>
> 本章会反复使用三个具体例子：
>
> 1. 程序刚启动时，为什么 `main()` 里先看到日志，再创建应用。
> 2. 编辑器控制台为什么既能看到引擎内部的错误，也能看到游戏项目自己的日志。
> 3. `Layer::OnUpdate(Timestep ts)` 里的 `ts` 到底是什么，为什么渲染、动画、VN、战斗系统都要靠它。

## 2.3 这一层在整个架构中的位置

Core 层做的事情很少，但它们都很基础：

- 提供统一的日志入口。
- 提供帧时间步这个最小的更新单位。
- 把“程序刚启动”和“每一帧都要做的事”变成稳定约定。

```text
应用层
    WheatearEditor / WheatearSandbox
        ↓
核心平台层
    Log / Timestep / Application / Layer / Event
        ↓
平台实现层
    GLFW / OpenGL / Windows
```

如果没有这一层，上层代码就会各写各的日志、各算各的时间、各传各的 delta，最后调试和排错会非常痛苦。  
所以你可以把 `Log` 理解成“引擎的公共说话方式”，把 `Timestep` 理解成“引擎对一帧时间的统一说法”。

## 2.4 需要阅读的源码

```text
Wheatear/src/Wheatear/Core/Log.h
Wheatear/src/Wheatear/Core/Log.cpp
Wheatear/src/Wheatear/Core/Timestep.h
Wheatear/src/Wheatear/Core/EntryPoint.h
Wheatear/src/Wheatear/Core/Application.cpp
Wheatear/src/Wheatear/Core/Layer.h

Wheatear/src/Platform/Windows/WindowsWindow.cpp
Wheatear/src/Platform/OpenGL/OpenGLContext.cpp
```

这一章最关键的是把三条链路读顺：

1. `main()` 先调用 `Log::Init()`，再创建 `Application`。
2. `Log::Init()` 建立两个 logger，并把日志镜像到编辑器缓冲区。
3. `Application::Run()` 每帧计算 `Timestep`，再把它传给所有 Layer 和系统。

## 2.5 为什么日志要放在核心平台层

日志不是玩法功能，也不是编辑器面板功能。  
它是整个引擎共同依赖的底层能力。

Wheatear 里，日志会被很多地方用到：

- 窗口创建失败时要打日志。
- OpenGL 上下文初始化时要打日志。
- 资源加载失败时要打日志。
- 玩法系统找不到动作表、技能表、剧情命令时要打日志。
- 编辑器控制台要显示日志。

这意味着日志必须先于大多数系统存在。  
所以 `Log::Init()` 放在 `main()` 很早的位置，甚至早于 `CreateApplication()`，这是有意为之，不是习惯问题。

## 2.6 `Log::Init()` 到底做了什么

入口文件 `EntryPoint.h` 里，程序启动顺序大致是这样的：

```cpp
int main(int argc, char** argv)
{
    EnablePerMonitorDpiAwareness();
    Wheatear::Log::Init();
    auto* app = Wheatear::CreateApplication({ argc, argv });
    app->Run();
}
```

这条链路很重要，因为它说明了一个原则：

> 先让引擎“会说话”，再让引擎开始干活。

`Log::Init()` 里做了四件事：

1. 统一日志格式。
2. 创建 Core Logger。
3. 创建 Client Logger。
4. 把日志同时送到终端和编辑器缓冲区。

### 2.6.1 统一日志格式

源码里用了类似这样的 pattern：

```text
[%T] logger_name: message
```

其中：

- `%T` 是时间。
- `%n` 是 logger 名称。
- `%v` 是真正的日志内容。
- `%^` / `%$` 是颜色控制。

这样做的好处是：  
你在终端、编辑器控制台、甚至未来的日志文件里，看到的日志格式都一致。

### 2.6.2 Core Logger 和 Client Logger

`Log.h` 里定义了两套 logger：

- `GetCoreLogger()`
- `GetClientLogger()`

对应的宏分别是：

- `WT_CORE_INFO(...)`
- `WT_CORE_WARN(...)`
- `WT_CORE_ERROR(...)`
- `WT_CLIENT_INFO(...)`
- `WT_CLIENT_WARN(...)`
- `WT_CLIENT_ERROR(...)`

它们的意义不是“名字好看一点”，而是明确区分两个世界：

| 类型 | 用途 | 典型调用者 |
|---|---|---|
| Core Logger | 引擎内部状态、平台初始化、底层错误 | `WindowsWindow`、`OpenGLContext`、`Renderer`、`AudioEngine` |
| Client Logger | 项目逻辑、玩法模块、编辑器脚本、业务信息 | 玩法系统、项目代码、工具脚本 |

这件事在面试里很好讲：  
**Core Logger 负责引擎自己说话，Client Logger 负责项目和玩法说话。**

### 2.6.3 为什么要有编辑器日志缓冲区

`Log.cpp` 里不是只把日志打印到终端，还做了一个 `EditorLogSink`，把所有日志再复制一份进编辑器缓冲区。

这个设计解决的是一个很现实的问题：  
如果编辑器只能看终端日志，那调试体验会非常差。

所以当你以后在编辑器里打开 Console 面板时，逻辑上大概会是这样：

```cpp
std::vector<LogMessage> pending;
Log::DrainEditorMessages(pending);
```

然后编辑器把 `pending` 里的内容追加到自己的列表中。  
`ClearEditorMessages()` 则用于清空控制台，比如切换项目、重置运行状态、或者手动清屏。

这里还有一个细节很值得记住：

- `spdlog` 负责把日志格式化和输出。
- `EditorLogSink` 负责把日志镜像到编辑器缓冲区。
- `LogMessage` 记录了级别、文本和时间，方便编辑器后面做筛选、着色和排序。

也就是说，Wheatear 的日志不是单纯“替代 `printf`”，而是一个能同时服务终端和编辑器的底层设施。

## 2.7 一个日志从哪里来，到哪里去

我们拿一个窗口创建失败的例子看链路：

1. `WindowsWindow` 初始化 GLFW。
2. 如果初始化失败，调用 `WT_CORE_ERROR(...)`。
3. 宏展开后进入 `Log::GetCoreLogger()`。
4. `spdlog` 写到终端。
5. 同时 `EditorLogSink` 把这条日志写进编辑器缓冲区。
6. 编辑器 Console 面板下次刷新时把它读出来显示。

这条链路的价值在于：

- 终端里能看到。
- 编辑器里也能看到。
- 日志来源统一，不用到处找 `std::cout`。

同样的事情也发生在资源、动画、战斗、场景、音频等模块里。  
所以你可以把 `Log` 理解成整个引擎的“公共黑匣子”。

## 2.8 `Timestep` 为什么不是一个普通 `float`

`Timestep.h` 很短：

```cpp
class Timestep
{
public:
    Timestep(float time = 0.0f) : m_Time(time) {}
    operator float() const { return m_Time; }
    float GetSeconds() const { return m_Time; }
    float GetMilliseconds() const { return m_Time * 1000.0f; }
private:
    float m_Time;
};
```

它看起来像“一个包着 float 的壳”，但这个壳很有意义。

### 2.8.1 它表达的是“帧时间”

`Timestep` 不是绝对时间，不是时钟，不是调度器。  
它表达的是**这一帧和上一帧之间隔了多久**。

这个语义很重要，因为很多系统都依赖它：

- 动画系统要知道这一帧该推进多少。
- VN 系统要知道脚本检查多久一次。
- 战斗系统要知道技能冷却推进多少。
- 编辑器相机要知道拖拽和缩放该移动多少。

### 2.8.2 为什么先用 `double` 算，再转成 `float`

`Application::Run()` 里，时间来源是 `glfwGetTime()`，它返回的是 `double`。  
引擎会先在 `double` 精度里计算差值，再在传给外部系统时缩成 `float`：

```cpp
const double nowTime = glfwGetTime();
Timestep timestep = static_cast<float>(nowTime - m_LastFrameTime);
m_LastFrameTime = nowTime;
```

这样做有两个好处：

1. 计时源头尽量保留精度。
2. 对外接口保持简单，和大多数游戏数学库的 `float` 风格一致。

也就是说，`Timestep` 不是拿来做高精度时钟累计的，它只是“把本帧 delta 带给上层”的统一载体。

### 2.8.3 为什么要提供 `GetSeconds()` 和 `GetMilliseconds()`

不同系统会偏好不同单位：

- 大多数更新逻辑用秒。
- 编辑器面板、调试器、统计信息可能更喜欢毫秒。

所以 `Timestep` 直接提供两个常用单位，避免每个调用点重复写乘法。

它还有一个隐式转换到 `float` 的运算符，方便老代码或简单公式直接使用。  
不过写教材时要提醒一点：  
**新代码最好优先用 `GetSeconds()`，这样语义最清楚。**

## 2.9 `Timestep` 怎样进入整条更新链

`Application::Run()` 每一帧都会把 `Timestep` 传给所有 Layer：

```cpp
for (Layer* layer : m_LayerStack)
    layer->OnUpdate(timestep);
```

然后再往下传到场景、系统和玩法模块。

典型链路像这样：

```text
Application::Run()
    ↓
Layer::OnUpdate(Timestep ts)
    ↓
Scene::OnUpdateRuntime(ts)
    ↓
RenderSystem / UISystem / AnimationSystem / PhysicsSystem
    ↓
VisualNovelSystem / SideCombatSystem / TurnCombatSystem
```

这就是为什么 `Timestep` 虽然小，但它是整个运行时更新链路的“血液”。

举两个具体例子：

1. `VisualNovelSystem::OnUpdateRuntime(Scene* scene, Timestep ts)` 会用 `ts.GetSeconds()` 累加脚本检查时间。
2. `UISystem::OnUpdateRuntime(Scene* scene, Timestep ts)` 会用 `ts.GetSeconds()` 推进 UI 动画。

也就是说，时间步不是孤立存在的，它会一路往下流，最后变成动作、动画、冷却和表现节奏。

## 2.10 和 Unity / Unreal 的对照

如果你面试时被问到“这和别的引擎有什么像”，可以这样说：

| Wheatear | Unity | Unreal |
|---|---|---|
| `WT_CORE_INFO` / `WT_CLIENT_INFO` | `Debug.Log` / `Debug.LogWarning` | `UE_LOG` |
| `Timestep` | `Time.deltaTime` | `DeltaSeconds` |
| 编辑器日志缓冲区 | Console 窗口 | Output Log |

它们的共同点是：  
都要有统一日志和每帧 delta。

不同点是：  
Wheatear 目前更轻、更显式，很多东西都直接写在自己的运行时里，不会像大引擎那样把时间、日志、调试和运行态拆得那么厚。

这对你这种以 2D 游戏和中小型项目为主的引擎来说，是很合理的。

## 2.11 这一层的好处、坏处和边界

### 好处

- 日志统一，排错效率高。
- Core/Client 分离清晰，面试好讲。
- 编辑器控制台可以直接复用运行时日志。
- `Timestep` 给了上层一个稳定的帧时间接口。

### 坏处

- `Timestep` 现在只是可变步长包装，离固定步长还很远。
- 日志缓冲区还是一个比较轻的实现，后面如果要做多线程日志、日志文件归档、过滤器，可能还要继续增强。
- 隐式 `float` 转换虽然方便，但不如显式 `GetSeconds()` 安全。

### 常见误区

1. 以为 `Log` 只是“替代 `std::cout`”。
   - 不是，它是引擎统一的消息入口。
2. 以为 `Timestep` 就是一个普通数值。
   - 不是，它承载的是“帧 delta”语义。
3. 以为 `Log::Init()` 可有可无。
   - 不是，很多后续系统都依赖它先建立起来。
4. 以为所有地方都应该直接传 `double`。
   - 也不是，运行时更新层通常更适合用 `float` 风格。

## 2.12 面试时怎么讲这章

如果面试官问“你们引擎的日志和时间步怎么做的”，你可以这样答：

> Wheatear 的日志层放在核心平台层，启动时先 `Log::Init()`，再创建 `Application`。  
> 我们把日志分成 Core Logger 和 Client Logger，前者给引擎内部、平台和底层系统用，后者给项目和玩法层用。  
> 同时还做了一个编辑器侧的日志镜像缓冲区，这样 Console 面板可以直接消费运行时日志。  
> 时间步用 `Timestep` 包装，每帧由 `Application::Run()` 计算后传给所有 Layer 和 Scene 系统，`GetSeconds()` 是最常用的接口。  
> 这样做的好处是日志和时间语义都统一，后续无论是 2D 渲染、动画、VN、战斗还是 UI，都能共用同一套更新节奏。

这段答案的重点不是背 API，而是把三件事说清楚：

1. 为什么它们属于核心平台层。
2. 它们解决了什么共同问题。
3. 它们怎样支撑后面的系统。

## 2.13 小结

这一章其实在讲两件事：

- `Log` 让引擎会统一地说话。
- `Timestep` 让引擎会统一地描述一帧时间。

它们都很小，但都很底层。  
前者决定你怎么排错，后者决定你怎么驱动整个运行时。  
读懂这一章以后，你再去看 `Layer::OnUpdate()`、`Scene::OnUpdateRuntime()`、`VisualNovelSystem`、`AnimationSystem`、`RenderSystem`，就会知道它们为什么都绕不开 `Timestep`，也会知道为什么任何底层错误都应该先经过 `Log`。

下一章就可以进入 **引擎服务层**，开始写真正支撑玩法和内容生产的系统了。
