# 第 2 编 02：事件与输入

> 本章所属层级：
> - 核心平台层：`Event`、`EventBus`、`Timestep`、`Application` 的事件路由
> - 引擎服务层：`Input`、`InputBindingService`、`InputActionCatalog`
> - 平台实现层：`WindowsInput`
>
> 本章目标：弄清楚“一个按键或鼠标动作”是怎样进入引擎、怎样被分发、怎样变成 action、怎样被编辑器和玩法系统消费的。
>
> 本章会反复使用三个例子：
> 1. 编辑器里拖动视口时，`EditorCamera` 为什么会跟着移动或缩放。
> 2. Sandbox 里点击 UI 按钮时，为什么按钮要在鼠标释放时才真正触发。
> 3. 横板战斗和 VN 里，为什么有些输入看 action，有些输入看原始按键。

## 3.1 这一层在架构中的位置

```text
应用层
    Editor / Sandbox
        ↓
核心平台层
    Event / EventBus / Application / Layer
        ↓
引擎服务层
    Input / InputBindingService / InputActionCatalog
        ↓
平台实现层
    WindowsInput / GLFW
        ↓
第三方库
    GLFW / ImGui
```

这一章很适合作为“Core 层”的下一章，因为它正好把上一章讲的主循环真正填上内容：

- `Application::Run()` 负责调用 `glfwPollEvents()` 和 `FlushEventQueue()`
- `WindowsWindow` 把 GLFW 回调翻译成引擎事件
- `EventBus` 把事件送给 Application、ImGuiLayer、Editor Layer、Runtime Layer
- `Input` 提供原始状态查询
- `InputBindingService` 把原始按键变成动作语义

换句话说：

```text
Event 解决“发生了什么”
Input 解决“现在按着什么”
InputBindingService 解决“这个输入代表什么动作”
```

## 3.3 先区分两条输入通路

Wheatear 里有两条不同但互相配合的输入通路。

### 通路一：事件通路

```text
GLFW 回调
    ↓
引擎 Event
    ↓
Application::OnEvent()
    ↓
EventBus::Queue()
    ↓
EventBus::Flush()
    ↓
Layer::OnEvent()
```

这一条更适合处理：

- 窗口关闭
- 窗口缩放
- 鼠标按下 / 释放
- 鼠标滚轮
- 键盘按下 / 释放
- ImGui 输入捕获

### 通路二：状态查询通路

```text
Input::IsKeyPressed()
Input::IsMouseButtonPressed()
Input::GetMouseDeltaX()
Input::GetMouseDeltaY()
InputBindingService::IsActionPressed()
InputBindingService::IsActionDown()
```

这一条更适合处理：

- 每帧都要问一次“当前是否按着”
- 角色移动
- 编辑器相机移动
- 视角拖拽
- 组合输入

### 为什么要分两条

因为“事件”和“状态”不是同一件事：

- 事件是离散的，发生一次就过去了
- 状态是连续的，按住就一直成立

比如：

```text
鼠标按下
    → 是一个事件

鼠标按着没放
    → 是一个状态
```

这也是为什么有些地方用：

```cpp
Input::IsMouseButtonPressed(WT_MOUSE_BUTTON_RIGHT)
```

有些地方用：

```cpp
InputBindingService::IsActionPressed("side.jump")
```

而按钮点击最终又要等到鼠标释放才确认。

## 3.4 `Event`：引擎自己的事件对象

### 3.4.1 `Event` 属于哪一层

`Event` 和 `EventBus` 属于 **核心平台层**。

它们不关心：

- 某个按钮是不是 VN 的按钮
- 某个输入是不是横板战斗的技能键
- 某个鼠标点击是不是要打开 Inspector

它们只负责把平台事件变成统一的引擎事件对象。

### 3.4.2 `EventType` 和 `EventCategory`

`EventType` 表示具体事件类型：

```cpp
WindowClose
WindowResize
KeyPressed
KeyReleased
KeyTyped
MouseButtonPressed
MouseButtonReleased
MouseMoved
MouseScrolled
```

`EventCategory` 表示分类：

```cpp
EventCategoryApplication
EventCategoryInput
EventCategoryKeyboard
EventCategoryMouse
EventCategoryMouseButton
```

这两个概念不是一回事：

```text
EventType
    具体是哪一个事件

EventCategory
    它属于窗口、键盘、鼠标还是输入
```

例如：

- `WindowResizeEvent` 属于 `EventCategoryApplication`
- `MouseMovedEvent` 属于 `EventCategoryMouse | EventCategoryInput`
- `MouseButtonPressedEvent` 属于 `EventCategoryMouse | EventCategoryInput`

### 3.4.3 为什么事件要带 `Clone()`

窗口回调里创建的事件通常是局部对象：

```cpp
MouseButtonPressedEvent event(button);
data.EventCallback(event);
```

但 `Application::OnEvent()` 会把它放进队列：

```cpp
m_EventBus.Queue(e);
```

所以事件必须能复制：

```cpp
virtual Scope<Event> Clone() const = 0;
```

各个具体事件通过宏生成自己的 `Clone()`，例如：

```cpp
return CreateScope<MouseButtonPressedEvent>(*this);
```

这样 EventBus 持有的是副本，不依赖 GLFW 回调栈上的临时变量。

### 3.4.4 `EventDispatcher` 的作用

`EventDispatcher` 是单个 Layer 或单个系统内部的小分发器。

典型写法：

```cpp
EventDispatcher dispatcher(event);
dispatcher.Dispatch<MouseScrolledEvent>(
    WT_BIND_EVENT_FN(EditorCamera::OnMouseScroll));
```

或者：

```cpp
dispatcher.Dispatch<KeyPressedEvent>(
    [this](KeyPressedEvent& e)
    {
        return OnKeyPressed(e);
    });
```

它解决的是：

```text
我已经收到一个 Event，但我还想在本对象内部按具体类型再分一下。
```

## 3.5 `WindowsWindow` 如何把 GLFW 事件翻译成引擎事件

### 3.5.1 平台实现层在这里做什么

`WindowsWindow` 属于 **平台实现层**。

它的职责是：

- 创建 GLFW 窗口
- 创建 OpenGL 上下文
- 注册 GLFW 回调
- 在回调里构造引擎事件
- 把事件交给 Application 的回调入口

### 3.5.2 事件翻译的典型路径

以鼠标按下为例：

```text
GLFW mouse callback
    ↓
MouseButtonPressedEvent
    ↓
WindowData::EventCallback
    ↓
Application::OnEvent
    ↓
EventBus::Queue
```

窗口调整大小也是同样流程：

```text
GLFW size callback
    ↓
WindowResizeEvent
    ↓
Application::OnEvent
    ↓
EventBus::Queue
```

### 3.5.3 具体例子：关闭窗口

当用户点窗口右上角关闭按钮时：

```text
GLFW_CLOSE
    ↓
WindowCloseEvent
    ↓
Application::OnEvent
    ↓
EventBus::Queue
    ↓
EventBus::Flush
    ↓
Application::OnWindowClose
    ↓
m_Running = false
```

这就是为什么应用能优雅退出，而不是让系统直接杀进程。

### 3.5.4 具体例子：鼠标移动

鼠标移动回调构造的是：

```cpp
MouseMovedEvent event(xPos, yPos);
```

然后进入 EventBus。

像 `EditorCamera` 这种系统会在 `OnEvent()` 里处理滚轮，而在 `OnUpdate()` 里读取鼠标位置和键盘状态。这个分工很典型。

## 3.6 `EventBus`：事件的集中调度器

### 3.6.1 `EventBus` 属于哪一层

`EventBus` 也属于 **核心平台层**。

它的任务不是“解释事件含义”，而是：

- 暂存事件
- 控制处理顺序
- 允许消费事件
- 允许订阅和退订
- 在帧内安全分发

### 3.6.2 订阅方式

`EventBus` 提供：

```cpp
Subscribe(EventType type, HandlerFn handler, int priority = 0)
SubscribeAll(HandlerFn handler, int priority = 0)
Subscribe<T>(Fn&& handler, int priority = 0)
```

其中：

- `Subscribe<T>()` 是类型安全包装
- `SubscribeAll()` 适合监听所有事件
- `priority` 决定谁先处理

### 3.6.3 优先级

源码里定义了几个常用优先级：

```cpp
Critical   = 10000
Application = 9000
UI          = 8000
Overlay     = 6000
Layer       = 1000
Low         = -1000
```

它表达的是：

```text
Application 先处理最关键窗口事件
UI / Overlay 再决定是否拦截输入
普通 Layer 最后处理剩余事件
```

### 3.6.4 `Queue()` 和 `Flush()` 的意义

`Application::OnEvent()` 不直接执行逻辑，而是：

```cpp
m_EventBus.Queue(e);
```

EventBus 内部存的是：

```cpp
std::deque<Scope<Event>> m_QueuedEvents;
```

真正处理发生在：

```cpp
Flush()
```

这能避免几个问题：

- GLFW 回调里的局部对象生命周期太短
- 事件处理顺序不稳定
- 事件处理时又触发新的事件，导致调用栈太乱

### 3.6.5 `Consume` 的意义

当某个处理器返回 `EventResult::Consume`，或者调用：

```cpp
event.Consume();
```

后面的处理器就不会再收到这个事件。

这在 UI 场景非常重要。

### 3.6.6 具体例子：ImGui 为什么能截获输入

`ImGuiLayer::OnEvent()` 里会根据：

```cpp
io.WantCaptureMouse
io.WantCaptureKeyboard
```

标记事件是否已处理。

这样当你正在输入文本框时：

```text
鼠标点击
    → ImGui 先接住
    → event.Handled = true
    → 后面的 EditorLayer 不再响应
```

结果就是：

- 你点的是 Inspector 文本框，而不是把场景对象选中
- 你打字是在输入框里，而不是触发场景快捷键

这就是“事件消费”最常见的实际效果。

### 3.6.7 具体例子：WindowResizeEvent

`Application` 对窗口大小事件有自己的处理器：

```cpp
bool Application::OnWindowResize(WindowResizeEvent& e)
```

它会：

- 检查是否最小化
- 切换 `m_Minimized`
- 调用 `Renderer::OnWindowResize()`

这说明有些事件确实属于 Application 层自己处理，而不是下发给玩法层。

## 3.7 `Input`：原始状态查询层

### 3.7.1 `Input` 属于哪一层

`Input` 属于 **引擎服务层**。

它比 Event 更靠近“当前帧的状态”。

### 3.7.2 `Input` 的核心接口

```cpp
Input::IsKeyPressed(int keycode)
Input::IsMouseButtonPressed(int button)
Input::GetMousePosition()
Input::GetMouseX()
Input::GetMouseY()
Input::GetMouseDeltaX()
Input::GetMouseDeltaY()
Input::SetMouseInputBounds(...)
Input::ClearMouseInputBounds()
Input::EndFrame()
Input::SetCursorMode(CursorMode::Normal)
```

### 3.7.3 `WindowsInput.cpp` 实际做了什么

平台实现很直接：

```cpp
glfwGetKey(window, keycode)
glfwGetMouseButton(window, button)
glfwGetCursorPos(window, &xpos, &ypos)
```

它还维护了两个本地状态：

```text
s_LastMousePosition
s_MouseInputBounds
```

### 3.7.4 为什么要有 Mouse Input Bounds

`Input::IsMouseButtonPressed()` 在查询鼠标前会先检查是否处于输入边界内。

这在编辑器和运行时都很重要。

具体例子：

- 编辑器里只想让视口区域接收点击
- Sandbox 里只想让游戏视口接收鼠标，不想点到窗口外还算作攻击输入

所以系统可以先设置：

```cpp
Input::SetMouseInputBounds(minX, minY, maxX, maxY);
```

离开时再：

```cpp
Input::ClearMouseInputBounds();
```

### 3.7.5 为什么 `EndFrame()` 必须每帧调用

`Input::EndFrame()` 会记录当前鼠标位置：

```cpp
s_LastMousePosition = GetMousePosition();
```

这样下一帧才能计算：

```cpp
GetMouseDeltaX()
GetMouseDeltaY()
```

这对于 `EditorCamera` 特别重要，因为视角旋转和拖拽都依赖鼠标增量。

## 3.8 `InputBindingService`: 把物理按键变成 action

### 3.8.1 为什么要有这层

如果游戏逻辑直接依赖：

```cpp
Input::IsKeyPressed(WT_KEY_SPACE)
```

那以后你想改键位、支持手柄、支持鼠标、支持快捷键重映射，会非常麻烦。

所以 Wheatear 额外加了一层：

```cpp
InputBindingService::IsActionPressed("side.jump")
InputBindingService::IsActionDown("vn.advance")
InputBindingService::IsActionPressed("game.pause")
```

这层属于 **引擎服务层**。

### 3.8.2 action 的语义

action 不代表某一个键，而代表一个游戏动作：

```text
side.jump
side.basic
side.dash
vn.advance
vn.auto
game.pause
move.left
move.right
move.up
move.down
```

这让游戏逻辑可以只关心“动作”，而不关心“按的是 A 还是左方向键”。

### 3.8.3 绑定编码

`InputBindingService` 用一个简单编码表达物理绑定：

- 正数：键盘键码
- 负数：鼠标键码

因此同一个 action 可以绑定：

- 键盘
- 鼠标
- 多个绑定同时生效

### 3.8.4 `IsActionDown`、`IsActionPressed`、`IsActionReleased`

这三个函数很关键：

```cpp
IsActionDown(actionId)
IsActionPressed(actionId)
IsActionReleased(actionId)
```

区别是：

- `Down`：只要按着就一直为真
- `Pressed`：只在从松开到按下的那一帧为真
- `Released`：只在从按下到松开的那一帧为真

### 3.8.5 `EndFrame()` 是它能工作的关键

`InputBindingService::EndFrame()` 会：

- 重新采样物理状态
- 更新 `Prev`
- 清掉当前帧查询标记
- 清掉注入标记

这就是它能正确判断“刚按下”和“刚松开”的原因。

如果没有 `EndFrame()`，边沿判断会混乱。

### 3.8.6 `InjectActionPress()` 的意义

这一点很有意思：

```cpp
InputBindingService::InjectActionPress("side.basic");
```

它不是物理按键，而是程序注入一个 action 的“按下”状态。

这个设计在玩法层很有用，因为：

- AI 可以模拟输入
- UI 或脚本可以模拟技能触发
- 游戏逻辑可以把命令统一路由到同一套输入路径

比如横板战斗里，某些命令字符串会被转成 action 注入，这样后面的玩家输入处理逻辑不用再写一套分支。

### 3.8.7 `GetKeys()` 的优先级

`GetKeys(actionId)` 会按这个顺序找绑定：

1. 用户设置里的重映射
2. `InputActionCatalog` 里的数据驱动默认值
3. `UserSettings::Defaults()` 里的 C++ 默认
4. 没找到则返回空

这表示：

```text
用户设置 > 数据表默认 > C++ 传统默认
```

### 3.8.8 为什么要有 `InputActionCatalog`

`InputActionCatalog` 负责从 YAML 文件加载动作定义。

它的核心目标是：

- 让动作定义可以在项目里改，不必改 C++
- 让编辑器能看到动作名、默认键位、是否禁用
- 让新动作可以先在数据表里出现，再由代码消费

默认数据路径是：

```text
assets/input/action_bindings.yaml
```

并且采用：

```text
项目根优先，Engine 根回退
```

### 3.8.9 `InputActionCatalog` 的数据 schema

它要求：

```text
schema: wheatear.input.actions.v1
```

YAML 里每个动作大致包含：

```text
id
label
defaults
disabled
```

你可以把它理解成：

```text
动作清单 = 动作 id + 显示名 + 默认按键 + 是否禁用
```

### 3.8.10 编辑器里怎么用这层

`InputBindingsPanel` 会用：

```cpp
InputBindingService::GetBindingLabel(actionId)
InputBindingService::GetKeys(actionId)
InputBindingService::SetKeys(actionId, keys)
```

所以编辑器能直接显示：

```text
vn.advance     Space
side.jump      J / Mouse Right
game.pause     Esc
```

这就是“数据驱动输入”的落地效果。

## 3.9 具体例子一：编辑器相机为什么会动

`EditorCamera` 是这一章最好的消费者例子之一，因为它直接把 raw input 用得很典型。

### 3.9.1 所属层级

`EditorCamera` 本身不属于 Input 层，它是 **编辑器侧的消费方**，但它依赖的是 Core + Input 服务。

### 3.9.2 `EditorCamera::OnUpdate()`

它会做这些事：

```cpp
bool rightMouseHeld = Input::IsMouseButtonPressed(WT_MOUSE_BUTTON_RIGHT);
```

如果右键按住，Orbit 模式切 Fly 模式。

如果松开右键，则回到 Orbit 模式。

然后在 Fly 模式里读取：

```cpp
Input::GetMouseDeltaX()
Input::GetMouseDeltaY()
Input::IsKeyPressed(WT_KEY_W)
Input::IsKeyPressed(WT_KEY_A)
Input::IsKeyPressed(WT_KEY_S)
Input::IsKeyPressed(WT_KEY_D)
Input::IsKeyPressed(WT_KEY_Q)
Input::IsKeyPressed(WT_KEY_E)
```

这说明编辑器相机更适合“原始状态输入”而不是 action 输入，因为它需要非常直接的 WASD 和鼠标控制。

### 3.9.3 `EditorCamera::OnEvent()`

它还会处理滚轮事件：

```cpp
dispatcher.Dispatch<MouseScrolledEvent>(
    WT_BIND_EVENT_FN(EditorCamera::OnMouseScroll));
```

在 Orbit 模式下滚轮是缩放，在 Fly 模式下滚轮改速度。

这个例子很好地说明了：

```text
MouseScroll = 事件
WASD / 右键状态 = 持续输入
```

两个通路同时存在，但用途不同。

### 3.9.4 结果感

当你在编辑器里：

- 按住右键拖动画面
- 滚轮缩放视角
- 用 WASD 飞行

背后不是“相机自己魔法般移动了”，而是：

```text
Window event
→ EventBus
→ EditorCamera::OnEvent

and

Input polling
→ EditorCamera::OnUpdate
```

两条通路共同工作。

## 3.10 具体例子二：VN 和横板战斗如何消费 action

### 3.10.1 VN 使用 action 的方式

`VisualNovelInputService::Sample()` 会采样：

```cpp
Input::IsMouseButtonPressed(WT_MOUSE_BUTTON_LEFT)
InputBindingService::IsActionDown("vn.advance")
InputBindingService::IsActionDown("vn.auto")
InputBindingService::IsActionDown("vn.history")
InputBindingService::IsActionDown("vn.save")
InputBindingService::IsActionDown("vn.load")
```

选择项则直接读数字键：

```cpp
Input::IsKeyPressed(WT_KEY_1 + i)
```

VN 的意思很清楚：

```text
鼠标左键可以推进对话
vn.advance 是语义化推进键
数字键用于选项
```

这说明 action 和 raw input 可以混用。

### 3.10.2 横板战斗怎么用 action

横板战斗更典型。

`SideCombatSystem` 里会根据命令注入 action：

```cpp
InputBindingService::InjectActionPress("side.basic");
InputBindingService::InjectActionPress("side.launcher");
InputBindingService::InjectActionPress("side.magic");
InputBindingService::InjectActionPress("side.support");
InputBindingService::InjectActionPress("side.dash");
InputBindingService::InjectActionPress("side.break_limit");
```

同时玩家输入也会直接读 action：

```cpp
InputBindingService::IsActionDown("move.left")
InputBindingService::IsActionDown("move.right")
InputBindingService::IsActionPressed("side.jump")
InputBindingService::IsActionPressed("game.pause")
```

这意味着横板战斗的输入层不是“键盘键位表”，而是：

```text
动作语义
    ↓
物理键或脚本命令
    ↓
InputBindingService
    ↓
战斗系统
```

### 3.10.3 为什么要注入 action

这样做可以把以下来源统一起来：

- 玩家按键
- UI 触发
- 剧情命令
- AI 或脚本模拟

最终都变成同一套：

```cpp
InputBindingService::IsActionPressed(...)
```

这能显著减少玩法代码分支数量。

## 3.11 具体例子三：UI 按钮为什么在释放时触发

### 3.11.1 所属层级

`UIInputSystem` 属于 **UI 运行时服务**，但它依赖 Input、Event、CommandBus 和 Scene。

### 3.11.2 鼠标按下只做状态记录

```cpp
void UIInputSystem::OnMousePressed(Scene* scene)
{
    s_MouseWasPressed = true;
    s_DragStartResolved = false;
}
```

### 3.11.3 鼠标释放才决定是不是点击

```cpp
void UIInputSystem::OnMouseReleased(Scene* scene)
{
    ...
    if (clickedButton != entt::null)
        FireOnClick(scene, clickedButton);
}
```

为什么不在按下时就触发？

因为按钮点击通常要区分：

- 按下
- 拖动
- 松开

这样才能支持：

- 滑动条
- 面板拖拽
- skill tree 拖拽
- 正常按钮点击

### 3.11.4 为什么这和 InputBounds 有关系

运行时或编辑器在需要时会限制鼠标输入范围。

这样可以避免：

```text
鼠标点到了窗口外
    → 还被当成游戏视口的点击
```

这也是为什么输入层和 UI 层必须配合，而不是互相孤立。

## 3.12 具体例子四：Sandbox 里一个按钮如何切场景

现在把整条链路串起来。

### 情况

玩家点击一个 UI 按钮，按钮的 `OnClickFunction` 是：

```text
scene:assets/scenes/Hub.wt
```

### 链路

```text
鼠标释放
    ↓
UIInputSystem::OnMouseReleased()
    ↓
FireOnClick()
    ↓
CommandBus::Execute(scene, "scene:assets/scenes/Hub.wt")
    ↓
SceneTransitionService::RequestLoadScene(...)
    ↓
RuntimeSceneLayer::ConsumeSceneTransitionRequests()
    ↓
RuntimeSceneLayer::LoadScene(...)
    ↓
SceneSerializer::DeserializeYaml(...)
```

### 这一链路说明了什么

它说明事件和输入不是孤立的底层细节，而是游戏流程的开头。

一个点击从最底层开始，最后能变成：

```text
加载新场景
切换游戏流程
开始新一轮运行时系统
```

这就是教材里一定要结合“实际结果”讲的原因。

## 3.13 本章的几个常见误区

### 误区一：把 Event 和 Input 视为同一层

不对。

```text
Event
    负责“发生过什么”

Input
    负责“当前按着什么”

InputBindingService
    负责“这个输入意味着什么动作”
```

### 误区二：所有输入都应该走 action

也不对。

像 `EditorCamera` 这种工具类，直接用原始键鼠更自然。

### 误区三：所有按钮点击都应该在按下时触发

也不对。

对于可拖拽 UI，松开时再确认点击更合理。

### 误区四：事件和状态只能选一种

也不对。

Wheatear 同时用了：

- 事件分发
- 状态查询
- action 语义

这是为了适应不同层的需求。

## 3.14 这套设计的优点

### 优点一：编辑器和游戏都能共享输入基础设施

编辑器工具、Sandbox、玩法模块都能读取同一套 `Input` 和 `InputBindingService`。

### 优点二：输入语义统一

```text
vn.advance
side.jump
game.pause
move.left
```

这些名字比“Space、J、Z、鼠标左键”更稳定。

### 优点三：可以数据化改键

`InputActionCatalog` 和 `UserSettings` 让键位不再写死在 C++ 里。

### 优点四：可以把命令注入到同一套输入路径

这对战斗、剧情、AI、UI 都很友好。

## 3.15 这套设计的代价

### 代价一：输入状态管理更复杂

你要同时维护：

- 物理键状态
- action 状态
- 当前帧 / 上一帧
- 鼠标边界
- 注入状态

### 代价二：action 多了以后命名要管理

如果 action 命名混乱，比如：

```text
Jump
jump
side_jump
side.jump
```

那输入系统会很难维护。

### 代价三：事件消费顺序很重要

如果事件订阅顺序乱了，UI 和编辑器就可能互相抢输入。

## 3.16 面试时怎么讲这一章

### 问题：你们的输入系统分几层？

可以回答：

```text
第一层是 GLFW 和 Window 回调，把原始键鼠事件转换成引擎 Event。
第二层是 EventBus，负责统一排队、按优先级分发和消费。
第三层是 Input，负责原始键鼠状态查询和鼠标增量。
第四层是 InputBindingService，把物理按键映射成 action 语义。
玩法层和编辑器层都只消费这两层之上的结果。
```

### 问题：为什么要有 action binding？

```text
因为游戏逻辑不应该直接依赖某一个具体按键。
action binding 让同一个动作可以绑定键盘、鼠标甚至命令注入，
以后重映射、存档、编辑器面板和 AI 输入都更容易处理。
```

### 问题：为什么 UI 按钮不在鼠标按下时就触发？

```text
因为 UI 需要支持拖拽、滑动和 hover 状态。
按下只表示开始交互，释放时才确认是否是一次点击。
这样可以兼容面板拖动、滑条拖动和普通按钮点击。
```

### 问题：EditorCamera 为什么不用 action？

```text
因为相机控制更接近原始操作，右键、鼠标位移、WASD
这些直接状态最自然，没必要再包一层语义 action。
```

## 3.18 本章小结

这一章的核心结论是：

```text
Event 解决“发生了什么”
Input 解决“现在按着什么”
InputBindingService 解决“这代表什么动作”
InputActionCatalog 解决“动作默认怎么定义、怎么保存、怎么显示”
```

把它们合起来后，Wheatear 的输入链路就是：

```text
GLFW
    → Window Event
    → Application
    → EventBus
    → Layer / Editor / UI
    → Input 状态查询
    → InputBindingService action
    → 玩法逻辑
```
