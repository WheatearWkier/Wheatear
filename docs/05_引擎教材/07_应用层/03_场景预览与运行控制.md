# 第 7 编 03：场景预览与运行控制

> 本章所属层级：**应用层**
>
> 本章目标：理解编辑器里的“场景预览”是怎么工作的，Play / Pause / Step / Stop 是怎么切换的，编辑态和运行态为什么要分开，以及命令总线、场景切换和存档状态如何在这个层级里闭环。

如果说上一章讲的是“内容怎么被看见、被打开、被改写”，  
那这一章讲的就是：

```text
场景是怎么被“跑起来”的？
编辑器里的预览为什么不是直接改原场景？
为什么按下 Play 以后，画面会进入另一套生命周期？
暂停、单步、Stop、切场景、读档，这些动作怎么串在一起？
```

这章很适合拿来讲面试。  
因为它不是单纯的 UI 工具，而是把下面几件事绑在一起了：

- 编辑器预览窗口
- 场景生命周期
- 运行态副本
- 输入隔离
- 命令转发
- 场景切换
- 存档上下文

Wheatear 这里的思路很明确：

```text
Editor 负责“看”和“改”
Sandbox 负责“跑”
Application 负责“把这些宿主挂起来”
Scene / Runtime Services 负责真正的游戏状态
```

所以，“场景预览与运行控制”并不是渲染层的章节，  
它是应用层里最像“宿主逻辑”的那部分。

## 7.2 这一层在架构中的位置

```text
应用层
    Editor / Sandbox
        ↓
核心平台层
    Application / Window / EventBus / LayerStack / Log / Timestep
        ↓
引擎服务层
    Renderer / Input / Audio / UI / AssetPath / Physics
        ↓
Scene ECS 层
    Scene / Entity / Components / Systems
```

这一层的职责，不是再造一套引擎，而是把引擎能力组织成两个很具体的宿主：

- `WheatearEditor`：内容制作、调试、预览、打包
- `WheatearSandbox`：独立运行、加载内容、执行玩法

它们都在用同一套核心，但生命周期并不一样。

这也是为什么本章要把“预览”和“运行控制”放在一起讲。  
因为编辑器里的预览不是一个普通面板，它其实是一条“小型运行链路”：

```text
预览窗口
  -> 场景副本
  -> 帧更新
  -> 输入处理
  -> 命令转发
  -> 场景切换 / 存档 / 结束
```

## 7.3 场景预览窗口是怎么搭起来的

编辑器里的场景预览，主要在 `EditorLayerBase::UI_Viewport()` 和 `EditorLayerBase::OnUpdate()` 里完成。

你可以把它理解成两层：

1. `OnUpdate()` 负责把场景真正渲染到 framebuffer
2. `UI_Viewport()` 负责把 framebuffer 显示进 ImGui，并处理鼠标、拖拽、拾取和上下文菜单

### 7.3.1 预览窗口不是直接画在 ImGui 上

编辑器不会把 Scene 直接“画进窗口控件”，而是先把场景渲染到自己的 framebuffer：

- `m_Framebuffer`：主预览 framebuffer
- `m_UIReferenceFramebuffer`：UI 画布编辑时的参考 framebuffer

`m_Framebuffer` 的附件配置也很有代表性：

- `RGBA8`：显示用颜色缓冲
- `RGBA16F`：高动态范围或中间光照结果
- `RED_INTEGER`：实体 ID 拾取
- `Depth`：深度测试

这说明编辑器预览不是单纯看图，它还承担了：

- 实体选中
- UI 命中测试
- 深度正确性
- 运行态视觉验证

### 7.3.2 预览窗口如何显示画面

在 `UI_Viewport()` 里，framebuffer 的颜色附件会被当成纹理交给 ImGui：

```text
Framebuffer color attachment
  -> ImGui::Image()
  -> Viewport 面板显示
```

这里还做了一个很小但很关键的转换：  
OpenGL 和 ImGui 的 UV 方向是反的，所以显示时要把上下翻转。

### 7.3.3 为什么要区分 viewport focused / hovered

编辑器会记录：

- `m_ViewportFocused`
- `m_ViewportHovered`
- `m_ViewportImageHovered`

这几个状态决定了：

- 键鼠事件是不是该给编辑器相机
- 是否允许在视口里拖拽选择
- 运行态输入要不要落到 UIInputSystem

换句话说，预览窗口不是“显示一下就完了”，  
它还决定了这一帧的输入焦点属于谁。

### 7.3.4 为什么要 `BlockEvents`

`UI_Viewport()` 里会调用：

```text
ImGuiLayer::BlockEvents(...)
```

意思不是“把事件删掉”，而是告诉 ImGui：

- 当编辑器不在 Play 模式，且视口没被激活时，不要让事件穿透到场景里
- 当视口处于可操作状态时，输入才应该进入编辑器相机或运行态输入系统

这一步很重要。  
因为如果不做，编辑器窗口、菜单栏、资源浏览器、视口会互相抢输入，体验会很乱。

### 7.3.5 UI 画布预览是怎么补上的

在 Edit 模式下，如果当前正在编辑 UI Canvas，编辑器还会额外渲染一个 `m_UIReferenceFramebuffer`。

这条链路大概是：

```text
主场景相机
  -> 按参考分辨率重置 viewport
  -> 渲染到 UI reference framebuffer
  -> 再恢复主 viewport
```

这样做的目的很直接：  
UI 不是只看“当前屏幕分辨率”的，它往往需要一个稳定的参考画布尺寸来做排版、锚点和对齐。

### 7.3.6 预览窗口里的拾取是怎么来的

编辑器会从 `RED_INTEGER` 附件读回鼠标位置对应的实体 ID：

```text
鼠标屏幕坐标
  -> 视口局部坐标
  -> framebuffer ReadPixel(2, x, y)
  -> Entity ID
```

这就是为什么你在视口里点一下就能选中实体。  
它不是“扫碰撞体”，而是典型的 ID 缓冲拾取。

## 7.4 编辑态和运行态是两套世界

这是本章最核心的概念。

Wheatear 编辑器不是一边改场景，一边让同一个 Scene 对象跑起来。  
它是明确分成两套：

- `m_EditorScene`：编辑态场景
- `m_ActiveScene`：当前正在使用的场景

再加一个状态机：

```text
SceneState::Edit
SceneState::Play
```

### 7.4.1 为什么不能直接在原场景上 Play

如果你直接拿编辑态场景去跑，问题会很多：

- 运行时生成的临时实体会污染编辑态
- 脚本、碰撞、动画、物理状态会把编辑器里的数据改坏
- Stop 以后很难干净地回到原来状态

所以编辑器按下 Play 时，做的不是“继续操作原对象”，而是：

```text
Scene::Copy(m_EditorScene)
```

也就是把编辑场景复制成运行副本。

### 7.4.2 `TransitionToEditScene()`

`TransitionToEditScene()` 负责进入编辑态。  
它一般在启动时调用，也可以在编辑器打开新场景后调用。

它会做这些事：

- 如果之前在 Play，先 `OnRuntimeStop()`
- 清空选中状态
- 清理鼠标边界
- 把 `m_SceneState` 切到 `Edit`
- 设置 `m_EditorScene` 和 `m_ActiveScene`
- 记录 `m_EditorScenePath`
- 刷新视口尺寸
- 调 `OnEditorStart()`
- 同步各个面板
- 清掉命令历史

这说明编辑态不是“没有运行”，而是一个有明确生命周期的工作模式。

### 7.4.3 `TransitionToPlay()`

按下 Play 时，编辑器会切进运行副本。

这条链路可以概括成：

```text
Edit Scene
  -> 清输入 / 清命令 / 清转场请求
  -> Scene::Copy(m_EditorScene)
  -> 记录当前场景路径
  -> GameProgress::SetSceneTransitionContext(...)
  -> EditorScene OnEditorStop()
  -> ActiveScene OnRuntimeStart()
```

里面有几个关键点。

#### 1. 先清状态

Play 之前会清掉：

- `UIInputSystem`
- `Input::ClearMouseInputBounds()`
- `CommandBus::ClearQueuedCommands()`
- `SceneTransitionService::DrainRequests()`
- `WAO::ActionDebugHistory`

原因很简单：  
你不希望上一次编辑/运行留下的脏状态跑到新一轮 Play 里。

#### 2. 用复制件当运行态

`Scene::Copy(m_EditorScene)` 是整个 Play Mode 的核心。

编辑态负责保存真实工程内容；  
运行态负责承接脚本、输入、物理、动画、战斗和 UI 的临时变化。

#### 3. 记录场景上下文

`GameProgress::SetSceneTransitionContext(previousPlayScenePath, m_PlayScenePath)` 会把当前场景路径写入进度系统。

这个动作是给后面的：

- 新游戏
- 读档
- 场景跳转

准备上下文的。

### 7.4.4 `TransitionToStop()`

Stop 的目标不是“把运行副本删掉就完事”，而是把编辑器完整地回收回来。

它会：

- 清掉自动读档槽
- 重置 UI 输入
- 清鼠标边界
- 清命令总线
- 清场景切换请求
- 调 `OnRuntimeStop()`
- `Renderer2D::EndScene()`
- 清掉选中
- 把 `m_ActiveScene` 切回 `m_EditorScene`
- 调 `OnEditorStart()`
- 取消暂停 / 单步状态

你可以把它理解成：

```text
Play 状态的所有临时副作用，都应该在 Stop 时被关掉。
```

这就是编辑器能稳定反复 Play / Stop 的原因。

## 7.5 Pause、单步和输入边界

这个部分很适合讲给新手听。  
因为它能把“运行了”和“看见了”分开。

### 7.5.1 暂停并不等于停止渲染

`TogglePlayPause()` 只切换：

- `m_PlayPaused`

`StepPlayFrame()` 则会：

- 先把 `m_PlayPaused = true`
- 再设 `m_StepOnce = true`

然后在 `OnUpdate()` 里：

```text
如果没暂停，或者需要单步，就执行一次 OnUpdateRuntime()
```

也就是说：

- 暂停后，场景仍然会渲染
- 只是运行时逻辑不再前进

这和很多引擎的 Play/Pause 行为是一致的。

### 7.5.2 为什么要有单步

单步的价值在于调试。

比如你怀疑：

- 某个命令是不是在这一帧触发的
- 某个动画帧是不是过早切换了
- 某个碰撞回调是不是重复执行了

这时你可以：

1. 进入 Play
2. 按 Pause
3. 按 Step 一帧
4. 看状态只前进一步

这比不断重跑方便太多。

### 7.5.3 为什么要限制鼠标输入边界

在 Play 模式下，编辑器会用 `Input::SetMouseInputBounds(...)` 把鼠标输入限定在视口区域。

原因是：

- 你希望游戏运行时的点击只落在预览画面里
- 你不希望菜单栏、资源面板、工具栏抢走游戏输入

所以 Play 模式下的输入处理是分区的：

- 视口里：交给运行态
- 视口外：交给编辑器 UI

### 7.5.4 Play 模式下怎么点实体

在运行中，`Ctrl + 左键` 仍然可以拾取当前实体。  
这很像一个很实用的“运行中检查”功能：  
你可以不停止游戏，就看看某个运行态实体的属性。

这类小细节，很适合面试时当例子讲。

## 7.6 运行时命令、场景切换和存档

编辑器的 Play Mode 不只是“自己跑一遍场景”，它还要接住运行时发回来的命令。

### 7.6.1 运行时命令从哪来

在 Play 模式下，编辑器会收两类命令：

- `DrainGameplayRuntimeCommands(...)`
- `CommandBus::DrainRuntimeCommands()`

这意味着命令既可能来自：

- 玩法层脚本
- UI 按钮
- 运行时事件
- 命令总线本身

### 7.6.2 为什么要统一收口

如果命令散落在各个系统里，最终会变成：

- 有的命令直接切场景
- 有的命令先改 GameProgress
- 有的命令在脚本里直接 load
- 有的命令只在某个 UI 层里生效

那就很难维护。

所以编辑器和沙盒都把命令收口到宿主层处理。  
这和上一章讲的 `CommandBus` 是连着的。

### 7.6.3 `ConsumePlayModeSceneTransitionRequests()`

`SceneTransitionService` 会积累一批场景切换请求。  
宿主层会调用 `DrainRequests()`，然后只取最后一个。

这表示：

```text
同一帧如果有多个场景请求，最后一个生效。
```

这是一个很务实的设计。  
因为很多时候剧情脚本、按钮和系统命令会在同一帧里先后发请求，宿主层必须给它一个明确的裁决规则。

### 7.6.4 `ExecutePlayModeSceneTransitionRequest()`

场景切换请求一般有三种：

- `LoadScene`
- `NewGame`
- `LoadGame`

它们对应的行为也不同。

#### LoadScene

直接加载指定场景。

#### NewGame

先 `GameProgress::ResetForNewGame()`，再加载场景。

#### LoadGame

先检查当前场景是否允许读取，再：

- 记录自动读档槽
- `GameProgress::LoadSlot(request.Slot)`
- 加载目标场景

这就把“场景跳转”和“存档上下文”串起来了。

### 7.6.5 为什么要记住场景上下文

`GameProgress::SetSceneTransitionContext(previousScenePath, sceneRequest)` /  
`GameProgress::SetSceneTransitionContext(previousPlayScenePath, m_PlayScenePath)` 这类调用很关键。

因为存档不是只有“数值状态”，还要知道：

- 现在在哪个场景
- 上一个场景是哪一个
- 当前这次跳转是新游戏、读档还是普通切换

这样一来，读档以后才能正确回到对应的场景和状态。

## 7.7 Sandbox 里的独立运行控制

编辑器里的 Play Mode 和沙盒里的独立运行，看起来都在“跑场景”，但本质不一样。

### 7.7.1 沙盒不是编辑器的简化版

`WheatearSandbox` 的目标不是给开发者看 UI，  
而是把项目内容作为一个独立程序跑起来。

它的核心层是 `RuntimeSceneLayer`。

### 7.7.2 `RuntimeSceneLayer::OnAttach()`

启动时，沙盒会做这些事：

- 清 `ActionDebugHistory`
- 读取 `RuntimePlayerConfig`
- 找 `player.config`
- 确定启动场景
- 解析命令行参数里的显式场景
- `LoadScene(requestedPath)`

这意味着沙盒不是靠“当前目录碰巧对了”，而是有明确的启动顺序。

### 7.7.3 `LoadScene()` 的关键步骤

沙盒加载场景时，也会先清状态：

- `UIInputSystem::Reset()`
- `CommandBus::ClearQueuedCommands()`
- 如果当前场景还在跑，先 `OnRuntimeStop()`

然后再：

- 解析路径
- 反序列化场景
- `GameProgress::SetSceneTransitionContext(...)`
- `ApplyPendingSceneAutoLoadSlot()`
- `OnRuntimeStart()`

和编辑器 Play Mode 一样，沙盒也严格遵守“先停旧的，再开新的”。

### 7.7.4 为什么沙盒的 viewport 更简单

沙盒没有编辑器那套 ImGui 预览窗口。  
它的 viewport 就是整个窗口：

```text
Window size
  -> RenderCommand::SetViewport()
  -> Scene::OnUpdateRuntime()
```

所以沙盒更纯粹：

- 没有编辑器面板抢输入
- 没有视口与工具栏的焦点切换
- 没有 Play/Stop 的复制与回收

它只负责把游戏跑起来。

### 7.7.5 运行时命令怎么被沙盒接住

`RuntimeSceneLayer::ConsumeRuntimeSceneCommands()` 会处理：

- `DrainGameplayRuntimeCommands(...)`
- `CommandBus::DrainRuntimeCommands()`
- `SceneTransitionService::DrainRequests()`

然后按顺序执行：

- 普通按钮命令
- `quit`
- 场景切换
- 新游戏
- 读档

这说明沙盒不是“画完就结束”，它还是一个完整的运行宿主。

## 7.8 一个完整例子：从编辑到运行

### 例子 1：编辑器里按 Play、Pause、Step、Stop

```text
打开场景
  -> 编辑态显示在 Viewport
  -> 按 Play
  -> TransitionToPlay()
  -> Scene::Copy(m_EditorScene)
  -> OnRuntimeStart()
  -> 运行态开始
  -> 按 F6 Pause
  -> 只停止 OnUpdateRuntime()
  -> 画面继续显示
  -> 按 F7 Step
  -> 精确推进一帧
  -> 按 Stop
  -> OnRuntimeStop()
  -> 回到 m_EditorScene
  -> OnEditorStart()
```

这个例子能很好地说明：

- 编辑态和运行态是分开的
- 暂停只停逻辑，不停渲染
- Stop 会把宿主收回编辑态

### 例子 2：剧情或按钮触发场景切换

```text
UI 按钮 / 剧情脚本
  -> CommandBus / SceneTransitionService
  -> 宿主层 DrainRequests()
  -> NewGame / LoadGame / LoadScene
  -> GameProgress 更新上下文
  -> LoadPlayScene() 或 RuntimeSceneLayer::LoadScene()
  -> 新场景 OnRuntimeStart()
```

这个例子能说明另一个关键点：

```text
场景切换不是脚本自己直接换掉的，
而是先发请求，再由宿主决定何时真正执行。
```

这就是为什么命令总线和场景切换服务必须在这一层被认真处理。

### 7.6.6 `TransitionToPlay()` / `TransitionToStop()` 到底切了什么

编辑器的 Play / Stop 不是“按钮换个图标”那么简单，而是真正切换两套场景状态。

`TransitionToPlay()` 做的事情可以直接记成一条链：

1. 清实体选中状态
2. 清自动读档槽和 WAO 调试历史
3. 重置 `UIInputSystem`
4. 清鼠标输入边界
5. 清命令队列和场景切换请求
6. 用 `Scene::Copy(m_EditorScene)` 生成运行副本
7. 记录 `GameProgress` 的场景上下文
8. `m_EditorScene->OnEditorStop()`
9. `m_ActiveScene->OnRuntimeStart()`

这一步的核心思想就是：**编辑态原件不动，运行态副本单独跑**。

`TransitionToStop()` 则是反方向收口：

- 清自动读档槽
- 重置输入系统
- 清鼠标输入边界
- 清命令队列和场景切换请求
- `OnRuntimeStop()`
- `Renderer2D::EndScene()`
- 切回 `m_EditorScene`
- `OnEditorStart()`

所以 Stop 的意义不是“暂停一下”，而是把运行态这一套完整关闭掉，
再把编辑态原件接回来。

### 7.6.7 Pause、Step 和运行时更新的关系

这一块最容易写错，但源码其实很清楚。

按钮和热键最终改的是两个状态：

- `m_PlayPaused`
- `m_StepOnce`

`TogglePlayPause()` 只是翻转暂停状态。  
`StepPlayFrame()` 则是：

- 先置成暂停
- 再把 `m_StepOnce = true`

真正决定有没有推进逻辑的是更新分支：

```text
if (!m_PlayPaused || m_StepOnce)
    m_ActiveScene->OnUpdateRuntime(ts);
    m_StepOnce = false;
```

这意味着：

- 暂停时，场景依然可以渲染
- 只是 runtime 逻辑不继续推进
- 单步会让逻辑精确跑一帧，然后立刻回到暂停

这也是为什么 F6 / F7 在调试时很好用：  
你可以一边看画面，一边让逻辑一帧一帧往前走。

### 7.6.8 `SceneTransitionRequest` 为什么要统一收口

在 Play 模式里，剧情、按钮、存档、关卡跳转都可能发出“我要换场景”的请求。  
Wheatear 没有把这些请求散到各个系统里，而是统一扔进 `SceneTransitionService`。

宿主层消费时是这样做的：

- `DrainGameplayRuntimeCommands()` 收集玩法系统的运行时命令
- `CommandBus::DrainRuntimeCommands()` 收集总线命令
- `SceneTransitionService::DrainRequests()` 收集场景请求
- 如果一帧里来了多个请求，就只执行最后一个

然后按模式分发：

- `LoadScene`：直接进新场景
- `NewGame`：先 `GameProgress::ResetForNewGame()`，再进场景
- `LoadGame`：先检查当前场景是否允许读档，再写入自动读档槽

这条链还会顺手维护 `GameProgress` 的场景上下文，
所以无论是“从菜单进游戏”，还是“打完战斗回结果页”，
后面的存档逻辑都知道自己现在处于什么阶段。

### 7.6.9 一个完整例子：按 Play、Pause、Step、Stop

把这一章的链路收成一个完整例子就是：

```text
编辑器里按 Play
  -> 复制编辑场景
  -> OnEditorStop()
  -> OnRuntimeStart()
  -> 运行时逻辑开始推进

按 F6 Pause
  -> m_PlayPaused = true
  -> 仍然渲染，但不再推进 runtime

按 F7 Step
  -> m_PlayPaused = true
  -> m_StepOnce = true
  -> 下一帧只跑一次 OnUpdateRuntime()
  -> 再次回到暂停

按 Stop
  -> OnRuntimeStop()
  -> Renderer2D::EndScene()
  -> 回到编辑态原场景
```

这一段最适合面试时讲，因为它能直接说明：

```text
Wheatear 不是“能跑场景”，而是“能控制场景怎么跑”。
```

## 7.9 和 Unity、UE、Godot 怎么对照

### Unity

Unity 最接近的概念是：

- Scene View
- Game View
- Play Mode
- Pause / Step

Wheatear 的编辑器 Play Mode 和它很像：  
都是在编辑器里开一条运行副本，而不是直接改原场景。

### Unreal

UE 里可以类比成：

- PIE
- SIE
- Standalone Game

Wheatear 的 `EditorLayerBase` 更像 PIE/SIE 的组合思路，  
而 `WheatearSandbox` 更像独立运行程序。

### Godot

Godot 里则更接近：

- 编辑器里的运行当前场景
- 运行整个项目
- 退出后回到编辑器

三者思路都类似：  
编辑器里的运行，不应该污染原始工程状态。

Wheatear 这里最有自己味道的地方在于：

```text
它把 Editor Play Mode 和 Sandbox 独立运行拆得很清楚，
但又让二者共享同一套 Scene / CommandBus / GameProgress / Runtime Services。
```

## 7.10 这一层的优点、坏处和常见误区

### 优点

- 编辑态和运行态分离，工程内容更安全
- Play Mode 可以直接预览，而不用每次都打包
- Pause / Step 让调试更细
- 命令总线和场景切换可以统一收口
- SandBox 能独立跑内容，适合最终验证

### 坏处

- 生命周期比普通 UI 面板复杂
- 运行态副作用很多，稍不注意就会污染编辑态
- 场景复制、输入重置、命令清空、切场景上下文都要小心处理
- Preview / Play / Sandbox 三套语义并存，初学者容易混

### 常见误区

- 以为 Play Mode 只是“把同一个场景继续跑”
- 忘了 Stop 时要回收输入、命令和场景状态
- 把暂停理解成“整个窗口不更新”
- 在编辑器里直接把运行时状态写回原场景
- 场景切换时忘了清 `CommandBus` 或 `SceneTransitionService`
- 只看 UI，不看 framebuffer 和实体 ID 拾取

## 7.11 面试时怎么讲

如果面试官问你：“Wheatear 的场景预览和运行控制是怎么做的？”

你可以这样答：

```text
编辑器里的预览窗口不是直接操作原场景，而是通过 EditorLayerBase 维护 Edit / Play 两套状态。
按下 Play 以后，编辑器会把 m_EditorScene 复制成 m_ActiveScene，
然后调用 OnRuntimeStart；按 Stop 时再把运行副本关掉，切回原编辑场景。
预览窗口本身用 framebuffer 承载场景画面，ImGui 只负责展示。
暂停和单步只影响运行时逻辑，不影响渲染。
命令和场景切换不会散落在各个系统里，而是统一通过 CommandBus 和 SceneTransitionService 收口到宿主层执行。
```

如果面试官继续追问：“为什么要这么设计？”

你可以补一句：

```text
因为这样可以保证编辑态内容不被运行时污染，
同时又能让同一套核心引擎在编辑器和沙盒里复用。
```

如果继续追问：“读档和新游戏怎么接？”

你就说：

```text
这些请求会先变成 SceneTransitionRequest，再由宿主层消费；
GameProgress 会记录场景上下文和存档槽，
最终由 LoadPlayScene 或 RuntimeSceneLayer::LoadScene 进入新的运行场景。
```

## 7.12 小结

这一章其实只讲了一件事：

```text
编辑器里的“跑起来”不是随便点一个按钮，
而是一整套受控的场景生命周期管理。
```

Wheatear 在这一层做了三件事：

- 用 `EditorLayerBase` 把 Edit / Play / Pause / Step / Stop 串成宿主状态机
- 用 framebuffer 把场景预览嵌进编辑器
- 用 `RuntimeSceneLayer` 把独立运行和编辑器预览分开

如果你把这一章看明白了，后面再学：

- 资源浏览器
- 场景生命周期
- 序列化与 Play Mode Copy
- 玩法运行服务

就会顺很多。  
因为你会知道：

```text
这些系统最后都要回到“谁在跑、谁在看、谁在改”这个问题上。
```
