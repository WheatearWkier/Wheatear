# 设计原则与系统导航

更新时间：2026-10-24

这一篇是整套引擎教材的“总纲”。它只回答两个问题：

1. Wheatear 为什么这样分层。
2. 读任何一个系统时，应该按什么顺序定位代码、状态和边界。

具体 API、执行顺序和源码细节放在各编章节，不在本篇重复。

## 五条核心原则

### 原则一：内容和执行分离

场景、动作、对白、动画和配置首先是内容数据，运行时再把这些数据解释成实际行为。

```text
动作配置：
    动作名称、冷却、消耗、命中时间、效果、音效、信号

运行状态：
    当前是否可用、当前冷却、当前资源、当前状态
```

如果把两者混在一起，编辑器无法稳定修改内容，运行时也难以重置。

### 原则二：编辑器和玩家运行时共享同一套语义

Editor 负责制作和观察，Sandbox 负责独立运行，但二者不各自实现一套“假的游戏逻辑”。

```text
Editor / Sandbox
        ↓
共享 Scene、Runtime Services、Systems 和 Gameplay Modules
```

编辑器只是额外提供工具、视口、Inspector、暂停和单步。这样可以避免“编辑器里能跑，最终包里不一样”。

### 原则三：稳定的公共语义和变化的玩法规则分开

不同玩法共享动作、资源消耗、冷却、状态、效果、音效和特效信号等概念，但落地规则不同：

- 横板战斗需要 hitbox、浮空、硬直和纵深移动。
- 回合制需要行动顺序和回合推进。
- 战棋需要格子、路径和范围。
- 弹幕玩法需要投射物和实时碰撞。

因此公共层统一“动作是什么”，玩法层解释“在这个玩法里怎么落地”。

### 原则四：高频状态和低频流程使用不同机制

```text
高频行为：
    Input / Gameplay System / Physics / Animation

低频流程：
    CommandBus / EventScript / SceneTransition / GameProgress
```

每帧移动、攻击、碰撞和物理走系统更新；剧情节点、菜单流程、场景切换和结算页走命令与流程脚本。这样既保留内容可编辑性，也避免脚本承担实时模拟。

### 原则五：不可逆变化要有明确的收口点

场景切换、销毁实体、应用动作效果、保存进度和切换运行模式都会改变系统状态。Wheatear 倾向于使用：

- 请求队列
- 帧边界
- 生命周期回调
- 统一宿主消费
- 结果账本

目的不是增加流程，而是避免状态在任意位置被突然修改。

## 系统导航卡

读一个系统时，按下面十项建立定位卡：

1. **系统目标**：这个系统为产品提供什么能力。
2. **架构位置**：它位于哪一层，上游和下游分别是谁。
3. **功能入口**：从哪些类、方法或数据进入。
4. **关键 API**：每个接口的语义是什么，而不是只列名字。
5. **状态归属**：哪些状态由它拥有，哪些只能读取或请求修改。
6. **输入输出**：同步返回什么，异步排队什么，最终由谁消费。
7. **职责边界**：它明确不负责什么。
8. **扩展入口**：增加功能时应该注册、继承、组合还是新增模块。
9. **故障定位**：出问题时先检查哪些状态和日志。
10. **完整链路**：用一个真实流程把它和其他系统串起来。

## 怎么读这套教材

- 第一次读：按 `01_第三方与平台层` → `07_应用层` 顺序走一遍，先建立调用链。
- 查代码：先看对应编的“源码入口”，再回到本篇的导航卡核对职责边界。
- 面试复习：先看 [引擎研发面试问答](../99_附录/06_引擎研发面试问答.md)，再用各编章节补源码细节。
- 做功能：先判断它属于公共语义、运行服务还是玩法规则，再决定放在哪一层。
