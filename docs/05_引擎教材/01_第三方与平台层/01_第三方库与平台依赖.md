# 第 1 编 01：第三方库与平台依赖

> 本章所属层级：**第三方与平台层**
>
> 本章目标：理解 Wheatear 为什么要依赖 GLFW、OpenGL、ImGui、entt、Box2D、yaml-cpp、stb 这些库，它们各自解决什么问题，以及它们为什么被放在引擎最底层。
>
> 先提醒一句：这一章不是在背“我用了哪些库”，而是在讲**这些库为什么是地基**。  
> 如果地基不稳，上面再漂亮的 Scene、ECS、战斗、剧情、编辑器都会被拖住。
>
> 所以这一章要回答的不是“库名叫什么”，而是：
> - 这个库替我解决了什么基础问题
> - 它和上层系统的边界在哪
> - 为什么我没有自己手搓同样的能力

## 1.1 为什么要单独写“第三方与平台层”

这一层的职责很简单，但很重要：

- 让程序能跑起来
- 让窗口能显示出来
- 让图形上下文能工作
- 让输入、资源、UI、物理和序列化有可靠基础

你可以把这一层理解成：

```text
操作系统 / 窗口系统 / 图形驱动
        ↓
GLFW / OpenGL / ImGui / entt / Box2D / yaml-cpp / stb
        ↓
Wheatear 的平台抽象和引擎服务
```

这一层的东西，基本都不直接表达玩法。
它们更多是在回答：

- 怎么开窗口
- 怎么收消息
- 怎么画第一帧
- 怎么把编辑器做出来
- 怎么组织场景里的数据
- 怎么把文件读写和图片加载接起来

## 1.2 本章先看哪些源码

建议按这个顺序看：

| 文件 | 作用 |
| --- | --- |
| `Wheatear/src/Wheatear/Core/Application.h/.cpp` | 主循环和层系统的宿主 |
| `Wheatear/src/Wheatear/Core/Window.h` | 跨平台窗口抽象 |
| `Wheatear/src/Platform/Windows/WindowsWindow.cpp` | GLFW 窗口实现、事件回调、VSync、全屏 |
| `Wheatear/src/Platform/OpenGL/OpenGLContext.cpp` | OpenGL 上下文初始化和缓冲交换 |
| `Wheatear/src/Wheatear/ImGui/ImGuiLayer.cpp` | ImGui 初始化、输入桥接和渲染 |
| `Wheatear/src/Wheatear/Scene/Scene.h/.cpp` | Scene / ECS / 系统挂接 |
| `Wheatear/src/Wheatear/Scene/Entity.h/.inl` | Entity 访问组件的统一入口 |
| `Wheatear/src/Wheatear/Scene/Components.h` | 场景组件聚合头 |
| `Wheatear/src/Wheatear/Renderer/*.cpp` | Renderer、Shader、Texture、Mesh、Material、2D/3D 渲染链路 |
| `Wheatear/src/Wheatear/Physics/ContactListener.cpp` | 物理接触回调 |
| `Wheatear/src/Wheatear/Assets/AssetPath.cpp` | 资源路径与可写根目录 |
| `Wheatear/src/Wheatear/Config/UserSettings.cpp` | 用户设置读写 |

如果你只想先抓主链路，就先看：

`Application` -> `Window` -> `OpenGLContext` -> `ImGuiLayer`

然后再看：

`Scene` -> `Entity` -> `Components` -> `Renderer / Physics / UI / Animation`

## 1.3 这些库分别干什么

### 1.3.1 GLFW

GLFW 主要负责：

- 创建桌面窗口
- 管输入回调
- 管 OpenGL 上下文挂载
- 管全屏、VSync、窗口大小
- 提供原生窗口句柄入口

在 Wheatear 里，`WindowsWindow` 本质上就是把 GLFW 包了一层。

为什么不用自己直接写 Win32？

- 因为 GLFW 已经把窗口、输入和上下文这部分跨平台地整理好了
- 你不需要把时间浪费在重复处理系统窗口细节上
- 你更应该把精力花在引擎架构和玩法上

### 1.3.2 OpenGL

OpenGL 负责真正的图形渲染命令。

在 Wheatear 里，它主要承担：

- 2D / 3D 图元绘制
- 着色器编译和使用
- 纹理、VAO、VBO、UBO、Framebuffer
- 渲染抽象层的最终落地

为什么选 OpenGL？

- 学习曲线和调试体验比较直接
- 对一个以 2D 为主的自研项目来说足够用
- 便于把渲染管线、shader 和批处理的概念讲清楚

### 1.3.3 Dear ImGui

ImGui 负责编辑器和调试 UI。

它的优点是：

- 界面搭得快
- 适合工具
- 非常适合内容编辑、调参、Inspector、Hierarchy、调试窗口

Wheatear 里大量编辑器面板都基于 ImGui 搭出来。
它不是游戏 UI 的最终答案，但它非常适合：

- 引擎编辑器
- 资源编辑器
- 调参窗口
- 场景检查器

### 1.3.4 entt

entt 是 Wheatear 场景 ECS 的核心底座之一。

它主要解决：

- entity / component 的组织
- registry 的管理
- view / 迭代 / 查询
- 生命周期和缓存结构

Wheatear 的 `Scene` 不是自己重新发明 ECS，而是建立在 entt 上。
这样做的好处是：

- 组件查询快
- 结构清楚
- 系统更新容易组织

### 1.3.5 Box2D

Box2D 是 2D 物理的基础库。

它主要解决：

- 刚体
- 碰撞体
- 碰撞检测
- 物理步进
- 接触回调
- 约束和模拟

在 Wheatear 里，Box2D 不是“玩法自己写的碰撞系统”，而是引擎服务层物理系统的底座。

### 1.3.6 yaml-cpp

yaml-cpp 负责 YAML 文件的读写和解析。

Wheatear 很多地方都依赖它：

- 场景序列化
- 玩法调参
- 成长内容
- 编辑器资产
- 保存 / 读回

为什么 YAML 适合这个项目？

- 结构直观
- 人工可读
- 适合内容编辑
- 很适合教程和调参文件

### 1.3.7 stb

stb 在 Wheatear 里主要拿来做图片加载，尤其是图标、窗口图标和一些纹理资源。

它的特点是：

- 轻
- 容易接
- 常见格式支持直接

对于一个 2D 项目来说，这类库很实用，因为你经常会需要：

- 读 png
- 读图集
- 读缩略图
- 读 UI 图标

## 1.4 平台层到底解决了什么

这层看上去像“接第三方库”，其实它真正解决的是平台差异。

### 1.4.1 窗口差异

不同操作系统创建窗口的方式不同。
你不应该把这些系统差异直接泄露到上层玩法里，所以 Wheatear 用 `Window` 抽象来统一。

### 1.4.2 图形上下文差异

OpenGL 不是“默认就能用”。
它必须先有窗口，再把上下文挂上去，再加载函数指针，再开始渲染。

### 1.4.3 输入差异

底层输入消息和上层玩法动作不是一回事。
平台层负责采集，输入层负责映射，玩法层负责消费。

### 1.4.4 文件和原生对话框差异

系统级文件对话框、窗口句柄、平台 API 都属于平台下钻的内容。
这也是为什么上层会需要一个受控的原生句柄出口。

## 1.5 `Window`：为什么它是最先要抽象出来的东西

`Window` 不是 GLFW，也不是 Win32。

它是一层很克制的跨平台抽象。

### 1.5.1 它提供什么

从 `Window.h` 可以看出，它主要负责：

- 创建和更新窗口
- 获取宽高
- 设置事件回调
- 设置 VSync
- 设置全屏
- 获取原生句柄

### 1.5.2 为什么它不负责更多

因为窗口不是引擎的全部。

上层真正关心的是：

- 这是不是一个能显示的表面
- 能不能收事件
- 能不能切全屏
- 能不能和图形上下文对接

所以 `Window` 的职责必须克制。

### 1.5.3 为什么它必须保留 `GetNativeWindow()`

因为有些平台功能、第三方库和调试工具需要原生句柄。

典型例子：

- GLFW 后端初始化 ImGui
- Windows 文件对话框
- 未来如果接更多系统级 API

所以这里的思路是：

> 平时上层只看抽象 `Window`，需要下钻的时候再通过 `GetNativeWindow()` 取原生句柄。

## 1.6 `WindowsWindow`：真正把桌面窗口造出来

`WindowsWindow` 是 `Window` 在 Windows 平台上的实现。

### 1.6.1 它做了什么

它主要做这几件事：

- 初始化 GLFW
- 创建 GLFW 窗口
- 载入窗口图标
- 创建 OpenGLContext
- 设置回调
- 管 VSync
- 管全屏
- 提供原生窗口句柄

### 1.6.2 为什么要有窗口计数

`WindowsWindow.cpp` 里有一个全局计数，目的是避免重复初始化和过早终止 GLFW。

这个细节很有平台层味道，因为它说明：

- 第一个窗口创建时才初始化 GLFW
- 最后一个窗口销毁时才终止 GLFW

### 1.6.3 为什么窗口回调在这里注册

因为 GLFW 的键盘、鼠标、窗口尺寸、关闭事件都要在窗口层采集。
然后它再把这些消息转换成引擎事件，送给 `Application` 的事件系统。

这也是平台层和核心平台层的分界：

- 平台层负责“采什么”
- 核心层负责“怎么分发”

## 1.7 `OpenGLContext`：上下文为什么要单独一层

窗口有了，不代表 OpenGL 就能画。

OpenGL 需要上下文。

### 1.7.1 它做什么

`OpenGLContext` 主要负责：

- `glfwMakeContextCurrent`
- `gladLoadGLLoader`
- `glfwSwapBuffers`

### 1.7.2 为什么初始化顺序这么重要

顺序必须是：

1. 先有窗口
2. 再挂上下文
3. 再加载 OpenGL 函数
4. 再初始化渲染层
5. 再开始画 ImGui 和场景

如果顺序错了，后面的渲染命令和后端绑定都可能出问题。

### 1.7.3 为什么 `SwapBuffers()` 在 context 里

因为“交换前后缓冲”本质上是图形上下文行为，不是窗口对象的核心语义。

你可以把它理解成：

- `Window` 提供宿主表面
- `GraphicsContext` 负责把一帧真正送到屏幕上

这就是这一层最重要的边界之一。

## 1.8 `ImGuiLayer`：为什么它必须依赖窗口和上下文

ImGuiLayer 是编辑器和调试 UI 的入口。

### 1.8.1 它的初始化链

它会做：

- 创建 ImGui Context
- 配置 docking 和 multi-viewport
- 加载字体
- 调整主题
- 用 GLFW 后端绑定窗口
- 用 OpenGL3 后端绑定渲染

### 1.8.2 为什么它要拿 `GetNativeWindow()`

因为 ImGui 的 GLFW 后端需要原生窗口句柄。

这说明上层虽然不该直接依赖 GLFW 细节，但工具层在接后端时，确实需要从抽象窗口拿到 native handle。

### 1.8.3 为什么它要看窗口尺寸

因为 ImGui 要知道当前窗口有多大，才能正确布局和渲染。

### 1.8.4 为什么它和应用层关系密切

因为 Editor、Sandbox 这类应用层都依赖 ImGui 做：

- 菜单
- Inspector
- Hierarchy
- 调参窗口
- 资源浏览器

所以它在本书里既属于第三方依赖，也属于工具链的关键入口。

## 1.9 `entt`：为什么 ECS 底座放它

### 1.9.1 `Scene` 为什么建立在 entt 上

因为 entt 很适合做：

- entity 管理
- component 存储
- view 查询
- 生命周期追踪

Wheatear 的 `Scene` 不是自己重写 ECS，而是在 entt 上建立自己的场景组织层。

### 1.9.2 `Entity` 和 `Registry` 的关系

`Entity` 在 Wheatear 里只是一个更安全的访问壳。

真正的数据都在 `entt::registry` 里。
`Entity` 只是帮你：

- 增加组件
- 查询组件
- 删除组件
- 检查是否有效

### 1.9.3 为什么这比自己手写 ECS 更合适

因为这可以把精力放到：

- 场景生命周期
- 组件分组
- 系统注册
- 序列化
- 编辑器工具

而不是重复造一个 ECS 容器。

## 1.10 `Box2D`：为什么物理基础库要放这一层

Box2D 是 2D 物理的地基。

### 1.10.1 它解决什么

- 刚体
- 形状
- 质量
- 速度
- 碰撞
- 接触监听
- 物理步进

### 1.10.2 为什么物理不能完全自己写

因为物理模拟牵涉：

- 几何
- 数值稳定性
- 碰撞检测
- 约束求解
- 接触回调

这些东西自己从零重写成本非常高，而且很容易不稳定。

### 1.10.3 `step()` 为什么重要

`step()` 是一帧物理推演的核心。

它代表：

- 这一帧碰撞怎么检测
- 这一帧力和速度怎么积分
- 这一帧约束怎么求解

你在面试里如果谈物理，不要只说“我用了 Box2D”。
要说的是：

> 我知道物理一帧里要先推进世界，再把结果回写到场景状态。

## 1.11 `yaml-cpp`：为什么它这么适合这套项目

YAML 是 Wheatear 非常核心的内容格式之一。

### 1.11.1 它适合什么

- 场景序列化
- 成长内容表
- 战斗调参
- 编辑器导入导出
- 存档 / 运行时数据

### 1.11.2 为什么不用把所有内容硬编码

因为内容驱动的项目，最怕的是：

- 改一个数就要改代码
- 改一个表就要重编译
- 非程序员无法维护配置

yaml-cpp 的意义，就是把这些内容变成可读、可维护、可热重载的数据。

### 1.11.3 为什么 YAML 比 JSON 更适合这一类教材

因为 YAML 更适合人读，尤其是结构化内容和分层配置。

对一个以教材和面试复盘为目标的项目来说，YAML 很适合作为“讲得清楚”的数据格式。

## 1.12 `stb`：为什么它在资源系统里很实用

stb 在这里主要用来做图片加载。

### 1.12.1 它做什么

- 读贴图
- 读图标
- 读简单图像资源

### 1.12.2 为什么不自己实现

因为图片加载是很典型的基础能力，没必要重复造轮子。

Wheatear 更应该把力气放在：

- 资源路径
- 缓存
- 图集
- 动画
- 编辑器工具链

## 1.13 这些库怎么串到 Wheatear 里

### 1.13.1 程序启动

`Application` 创建 `Window`，`Window` 创建 `OpenGLContext`，`OpenGLContext` 初始化 OpenGL 函数，然后 `ImGuiLayer` 绑定后端，最后整个引擎才进入主循环。

### 1.13.2 场景组织

`Scene` 依赖 `entt` 组织 entity 和 component，再挂上各类系统。

### 1.13.3 资源和内容

图片、字体、场景、调参和成长内容，通过 `AssetPath`、`yaml-cpp`、`stb`、资源别名等模块接起来。

### 1.13.4 物理和碰撞

2D 物理由 Box2D 提供底座，Wheatear 的物理系统负责把它接到 Scene、Component 和回调上。

## 1.14 这一层的好处、坏处和常见误区

### 1.14.1 好处

- 让引擎真正能跑起来
- 把平台差异挡在底下
- 让上层专注玩法和工具
- 资源、UI、物理、场景都有可靠底座

### 1.14.2 坏处

- 这一层最容易被忽略
- 库一多，依赖关系容易散
- 如果边界没写清楚，上层会误以为自己“能直接碰底层”

### 1.14.3 常见误区

1. 以为 GLFW 就是引擎窗口本身。
2. 以为 ImGui 只是 UI，和引擎架构无关。
3. 以为 entt 就等于完整 ECS。
4. 以为 Box2D 只负责碰撞，不负责模拟。
5. 以为 yaml-cpp 只是读个配置，和架构无关。

## 1.15 面试时怎么讲

如果面试官问你“你为什么把这些库放在第一层”，你可以这样说：

> 因为这一层决定了引擎能不能稳定起步。GLFW 负责窗口和输入，OpenGL 负责渲染上下文，ImGui 负责编辑器 UI，entt 负责 ECS 底座，Box2D 负责 2D 物理，yaml-cpp 负责场景和内容数据，stb 负责图像加载。  
> 我把它们放在第三方与平台层，是为了让上层 Scene、渲染、战斗、进度和编辑器都能站在统一的基础上，而不是直接碰系统细节。

如果对方继续追问，你可以继续接：

- 为什么要有 `Window` 抽象
- 为什么要把 `SwapBuffers()` 放进 context
- 为什么要保留原生窗口句柄
- 为什么 `Scene` 要基于 entt
- 为什么 `step()` 是物理章的核心

## 1.16 小结

这一章最重要的一句话是：

**第三方和平台层不是“用了哪些库”，而是“引擎最底下那块必须稳住的地基”。**

如果这一层稳了，上面的 Scene、Renderer、Physics、UI、Progression、Editor 才有机会清楚地组织起来。
