# 第 6 编 01：VN 模块

> 本章所属层级：**玩法层**
>
> 本章目标：理解 Wheatear 里的 VN 模块是怎样把“文本脚本、选择分支、场景绑定、输入、存读档、热重载、编辑器工具”串成一条完整链路的。
>
> 先提醒一句：这里的 `VN` 不是单纯“对话框 UI”，也不是“把剧情写成一份文本就完事了”。它更像一个**可运行的剧情玩法模块**。  
> 你可以把它理解成：`VisualNovelScript` 负责“写什么”，`VisualNovelRuntime` 负责“怎么跑”，`VisualNovelSystem` 负责“怎么接进每帧游戏循环”，`VisualNovelComponent` 负责“这一幕场景要绑定哪些对象”。
>
> 本章会反复使用两个常见链路：
> 1. 主菜单 `menu_new_game` 为什么能进入 `Intro`。
> 2. 选择项为什么可以直接跳到 `scene:`、`newgame:`、`loadgame:`、`event:` 这些外部命令。

## 6.1 VN 在架构里属于哪一层

如果按我们前面约定的分层来看，`VN` 不属于核心平台层，也不属于引擎服务层。
它属于**玩法层**，原因很简单：

- 它直接描述的是“这段剧情怎么玩”。
- 它关心的是对白、立绘、背景、选择、跳转、存读档、自动播放这些玩法语义。
- 它会调用更底层的系统，但它本身不是底层系统。

更直白一点说：

```text
CommandBus
    ↓
EventScript
    ↓
VN / SideCombat / TurnCombat / TacticalCombat / Arcade
```

`EventScript` 更像“剧情导演和流程编排器”。
`VN` 更像“剧情玩法本体”。

这层的价值在于：  
你不必把所有剧情都写死在场景代码里，也不必为了做一个简单的视觉小说式过场就上过重的对话框框架。  
它刚好落在“足够统一”和“足够轻”之间。

## 6.3 这一模块到底是什么

VN 模块的整体结构可以这样理解：

```text
Scene
  └─ VisualNovelComponent
        ├─ ScriptPath
        ├─ Entity binding names
        ├─ Auto/History/SaveLoad settings
        └─ RuntimeRequestedCommand

VisualNovelScript
  └─ 文本脚本资产，定义对白、选择、跳转、条件、背景、音乐

VisualNovelRuntime
  └─ 运行时解释器，负责当前行、逐字显示、历史、变量、存状态

VisualNovelSystem
  └─ 每帧驱动，接输入、执行命令、更新 UI、热重载、存读档

VisualNovelScriptEditorPanel / VisualNovelDrawer
  └─ 编辑器工具链
```

所以它不是“一个 UI 控件”，而是一个完整的**剧情执行管线**。

你在面试里可以直接这么讲：

> VN 模块把剧情表达拆成四件事：脚本、运行时、场景绑定和编辑器。  
> 脚本负责内容，运行时负责状态，系统负责接入主循环，编辑器负责让策划或自己能改得动。

## 6.4 `VisualNovelComponent`：场景里的配置中心

`VisualNovelComponent` 是这章最值得先看的地方，因为它决定了“这一幕 VN 到底绑哪些对象”。

它的字段大致分四类：

### 6.4.1 脚本与播放

- `ScriptPath`
- `CharactersPerSecond`
- `PlayOnStart`
- `RestartOnFinish`

这几个字段回答的是：

- 这幕剧情脚本在哪
- 打字速度是多少
- 进场要不要自动开始
- 播完要不要重来

### 6.4.2 场景绑定

它会把场景里的实体名作为绑定点，例如：

- `SpeakerTextEntityName`
- `BodyTextEntityName`
- `AdvanceHintEntityName`
- `BackgroundEntityName`
- `FloorEntityName`
- `CharacterEntityPrefix`
- `ChoiceEntityPrefix`
- `MaxVisibleChoices`

这说明一件事：  
VN 的 UI 不是硬编码死在系统里，而是**绑定到场景中的实体**。

这很适合简单 2D 游戏，因为很多时候你只是需要：

- 背景图一张
- 角色立绘一两张
- 对白框一个
- 选择按钮几个
- 命令栏一条

### 6.4.3 辅助页面

VN 还有一批辅助界面配置：

- `AutoPlayOnStart`
- `AutoPlayDelay`
- `HistoryTextEntityName`
- `AutoPlayIndicatorEntityName`
- `CommandBarEntityName`
- `CommandTooltipEntityName`
- `HistoryPanelEntityName`
- `SettingsPanelEntityName`
- `SaveLoadPanelEntityName`
- `SystemMessageEntityName`
- `MusicNoticePanelEntityName`
- `MusicNoticeTextEntityName`

这些字段告诉你，VN 不只是“对白+选择”。
它还会带上：

- 历史回看
- 自动播放
- 设置
- 存档/读档
- 系统提示
- 音乐提示

### 6.4.4 外部命令

`RuntimeRequestedCommand` 是一个很关键的桥。

它的意思是：  
VN 的某些选择不只是“在 VN 内部跳到下一句”，而是要直接发出外部命令，比如：

- `scene:...`
- `newgame:...`
- `loadgame:...`
- `event:...`

这也是为什么这个模块能把剧情和真正的玩法流程接起来。

## 6.5 `VisualNovelScript`：剧情脚本怎么写

`VisualNovelScript` 是文本资产格式。

它本质上不是“小说全文”，而是一个带命令的**剧情 DSL**。

### 6.5.1 常见语法

当前脚本里常见的命令大概有这些：

- `@background`
- `@music` / `@bgm`
- `@speed`
- `@label`
- `@goto`
- `@end`
- `@choice`
- `@expression`
- `@show`
- `@hide`
- `@character`
- `@sheet`
- `@char`
- `@set`
- `@if`

普通对白则长这样：

```text
Alice: 早上好。
Bob: 今天的剧情从这里开始。
```

### 6.5.2 选择分支

`@choice` 是 VN 的核心。

它不只是“给玩家三个按钮”，还支持条件过滤。
一个选项可以带：

- `if flag <id>` / `if flag:<id>`
- `if <expr>`

也就是说，某个分支是否出现，既可以看全局故事旗标，也可以看脚本内局部变量。`if` 之后可以写完整表达式，不再限制为两个 token，例如：

```text
@choice prompt:要接受委托吗？ | 接受 -> accept if gold >= 5 and flag:CH02 | 拒绝 -> decline
```

选项文本和目标标签可以用引号包住，因此文本里出现 `|` 或 `->` 也不会破坏解析。

### 6.5.3 条件表达式

`VisualNovelRuntime::EvaluateVNExpression()` 使用共享逻辑表达式语言：

- `always` / `never`
- `flag <id>`、`skill`、`dungeon`、`completed`、`equipment`、`material`
- 局部变量比较、算术、`and` / `or` / `not`
- `min` / `max` / `clamp` / `abs` / `round` / `floor` / `ceil` / `if`

`@set` 也使用同一套表达式，因此可以写：

```text
@set gold = 10
@set gold = gold + reward
@set tired = hp < maxhp * 0.3
```

这里有个很重要的分层点：

- `flag` 读的是 `GameProgress::StoryFlags`
- 局部变量读的是 VN runtime 自己的变量表

这就是“全局进度”和“当前剧情局部状态”的分离。

### 6.5.4 校验、快捷键与热重载

- 加载 `.vn` 时校验重复标签、悬空的 `@goto` / `@if` / 选项目标、非法条件和 `@set` 表达式；错误带文件行号，进入 `Diagnostics -> Logic Diagnostics`。
- VN 编辑器保存前执行同一套校验，存在 Error 时会阻止保存。
- `F5` 打开存档菜单，`F9` 打开读档菜单；`PlayOnStart` 关闭时脚本不会自动加载，可用 `vn:start` / `vn:restart` 启动。
- 热重载保留变量和历史，并优先恢复到当前行之前最近的标签，不再跳回第一行。
- 存档格式为 `VNSTATE 2`，记录脚本哈希、最近标签和偏移；改剧本后优先按标签恢复，旧 `VNSTATE 1` 存档仍可读取。
- 所有选项都被条件过滤时，系统会提示并跳过该选项节点，不会卡死。

### 6.5.5 外部选择目标

`IsExternalChoiceCommand()` 会把这些目标识别成外部命令：

- `scene:`
- `newgame:`
- `loadgame:`
- `event:`

这意味着一个选择不一定只在 VN 里转场，它也可以直接进入：

- 新场景
- 新游戏
- 读档流程
- 事件系统

这条桥接非常适合面试讲。

### 6.5.5 一个具体例子：主角和女主在校道上

你刚才问的“能不能给一个很具体的例子”，这里就直接拿 `Intro` 这段来讲。

场景里先挂的是这个组件：

```yaml
VisualNovelComponent:
  ScriptPath: assets/vn/intro.vn
  CharactersPerSecond: 48
  PlayOnStart: true
  RestartOnFinish: true
  SpeakerTextEntityName: VN_SpeakerText
  BodyTextEntityName: VN_BodyText
  BackgroundEntityName: VN_Background
  FloorEntityName: VN_Floor
  CharacterEntityPrefix: VN_Character_
  ChoiceEntityPrefix: VN_Choice_
  MaxVisibleChoices: 3
```

它的意思很简单：

- 这幕剧情脚本用 `intro.vn`
- 对白框、正文框、背景、角色、选择按钮都已经在场景里准备好了
- `VisualNovelSystem` 只需要把脚本里的内容灌进这些绑定点

然后脚本里真正写的是这种内容：

```text
@label start
@background assets/sandbox/vn/backgrounds/bg_modern_schoolroad_morning.png
@music assets/sandbox/audio/bgm/vn_school_morning.wav "晨路微光"
@speed 42
@character Mira 青梅 assets/sandbox/vn/portraits/aoba_{expression}.png
@character Leo 主角 assets/sandbox/vn/portraits/protag_school_{expression}.png
@show Mira:smile Leo:neutral
Mira: 今天也一起走吧。你要是再赖床，我就把你的早餐拿去喂楼下的猫。
Leo: 你这人说话怎么总像在宣布命令。
Mira: 因为你总是要被命令才会动呀。
@background assets/sandbox/vn/backgrounds/bg_modern_schoolroad_unease.png
@expression Mira worried
@music assets/sandbox/audio/bgm/vn_unease.wav "路口异兆"
Mira: 不过，今天早上有点奇怪。路口那个人，从刚才开始就一直看着我们。
@expression Leo shocked
Leo: 等等，他手里是不是有刀？
@choice 进入第一章假玩法 -> event:go_fake_combat | 先吐槽两句 -> roast
```

这段脚本在运行时的效果可以按顺序理解：

1. `@background` 把背景切到清晨校道。
2. `@music` 播放“晨路微光”。
3. `@character` 先声明两个角色的立绘资源模板。
4. `@show Mira:smile Leo:neutral` 让两人先以指定表情出现在画面上。
5. 三句对白依次显示到 `VN_SpeakerText` / `VN_BodyText` 对应的文本实体里。
6. `@background` 再切一次图，气氛从日常过渡到不安。
7. `@expression Mira worried` 和 `@expression Leo shocked` 会让立绘表情变掉。
8. `@choice` 让剧情停在这里，等待玩家按键或点按钮。

你可以把它理解成“脚本在描述镜头变化，系统在把镜头内容投到场景实体上”。

再往下看，第二段吐槽分支又会长这样：

```text
@label roast
@expression Leo skeptical
@music assets/sandbox/audio/bgm/vn_comedic_roast.wav "假玩法吐槽"
Leo: 等一下。为什么我的武器看起来像从隔壁小游戏借来的？
Mira: 也许这是命运给你的试炼。
Leo: 这不是试炼，这是项目早期原型。
@choice 行吧，先把假玩法打完 -> event:go_fake_combat
```

这一段很适合拿来讲“对话不是单纯换文本”：

- `@label roast` 说明它是一个分支节点
- `@expression Leo skeptical` 说明主角表情切到吐槽脸
- `@music` 说明 BGM 也可以跟着剧情气氛变
- 最后的 `@choice` 又把剧情送回外部事件命令

如果把这段链路拆开，你就会看到它其实是：

```text
脚本行
  -> VisualNovelRuntime 解析当前行
  -> VisualNovelSystem 把背景/音乐/立绘状态推到场景
  -> 玩家做出选择
  -> 外部选择写进 RuntimeRequestedCommand
  -> 通用运行时把命令交给 CommandBus
  -> EventScript 或场景切换接住后续流程
```

这就是一个很典型的“主角和女主对话，镜头和表情跟着变，最后把剧情推到下一段玩法”的完整例子。

## 6.6 `VisualNovelRuntime`：运行时状态机

如果说脚本是“内容”，那 `VisualNovelRuntime` 就是“会跑的剧情机”。

它保存的核心状态包括：

- 当前脚本
- 当前行号
- 已显示字符数
- 是否结束
- 自动播放状态
- 历史记录
- 局部变量

### 6.6.1 推进逻辑

`Advance()` 的逻辑可以粗略理解成：

- 如果已经结束，就重启
- 如果当前文本还没显示完，就先补完文本
- 如果当前行是对白，就记录历史并往下走
- 如果当前行是选择，就停住等玩家选

所以“按一次继续”并不总是“直接跳下一句”。
它先要处理当前文本显示状态。

### 6.6.2 选择逻辑

`Choose(choiceIndex)` 会：

- 把这次选择记录到历史里
- 跳转到对应标签
- 如果没有目标标签，就按默认流程继续

这里最容易出错的地方是：  
**脚本里的选择顺序，不一定等于最终屏幕上看到的按钮顺序。**

因为有些选择会被条件过滤掉。

### 6.6.3 存读档状态

`SaveState()` / `LoadState()` 说明 VN runtime 是能独立保存的。

保存里会有这些内容：

- `SOURCE`
- `INDEX`
- `VISIBLE`
- `FINISHED`
- `AUTOPLAY`
- `HISTORY`
- `VARS`

这就把“当前看到哪一句”“历史说过什么”“局部变量是什么”都保存下来了。

这个设计的好处是：  
你可以把同一份剧情脚本，在不同存档点继续跑，而不用重算整个剧情树。

## 6.7 `VisualNovelSystem`：怎么接进每帧循环

`VisualNovelSystem` 是 VN 模块真正进入游戏循环的入口。

它做的事情很多，但可以总结成一句话：

> 它把输入、脚本、UI、命令、存读档、热重载和音频都接到了 VN runtime 上。

### 6.7.1 启动与停止

当场景运行时，如果 `PlayOnStart` 开启，系统会加载 runtime。
当场景停止时，它会清理 runtime 状态并停止 BGM。

### 6.7.2 每帧更新

`OnUpdateRuntime()` 大致在做这些事：

- 先从 `CommandBus` 拿 `vn:` 命令
- 再检查脚本是否变化，必要时热重载
- 再处理输入
- 再更新自动播放 / 跳过
- 再推进 runtime
- 最后同步 BGM、提示与场景绑定

这说明 VN 不是“点一下按钮就完事”，而是一个真正持续跑的模块。

### 6.7.3 命令执行

`ExecuteCommand()` 处理的是 VN 自己的命令，比如：

- `vn:auto`
- `vn:history`
- `vn:save`
- `vn:load`
- `vn:skip`
- `vn:advance`
- `vn:settings`

而 `ExecuteGameSaveCommand()` 则把这些命令和全局存读档流程接起来。

## 6.8 输入、命令栏与选择按钮

VN 的输入不是只看键盘。
它会同时看：

- 键盘
- 鼠标
- 选择按钮
- 命令栏按钮

`VisualNovelInputService::Sample()` 返回的快照里，核心字段有：

- `PrimaryMousePressed`
- `AdvanceActionPressed`
- `AutoPressed`
- `HistoryPressed`
- `SavePressed`
- `LoadPressed`
- `ChoicePressed[9]`

这意味着：

- 回车 / 左键可以推进
- 数字键或按钮可以选项
- 自动播放、历史、存档、读档都有统一入口

系统里还有一组 `Previous...Pressed` 标记，用来做边沿触发，避免长按时反复触发同一命令。

这部分特别适合拿来给初学者讲一个常识：

> 做输入时，不是“按着就触发”，而是“这一帧刚按下才触发”。

## 6.9 选择显示为什么不会乱

`CollectVisibleChoiceIndices()` 做的是一个很细但很重要的活。

它会把真正可见的选择项收集出来，依据是：

- `RequiredFlag`
- `RequiredCondition`

然后把“脚本里的选择序号”映射成“屏幕上可见按钮的序号”。

这一步很重要，因为如果有两个选项被条件隐藏了，你不能让按钮编号直接乱掉。

你可以这样理解：

- 脚本编号是“原始编号”
- 屏幕按钮是“可见编号”
- runtime 负责把这两者对齐

这就是为什么一个成熟的 VN 系统不能只靠 `if` 把按钮藏掉就算完。

## 6.10 存档、读档和 `GameProgress`

VN 模块里的存读档分成两层：

### 6.10.1 全局进度

`GameProgress` 管的是全局状态，例如：

- 章节
- 旗标
- 解锁
- 存档槽信息
- 场景切换上下文

### 6.10.2 VN runtime 状态

`VisualNovelRuntime` 管的是当前剧情实例状态，例如：

- 当前行
- 当前显示到多少字
- 历史
- 局部变量

### 6.10.3 为什么要分开

因为“全局进度”和“当前剧情进行到哪”不是一回事。

举个例子：

- 你可能已经解锁了某个章节
- 但当前读档点停在一段对白中间

这两个状态应该分开保存。

这也是 `SaveToSlot()` 里为什么既会保存 `GameProgress`，也会保存 `VisualNovelRuntime` 的原因。

### 6.10.4 相关链路

这条链路可以这样记：

```text
SaveLoad 菜单
    ↓
GameProgress::SaveSlot / LoadSlot
    ↓
VisualNovelRuntime::SaveState / LoadState
    ↓
Scene 重新绑定后恢复 VN 现场
```

还有一个很实用的点：  
`BuildLoadGameCommand()` 会把“加载哪个槽位”变成一条命令，这样 VN、事件脚本、进度系统就能用统一的命令链沟通。

## 6.11 热重载和编辑器工具链

VN 模块不是只给运行时用的，它也有一整套编辑器支持。

### 6.11.1 热重载

系统会周期性检查脚本文件时间戳。
如果脚本变了，就重新加载。

这对写剧情特别有用，因为你不需要每改一句对白就重启整个程序。

源码里还有一个很实用的保护：  
如果重载时文件看起来暂时是空的，系统会把它当成“正在写入”，先延迟重载，避免半截文件把运行时冲坏。

### 6.11.2 `VisualNovelScriptEditorPanel`

这个面板是“时间线优先”的。
它不是让你直接手写一大坨文本，而是让你在面板里加：

- Dialogue
- Choice
- Label
- Background
- Music
- Speed
- Show
- Hide
- Set
- If
- Goto
- End

然后再导出成脚本文本。

这很适合教材里讲一个现实经验：

> 对初学者来说，文本脚本能学表达；  
> 对自己来说，编辑器能提高产能。

### 6.11.3 `VisualNovelDrawer`

Inspector 负责配置场景绑定。

它会让你直接看到：

- 对白框绑哪个实体
- 背景图绑哪个实体
- 命令栏和历史页绑哪个实体
- 选择按钮怎么摆

这比写死在代码里更好调，也更适合面试时讲“我做了内容工具链”。

## 6.12 两条最典型的链路

### 6.12.1 主菜单新游戏

`Projects/WheatearDemo/assets/events/sandbox_flow.wts` 里有一条很清楚的链路：

```text
event menu_new_game: newgame:assets/scenes/Intro.wt
```

这条链路说明：

1. 用户点“新游戏”
2. `EventScript` 发出 `newgame:` 命令
3. `CommandBus` 分发给对应服务
4. 场景切到 `Intro`
5. `VisualNovelSystem` 在新场景里加载对应脚本
6. VN 开始讲第一段剧情

这就是“菜单 -> 剧情开场”的完整链路。

### 6.12.2 选择跳到战斗或事件

再看另一类分支：

```text
event go_fake_combat: progression:set_flag:FLAG_CH01_FAKE_COMBAT_STARTED; scene:assets/scenes/VisualNovelBattle.wt
event fake_combat_victory: progression:set_flag:FLAG_CH01_FAKE_COMBAT_CLEARED; wait 0.10; scene:assets/scenes/TurnCombat.wt
```

这说明 VN 的某个选择或事件，不一定只是“继续讲故事”。
它也可以直接进入战斗层。

如果从 VN 里的选择去讲这条链路，你可以这样概括：

- 选择项触发外部命令
- 命令进入事件脚本
- 事件脚本改进度、切场景
- 新场景进入战斗模块

这就是玩法层之间互相接力的样子。

## 6.13 和 Unity / UE / Godot 的对照

面试时常会被问：

“你这个 VN 模块和别的引擎里常见做法有什么区别？”

你可以这样讲。

### Unity

Unity 里常见做法是：

- `Canvas` / `TextMeshPro` 负责显示
- `ScriptableObject` 或文本资产负责内容
- 第三方叙事工具或自定义状态机负责分支

它和 Wheatear 的相似点是：  
也会把“脚本、UI、状态”拆开。

它的不同点是：  
Wheatear 更像是从源码层把这一整条链直接揉进引擎里。

### Unreal Engine

UE 里常见做法是：

- `UMG` 做界面
- 数据资产 / 蓝图做剧情配置
- 关卡切换和任务状态由更大的游戏逻辑管理

它和 Wheatear 的相似点是：  
也会把剧情和场景、进度、UI 串起来。

它的不同点是：  
UE 更适合做大体量系统分工，Wheatear 更像一个轻量、源码可读、适合学习的实现。

### Godot

Godot 里常见做法是：

- `Control` 节点做 UI
- 场景树做层级组织
- 脚本和资源文件做对话数据

它和 Wheatear 的相似点是：  
都很适合用“场景 + 绑定 + 资源”来组织 VN。

它的不同点是：  
Wheatear 的重点是让你读明白一套 C++ 引擎怎么把这些东西接起来。

## 6.14 这一层的好处和坏处

### 好处

- 结构清楚，剧情、UI、输入、存档各管各的
- 文本脚本可热重载，改剧情很快
- 选择可以直接接外部命令，和玩法层其它模块能打通
- 对简单 2D 游戏很合适，不会太重
- 面试时很好解释“我为什么这样拆”

### 坏处

- 分支一多，脚本会很快变复杂
- 选择过滤、变量、存档状态一多，调试会变麻烦
- 文本脚本如果没有编辑器辅助，作者体验会下降
- 如果把全局进度和局部 runtime 混在一起，后面会很难维护

所以这层不是“越抽象越好”，而是“够用且能持续维护”最好。

## 6.15 常见误区

- 把 VN 当成“纯 UI 系统”
- 把脚本当成“只会显示文本的配置文件”
- 让选择按钮直接决定场景切换，绕开命令总线
- 把全局进度和 VN runtime 状态混成一个存档对象
- 用按钮序号直接代替脚本选择序号
- 在多个地方硬编码 `scene:`、`newgame:`、`loadgame:` 字符串
- 以为热重载只是“文件改了就 reload”，却忽略了半写入文件的问题

## 6.16 面试时怎么讲

你可以准备三句话。

### 6.16.1 先讲定位

“VN 模块在我的引擎里属于玩法层，它负责把剧情脚本、选择分支、场景绑定、存读档和编辑器工具串成一条链。”

### 6.16.2 再讲拆分

“我把它拆成脚本格式、运行时状态机、场景组件和系统四层。脚本管内容，runtime 管状态，component 管场景绑定，system 管每帧驱动和输入命令。”

### 6.16.3 最后讲亮点

“它的亮点是选择项可以通过外部命令直接接到 `scene:`、`newgame:`、`loadgame:`、`event:`，所以 VN 不只是对话系统，而是能和整个玩法流程接起来。”

## 6.17 初学者建议怎么读

如果你是第一次看这章，建议按这个顺序：

1. 先看 `VisualNovelComponent`，知道场景里要绑什么。
2. 再看 `VisualNovelScript`，知道脚本能写什么。
3. 再看 `VisualNovelRuntime`，知道一段剧情怎么跑起来。
4. 再看 `VisualNovelSystem`，知道它怎么接到每帧更新里。
5. 最后看编辑器，理解它怎么被真正制作和调试。

如果你只想先把“结果是怎么出来的”搞明白，先盯这三条链就行：

- `menu_new_game -> newgame: -> Intro`
- `@choice -> RuntimeRequestedCommand -> CommandBus`
- `SaveLoad -> GameProgress + VisualNovelRuntime`

## 6.18 小练习

1. 给一个 VN 脚本加三条选择，其中一条用 `flag` 隐藏。
2. 写一个 `@set` 和 `@if`，让对白根据变量变化。
3. 在场景里绑定一组新的对白框和背景实体名。
4. 给一个外部选择命令接到 `event:`，让它切去战斗场景。
5. 试着只改脚本文件，不重启程序，看热重载能不能把变化吃进去。

## 6.19 本章总结

VN 模块的本质，不是“显示文本”，而是“把文本剧情做成一个能运行、能保存、能分支、能跳场景、能接玩法的系统”。

它在架构里的位置很明确：

- 往下接引擎服务层的输入、命令、场景、资源和存档
- 往上承接剧情、菜单、分支和过场这些玩法内容

所以你以后再看这套源码时，心里要记住一句话：

> `VisualNovelScript` 负责表达，  
> `VisualNovelRuntime` 负责执行，  
> `VisualNovelSystem` 负责接入游戏，  
> `VisualNovelComponent` 负责把这一幕绑到场景上。
