# Wheatear Architecture

Wheatear is organized as a small editor-first game engine. The codebase should
keep runtime systems reusable by the editor, the standalone player, and future
tools.

## Projects

- `Wheatear`: core runtime library. Owns application lifetime, logging, input,
  events, assets, scene data, renderer abstractions, scripting, UI runtime, and
  built-in gameplay modules.
- `WheatearEditor`: editor executable. Owns editor-only layers, panels,
  inspectors, content browsing, build packaging, and authoring workflows.
- `WheatearSandbox`: standalone player/runtime host. It should depend on public
  Wheatear APIs and load packaged or editor-authored scenes.
- `Wheatear-ScriptCore`: managed script API exposed to user C# gameplay code.
- `Wheatear/vendor`: third-party dependencies. Engine code should wrap vendor
  APIs at subsystem boundaries instead of leaking them into game/editor code.

## Runtime Layers

- `Core`: application lifetime, platform-neutral services, logging, asserts,
  smart pointer aliases, filesystem helpers, player configuration, and
  engine-wide metadata.
- `Platform`: OS and graphics backend implementations. Public engine code
  should depend on interfaces in `Core` or `Renderer`, not platform files.
- `Renderer`: backend-neutral rendering API, resources, cameras, materials, and
  batching. Backend implementations live under `Platform/OpenGL`.
- `Scene`: ECS entities, components, serialization, prefab/material scene data,
  and runtime lifecycle.
- `Systems`: required engine scene systems such as physics, scripting,
  animation, audio, UI, and rendering. Systems should work from component data
  and avoid editor-only dependencies.
- `Modules`: optional gameplay/domain features layered on top of scene data.
  Visual novel and arcade combat live here because a game can opt into them
  without making them part of the core scene pipeline.
- `Scripting`: Mono host, native bindings, script class metadata, and managed
  instance lifetime. C# is optional for packaged players; the native `.wts`
  event script system lives here as a lightweight event sequencer for games
  that do not want to enable Mono. Default native builds keep C#/Mono disabled
  at compile time; regenerate projects with premake `--csharp-scripting` when
  C# script hosting is needed.
- `Runtime`: runtime-facing coordination services such as `CommandBus` and
  `SceneTransitionService`. UI buttons, VN choices, event scripts, and gameplay
  modules should request actions through these services instead of depending on
  a specific host layer.
- `UI`: runtime UI components, layout/input helpers, and rendering glue.
  Large authored UI widgets should be represented as data components, not as
  many ad hoc scene entities. For example, `UISkillTreeViewComponent` stores a
  full skill graph, while `UIPathComponent` exposes reusable polyline and
  Bezier path drawing for maps, routes, and skill-tree decoration. Both use
  `Renderer2D::DrawPolyline` under the UI clipping/layout layer.

## Asset And File Conventions

- Scene files use `.wt`.
- Prefabs use `.wtprefab`.
- Materials use `.wtmaterial`.
- Shared names, extensions, and default paths live in
  `Wheatear/Core/EngineInfo.h`.
- Runtime paths should go through `Wheatear::AssetPath` so editor, player, and
  packaged builds can resolve assets consistently.
- File operations that need normalization, subpath checks, recursive copy, or
  text writes should go through `Wheatear::FileSystem`.
- Packaged player settings live in `assets/game/player.config` and should be
  read/written through `Wheatear/Core/PlayerConfig.h`.
- Player packages are scriptless by default. Mono and managed assemblies are
  copied only when `PlayerPackageOptions::EnableScripts` is true, so C++-only
  vertical slices do not pay the Mono package-size cost.
- Default engine builds also avoid linking Mono. This keeps the current
  command/data/.wts pipeline fast while preserving C# as an opt-in extension
  path.

## Application Startup

Application entry points should prefer `Wheatear::ApplicationSpecification`
over long constructor argument lists. The specification owns window title,
command line arguments, project root, asset directory name, and whether the
Mono scripting runtime is enabled.

`WheatearSandbox` reads `assets/game/player.config` for the default scripting
mode. Command-line flags can override it: `--scripts` / `--enable-scripts` turn
Mono on, while `--no-scripts` / `--disable-scripts` keep the runtime native-only.

Editor and runtime hosts should set `ProjectRoot` through
`AssetPath::DiscoverProjectRoot()` or an explicit project selection result
before systems start. This keeps resource lookup deterministic across editor,
player, packaged builds, and future project-manager UI.

## Scene Systems And Modules

`Scene` owns an ordered list of `ISystem` instances and exposes
`SceneExecutionMode` to distinguish edit mode from runtime mode.

- Core runtime systems are registered in `Scene::ConfigureRuntimeSystems`.
- Optional runtime systems are registered through `SceneSystemRegistry` by the
  host application or a module bootstrap.
- Editor systems are registered in `Scene::ConfigureEditorSystems`.
- Startup and shutdown are centralized through `StartSystems` and
  `StopSystems`, with shutdown running in reverse registration order.
- `ISystem` provides runtime and editor lifecycle hooks. Editor hooks default to
  runtime hooks so existing systems remain compatible, but new systems can
  separate editor-only setup from game runtime setup.
- `RegisterDefaultGameplayModules()` enables the built-in VisualNovel and
  ArcadeCombat modules for the editor and WheatearSandbox. A future game host
  can register only the modules it actually uses.

## Commands, Data, And Event Scripts

Wheatear's native content-driving stack is `CommandBus + data tables + .wts
event scripts`.

- `CommandBus` executes short commands such as `progression:save_1`,
  `ui:pager:Equipment_Pager:next`, and `event:FlowController:open_skill_tree`.
- `SceneTransitionService` stores structured scene transition requests from
  `scene:`, `newgame:`, and `loadgame:` commands. Hosts consume those requests
  and perform actual scene loading.
- Data tables own broad editable content, for example VN `.vn` scripts and
  `side_combat_tuning.yaml`.
- `.wts` event scripts sequence commands with `wait` and simple `if` conditions.

This keeps event scripts host-agnostic: a script requests a scene transition
through the engine, while `WheatearSandbox` or editor Play Mode decides how to
load the scene.

## Editor Component Inspectors

The scene hierarchy panel owns generic editor chrome only: entity selection,
the Add Component popup, and the Properties panel container.

- Core component inspectors are registered by `RegisterCoreEditorComponents()`.
- Optional gameplay inspectors are registered by
  `RegisterDefaultGameplayEditorModules()`.
- `EditorComponentRegistry` stores category labels, add callbacks, and draw
  callbacks so the panel does not directly depend on gameplay module types.
- Gameplay-specific inspector code belongs under
  `WheatearEditor/src/Modules/<ModuleName>`.

## Extension Rules

- Add new engine-facing public APIs under `Wheatear/src/Wheatear`.
- Add editor-only UI and authoring code under `WheatearEditor/src`.
- Add platform-specific code under `Wheatear/src/Platform/<PlatformOrBackend>`.
- Add required engine runtime systems under `Wheatear/src/Wheatear/Systems`.
- Add optional gameplay/domain systems, components, and runtime helpers under
  `Wheatear/src/Wheatear/Modules/<ModuleName>`.
- Add optional gameplay editor inspectors under
  `WheatearEditor/src/Modules/<ModuleName>`.
- Add managed script API in `Wheatear-ScriptCore/Source/Wheatear`.
- Keep vendor includes in implementation files whenever possible; expose small
  Wheatear-owned types at module boundaries.

## Build

Root text and asset conventions are guarded by `.gitattributes` and
`.editorconfig`. Source, script, scene, YAML, JSON, Markdown, and shader files
should stay UTF-8; Visual Studio project files and PowerShell scripts keep
Windows-friendly CRLF line endings.

Generate Visual Studio projects with:

```powershell
vendor\bin\premake\premake5.exe vs2022
```

Build the default debug workspace with Visual Studio or the sanitized Windows
build entry point:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts\Build-Windows.ps1 -ProjectPath Wheatear.sln -Configuration Debug -Platform x64
```

`scripts/Build-Windows.ps1` reconstructs a clean process environment before it
starts MSBuild. This avoids failures from parent shells that contain duplicate
case variants such as `Path` and `PATH`.

For daily editor work, the shorter helper is:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts\Build-WheatearEditor.ps1
```

`Wheatear` uses `wtpch.h` as its engine precompiled header. `WheatearEditor`
uses its own `src/wepch.h / src/wepch.cpp`, configured in
`WheatearEditor/premake5.lua` with `pchheader`, `pchsource`, and
`forceincludes`. Keep PCH content stable and broadly reused; module-specific
gameplay/editor headers should remain in their implementation files so changing
one feature panel does not invalidate the whole editor PCH.

Large translation units should be split by responsibility instead of relying on
MSVC `/bigobj`. `SceneSerializer` is now grouped by component domain, while
`EditorLayerBase` is split into lifecycle, scene/build, and UI/viewport files.
`SceneHierarchyPanel` keeps hierarchy tree drawing and Inspector component
drawing in separate files. Remaining compile-size hotspots include
`SideCombatSystem.cpp`, `GameProgress.cpp`, and `ProgressionSystem.cpp`; split
them only in behavior-preserving steps with a build and smoke test after each
step.
