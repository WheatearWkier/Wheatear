# 类型化引擎路线与项目体检

更新日期：2026-07-31

## 1. 引擎方向

Wheatear 后续不追求做成“大而全但每个方向都很浅”的通用引擎，而是做成偏向特定 2D 游戏类型的生产型引擎。

当前内置玩法方向：

- 弹幕 / 假玩法模块：适合短流程、剧情反差、小游戏关卡。
- 回合制战斗：适合过渡章节、策略选择、角色技能表现。
- 2D 横版格斗：当前主玩法方向，重点是空连、滞空、断限追击、技能树和装备成长。
- 战棋战斗：适合假玩法、章节变体，后续也可扩展成独立战棋项目。
- VN / Galgame：承担剧情、角色关系、好感度、选择、存读档和 BGM 演出。

这些玩法模块应当复用同一套引擎公共层，而不是各自重复造轮子。

## 2. 公共层拆分原则

多个玩法都会用到的能力，应放到公共层：

- 场景与实体：`Scene`、`Entity`、`UUID`、`EntityReference`。
- 资源与打包：`AssetPath`、`AssetDependencyScanner`、`.wtpack`、打包报告。
- UI：Canvas、Widget、Panel、Pager、ScrollView、SkillTreeView、Path。
- 动画：SpriteSheet、AnimationClip、动画事件、`anim:` 命令。
- 音频：BGM、SFX、音量设置、AudioSource。
- 流程：`CommandBus`、`.wts`、`SceneTransitionService`。
- 成长数据：经验、材料、装备、技能、好感度、支援。

玩法模块只负责自己的规则、状态机、AI、关卡逻辑和专属表现。例如 SideCombat 不应该自己实现一套资源依赖扫描，战棋也不应该自己实现一套分页 UI。

## 3. UUID 引用规范

Wheatear 使用 UUID 作为稳定实体引用。编辑器中不要求用户手填 UUID，用户看到的应该是对象槽、实体名、选择按钮和清除按钮；底层保存 UUID。

推荐数据形态：

```yaml
TargetEntity: 17382910492300000000
```

规则：

- 优先通过 `TargetEntity` / UUID 解析。
- 名字和 Tag 只用于显示、搜索、编辑器检索和人类阅读，不再作为运行时主引用。
- 运行时目标引用必须保存 UUID；旧的名字 / Tag 目标写法不再作为兼容路径保留。
- 跨场景引用未来需要同时保存场景路径或场景资源 GUID。

当前命令系统的目标选择规则：

```text
event:open_skill_tree
event:@17382910492300000000:open_skill_tree
anim:play:@17382910492300000000:idle
ui:pager:@17382910492300000000:next
```

`event:<name>` 表示广播给当前场景所有 `EventScriptComponent`；如果需要指定实体，使用 `event:@<UUID>:<name>`。`anim:` 和 `ui:pager:` 这类必须锁定具体目标的命令统一使用 `@UUID`。

## 3.1 玩法公共服务层首批落地

四类玩法的第一批公共能力已经抽到 `Wheatear/Modules/Common`：

- `GameplayAudioService`：统一 BGM / SFX 音量、主音量和播放入口，玩法模块不再各自计算音量。
- `GameplayCombatService`：统一基础伤害、防御、治疗、死亡判断，避免假玩法、横板、回合制、战棋各写一套公式。
- `GameplayEntityService`：统一通过 UUID 解析运行时实体，配合上面的引用规范。
- `GameplayFlowService`：统一处理胜利、失败、结算等延迟命令派发。

当前已经接入这些服务的玩法：弹幕假玩法、2D 横版格斗、回合制战斗、战棋战斗。

第二批已经补上的公共服务：

- `GameplayTextService`：命令分割、帧序列路径格式化、数值格式化。以后不要在各玩法里重复写 `SplitCommand` / `{frame}` 替换。
- `GameplayVisualService`：共享贴图缓存、Sprite / UI 序列帧应用。以后临时单帧和 spritesheet 迁移前的帧条都先走这里。
- `GameplayTargetingService`：按组件收集实体、队伍存活判断、最近/最低血目标选择。回合制、战棋、横板 AI 都能复用。
- `GameplayUIService`：血条、资源条、tooltip 等 HUD 小原语。玩法模块只给实体名和数值，不再重复写显示细节。
- `GameplayUILayoutService`：运行时创建/同步 Pager、ScrollView、Text、Button、Slider、PageItem 等页面组件。Progression 的装备页、存档页、设置页已开始复用。
- `GameplayRewardService`：奖励摘要解析、掉落数量判断。结算页掉落图标不再把解析逻辑写死在 Progression 里。

后续继续拆的方向是：`SideCombatTuningService`、`SideCombatActionService`、`CombatResultService`、`AnimationEventBridgeService`、以及 Progression 下的 `Inventory / Equipment / SkillTree / Relationship / SaveGame` 子服务。

## 4. Project Health

`View / Project Health` 是项目体检面板，用于交付前检查：

- 从启动场景递归扫描资源依赖。
- 解析 `.wt`、`.wtprefab`、`.wtmaterial`、`.vn`、`.wts`、`.yaml`、`.yml`、`.json`。
- 列出会被打包的资源。
- 列出缺失引用。
- 列出未被启动流程引用的资源。
- 显示已解析文本资产和扫描警告。

这解决的问题是：编辑器、打包器、运行版使用同一套依赖判断，避免“编辑器能看到，打包版缺资源”的情况。

## 5. 打包报告

`Package Player` 成功后，输出目录会生成：

```text
package_report.txt
```

报告包含：

- 启动场景。
- 是否启用 C# 脚本。
- 打包资源数量。
- 源资源大小。
- `.wtpack` 大小。
- 缺失引用。
- 实际写入 `.wtpack` 的资源列表。

以后每次准备发给别人试玩前，应先看 `Project Health`，再打包并检查 `package_report.txt`。

## 6. 下一步工程化目标

短期优先：

- Inspector 对象槽：把常见实体名字字段升级成可选择实体的 UUID 引用槽。
- Command 自动补全：根据场景实体、事件名、资源路径提示命令。
- SideCombat 拆分：输入/手感、动作状态机、命中解析、AI、HUD、掉落结算、调参加载分文件。
- Progression 拆分：Inventory、Equipment、SkillTree、Relationship、SaveGame 分模块。
- Project Health 扩展：增加脚本事件不存在、场景跳转不存在、重复 Tag、孤儿 UI、未挂 Canvas UI 的检查。

长期目标：

- 所有类型玩法共享 UI、动画、资源、存档、命令、音频、调参工具。
- 每种玩法只保留自己的核心规则和编辑器内容面板。
- 编辑器尽量让策划通过面板完成内容制作，减少手写 YAML 和手改场景文件。

## 7. 2026-07-31 模块服务层落地规则

本轮开始把“玩法系统大文件”拆成稳定层级：

- `System`：只做运行时入口、每帧调度、场景生命周期桥接。
- `TuningService`：加载 YAML/数据表、默认参数、热重载缓存、章节解锁 profile 查询。
- `ResultService`：评分、经验、奖励结算、结算摘要等可独立测试的公式。
- `PageService`：某个具体运行时页面的 UI 组装、分页、tooltip、拖动画布、局部刷新。
- `Common Gameplay Service`：多个玩法共用的文字、目标选择、音频、奖励、通用 UI、运行时布局等小原语。

当前已落地示例：

- 横板战斗：`SideCombatTuningService`、`SideCombatResultService`。
- 成长/据点页面：`ProgressionEquipmentPageService`、`ProgressionResultPageService`、`ProgressionSaveLoadPageService`、`ProgressionSettingsPageService`、`ProgressionSkillTreePageService`。

后续新增弹幕、回合制、横板格斗、战棋功能时，先判断逻辑属于规则、数据、页面、结果、流程还是公共原语，再放入对应层级。不要再把目标选择、奖励掉落、HUD 构建、调参加载、存档页刷新直接堆到玩法主系统文件里。
## 8. 2026-07-31 玩法系统继续服务化原则

Wheatear 后续的玩法模块按“玩法是状态机，能力是服务”的原则继续拆分。玩法系统本体只保留本玩法独有的循环、阶段切换、输入入口和调度顺序；凡是可以被多个玩法复用，或者可以独立测试、独立配置、独立编辑的逻辑，都优先放入服务层。

### System 层

System 层回答“当前玩法这一帧处于什么阶段、应该调用哪些服务”。例如横板战斗的起手、浮空、断限、结算阶段；回合制的等待指令、选择目标、行动演出、胜负判断；战棋的选单位、移动、技能目标、敌方回合。System 不再承载大块技能库、掉落计算、UI 页面构建、投射物细节、棋盘寻格等通用能力。

### Service 层

Service 层回答“具体能力怎么做”。同一种能力可以服务于多种玩法，例如：

- SkillService：技能定义、技能查找、槽位解析、技能消耗、伤害/治疗基础公式。
- TargetService：目标收集、阵营过滤、最低血量/最近距离/合法目标选择。
- BoardService：格子坐标、范围判断、占位查询、可移动格、简单 AI 步进。
- ProjectileService：投射物创建、贴图选择、生命周期、碰撞、遮挡。
- ResultService：胜负、评级、奖励、掉落、结算页面数据。
- UIService：血条、资源条、tooltip、分页、滚动、技能栏表现。

### 数据和脚本

服务层不应该把未来内容锁死在 C++ 中。当前竖切可以先保留内置默认库，保证 demo 可运行；但服务 API 要向数据表友好，后续可以把技能、敌人、掉落、AI 策略、章节条件迁移到 YAML/编辑器表，再由事件脚本串起流程。

### 这轮拆分目标

本轮继续把四种玩法中最稳定的公共能力拆出去：

- 回合制：技能库与目标选择从 `TurnCombatSystem` 拆到 `TurnCombatSkillService` / `TurnCombatTargetService`。
- 战棋：技能库与棋盘格逻辑从 `TacticalCombatSystem` 拆到 `TacticalCombatSkillService` / `TacticalCombatBoardService`。
- 假弹幕玩法：投射物创建、清理、碰撞从 `ArcadeCombatSystem` 拆到 `ArcadeCombatProjectileService`。
- VN：暂时保持剧情状态机主体不动，后续优先把设置页、存档页、历史记录页拆成独立 presentation/service。

最终目标是：以后新增玩法时，只新增“状态机和少量规则胶水”，而不是复制一整套战斗、UI、掉落、目标选择和数据处理代码。

## 9. 2026-07-31 横板战斗服务层第二批拆分

横板战斗继续按“System 只负责循环，Service 负责能力”的方式拆分。当前 `SideCombatSystem` 保留玩家输入、敌人 AI 阶段、命中结算规则、物理推进、死亡胜负和场景流程。下面能力已经拆出去：

- `SideCombatTuningService`：参数读取、默认值、技能解锁、Boss 保护条/断限 UI 显示条件。
- `SideCombatResultService`：结算评级、经验奖励、结果摘要。
- `SideCombatHudService`：战斗 HUD、技能栏、冷却遮罩、tooltip、道具栏、血条/连击/奖励文字。
- `SideCombatActionService`：玩家/敌人动作运行态、动作持续时间、取消窗口、动作清理、挥动音效入口。
- `SideCombatHitboxService`：hitbox 创建、归属销毁、帧贴图更新、空间重叠检测。

这次没有把完整命中结算直接搬出 `SideCombatSystem`，因为它仍然和浮空、断限、Boss 保护条、连击计数、魔剑槽、受击状态、敌我动作打断紧密耦合。下一步更合理的拆法是先定义一个 `SideCombatHitResult` 数据结构，再把命中结算拆成：

- `SideCombatHitResolutionService`：伤害、硬直、击飞、受击状态、保护条增长/破防。
- `SideCombatComboService`：连击计数、空中命中奖励、魔剑槽增长、断限条件结果。
- `SideCombatPickupService`：掉落物创建、吸附、拾取入库。

这样拆分后，`SideCombatSystem` 会进一步收缩成横板动作状态机：输入采样、玩家状态推进、敌人状态推进、物理推进、调用命中/表现/奖励服务。
## 10. 2026-07-31 横板命中与连击服务拆分

本轮把横板战斗的命中结算继续从 `SideCombatSystem` 拆出，保持“玩法系统是状态机，服务层负责能力”的原则。

新增服务：

- `SideCombatHitResolutionService`：负责命中后的扣血、受击硬直、击飞、死亡状态、玩家受击计数、敌我动作打断、Boss 保护条增长与破防。
- `SideCombatComboService`：负责连击计数、断连计时、玩家空中命中奖励、魔剑槽增长。

当前边界：

- `SideCombatSystem` 仍然负责输入采样、玩家行动选择、敌人 AI 阶段、hitbox 扫描循环、物理推进、死亡/胜负流程。
- `SideCombatHitboxService` 负责“是否发生空间命中”和 hitbox 生命周期。
- `SideCombatHitResolutionService` 负责“命中后目标变成什么状态”。
- `SideCombatComboService` 负责“玩家因为命中获得什么连招收益”。

这样拆完后，横板战斗的核心命中段不再直接散落大量扣血、击飞、保护条、连击和魔剑槽代码。下一步如果继续优化，应优先拆：

- `SideCombatPickupService`：掉落物创建、吸附、拾取入库。
- `SideCombatPhysicsService`：横板纵深移动、空中高度、重力、落地、Boss 保护恢复。
- `SideCombatEnemyAIService`：敌人接近、攻击选择、Boss 阶段行为。

## 11. 2026-07-31 横板战斗完整服务层收束

这轮把 `SideCombatSystem` 从“玩法大文件”收束成调度层。主系统现在只负责：

- 采样输入。
- 找到当前关卡、玩家、Boss。
- 处理暂停和 hit pause 的时间缩放。
- 按顺序调度横板服务。
- 刷新 HUD。

横板战斗服务边界如下：

- `SideCombatLifecycleService`：关卡运行时状态重置、角色运行时字段初始化、玩家属性和 Boss 参数应用。
- `SideCombatPlayerService`：玩家输入解释、移动、跳跃缓冲、技能起手、空中动作次数、断限追击起手。
- `SideCombatEnemyAIService`：敌人醒来、接近玩家、横向/纵深走位、Boss 血量阶段技能选择、敌人攻击动作推进。
- `SideCombatHitboxService`：hitbox 创建、贴图帧更新、生命周期、空间重叠检测、命中扫描。
- `SideCombatHitResolutionService`：命中后的伤害、受击状态、击飞、死亡、玩家受击计数、Boss 保护条。
- `SideCombatComboService`：连击计数、断连计时、空中命中奖励、魔剑槽增长。
- `SideCombatPhysicsService`：横板纵深移动、空中高度、重力、落地、保护恢复、角色视觉同步入口。
- `SideCombatPickupService`：掉落创建、吸附、拾取入库。
- `SideCombatOutcomeService`：敌人死亡处理、胜利判定、结算记录、胜负后场景跳转。
- `SideCombatFeedbackService`：音效、hit pause、镜头震动、开场/结算淡入淡出。
- `SideCombatVisualService`：角色动画 clip 选择、SpriteAnimator 接入、受击/霸体/死亡颜色反馈、影子同步。
- `SideCombatTargetService`：横板玩法内目标选择，例如最近存活敌人。

这就是后续类型化玩法的参考结构：`System` 是状态机和调度器，`Service` 是可测试、可复用、可编辑器化的能力单元。以后新增弹幕、回合制、战棋、横板新章节时，不应该再把目标选择、奖励、UI、物理、动画、命中、AI 直接堆回 System。

## 12. 2026-07-31 三种玩法主系统大清洗

本轮把类元气假玩法、回合制战斗、战棋战斗也按同一架构原则完成服务化：`System` 只保留玩法循环、输入入口、命令分发和服务调度；具体能力拆到模块服务。这样以后新增同类型玩法时，可以直接参考对应模块，而不是继续复制大文件。

公共层边界保持克制：
- `Modules/Common` 只放真正跨玩法稳定复用的小能力，例如音频播放、基础伤害/治疗公式、实体 UUID 解析、奖励解析、通用 UI 原语、文本命令工具、目标集合筛选。
- 浮空、断限、格子移动、回合队列、弹幕投射物节奏这类规则虽然都属于“战斗”，但数据结构和手感骨架不同，保留在各自玩法模块。

- `TacticalCombatSkillService`：战棋技能定义、技能槽、范围、伤害/治疗和特效帧。
- `TacticalCombatFeedbackService`：战棋模块音效入口。
- `TacticalCombatVisualService`：单位视觉、血条颜色、选中标记、行动特效和隐藏。
- `TacticalCombatActionService`：行动开始、移动/攻击/治疗结算、行动结束。
- `TacticalCombatAIService`：敌方单位回合、靠近玩家、攻击选择和阶段切换。
- `TacticalCombatCommandService`：`tactic:` 命令解析、格子点击、技能点击和目标选择。
- `TacticalCombatUIService`：棋盘格显示、状态文字、技能按钮、行动详情。
- `TacticalCombatFlowService`：关卡重置、玩家/敌方回合阶段、胜负、淡入和每帧更新。

### 后续约束

新增或修改玩法时先问三个问题：
- 这是跨玩法稳定原语吗？是的话放 `Modules/Common`。
- 这是某个玩法独有能力吗？是的话放 `Modules/<玩法>/<玩法>...Service`。
- 这是本玩法当前阶段怎么流转吗？是的话才留在 `*System`。

这条规则优先级高于“为了少建文件而临时写进 System”。System 文件如果重新膨胀到几百行，说明应该继续拆。

## 13. 2026-08-01 玩法层后续统一模板

当前玩法层已经够支撑竖切开发，但后续为了继续增加更多玩法，新增或重构玩法模块时统一按下面模板组织：

- `*System`：只做玩法循环、阶段切换、输入采样、服务调度、运行时生命周期。
- `*ActionCatalog`：把技能、武器、敌人招式、行动定义映射为 WAO `ActionRecipe`。
- `*ActionService`：处理动作运行态、动作开始/结束、命中帧、取消窗口、动作资源消耗。
- `*TargetService`：处理玩法内目标选择；如果规则稳定且跨玩法可复用，再下沉到 `Modules/Common`。
- `*ResultService`：处理胜负、评分、奖励、结算摘要。
- `*HudService` / `*UIService`：处理运行时 HUD 和页面刷新，不把 UI 细节堆回 System。
- `*VisualService` / `*FeedbackService`：处理动画、VFX、音效、hit pause、震屏等表现。
- `*TuningService`：处理 YAML/数据表加载、默认参数、热重载、章节 profile。
- `EditorPanel` / `Drawer`：处理该玩法的编辑器内容生产入口。

WAO 在这个模板中的位置：

- `ActionRecipe` 描述动作语义、时序、冷却、资源、效果预览和表现信号。
- `ActionDebugHistory` 记录运行时动作和效果账本，服务编辑器调试。
- `ActionSignalRouter` 负责把动作表现信号发给音频、VFX、UI、脚本等 handler。
- 玩法独有的命中、格子、浮空、投射物、回合队列暂时不强行公共化；未来通过 `ActionResolver` 做适配层。

当前最值得继续打磨的点：

1. 横板战斗：把真实命中后的伤害、浮空、保护条、魔剑槽、连击奖励写入 `EffectLedger`。
2. 弹幕玩法：把投射物创建从硬编码调用逐步迁成 `ActionSignalRouter` handler。
3. 回合制/战棋：把技能定义进一步映射为 `ActionRecipe`，让 WAO 面板也能看这些技能。
4. 编辑器：给 WAO Action Debugger 增加“按玩法模块分组”和“从 recipe 跳转到调参表/资源”的能力。

## 14. 2026-08-01 工程接入自动校验

本轮新增工程源文件同步检查，解决 C++ 大工程里常见的一个问题：新增 `.cpp/.h/.inl` 后忘记加入 `.vcxproj`，导致本机某些构建方式能过、Visual Studio 或打包构建不过。

命令行入口：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts\Check-ProjectSources.ps1
```

当前检查范围：

- `Wheatear/src` 对应 `Wheatear/Wheatear.vcxproj`
- `WheatearEditor/src` 对应 `WheatearEditor/WheatearEditor.vcxproj`
- `WheatearSandbox/src` 对应 `WheatearSandbox/WheatearSandbox.vcxproj`

编辑器入口：

```text
View -> Project Health -> Source Sync
```

它会列出两类问题：

- `Missing From Project`：磁盘上有源码，但工程文件没有登记。
- `Stale Project Entry`：工程文件登记了源码，但磁盘上没有这个文件。

这属于“工业化护栏”，不是玩法功能。以后每次新增服务、面板、玩法模块，都应先跑一次这个检查，再跑构建。

## 15. 2026-08-01 数据资产进入打包依赖

`AssetDependencyScanner` 已把下面目录作为引擎运行所需的内置数据资产加入打包依赖：

```text
assets/gameplay/actions
```

因此 WAO action YAML 不需要被某个具体场景逐个显式引用，也会进入运行包。这样技能/武器/玩法 action 数据可以独立于场景存在，后续也更适合编辑器化和批量维护。
## 16. 2026-08-01 运行时偏好与打包门禁

本轮把两类“交付前必须稳定”的能力继续工程化：

### 运行时偏好

`Window` 接口新增 `SetFullscreen` / `IsFullscreen`，Windows 平台实现基于 GLFW monitor/windowed 切换，并保留窗口模式下的位置与尺寸。`GameProgress::ApplySettingsToRuntime()` 会把存档里的全屏偏好应用到当前窗口；新游戏、读档和设置页命令都会走这一入口。

音量默认值下调到更适合试玩的区间，仍然通过 `AudioEngine::PercentToGain()` 的非线性曲线进入 `GameplayAudioService` 和 `AudioSystem`。震屏开关继续由 `GameProgress::Settings.ScreenShake` 统一控制，横板战斗反馈服务每次触发震屏前都会读取该设置。

### 打包门禁

`AssetDependencyScanner` 现在会额外提取这些流程命令中的场景目标：

```text
scene:assets/scenes/xxx.wt
newgame:assets/scenes/xxx.wt
loadgame:assets/scenes/xxx.wt:1
```

扫描结果会分成：

- `SceneTransitions`：当前依赖图里发现的所有场景跳转。
- `MissingSceneTransitions`：跳转目标不存在或断链的场景。
- `MissingReferences`：普通资源引用缺失。

`Project Health` 新增 `Scene Links` 页签，打包报告新增 `Scene Transition List` 和 `Missing Scene Transitions` 小节。`Package Player` 在写入 `content.wtpack` 前会执行 preflight：如果存在缺失资源或缺失场景跳转，会生成 `package_preflight_report.txt` 并停止打包，避免产出一个运行时才断流程的包。
