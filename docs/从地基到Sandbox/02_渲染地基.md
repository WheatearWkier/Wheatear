# Part 2 · 渲染地基：GL 抽象、纹理与 2D 合批

> 目标：把 OpenGL 关进抽象层，实现纹理加载与 2D 合批渲染。
> 读完本 Part，引擎应该能：加载 PNG、以极少 draw call 绘制上千个
> 精灵/UI 元素。结尾用一个真实例子走完
> **「技能图标从 YAML 场景文件到屏幕像素」** 的全程。

## 2.1 分层：为什么要有三层渲染代码

```
RendererAPI（Platform/OpenGL）      ← 真正碰 GL 的地方（glDrawElements...）
    ↑
RenderCommand（Renderer/）          ← 静态门面：SetClearColor / DrawIndexed...
    ↑
Renderer2D（Renderer/）             ← 高层：合批、精灵/圆/线/文本提交
```

- `RendererAPI` 是抽象接口，`OpenGLRendererAPI` 是唯一实现。
  所有 GL 调用（`glClearColor`、`glDrawElements`）都锁在这个文件里。
- `RenderCommand` 是**静态门面**：引擎其他部分只调 `RenderCommand::Clear()`，
  永远不出现 `gl` 前缀。换 Vulkan 后端时，只有 `Platform/` 下的实现要动，
  上层零改动。
- `Renderer2D` 负责"画什么、怎么合批"：场景渲染循环调它提交精灵，
  它攒够一批再一次性交给 RenderCommand。

为什么要为"换后端"留这一层？因为**渲染代码是引擎里最容易被平台绑死的
部分**，接口先行，实现后置，是引擎工程的第一纪律（面试高频题：
"你的渲染器怎么支持多后端？"——答案就是这层抽象）。

## 2.2 纹理：从 PNG 到 GPU

### 2.2.1 加载与翻转约定

`Platform/OpenGL/OpenGLTexture.cpp`：

```cpp
stbi_set_flip_vertically_on_load(1);          // ← 关键约定
stbi_uc* data = stbi_load(path, &w, &h, &ch, 0);
glTextureSubImage2D(...);                     // 上传为 GL 纹理
```

`flip=1` 让 stb 解码时把图片上下翻转。于是 **GL 纹理的 v=0 行是图像的
底部**（OpenGL 的纹理坐标原点在左下）。这带来一个贯穿全引擎的约定：

> **组件和动画链路的 UV 一律使用 v=0=底部（GL 约定）**，`UVMin/UVMax`
> 直接可交给渲染器。只有 ContentBrowser 缩略图在贴到 ImGui 时翻转一次
> （ImGui 的屏幕坐标原点在左上）。

这个约定曾经是 top-left，导致 sheet 渲染上下颠倒——教训是：
**坐标系约定必须在边界统一处理，而不是到处临时改符号**。

### 2.2.2 纹理缓存：同一张图只进一次 GPU

`Renderer/Texture.cpp` 维护全局 LRU 缓存：

```cpp
static std::unordered_map<std::string, TextureCacheEntry>& TextureCache();
// TextureCacheEntry { Ref<Texture2D> Texture; uint64_t LastUsedTick; uint64_t Bytes; }
```

`Texture2D::Create(path)` 的规则：

1. **命中缓存** → 返回同一个对象（GPU 纹理只建一份）。
2. **未命中** → 创建 + 缓存，记录字节数。
3. **512MB VRAM 预算**：超出后淘汰「没人引用（use_count==1）」的最久未用项。

为什么 dedup 是**合批的前提**？看 2.3 的纹理槽机制就明白：
合批要求"同一批里相同纹理的精灵共享一个纹理槽"，
如果同一路径每次加载都是新 GL 纹理（新 rendererID），
槽位查找永远 miss，几十个同图精灵就会把 32 个槽撑爆、
每帧强制拆批几十次——渲染性能直接崩。
缓存的存在让"同一路径 == 同一个 rendererID"，合批才能成立。

为什么 512MB 预算 + 无引用淘汰？编辑器长会话会打开几百张图，
不设预算会占满显存；而业务侧（组件）自己持有 `Ref`，
缓存里的引用计数为 1 时就说明"没人用了"，可以安全淘汰。

## 2.3 Renderer2D：合批是怎么工作的

### 2.3.1 顶点格式：一个顶点里装了什么

`Renderer/Renderer2DVertices.h`：

```cpp
struct QuadVertex
{
    glm::vec3 Position;      // 世界坐标（transform * 局部顶点）
    glm::vec4 Color;         // 顶点色（精灵颜色/淡出）
    glm::vec2 TexCoord;      // UV（纹理坐标）
    float     TexIndex;      // 纹理槽索引（合批的关键！）
    float     TilingFactor;  // 平铺系数（Tiling 纹理用）
    int       EntityID;      // 实体 UUID（编辑器 picking 用）
};
```

`TexIndex` 是理解合批的钥匙：**一个 draw call 可以绑定 32 张纹理**
（`k_MaxTexSlots`），顶点通过 `TexIndex` 指明自己用哪张。
所以只要纹理种类 ≤ 32，几千个精灵也能一次 draw call 画完。

### 2.3.2 数据布局：四个批量缓冲

`Renderer2D.cpp` 里 `s_Data` 持有四个 `RenderBatch`（Quad/Circle/Line/Text），
每个是预分配的顶点缓冲：

```cpp
static constexpr uint32_t k_MaxQuads = 10000;      // 单批最多 1 万 quad
static constexpr uint32_t k_MaxVertices = k_MaxQuads * 4;
static constexpr uint32_t k_MaxIndices  = k_MaxQuads * 6;
```

`RenderBatch`（`Renderer/RenderBatch.h`）在创建时分配
`m_MaxVertices` 个顶点 + 对应索引，`AllocVertex()` 只是指针后移——
**帧内提交零分配**（没有 new、没有 vector push 的扩容抖动）。

### 2.3.3 提交路径：一个精灵怎么进去的

场景渲染循环每帧调用：

```cpp
Renderer2D::BeginScene(camera, cameraTransform);   // 设置视图投影
// ... 场景里每个可见精灵调用一次：
Renderer2D::DrawSprite(transform, spriteComponent, entityID);
Renderer2D::EndScene();                            // 统一 Flush 提交
```

`DrawSprite` 内部：

```cpp
void Renderer2D::DrawSprite(const glm::mat4& transform, SpriteRendererComponent& src, int entityID)
{
    glm::mat4 drawTransform = transform;
    // 1. PPU > 0 时按内容像素/PPU 缩放 quad，保持真实宽高比（Part 6 详讲）
    // 2. 应用 DrawOffset / DrawScale
    // 3. 查纹理槽 → 生成 4 个顶点 → 写入 QuadBatch
    const float texIndex = GetOrAllocTextureSlot(src.Texture);
    SubmitQuadVertices(drawTransform, src.Color, uvs, texIndex, ...);
}
```

`GetOrAllocTextureSlot`：

```cpp
for (uint32_t i = 1; i < s_Data.TextureSlotIndex; i++)
    if (*s_Data.TextureSlots[i] == *texture)   // rendererID 比较（缓存保证同图同 ID）
        return i;                              // 已占用 → 复用槽位
if (s_Data.TextureSlotIndex >= k_MaxTexSlots)
    FlushAndReset();                           // 槽满 → 先提交再继续
s_Data.TextureSlots[s_Data.TextureSlotIndex++] = texture;
```

- 槽位查找是线性扫描（≤32 次比较），配合纹理缓存命中率极高。
- 超过 32 种纹理 → 强制 `Flush`（把已攒的顶点提交出去，重置槽位）。
  这是合批的"天花板"：一帧内同屏纹理种类超过 32 才会拆批。

`EndScene → Flush` 时做什么：

```cpp
void Renderer2D::Flush()
{
    s_Data.QuadBatch->Flush(s_Data.Stats);   // glBindTexture(槽) + glDrawElements
    // ... Circle/Line/Text 各批次
    s_Data.TextureSlotIndex = 1;             // 槽位重置（0 号留给白纹理）
}
```

`RenderBatch::Flush` 绑定 0..N-1 号纹理槽（0 号是白纹理，1..N-1 是实际贴图），
一次 `glDrawElements` 画出本批所有顶点——**一千个精灵 = 一个 draw call**
（纹理不超 32 时）。

### 2.3.4 为什么"攒到 EndScene 才提交"

帧内提交有两大好处：

1. **排序自由**：场景可以先画不透明再画透明（深度测试开关），
   合批不受提交顺序限制——攒起来后按批次统一处理。
2. **状态切换最小化**：`glBindTexture`/`glBindVertexArray` 是开销大头，
   每帧只做一次批量绑定，而不是每个精灵绑一次。

代价是：**同一帧内纹理种类 ≤ 32 的限制**。对 2D 游戏这是合理上限——
HUD、角色、特效通常共用图集，Part 10 的战斗场景一帧也就十来张纹理。

## 2.4 相机与视图投影

- `Renderer/Camera.h`：`Camera` 基类，持有投影矩阵；`SceneCamera` 支持
  正交（2D 场景）与透视（3D 预览）切换。
- `EditorCamera`（编辑器专用）：轨道/飞行双模式相机——**按住 Alt**：
  Alt+左键旋转、Alt+中键平移、Alt+右键缩放（滚轮也可缩放）；
  **按住右键进入飞行模式**（WASD 平移、Q/E 升降、Shift 加速、Ctrl 减速），
  松开回到轨道模式——Part 5 编辑器视口用。
- 每帧 `SetViewProjection(vp)` 把 `ViewProjection` 上传进
  `CameraUniformBuffer`（Uniform Buffer Object，Renderer2D 内部持有），
  顶点着色器用它把 `Position` 变换到裁剪空间。

## 2.5 实例走读：技能图标从场景文件到屏幕像素

现在用 Sandbox 战斗 HUD 里真实的技能图标走完整条渲染链。
战斗场景 `SideCombatBeastPath.wt` 里有一个实体：

```yaml
- Entity: 946201001
  TagComponent:
    Tag: SC_SkillIcon_J          # 技能图标 J（上挑攻击）
  TransformComponent:
    Scale: [1, 1, 1]
  UIWidgetComponent:
    Position: [0.898, 0.810]     # 屏幕坐标（0~1 归一化）
    Size: [0.072, 0.128]         # 图标尺寸
    SortOrder: 64                # 绘制顺序
    ParentEntity: 946209004      # 挂在 HUD 面板下
  UIImageComponent:
    TexturePath: assets/vertical_slice/side_combat/ui/sidecombat_ui_sheet.png
    SpriteSheet: assets/vertical_slice/side_combat/ui/sidecombat_ui_sheet.wtsheet
    SubRect: SC_SkillIcon_J      # ← 命名矩形引用（Part 4/6 的资产管线）
    UVMin: [0.112891, 0.170833]  # 烘焙 UV（兜底）
    UVMax: [0.186719, 0.298611]
  UIButtonComponent:
    OnClickFunction: "side:basic"  # 点击触发技能（CommandBus 链路）
```

**第一步 · 场景加载**：`SceneSerializer` 读 YAML，`UIImageComponent`
的 `SpriteSheet/SubRect` 字段被反序列化（Part 3 讲模板序列化器）。
UV 是旧烘焙值，但 `SubRect` 是权威引用。

**第二步 · 每帧解析**：`SpriteSheetSystem::OnUpdateRuntime` 遍历所有带
SpriteSheet 的组件，`SubRect` 非空 → `SpriteSheetAsset::ResolveCell(sheet, "SC_SkillIcon_J", resolved)`
——从 `.wtsheet` 的 `rects:` 列表找到该矩形（像素框）→ 换算 UV +
内容尺寸 + 可选碰撞框。**改 `.wtsheet` 里矩形的位置/大小，HUD 下一帧自动
跟随**（这是资产化 vs 烘焙的核心差异）。

**第三步 · 布局计算**：`UIRenderer` 按 UIWidget 的 Position/Size/Anchor
把归一化屏幕坐标换算成像素矩形。`SortOrder` 决定绘制顺序
（技能图标在面板背景之上）。

**第四步 · 合批提交**：UIImage 走 `Renderer2D::DrawSprite`（UI 与场景
精灵共用同一套合批器——所以 UI 元素和精灵可以同批绘制）：

1. `GetOrAllocTextureSlot(sidecombat_ui_sheet)`：HUD 里 23 个元素
   都引用这**同一张**纹理（纹理缓存 dedup → 同一个 rendererID），
   全部命中槽 0 之前的同一个槽——**整个 HUD 图标一次 draw call 画完**。
2. 生成 4 个顶点：屏幕矩形四角 + `SubRect` 解析出的 UV + 纹理槽索引。
3. 写入 `QuadBatch`（指针后移，零分配）。

**第五步 · 光栅化**：`EndScene → Flush`：
绑定纹理槽 → `glDrawElements` → 顶点着色器用 `ViewProjection`
变换位置 → 片元着色器按 `TexIndex` 采样对应纹理 → 屏幕上出现
技能图标。按下它 → `OnClickFunction: "side:basic"` 走 CommandBus
触发主角上挑攻击（Part 10）。

> 这个例子浓缩了四个设计：
> **资产化引用**（SubRect 而非裸 UV）、**缓存 dedup**（同图共享纹理槽）、
> **合批**（HUD 一次 draw call）、**UI 与精灵同管**（同一合批器）。

## 2.6 性能动机问答（面试向）

**Q：为什么不直接逐精灵 glDraw？**
A：每次 draw call 有固定的 CPU→GPU 提交成本（状态绑定、命令提交），
一千个精灵逐个画 = 一千次提交；合批后 = 一次提交 + 顶点缓冲指针移动。
现代 GPU 每秒能画几千万三角形，瓶颈在 CPU 的提交次数——合批是
2D 引擎性价比最高的优化。

**Q：为什么纹理槽限制是 32？**
A：`k_MaxTexSlots = 32` 是引擎常量，与主流显卡的纹理单元数量兼容，
也和 OpenGL 每片元阶段纹理单元数的常见上限（GL_MAX_TEXTURE_IMAGE_UNITS，
现代显卡普遍 ≥ 32）对得上。2D 游戏同屏纹理种类通常远小于 32
（图集文化），超限才拆批。

**Q：合批和缓存的关系？**
A：缓存 dedup 保证"同路径同 rendererID"，槽位查找才能命中；
没有 dedup，同图多精灵会把槽撑爆强制拆批——两个机制缺一不可。

**Q：还有哪些渲染层优化？**
A：预分配顶点缓冲（帧内零 new）、四批分离（文本/圆/线不互相打断）、
`WT_PROFILE_SCOPE` 探针监控每批耗时（编辑器性能面板可看）。
Part 4 还会讲资产侧的热重载降频（文件系统探测 250ms 闸）。
