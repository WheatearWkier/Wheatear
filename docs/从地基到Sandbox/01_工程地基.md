# Part 1 · 工程地基：构建系统、主循环与事件

> 目标：把三个工程的骨架、构建流程、窗口、事件循环搭起来。
> 读完本 Part，引擎应该能：开一个 GLFW 窗口、收到键盘鼠标事件、
> 按帧循环更新、打日志——Sandbox 的一切都建立在这块地基上。

## 1.1 工程拓扑

仓库根目录下是四个 Visual Studio 工程（由 premake5 生成）：

| 工程 | 类型 | 作用 |
| --- | --- | --- |
| `Wheatear` | 静态库 | 引擎本体：渲染/ECS/资产/动画/输入/物理/玩法模块 |
| `WheatearEditor` | exe | 编辑器：ImGui 面板 + 内容生产工具，链接引擎静态库 |
| `WheatearSandbox` | exe | 独立运行器：加载 `assets/` 数据直接播放完整流程 |
| `Wheatear-ScriptCore` | exe | 可选 C# 脚本宿主（默认构建不强依赖） |

为什么引擎是**静态库**而不是源码编译进每个 exe？
因为编辑器与游戏必须**共享同一份引擎状态与行为**（同一个场景数据结构、
同一套序列化、同一套解析），静态库链接保证了"一份实现，两处使用"，
也把引擎与平台代码（GLFW/GLAD）隔离成清晰边界。

## 1.2 premake5：生成而不是手写 .vcxproj

`premake5.lua` 定义了三个工程。核心约定：

```lua
-- premake5.lua（节选）
workspace "Wheatear"
    configurations { "Debug", "Release" }
    architecture "x86_64"

project "Wheatear"
    kind "StaticLib"
    language "C++"
    cppdialect "C++17"
    files { "Wheatear/src/**.h", "Wheatear/src/**.cpp" }  -- glob 收集源码
    pchheader "wtpch.h"
    pchsource "Wheatear/src/wtpch.cpp"
```

两个重要设计：

1. **glob 收集源码**：新增 `.cpp/.h` 不需要改工程文件，重新生成一次即可。
   代价是构建系统不如显式列表可预测，但单人项目收益更大。
2. **每个工程一个 PCH**：`wtpch.h`（引擎）、`wepch.h`（编辑器），见 1.4。

生成解决方案：

```powershell
vendor\bin\premake\premake5.exe vs2022
```

## 1.3 引擎目录结构

```
Wheatear/src/
├── wtpch.h                 预编译头（glm/entt/Log）
├── Wheatear/
│   ├── Core/               Application / Layer / Log / Timestep / UUID / Window 抽象
│   ├── Events/             Event 基类 + EventBus（队列分发）
│   ├── Renderer/           Renderer2D / Texture / Framebuffer / Camera / Mesh...
│   ├── Scene/              Entity / Scene / Components/ / Serialization/
│   ├── Assets/             资产格式与解析（SpriteSheetAsset / AssetPath）
│   ├── Animation/          AnimationClip / 序列化
│   ├── Input/              事件查询 + 动作绑定层
│   ├── Systems/            系统集合（AnimationSystem / SpriteSheetSystem / PhysicsSystem）
│   ├── Gameplay/           服务层（视觉 / 文本 / WAO 动作编排）
│   ├── Modules/            玩法模块（VisualNovel / SideCombat / TurnCombat / Tactical）
│   └── Runtime/            CommandBus（命令总线）
└── Platform/
    ├── Windows/            WindowsWindow（GLFW 封装）
    └── OpenGL/             OpenGL 渲染 API 实现
```

分层原则：**Core 与 Events 不依赖任何上层**；Renderer 只依赖 Core；
Scene 依赖 Renderer；Systems 依赖 Scene；Gameplay/Modules 依赖以上全部。
方向一旦写反（模块直接操作 GL），就在代码评审里拉回来——这是引擎能
保持"编辑器与运行器共用"的根基。

## 1.4 预编译头：编译速度的第一桶金

`wtpch.h` 里放进**稳定且昂贵**的头：

```cpp
// wtpch.h（节选）
#include "entt.hpp"                      // ECS，~31 个 TU 使用
#include <glm/glm.hpp>                   // 数学，~54 个 TU 使用
#include <glm/gtc/matrix_transform.hpp>
#include <glm/gtc/type_ptr.hpp>
#include "Wheatear/Core/Log.h"
#include "Wheatear/Debug/Instrumentor.h"
```

把 glm/entt 放进 PCH 后，每个包含它们的 TU 不再重复解析这几万行模板代码。
实测效果：**增量编译单个文件约 3 秒**（配合 MSBuild `/m` 并行）。
编辑器 PCH `wepch.h` 再叠一层：`imgui/imgui.h`、`imgui_internal.h`、`imgui_stdlib.h`
加上常用 STL（`<filesystem>` `<chrono>` 等），编辑器 65 个 TU 共享。

> 教训：PCH 放"稳定大头"，不放业务头。业务头一改，全工程重编。

## 1.5 入口点：main() 只有三行

`Wheatear/Core/EntryPoint.h` 提供统一入口，各 exe 只需实现 `CreateApplication`：

```cpp
int main(int argc, char** argv)
{
    auto app = Wheatear::CreateApplication({ argc, argv });  // 具体 app 由各工程实现
    app->Run();                                              // 进入主循环
    delete app;
}
```

- `WheatearSandbox` 的 `CreateApplication` 返回一个只挂了 `SandboxLayer` 的 Application。
- `WheatearEditor` 的返回挂 `EditorLayer`（所有面板都挂在这一层上，Part 5 展开）。
- 编辑器与运行器**共用同一个主循环**——没有两套帧循环需要维护。

## 1.6 主循环：Application::Run 代码走读

`Wheatear/Core/Application.cpp`：

```cpp
void Application::Run()
{
    while (m_Running)
    {
        glfwPollEvents();                 // ① GLFW 拉取窗口事件
        FlushEventQueue();                // ② 事件总线统一分发

        InputBindingService::EndFrame();  // ③ 动作层边沿状态机收尾
        Input::EndFrame();                //     + 鼠标增量基线

        const double nowTime = glfwGetTime();
        Timestep timestep = float(nowTime - m_LastFrameTime);  // ④ 帧间隔
        m_LastFrameTime = nowTime;

        if (!m_Minimized)
        {
            for (Layer* layer : m_LayerStack)   // ⑤ 逻辑更新（正向）
                layer->OnUpdate(timestep);

            m_ImGuiLayer->Begin();              // ⑥ UI 渲染（ImGui）
            for (Layer* layer : m_LayerStack)
                layer->OnImGuiRender();
            m_ImGuiLayer->End();
        }

        m_Window->OnUpdate();                   // ⑦ 交换缓冲
    }
}
```

逐点说明**为什么这么排**：

- **① + ② 事件不在 GLFW 回调里立即分发**，而是入队后在帧首统一派发。
  GLFW 回调可能发生在任意时刻（甚至渲染中间），立即分发会让同一个帧里
  不同阶段的代码看到不一致的输入状态。队列化后，一帧内所有处理器看到
  的是同一批事件。
- **③ 输入状态机在事件分发之后、逻辑更新之前收尾**：
  `IsActionPressed()` 这类"边沿检测"需要知道"这一帧按下了什么"，
  而按下状态是事件处理阶段写入的——EndFrame 把"当前帧按下"滚动为
  "上一帧按下"，供下一帧查询（Part 7 详细讲）。
- **④ 用 `double` 累计时间再转 `float`**：`glfwGetTime()` 的 double 精度
  在 float 里累计 77 秒后开始丢失毫秒精度，先减后转可以避免
  "长时间运行后 deltaTime 抖动"的经典 bug。
- **⑤⑥ 更新与渲染分离**：`OnUpdate` 做逻辑（系统跑 ECS、物理步进），
  `OnImGuiRender` 只做 UI。引擎渲染（场景到 framebuffer）发生在 Layer 的
  OnUpdate 里（Part 5 的视口渲染），ImGui 只是把结果贴到窗口。
- **⑦ 窗口交换缓冲**在 ImGui 提交之后，保证 UI 与场景一帧完整呈现。

## 1.7 窗口层：把 GLFW 关进笼子里

`Core/Window.h` 是抽象接口，`Platform/Windows/WindowsWindow.cpp` 是 GLFW 实现：

```cpp
// WindowsWindow.cpp（节选）
glfwSetKeyCallback(m_Window, [](GLFWwindow* w, int key, int scancode, int action, int mods)
{
    // 把 GLFW 数字码翻译成引擎 Event，投递给 Application::OnEvent
    switch (action)
    {
        case GLFW_PRESS:   dispatcher.Dispatch(KeyPressedEvent(key, 0)); break;
        case GLFW_RELEASE: dispatcher.Dispatch(KeyReleasedEvent(key));    break;
    }
});
```

回调里做的唯一一件事：**翻译成引擎事件类型并入队**（`Application::OnEvent`
只是 `m_EventBus.Queue(e)`）。这样：

- 引擎代码从不接触 GLFW 类型（`WT_KEY_*` 是我们自己的 KeyCodes）。
- 换窗口后端（SDL/Win32 原生）时只有这一个文件受影响。

## 1.8 事件系统：类型化事件 + 队列分发

`Events/Event.h` 定义事件基类与类型分发的核心机制：

```cpp
enum class EventType { WindowClose, WindowResize, KeyPressed, KeyReleased,
                       MouseMoved, MouseButtonPressed, MouseScrolled, ... };

class Event
{
public:
    virtual EventType GetEventType() const = 0;
    bool Handled() const { return m_Handled; }
    // ...
};

class EventDispatcher
{
public:
    template<typename T, typename F>
    bool Dispatch(const F& func)   // 类型安全分发
    {
        if (!m_Event.Handled() && m_Event.GetEventType() == T::GetStaticType())
        {
            m_Event.m_Handled = func(static_cast<T&>(m_Event));
            return true;
        }
        return false;
    }
};
```

每个具体事件（`KeyPressedEvent` 等）通过宏携带静态类型信息：
`EVENT_CLASS_TYPE(KeyPressed)`。消费者用 `EventDispatcher` 按类型取事件，
**处理过了就置 Handled，后面的处理器不再收到**——这就是 Hazel 系引擎的
经典模式，也是"先到先得"的输入优先级的实现基础。

`Events/EventBus.h` 提供队列：

```cpp
void Queue(const Event& event);   // 帧内任意时刻入队
void Flush(size_t maxEvents);     // 帧首统一派发（见 1.6 的 ②）
```

事件总线还承担**跨系统通信**：`CommandBus`（Part 3/10）复用同样的
队列模式把"玩法命令"（`anim:play:...`）路由给各模块——事件系统是
整引擎的消息骨架。

## 1.9 日志与性能探针

- `Core/Log.h`：基于 spdlog 的 `WT_CORE_INFO / WT_CORE_WARN / WT_CORE_ERROR`，
  双 logger（引擎 / 客户端）。spdlog 在 PCH 里。
- `Debug/Instrumentor.h`：`WT_PROFILE_SCOPE("name")` 微秒级计时，
  `WT_PROFILE_FUNCTION()` 自动记录函数名。剖面数据由编辑器性能面板读取
  （`WT_ENABLE_PROFILING` 宏控制开关，发布构建默认关闭）。
- 这些是后续所有性能调优（Part 2/4）的"体温计"。

## 1.10 LayerStack：分层更新的骨架

`Core/LayerStack.h` 管理有序 Layer 列表：

```cpp
class Layer
{
    virtual void OnAttach() {};       // 挂载：创建资源
    virtual void OnDetach() {};       // 卸载：释放资源
    virtual void OnUpdate(Timestep) {};   // 每帧逻辑
    virtual void OnImGuiRender() {};      // 每帧 UI
    virtual void OnEvent(Event&) {};      // 事件
};
```

Sandbox 挂一个 `SandboxLayer`；编辑器把 `EditorLayer` 作为唯一主 Layer
（面板内部再分派）。Layer 的增减有"待办队列"（`m_PendingOverlaysToPush`），
避免在遍历中修改容器——同样是"不要在循环里改结构"的纪律。

## 1.12 端到端示例：一次点击，从 GLFW 回调到 VN 下一句

地基讲完了，用 Sandbox 里最真实的场景把整条链路串一遍：
**玩家在 VN 剧情里点了一下鼠标左键，屏幕上的对话前进到下一句。**
这件事跨了事件系统、输入状态机、VN 模块三层，每一层各司其职。

### 第 0 步：静止状态

游戏正在播放 VN 场景（`VisualNovelIntro.wt`）。屏幕上有立绘、对话框、
"继续"按钮。玩家把鼠标移到对话框上，按下左键。

### 第 1 步：GLFW 回调 → 事件入队（事件层）

GLFW 在系统消息循环里收到鼠标按下，调用我们注册的回调
（`Platform/Windows/WindowsWindow.cpp`）：

```cpp
glfwSetMouseButtonCallback(m_Window, [](GLFWwindow*, int button, int action, int mods)
{
    // 翻译成引擎事件，投递给 Application::OnEvent
    dispatcher.Dispatch(MouseButtonPressedEvent(button));
});
```

`Application::OnEvent` 只做一件事：`m_EventBus.Queue(e)` —— **入队，不处理**。
为什么要入队而不是立即分发？因为 GLFW 回调可能发生在帧的任意时刻
（甚至正在渲染中途），立即分发会让同一帧内不同阶段的代码看到不一致的输入。
队列化后，下一帧帧首统一派发，一帧内所有消费者看到的是同一批事件。

### 第 2 步：帧首派发 + 输入状态机收尾（输入层）

下一帧 `Application::Run()` 循环顶部：

```cpp
glfwPollEvents();        // GLFW 把新事件交给回调 → 入队
FlushEventQueue();       // 队列里的事件统一分发（EventBus::Flush）
InputBindingService::EndFrame();   // 动作层：把"本帧按下"滚动为"上帧按下"
Input::EndFrame();       // 更新按键位 + 鼠标增量基线
```

这里有一个容易忽略但至关重要的细节：**点击还没到 VN，先被输入状态机消化了**。

- `FlushEventQueue` 把 `MouseButtonPressedEvent` 分发给各 Layer。引擎的
  `WindowsInput` 在收到事件时写入"按下"状态位（`IsMouseButtonPressed(LEFT)` 从这读）。
- `InputBindingService` 维护动作层（`vn.advance` 这类语义动作）：事件处理阶段
  把"动作当前按下"置位，`EndFrame` 把它滚动成"上一帧按下"。

为什么滚动？因为**边沿检测需要历史**。VN 判断"这一次点击"用的是
"当前按下 && 上一帧没按下"（上升沿）。如果没有 EndFrame 滚动，
按住鼠标就会每帧都触发"新点击"，对话会一页一页狂跳。

### 第 3 步：VN 系统轮询快照（玩法层）

帧循环进入 `OnUpdate` 阶段，`VisualNovelSystem` 被场景系统集调用。它不直接
问 GLFW、也不接收事件回调——而是**每帧采样一次输入快照**：

```cpp
// Modules/VisualNovel/VisualNovelInputService.cpp
InputSnapshot Sample()
{
    snapshot.PrimaryMousePressed   = Input::IsMouseButtonPressed(WT_MOUSE_BUTTON_LEFT);
    snapshot.AdvanceActionPressed  = InputBindingService::IsActionDown("vn.advance");
    // vn.auto / vn.history / vn.save / vn.load / 数字键选分支 ...
    return snapshot;
}
```

注意 `vn.advance` 是**语义动作**而不是裸按键——它的默认绑定是
`SPACE / ENTER / RIGHT`（`Config/UserSettings.cpp`），玩家在
"输入绑定"面板里可以改成任何键，VN 代码一行都不用动。
鼠标左键是 `PrimaryMousePressed`，与动作层并列采样。

### 第 4 步：边沿检测 + 推进剧本

`VisualNovelSystem` 拿到快照后做判断（`VisualNovelSystem.cpp`）：

```cpp
const bool advancePressed =
    input.AdvanceActionPressed ||
    (input.PrimaryMousePressed && !commandButtonMousePressed);
//        ↑ 点了"继续"按钮等命令按钮时不推进剧情，而是触发按钮

if (pressed && !state.PreviousAdvancePressed)   // 上升沿：一次点击只触发一次
{
    if (component.RestartOnFinish || !state.Runtime.IsFinished())
        state.Runtime.Advance();                // 推进到下一句
}
state.PreviousAdvancePressed = pressed;         // 记录，供下一帧比较
```

`state.Runtime.Advance()` 进入 `VisualNovelRuntime`（剧本解释器）：
取当前行 → 执行行内命令（立绘切换、音乐、跳转标签）→ 定位到下一行 →
对话框文本更新 → 下一帧渲染出新的一句。

### 第 5 步：下一句显示出来

对话文本是场景里的 UI 实体（`UITextComponent`）。VN 系统更新实体文本后，
下一帧 `UIRenderer` 把文本合批进 2D 渲染（Part 2 讲合批），
ImGui 提交后交换缓冲——玩家看到新一句对话。

### 这条链路的设计要点（面试可讲）

1. **事件驱动 + 轮询快照分工**：GLFW 用回调（事件驱动），玩法用快照
   （每帧采样）。事件负责"把外部输入变成内部状态"，玩法层永远只读
   内部状态——所以输入来源（键盘/手柄/命令注入）可以替换而不动玩法代码。
2. **边沿检测状态机**：`Previous*Pressed` 成员记录上帧，动作层 EndFrame
   滚动状态——"按一下只触发一次"是所有交互的基础。
3. **语义动作层**：`vn.advance` 是动作名，键位是配置——重映射 UI、
   命令注入（脚本模拟输入）都建立在同一层上。
4. **一次点击跨三层**：事件层（GLFW→队列）、输入层（状态机→快照）、
   玩法层（边沿→Advance），每层只做自己的事，接口只有十行。
