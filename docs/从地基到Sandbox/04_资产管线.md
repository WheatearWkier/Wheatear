# Part 4 · 资产管线：路径解析、注册表、热重载与打包

> 目标：理解资产从"磁盘文件"到"引擎可引用对象"的完整旅程——
> 路径解析的双路径（loose/pack）、资产注册表、热重载的降频策略、
> 以及打包发布如何复用同一套代码。结尾用 `.wtsheet` 的加载链路收束。

## 4.1 资产引用的总原则

引擎里所有资产引用都是**项目相对路径字符串**（`assets/scenes/xxx.wt`、
`assets/sandbox/side_combat/ui/sidecombat_ui_sheet.wtsheet`），
而不是绝对路径、也不是对象指针。为什么？

1. **可序列化**：YAML 场景里直接写路径字符串，人类可读、可 diff。
2. **可打包**：同一路径在编辑器（loose 文件）和 Player（pack）里都能解析。
3. **可热重载**：路径 → 文件 → mtime 比较，改了重读。

对象层面，资产由 `Ref<T>`（shared_ptr）持有，配合 Part 2 的纹理 LRU
缓存、Part 6 的 sheet 解析缓存——**路径是身份，缓存是实例**。

## 4.2 AssetPath：一套路径，两条解析链

`Assets/AssetPath.h/.cpp` 是资产路径的核心。几个关键函数：

```cpp
static std::filesystem::path GetAssetRoot();          // 项目根（向上找 assets/ 目录）
static std::filesystem::path Resolve(path);           // 相对 -> 绝对（项目根下）
static std::filesystem::path ToProjectRelative(path); // 绝对 -> 相对（存文件用）
static std::filesystem::path ResolveRuntimeData(path);// 运行时解析：loose 优先
```

### 4.2.1 项目根发现

`DiscoverProjectRoot()` 从当前工作目录**向上逐级找**"含有可用 assets/
目录"的目录。这解决了一个真实痛点：编辑器从任意工作目录启动都能
找到资产（双击 exe、从 IDE 启动、从打包目录启动行为一致）。

### 4.2.2 ResolveRuntimeData：loose/pack 双路径

```cpp
std::filesystem::path AssetPath::ResolveRuntimeData(const std::filesystem::path& path)
{
    if (path.is_absolute())
        return exists(path) ? Normalize(path) : path.lexically_normal();

    const std::filesystem::path loosePath = FindLooseRuntimeData(path);
    if (!loosePath.empty())
        return loosePath;                          // ① loose 文件优先

    return Resolve(path);                          // ② 回落项目根解析
}
```

`FindLooseRuntimeData`：以 `assets/...` 相对路径从当前目录**向上逐级
探测**同名文件——打包后的 Player 目录里有自己的 `assets/`，
运行器从 Player 目录启动时直接命中；编辑器从项目根启动时命中项目
的 `assets/`。**同一段代码，编辑态与发布态零分支**。

打包输出（`Builds/Windows/Player/<打包名>/`，固定 Release、无配置目录；`<打包名>` 来自项目 `player.config` 的 `PackageName`）：

```
WheatearSandbox.exe
assets/                    ← loose 拷贝（场景/图集/脚本/配置）
content.wtpack             ← 打包索引（依赖扫描产物）
package_report.txt         ← 打包报告
```

## 4.3 资产注册表：编辑器侧的分类与元数据

`WheatearEditor/src/Assets/AssetRegistry.h` 是**编辑器进程**的资产数据库：

```cpp
enum class EditorAssetKind { Unknown, Scene, Texture, Audio, Script, Prefab,
                             UITemplate, AnimationClip, SpriteSheet, ... };

class AssetRegistry
{
    static EditorAssetKind DetectKind(const std::filesystem::path& relativePath);
    // 按扩展名分类：.wt -> Scene、.wtsheet -> SpriteSheet、.wtanim -> AnimationClip ...
};
```

- 注册表数据持久化在 `assets/.wheatear/asset_registry.yaml`（UUID、
  类型、纹理导入参数如 Filter/PPU）。
- `DetectKind` 是 ContentBrowser 图标、双击行为、Inspector 导入面板
  的分发依据。
- **引擎侧不依赖注册表**——运行时只需要路径解析 + 格式解析。
  注册表是编辑器的"内容生产层"。

## 4.4 热重载：轮询 mtime + 降频闸

热重载的通用模式：**缓存记录文件的 last_write_time，每次探测比较**。
引擎里三处应用，频率分级：

| 资产 | 探测频率 | 实现 |
| --- | --- | --- |
| VN 剧本 | 500ms | `VisualNovelSystem::OnUpdateRuntime`（last_write_time 变化则重载并保留变量表） |
| 战斗数据 YAML（tuning） | 500ms | `SideCombatTuningService`（逐 TuningPath 缓存） |
| WAO 动作清单 | 500ms | `GameplayModuleRuntime::UpdateActionHotReload`（action_sets.yaml） |
| `.wtsheet` 解析缓存 | 250ms 闸 | `SpriteSheetAsset::GetCachedSheet` |
| 资产浏览器目录 | 250ms 闸 | `ContentBrowserPanel::GetFilteredEntries` |

以 sheet 为例（`SpriteSheetAsset.cpp`）：

```cpp
constexpr auto kSheetProbeInterval = std::chrono::milliseconds(250);

const CachedSheet* GetCachedSheet(const std::string& sheetPath)
{
    const auto now = std::chrono::steady_clock::now();
    const bool probeFiles = (now - SheetProbeClock()) >= kSheetProbeInterval;
    if (probeFiles)
        SheetProbeClock() = now;              // 全局闸：250ms 内只探一次
    else if (cached.Loaded)
        return &cached;                       // 闸内直接命中缓存

    const auto writeTime = exists(resolved) ? last_write_time(resolved) : {};
    if (cached.Loaded && cached.WriteTime == writeTime)
        return &cached;                       // 文件没变
    // ...重读 YAML、重载纹理、更新缓存...
}
```

**为什么降频**：文件系统调用（exists + last_write_time）是 syscall，
场景里 100 个 sheet 实体每帧探测 = 每帧 100 次系统调用。
250ms 闸后每帧最多一次探测——编辑模式热更新延迟 ≤0.25s（人眼无感），
运行态（打包后文件不变）几乎零开销。这是"**先定位热路径再优化**"
的教科书案例：不是所有轮询都要每帧。

## 4.6 实例：.wtsheet 的完整加载链路

以战斗 HUD 图集为例（Part 2 用过它的 `SC_SkillIcon_J`）：

```
编辑器：分割器 Save As Sheet
        → assets/sandbox/side_combat/ui/sidecombat_ui_sheet.wtsheet
        （texture + rects: 23 个命名矩形）

引用方：场景 UIImageComponent.SpriteSheet = ".../sidecombat_ui_sheet.wtsheet"
        SubRect = "SC_SkillIcon_J"

每帧：  SpriteSheetSystem::ResolveCell(path, "SC_SkillIcon_J", resolved)
        ① GetCachedSheet：250ms 闸内命中缓存
        ② 解析 rects → 像素框 → UV/内容尺寸/碰撞框
        ③ 填组件 Texture/UV → 渲染（Part 2 合批）

编辑场景改 .wtsheet（改矩形位置）→ 保存
        → mtime 变化 → 250ms 后缓存重读 → HUD 全部跟随
```

## 4.7 项目化：一个引擎，多个项目

Wheatear 定位是**特定方向（弹幕/回合/战旗/横板格斗）的轻量引擎**，
玩法模块编译在引擎内（类似引擎插件），而**项目 = 资产目录**：

```
仓库根/
├── WheatearEditor/assets/      ← 引擎内置 shader
├── WheatearEditor/ContentTemplates/ ← 新项目模板（fonts/gameplay/input 等）
├── Projects/
│   ├── WheatearDemo/assets/    ← 第一个项目（Sandbox demo：场景/图集/数据表）
│   └── <新项目>/assets/        ← 启动器新建的项目（含模板场景）
└── Builds/Windows/Player/<打包名>/  ← 打包产物（固定 Release，如 Demo）
```

- **启动器**：编辑器启动先进入 `ModeSelectLayer`——选择 2D/3D 模式 +
  项目区（当前项目显示、`Projects/` 列表切换、新建项目）。
- **默认项目**：无参数启动时按 最近项目 → `Projects/WheatearDemo` →
  自动发现 的顺序解析；`--project <目录>` / `WHEATEAR_PROJECT` 显式指定。
- **双根解析**：`AssetPath` 区分**项目根**（场景/图集/玩法数据等资产）与
  **引擎根**（内置 shader 与编辑器模板来源）——`Resolve` 先查项目根，
  未命中回退引擎根。字体、WAO action、Progression 内容和输入绑定由
  `ContentTemplates` 同步进项目；打包器依赖扫描与拷贝同样尊重项目根和引擎根。
- 打包：`--package-player` 默认打当前/默认项目；`--project` 指定其他项目。输出固定为 Release，落到 `Builds/Windows/Player/<打包名>/`，目录名取项目 `player.config` 的 `PackageName`（例如 `Projects/WheatearDemo` 配置了 `PackageName=Demo` → `Builds/Windows/Player/Demo/`）；未配置则用项目短名。编辑器包平铺在 `Builds/Windows/Editor/`。
