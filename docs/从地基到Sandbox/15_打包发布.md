# Part 14 · 打包发布：依赖扫描、Player 构建与发布

> 目标：理解把"编辑器里的项目"变成"可发布的游戏"的全过程——
> 依赖扫描（不打包多余资产）、Player 目录组装、运行时配置，
> 以及为什么打包后还能用同一套代码（Part 4 的双路径解析）。

## 14.1 打包的目标

`WheatearEditor` 的"打包"（Player Packager）产出一个**独立可运行目录**：

```
Builds/Windows/Player/<打包名>/
├── WheatearSandbox.exe      ← 运行器
├── assets/                  ← 运行时数据（只含被依赖的资产）
├── content.wtpack           ← 打包索引（依赖清单）
└── package_report.txt       ← 打包报告（清单/校验/耗时）
```

打包即最终产物：固定 Release 构建，路径不带构建配置目录。
`<打包名>` 取项目的 `assets/game/player.config` 里的 `PackageName`
（例如 `Projects/WheatearDemo` 配置了 `PackageName=Demo` → 打包到
`Builds/Windows/Player/Demo`）；未配置时回退为项目相对仓库路径
去掉 `Projects/` 容器的短名。编辑器是工具本体，打包后直接平铺在
`Builds/Windows/Editor/`（无工程嵌套）。

核心入口 `PlayerPackager::PackagePlayer(options)`：
`WheatearEditor/src/Build/PlayerPackager.cpp`。

编辑器里的实际操作入口是 `Build / Package Player + Editor`。弹窗只要求选择
`Startup Scene`，并校验路径必须以 `assets/scenes/` 开头；GUI 打包固定使用
Release，因为这个按钮面向最终试玩包。构建状态在 `Player Build` 窗口显示，
完成后可以用 `Build / Open Player Folder` 和 `Build / Open Editor Folder`
打开输出目录。

命令行打包仍保留开发选项，可以用 `--configuration Debug|Release`
显式指定配置；无显式参数时会读取项目根的 `assets/game/player.config`。

## 14.2 依赖扫描：不打包多余资产

`AssetDependencyScanner` 从**启动场景出发**做闭包扫描：

```
启动场景（StartupScene）
  → 场景引用的纹理/图集/动画/脚本/音频
  → .wts 事件脚本引用的场景
  → .wtsheet 引用的 PNG
  → 数据表（tuning YAML）
  → 配置（player.config）
  → ……递归直到闭包
```

为什么必须扫描而不是整目录拷贝？

- 素材批次目录里可能有几十张未使用的立绘/背景（Part 13 的
  生产包），整拷会把包撑大几十倍。
- 扫描保证**发布内容 = 运行时实际需要**，缺资产在打包期报错
  （`PackageReport` 列出每个场景的依赖树），而不是运行时黑屏。

## 14.3 Player 组装

`PlayerPackager.cpp` 的流程：

1. **收集资产**：依赖扫描结果（场景/纹理/音频/脚本/图集定义）。
2. **写 content.wtpack**：打包索引（相对路径 + 大小 + 校验），
   供运行器/诊断工具核对完整性。
3. **拷贝 loose 资产**：`assets/` 目录结构原样拷贝
   （Part 4 的 `ResolveRuntimeData` loose 优先路径直接命中）。
4. **写运行时配置**：`assets/game/player.config`
   （启动场景、窗口模式、初始存档等）。
5. **输出报告**：package_report.txt（依赖清单、打包数、耗时）。

## 14.4 运行时为什么零改动

打包后的运行器启动流程与编辑器内运行完全一致：

```
WheatearSandbox.exe（工作目录 = 项目打包目录）
  → AssetPath::DiscoverProjectRoot 找到当前项目包目录
  → 读 player.config → 启动场景
  → 场景/资产按 ResolveRuntimeData 解析（loose 命中）
  → 播放完整流程
```

Part 4 的"**同一段代码，编辑态与发布态零分支**"在这里兑现：
打包没有生成任何"发布专用代码路径"——只是文件摆放不同，
路径解析自动适应。这也是整个引擎"数据驱动"哲学的最终检验：
**游戏 = 引擎 + 数据**，发布 = 拷贝数据。

## 14.5 构建脚本

`scripts/` 下的构建工具链：

| 脚本 | 作用 |
| --- | --- |
| `Build-WheatearEditor.ps1` | 生成 + 编译编辑器（开发日常） |
| `Build-Windows.ps1` | 完整 Windows 构建（编辑器 + 运行器 + 打包） |
| `Check-ProjectSources.ps1` | 工程健康检查（源码/引用完整性） |

## 14.6 发布检查清单（面试可讲）

1. **依赖闭环**：打包报错 = 资产缺失，必须在打包期暴露。
2. **热重载零成本**：发布后文件不变，250ms/500ms 探测闸
   在运行态几乎零开销（Part 4）。
3. **配置外置**：player.config 改启动场景/窗口模式不需要重打包。
4. **同构开发/发布**：编辑器运行与 Player 运行共用同一套
   资产解析——"所见即所得"延伸到发布。
5. **打包前体检**：先看 `Project Health` 的 Missing、Scene Links、
   Entity Bindings、System Bindings、Packed Assets 和 Source Sync；
   如果 preflight 发现缺资源或缺场景跳转，打包会写
   `package_preflight_report.txt` 并停止产出可运行包。

## 14.7 全系列总结：从地基到 Sandbox

14 个编号 Part 加上 Part 9.5 串起来，就是一条完整建造链：

```
Part 1  工程与主循环          窗口、事件、帧循环
Part 2  渲染地基              纹理、合批、相机
Part 3  ECS 与场景            实体、序列化、双系统集
Part 4  资产管线              路径、缓存、热重载
Part 5  编辑器地基            面板、视口、浏览器
Part 6  动画与图集            Clip、分割器、sheet 资产
Part 7  输入                  事件、查询、动作层
Part 8  物理                  Box2D、动画驱动碰撞
Part 9  VN                    剧本解释器、立绘、选项
Part 9.5 WTS 事件脚本         流程编排、命令总线、场景跳转
Part 10 SideCombat            数据表、服务、WAO
Part 11 其他玩法              回合/战棋/弹幕复用底座
Part 12 成长与据点            全局状态、技能树、存档
Part 13 素材管线              四类素材 → 引擎资产
Part 14 打包发布              依赖扫描、Player 组装
```

**一句话总结**：Wheatear 是一座"数据驱动"的引擎——资产是数据、
场景是数据、动作是数据、玩法参数是数据；引擎提供可组合的底座
（渲染/ECS/资产/输入/动画/物理），编辑器是底座上的生产工具，
Sandbox 是底座上的完整游戏。三者共用同一份引擎与同一份数据，
这就是整个项目的核心设计。
