# 面试准备：引擎高频问答

> 用途：针对 Wheatear 引擎项目，面试官可能追问的底层知识与设计动机。
> 每个问题给出「怎么答」要点与代码位置，答的时候先讲设计动机，再讲实现细节。

## 一、渲染

### Q1：2D 渲染是怎么合批的？为什么不用逐物体 draw call？

**怎么答：**

- 自研 `Renderer2D`：单一大 VBO（`RenderBatch`），每帧把所有 quad/circle/line/text 顶点攒进批，`EndScene` 时一次提交。
- 顶点带 `TexIndex`（纹理槽）+ `EntityID`（用于编辑器 picking），纹理切换通过 `GetOrAllocTextureSlot` 分配槽位，槽满或纹理数超上限时 `Flush`。
- 相同纹理的物体自动合批；同帧超过 32 种纹理才强制刷批（配合全局纹理缓存 dedup，同一路径共享同一个 GL 纹理，所以同图多实体不会碎批）。
- 文本（SDF）、UI 走同一套批渲染。

**代码位置：** `Wheatear/src/Wheatear/Renderer/Renderer2D.cpp`、`RenderBatch.h`。

### Q2：纹理缓存为什么存在？怎么管理生命周期？

**怎么答：**

- `Texture2D::Create(path)` 有全局 LRU 缓存：同一路径返回同一对象（GPU 纹理只建一份，也是合批的前提）。
- 512MB VRAM 预算，超出后淘汰「无人引用（use_count==1）」的最久未用项，防止编辑器长会话累积纹理。
- 缓存持有 `shared_ptr`，业务侧也持引用，卸载是引用计数自然完成。

**代码位置：** `Wheatear/src/Wheatear/Renderer/Texture.cpp`。

### Q3：SpriteSheet 的 UV 坐标系约定？

**怎么答：**

- 引擎纹理加载 `stbi_set_flip_vertically_on_load(1)`，因此 GL 纹理 v=0 是图像底部；组件/动画链路统一使用该约定（旧实现曾是 top-left 约定导致渲染颠倒，已统一修复）。
- `.wtsheet` 格子索引行主序（row 0 = 图像顶部），`ResolveCell` 输出内容框的 GL UV；ContentBrowser 缩略图按 ImGui 约定再翻转一次。
- 面试加分：讲「统一约定 + 在边界翻转」而不是到处改符号。

### Q4：PPU（Pixels Per Unit）解决了什么问题？

**怎么答：**

- 传统 quad 是 1×1×scale，非方形纹理会被拉伸；动画帧内容尺寸变化（站立→躺下）时更明显。
- `PixelsPerUnit > 0` 时渲染尺寸 = UV 覆盖的像素数 ÷ PPU，quad 保持真实宽高比；动画播放时每帧尺寸自动跟随内容。
- 同一 PPU 也是碰撞盒像素→世界单位的换算基准，渲染与物理共用一套尺度。

## 二、Scene / ECS

### Q5：为什么用 entt？组件系统怎么组织的？

**怎么答：**

- entt 是 header-only 的 ECS：组件是 POD 结构体，存储是 SoA 的 sparse set，遍历快、缓存友好。
- 主题化组件头文件（Core/Physics2D/Rendering/UI/Animation...）而非单一大头，减少 include 面。
- 场景序列化用模板特化 `ComponentSerializer<T>`，YAML 键名与组件一一对应，新增组件只需加一个特化。

**代码位置：** `Wheatear/src/Wheatear/Scene/`、`Scene/Serialization/`。

### Q6：系统（System）是怎么组织的？编辑器和运行时共用吗？

**怎么答：**

- 每个系统实现 `ISystem`（OnRuntimeStart/OnUpdateRuntime/OnUpdateEditor/OnEntityCreated...），场景在 `ConfigureRuntimeSystems` / `ConfigureEditorSystems` 注册。
- 编辑器里跑的是「编辑系统集」（SpriteSheet 解析、动画预览帧同步、编辑器相机等），进入 Play 切换为运行时系统集——同一份场景数据，两套行为。
- 好处：编辑器所见即所得（预览帧、碰撞框跟随都在编辑态生效）。

### Q7：运行时和编辑器之间怎么切换状态？

**怎么答：**

- `SceneState`（Edit/Play）由 EditorLayer 管理，切换时序列化场景为临时内存副本（或直接深拷贝场景），运行时改动不影响编辑场景。
- 实体激活（activate/deactivate）、延迟操作（拖放资产落地）走队列，避免渲染循环中修改 ECS。

## 三、事件脚本 / CommandBus

### Q8：.wts 事件脚本是什么？为什么要做？

**怎么答：**

- 流程不硬编码：`CommandBus` 统一命令入口，`.wts` 用 YAML 描述「什么时候做什么」（场景切换、剧情节点、UI、存读档、战斗结算）。
- 引擎只提供命令原语，玩法流程是数据——策划/编辑器可直接改文本资源，不用重编。
- 编辑器有事件脚本图面板（可视化组织），运行时 500ms 热重载，改脚本即生效。

**代码位置：** `Wheatear/src/Wheatear/Runtime/CommandBus.h`、`assets/events/*.wts`。

### Q9：动画事件和 .wts 的关系？

**怎么答：**

- 动画事件在指定时间发 `Command`（带 `{entity}/{clip}/{event}` 占位符），动画系统不关心命令含义。
- 命令落到 CommandBus 后被各模块消费（伤害结算、音效、镜头、切场景）——动画系统与玩法解耦。

## 四、WAO 动作系统

### Q10：WAO 是什么？和 GAS 有什么区别？

**怎么答：**

- WAO（Wheatear Action Orchestration）是动作编排层：`ActionIntent（意图）-> ActionRecipe（配方）-> RuleResolver（规则）-> EffectBundle（效果束）-> EffectLedger（结算账本）-> SignalRouter（信号路由）`。
- 输入、AI、事件脚本都能产生 Intent，进入同一套动作入口；技能、冷却、资源、效果、表现分层。
- 相比 GAS：不做网络/预测/属性集那一套，聚焦单机 2D 多玩法复用；配 `Action Debugger` 编辑器追踪动作结果。

**代码位置：** `Wheatear/src/Wheatear/Gameplay/Action/`。

## 五、资产系统

### Q11：.wtsheet 为什么设计成「引用」而不是「烘焙」？

**怎么答：**

- 组件/动画帧存 (sheet 路径 + 格子号)，运行时 `ResolveCell` 统一解析，sheet 文件 mtime 变化即热重载——改网格/裁切，所有引用方下一帧更新，无需重新导出资源。
- 同一份网格定义被实体、动画、碰撞复用，不会出现「改一次图集要重导 N 份」。
- 打包：`ResolveRuntimeData` 兼容 loose 文件与 `content.wtpack`，同一套代码两条路径。

**代码位置：** `Wheatear/src/Wheatear/Assets/SpriteSheetAsset.cpp`、`AssetPath.cpp`。

### Q12：热重载怎么做的？性能考虑？

**怎么答：**

- 轮询 `last_write_time`，与缓存记录比较，变了才重读（不是每帧解析文件）。
- 探测频率按场景分级：VN/战斗脚本 500ms；sheet 解析在热路径上加 250ms 闸，避免大量实体每帧做文件系统调用。
- 编辑器资产浏览器目录扫描同样做了 (目录, 搜索词) 键控缓存 + 250ms 闸。

## 六、输入

### Q13：输入系统分几层？

**怎么答：**

- 底层：GLFW 回调 → 事件分发（KeyEvent/MouseEvent）。
- 中间：`Input` 静态查询（IsKeyPressed 等，带边沿检测状态机）。
- 上层：`InputBindingService` 动作绑定（action → 键/鼠标/组合），支持重映射 UI（Input Bindings 面板）、命令注入（AI/脚本模拟输入）、EndFrame 状态同步。

**代码位置：** `Wheatear/src/Wheatear/Input/`。

## 七、物理

### Q14：Box2D 怎么和 ECS 集成？动画驱动的碰撞怎么实现？

**怎么答：**

- 运行时会话创建 b2World，`OnRuntimeStart` 从组件数据建 body/fixture（组件存 RuntimeBody/RuntimeFixture 指针）。
- 每帧 Step 后 body 位置写回 Transform；组件改动（如 Inspector 调尺寸）通过重建 fixture 同步——普通碰撞是「创建时拷贝」，动画驱动是「每帧比对组件数据与 fixture shape，变化才重建」。
- `BoxCollider2DComponent.FollowAnimation`：精灵系统/动画系统每帧按格子碰撞框（像素）÷ PPU 写 Offset/Size，物理系统检测变化重建 fixture——人倒下碰撞盒跟着变。

**代码位置：** `Wheatear/src/Wheatear/Systems/PhysicsSystem.cpp`、`SpriteSheetSystem.cpp`。

## 八、编辑器架构

### Q15：编辑器为什么是面板体系？浮动窗口怎么做？

**怎么答：**

- 全部 ImGui：SceneHierarchy/Inspector/ContentBrowser/AnimationEditor 等面板，EditorLayer 统一调度。
- 浮动窗口通过 `EditorFloatingWindow`（可停靠/分离），面板内容与窗口框架解耦，同一面板可浮动可嵌入。
- ContentBrowser 支持 UE 式抽屉模式（底部折叠栏）。

### Q16：编辑器「离屏缩略图」怎么实现的？

**怎么答：**

- 非图片资产（场景/Prefab/UI 模板/Mesh/动画）排队进 `RenderThumbnail`：建临时场景 → 离屏 FBO（128×128）→ `ReadPixels` → 上传为缩略图纹理 → 缓存。
- 每帧只渲染队列中的一个，避免卡顿；结果缓存到 `m_ThumbnailCache`。

## 九、工程实践

### Q17：编译速度怎么优化的？

**怎么答：**

- 预编译头：glm/entt/imgui 等稳定大头进 PCH（引擎与编辑器各一份），单文件增量编译约 3 秒。
- MSBuild 并行编译（/m）。
- include 治理：主题化组件头、模块内聚、避免模块间交叉 include。

### Q18：性能上做过哪些实测优化？

**怎么答：**

- 纹理 LRU 缓存（dedup，合批前提 + VRAM 预算）。
- 文件系统探测降频（sheet 解析 250ms 闸、目录扫描缓存）。
- 音频解码缓存；热路径避免重复分配（如 animator 绑定缓存避免每帧重建属性轨道 writer）。
- 上述都是「先定位热路径再优化」，不是盲目微优化。

## 十、可以主动展示的亮点

1. **SpriteSheet 引用式资产闭环**：资产化 → 热更新 → trim → PPU → 碰撞联动 → 编辑器拖放，一条链。
2. **编辑器/运行时同一场景两套系统**：编辑态预览与运行时行为一致。
3. **数据驱动流程**：.wts + CommandBus + 数据表，玩法逻辑可编辑。
4. **WAO 动作编排**：多玩法复用的动作语义层。
5. **工程习惯**：PCH/增量编译、主题化头文件、模板序列化器、提交粒度清晰。
